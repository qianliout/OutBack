`FOR UPDATE SKIP LOCKED` 是一种**数据库行级锁机制**，主要用于高并发场景下避免事务因等待锁而阻塞。其核心作用是：**查询并锁定当前未被其他事务占用的符合条件的行，同时自动跳过已被锁定的行，而非等待锁释放**。这一特性显著提升了任务分发类场景的并发处理能力，尤其适用于任务队列、分布式抢购等需避免锁竞争的系统。

---

## 一、核心机制解析

### 1. **基础组件功能**

- **`FOR UPDATE`**：  
    对查询到的行加**排他锁（X锁）**，阻止其他事务修改或删除这些行，直到当前事务提交或回滚。
- **`SKIP LOCKED`**：  
    作为 `FOR UPDATE` 的修饰符，**跳过已被其他事务锁定的行**，而非等待锁释放。若目标行已被锁定，查询结果将**直接忽略该行**，继续处理后续符合条件的行。

### 2. **与普通 `FOR UPDATE` 的关键区别**

- **普通 `FOR UPDATE`**：  
    若目标行已被锁定，事务会**阻塞等待**，直到锁释放或超时（可能导致队头阻塞问题）。
- **`FOR UPDATE SKIP LOCKED`**：  
    遇到已锁定行时**立即跳过**，返回其他可锁定的行，**避免阻塞**，确保系统吞吐量。

---

## 二、典型应用场景

### 1. **任务队列系统（最常见用途）**

- **问题背景**：  
    多个工作进程需从同一任务表中领取待处理任务（如 `status = 'pending'`）。若使用普通 `FOR UPDATE`，所有进程可能因竞争同一行而阻塞。
- **解决方案**：  
    各进程执行以下语句，**各自获取不同任务**：
    
    ```sql
    SELECT id, payload 
    FROM job_queue 
    WHERE status = 'pending' 
    ORDER BY priority DESC, created_at 
    LIMIT 1 
    FOR UPDATE SKIP LOCKED;
    ```
    
    - **效果**：进程A锁定任务1后，进程B会跳过任务1，直接获取任务2，实现**真正的并行处理**。

### 2. **分布式抢购/秒杀系统**

- 多个用户同时抢购有限库存时，通过 `SKIP LOCKED` 快速分配库存，避免因锁等待导致请求堆积。

## 三、使用注意事项

### 1. **必要前提条件**

- **数据库支持**：  
    仅 MySQL 8.0+ 和 PostgreSQL 原生支持，其他数据库（如 SQL Server、Oracle）需通过 `NOWAIT` + 应用层重试模拟。
- **必须在事务中使用**：  
    锁的生命周期依赖事务边界（需显式 `BEGIN` 和 `COMMIT`/`ROLLBACK`）。

### 2. **关键性能优化点**

- **索引设计**：  
    `WHERE` 和 `ORDER BY` 条件**必须命中索引**（如任务队列中的 `status` + `created_at`），否则可能退化为表锁，导致性能骤降。
- **限制返回行数**：  
    务必使用 `LIMIT` 控制锁定范围，避免一次性锁定过多行。
- **避免饥饿问题**：  
    长期被跳过的行可能因高竞争而“饥饿”，需配合优先级策略或定期重扫机制缓解。

### 3. **与 `NOWAIT` 的区别**

|特性|`SKIP LOCKED`|`NOWAIT`|
|---|---|---|
|**已锁定行的处理**|跳过该行，返回其他可锁定行|**立即报错**，不返回任何结果|
|**适用场景**|需快速获取可用资源（如任务队列）|需明确感知锁冲突（需应用层处理异常）|

---

## 四、常见误区

1. **数据一致性风险**：  
    `SKIP LOCKED` 返回的结果是**当前未被锁定的行**，但**不保证数据一致性**。官方文档明确提示：_“Queries that skip locked rows return an inconsistent view of the data”_，因此**不适用于需强一致性的事务**（如金融转账），仅推荐用于队列类场景。
    
2. **索引缺失导致表锁**：  
    若查询条件未命中索引，InnoDB 可能升级为**表级锁**，反而加剧阻塞。务必通过 `EXPLAIN` 验证执行计划。
    
3. **无结果不报错**：  
    若所有符合条件的行均被锁定，查询将返回空结果集（而非错误），需在应用层处理“无可用任务”的逻辑。
    

---

**总结**：`FOR UPDATE SKIP LOCKED` 的核心价值在于**通过非阻塞式锁获取提升并发吞吐量**，但需严格限定于任务队列等**允许数据短暂不一致**的场景，并确保索引优化到位。若项目中用于任务分发，其设计目标应是**避免进程因锁竞争而空转**，而非保证强事务一致性。
