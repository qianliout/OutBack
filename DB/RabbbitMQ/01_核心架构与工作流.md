# 01_核心架构与工作流

## 核心架构与基本概念对比

### RabbitMQ Broker 与 Kafka Broker 的定位差异
RabbitMQ 被设计为智能代理。它在服务端负责复杂的路由逻辑，维护每个消费者的状态，将消息主动推送给消费者。
Kafka 被设计为哑代理。它只负责追加存储和简单的数据分发，复杂的消费逻辑和偏移量维护交给客户端处理。

### Exchange 与 Queue 架构对比 Kafka Topic 与 Partition
RabbitMQ 使用 Exchange 接收消息，再根据规则路由到一个或多个 Queue。Queue 是真实物理存储消息的地方。
Kafka 使用 Topic 作为逻辑概念，底层分为多个 Partition。Partition 是物理存储单元。

### Binding 与 Routing Key 的灵活路由机制
RabbitMQ 生产者不直接发消息给 Queue，而是发给 Exchange，并带上 Routing Key。Exchange 根据 Binding 规则进行匹配。
Kafka 生产者直接向 Topic 发送消息，根据 Key 的哈希值或轮询算法决定进入哪个 Partition，没有服务端的路由计算。

### 生产者与消费者模型差异
RabbitMQ 的消费者是竞争关系。多个消费者监听同一个 Queue，一条消息只会被其中一个消费者处理。
Kafka 的消费者基于 Consumer Group。同一个 Group 内的消费者平分 Partition，不同 Group 可以独立消费全量消息。

## 工作流与数据传输机制

### AMQP 协议模型解析
RabbitMQ 原生基于 AMQP 高级消息队列协议。该协议定义了统一的网络传输格式和基础概念，是一个应用层标准协议。
Kafka 使用自定义的基于 TCP 的二进制协议，专为高吞吐量和零拷贝优化。

### Connection 与 Channel 的复用机制
RabbitMQ 客户端与服务端建立 TCP 连接后，会在内部创建多个 Channel 信道。所有的操作都在 Channel 上进行，复用单一 TCP 连接以节省资源。
Kafka 的连接是直接面向 Broker 节点的，不需要信道复用机制。

### RabbitMQ 推模型与 Kafka 拉模型的本质区别
RabbitMQ 默认采用推模型。服务端主动将消息推送给消费者，配合 Prefetch 限制未确认消息的数量。
Kafka 完全采用拉模型。消费者根据自己的处理能力，主动向服务端请求批量数据。

### 消息从生产到消费的完整生命周期
RabbitMQ 流程：生产者建立连接，创建信道，声明交换机和队列，发送消息到交换机，交换机路由到队列，服务端推送给消费者，消费者处理完毕后返回确认，服务端从队列删除消息。
Kafka 流程：生产者建立连接，请求元数据，将消息批量发送到指定分区的 Leader 副本，消费者主动拉取数据，处理完毕后提交偏移量，消息依然保留在磁盘上。
