# 03_存储与消费机制

## 数据存储与持久化机制

### 内存与磁盘存储的双层设计
RabbitMQ 默认优先将消息存储在内存中以保证低延迟。当内存不足时，会将消息换页到磁盘。
Kafka 设计之初就将消息以追加日志的方式直接写入磁盘，依赖操作系统的 Page Cache 提供极高的读写性能。

### 队列持久化与消息持久化
RabbitMQ 要实现真正的持久化，必须同时满足三个条件：交换机持久化、队列持久化、消息模式设置为持久化。
Kafka 的数据默认就是持久化的，不需要像 RabbitMQ 那样在发送每条消息时专门指定。

### 存储性能与数据检索方式差异
RabbitMQ 内部采用 B 树类似结构管理消息索引。消息被消费并确认后会被立即标记删除，类似于传统的队列数据结构。
Kafka 的存储是纯粹的追加日志加上稀疏索引。消息基于全局递增的 Offset 进行顺序读取，读写性能极高，不会因为消息积压而显著降低性能。

## 消息消费与确认机制

### 自动确认与手动确认的实现
RabbitMQ 消费者可以选择自动确认或手动确认。自动确认在消息发出后立即视为成功，容易丢失数据。手动确认则由业务代码在处理完毕后显式调用确认接口。

### QoS 与 Prefetch 预取机制
RabbitMQ 推模型中为了防止压垮消费者，需要配置 Prefetch 数量。它限制了客户端可以同时持有的未确认消息数量，是实现消费端限流的核心。

### 消息拒绝与重新投递
RabbitMQ 消费者可以通过 Nack 或 Reject 拒绝单条或批量消息，并选择是否将消息重新放回队列头部。
Kafka 没有针对单条消息的拒绝机制。如果消费失败，通常需要在业务代码中捕获异常，并记录到单独的死信 Topic 中，然后继续提交 Offset。

### 对比 RabbitMQ ACK 机制与 Kafka Offset 提交机制
RabbitMQ 的 ACK 是基于单条消息的状态机管理。消息确认后立即从服务端删除标记。
Kafka 的 Offset 是基于分区维度的游标标记。提交 Offset 只表示游标向前移动，消息依然保留在磁盘上，随时可以重置游标重新消费历史数据。

## 消费后的数据去向与生命周期

### 正常消费后的数据立即销毁机制
RabbitMQ 将队列视为中转站，数据被消费并确认后，会被立即从内存或磁盘中删除，不具备历史数据追溯能力。

### 对比 Kafka 基于时间或大小的持久化保留策略
Kafka 将消息视为不可变的日志。数据消费后依然保留，直到满足配置的保留时间或保留大小阈值才会被清理线程删除。

### 死信队列的触发条件与配置
RabbitMQ 原生支持死信队列。当消息被拒绝且不重试、消息过期时间到达、或队列长度达到上限时，消息会被自动路由到指定的死信交换机。
Kafka 没有原生的死信队列功能，需要开发者在消费逻辑中手动将处理失败的数据发送到另一个 Topic。

### 消息的生存时间控制
RabbitMQ 可以为整个队列设置统一的过期时间，也可以为单条消息单独设置生存时间 TTL。
Kafka 只有统一的 Topic 级别的保留时间，无法为单条消息设置不同的过期时间。
