# 第二部分：向量数据库系统架构全景

本部分将带你深入理解向量数据库的**系统级架构设计**，从与传统数据库的根本差异，到现代向量数据库的典型分层结构，再到分布式架构模式与存算分离理念。这些知识是理解后续索引构建、查询优化和生产部署的基础。

---

## 1. 与传统数据库的根本差异（向量不是标量）

### 原理讲解

传统数据库（如 MySQL、PostgreSQL）主要处理**结构化数据**（标量：整数、字符串、时间戳），其核心操作是精确匹配、范围查询和连接（JOIN）。而向量数据库的核心任务是**近似最近邻搜索（ANN）**，即在高维空间中快速找到与查询向量“语义相似”的向量。

| 维度 | 传统数据库 | 向量数据库 |
|------|------------|------------|
| **数据类型** | 标量（int, string, datetime） | 高维浮点向量（float32[768]） |
| **核心操作** | 精确查询、索引查找、JOIN | 近似最近邻搜索（ANN）、相似度排序 |
| **索引目标** | 快速定位精确值 | 快速剪枝，缩小搜索范围 |
| **性能指标** | QPS、延迟、TPS | 查询延迟、召回率（Recall）、吞吐量 |
| **存储需求** | 行/列式存储，压缩率高 | 大量浮点数，内存密集型 |
| **扩展模式** | 主从复制、分片 | 存算分离、水平扩展计算节点 |

> 💡 **关键洞察**：向量数据库的“索引”不再是 B+ 树或哈希表，而是复杂的图结构（HNSW）、聚类结构（IVF）或量化编码（PQ），其构建和维护成本远高于传统索引。

---

## 2. 典型架构层次图

现代向量数据库通常采用**多层解耦架构**，将不同职责分离，便于独立扩展和维护。典型分层如下：

```
+---------------------+
|    接入层 (Access)   |
|  - REST/gRPC API     |
|  - 认证、限流、日志   |
+----------+----------+
           |
+----------v----------+
|    查询层 (Query)    |
|  - 查询解析、优化    |
|  - 过滤下推、结果排序 |
+----------+----------+
           |
+----------v----------+
|    索引层 (Index)    |
|  - HNSW、IVF、PQ     |
|  - ANN 搜索执行      |
+----------+----------+
           |
+----------v----------+
|    存储层 (Storage)  |
|  - 向量数据持久化    |
|  - WAL、LSM-tree     |
+----------+----------+
           |
+----------v----------+
|   元数据层 (Metadata)|
|  - 集合元信息、索引状态 |
|  - etcd / MySQL      |
+---------------------+
```

### 各层职责详解

| 层级 | 职责 | 典型实现 |
|------|------|----------|
| **接入层** | 提供 API 接口，处理客户端连接 | gRPC Server、REST Gateway |
| **查询层** | 解析查询请求，执行查询计划优化（如过滤下推） | 查询优化器、执行引擎 |
| **索引层** | 管理向量索引的构建、更新、搜索 | HNSW 图、IVF 聚类中心 |
| **存储层** | 持久化向量数据，保证写入可靠性 | WAL + LSM-tree（如 RocksDB）、对象存储（S3/MinIO） |
| **元数据层** | 存储集合 schema、索引状态、节点信息 | etcd、ZooKeeper、MySQL |

> ✅ **设计优势**：各层可独立部署和扩展。例如，计算密集型的“索引层”可水平扩展，而“元数据层”通常为高可用小集群。

## 3. 分布式架构设计模式

### (1) Milvus：微服务架构典范

Milvus 是目前最典型的**存算分离 + 微服务拆分**的向量数据库，其架构如下：

```
+----------------+     +----------------+     +----------------+
|   Proxy        |<--->|   QueryNode    |<--->|   DataNode     |
| (接入/查询)     |     | (ANN 搜索)      |     | (写入/持久化)   |
+-------+--------+     +-------+--------+     +-------+--------+
        |                      |                      |
        v                      v                      v
+----------------+     +----------------+     +----------------+
|   QueryCoord   |     |   DataCoord    |     |   Storage      |
| (查询调度)      |     | (数据调度)      |     | (MinIO/S3)     |
+-------+--------+     +-------+--------+     +----------------+
        |                      |
        v                      v
+----------------+     +----------------+
|   RootCoord    |<--->|   etcd         |
| (元数据管理)     |     | (服务发现)      |
+----------------+     +----------------+
```

#### 核心组件说明

| 组件 | 职责 |
|------|------|
| **Proxy** | 接入层，接收客户端请求，转发给协调节点 |
| **RootCoord** | 元数据总控，管理集合、分区、索引的生命周期 |
| **QueryCoord** | 协调 QueryNode，分配数据分片（Segment）查询任务 |
| **QueryNode** | 执行 ANN 搜索，加载索引到内存 |
| **DataCoord** | 协调 DataNode，管理数据分片的持久化和版本 |
| **DataNode** | 接收写入请求，写入 WAL 并持久化到对象存储 |
| **etcd** | 存储元数据、节点状态、服务发现 |
| **MinIO/S3** | 存储原始向量数据和索引文件 |

> 📌 **优势**：
> - 高可扩展性：QueryNode 和 DataNode 可独立扩展
> - 高可用：协调节点可多副本部署
> - 易运维：Kubernetes 友好，支持 Helm 部署

> 📚 **官方架构图**：[Milvus Architecture](https://milvus.io/docs/architecture_overview.md)

### (2) Qdrant：轻量级但可扩展

Qdrant 采用更简洁的架构，但仍支持分布式部署：

```
+----------------+
|   API Gateway  |
+-------+--------+
        |
+-------v--------+
|   Searcher     |<----+
| (ANN 搜索)      |     |
+-------+--------+     |
        |              |
+-------v--------+     |  +----------------+
|   Storage      |<----+->|   Peer-to-Peer |
| (RocksDB)      |        |   Replication  |
+----------------+        +----------------+
```

- **单机模式**：所有功能集成在一个进程中，适合开发测试
- **集群模式**：通过 gRPC 实现节点间复制和分片，支持水平扩展
- **特点**：Rust 编写，性能高，内存占用低，适合中等规模部署

> 🔗 官方文档：https://qdrant.tech/documentation/

## 4. 存算分离理念及其优势

### 什么是存算分离？

将**计算资源**（CPU、内存，用于索引搜索）与**存储资源**（磁盘、对象存储，用于数据持久化）解耦，允许独立扩展。

### 优势

| 优势 | 说明 |
|------|------|
| **弹性扩展** | 搜索压力大时，只扩展 QueryNode；数据增长快时，只扩展存储 |
| **成本优化** | 使用廉价对象存储（S3/MinIO）保存冷数据，热数据缓存在内存 |
| **高可用** | 存储层通常为多副本，计算节点可无状态重启 |
| **快速恢复** | 节点宕机后，可从对象存储重新加载索引 |

> ✅ **生产级必备**：Milvus、Weaviate、Pinecone 等均采用存算分离设计。

# 第三部分：核心索引算法的底层实现

本部分将深入剖析主流 ANN 索引算法的**内部工作原理**，包括 HNSW、IVF、PQ 的构建、搜索、更新机制，以及索引的持久化流程。

---

## 1. HNSW：Hierarchical Navigable Small World

### 原理讲解

HNSW 是目前**性能最好、应用最广**的 ANN 算法，其核心思想是构建一个**多层导航图**，高层用于快速“粗略导航”，底层用于“精细搜索”。

#### (1) 图结构构建过程

- **分层结构**：向量被随机分配到多个层级（0 ~ L），高层节点少，底层节点多
- **入口点（EntryPoint）**：每层有一个入口点，搜索从最高层开始
- **近邻连接**：每个节点在每层连接若干“最近邻”节点，形成图结构

> 📌 **类比**：像地图导航——先看国家（高层），再看城市（中层），最后看街道（底层）

#### (2) 动态插入策略

- 新向量从高层开始插入
- 在每层使用“贪婪搜索”找到最近邻
- 随机决定是否提升到更高层（类似跳表）
- 更新邻居连接，保持图连通性

#### (3) 搜索过程（`ef_search` 参数控制精度）

1. 从最高层入口点开始
2. 在当前层找到 `ef_search` 个最近邻
3. 下降到下一层，以这些点为起点继续搜索
4. 重复直到最底层，返回 Top-K 结果

> ⚠️ **参数说明**：
> - `M`：每个节点的最大连接数（影响内存和搜索速度）
> - `ef_construction`：构建时的候选数（影响索引质量）
> - `ef_search`：搜索时的候选数（越大越准，越慢）

#### (4) 内存占用分析

- HNSW 是**内存密集型**索引
- 内存 ≈ `N * M * 4 bytes`（N 为向量数，M 为连接数）
- 例如：1M 向量，M=16 → 约 64GB 内存

> 📚 **原始论文**：[HNSW: Hierarchical Navigable Small World Graphs](https://arxiv.org/abs/1603.09320)

---

## 2. IVF：Inverted File with Quantization

### 原理讲解

IVF 将向量空间划分为 `nlist` 个聚类（由 k-means 训练），每个向量归属一个聚类。搜索时只搜索“最可能相关”的若干聚类（`nprobe`）。

#### (1) 聚类中心训练（k-means）

- 使用 k-means 算法在训练集上学习 `nlist` 个聚类中心
- 所有向量根据距离归属最近的聚类

#### (2) 量化误差

- 向量与其聚类中心的距离称为“残差”
- 可结合 PQ 对残差进行压缩，进一步减少内存

#### (3) 搜索时的“探查列表”机制

- 计算查询向量与所有 `nlist` 个聚类中心的距离
- 选择距离最近的 `nprobe` 个聚类
- 在这些聚类内部进行暴力搜索或结合 HNSW

> ⚠️ **参数说明**：
> - `nlist`：聚类数量（越大越准，索引越慢）
> - `nprobe`：探查聚类数（越大越准，越慢）

#### (4) 优缺点

| 优点 | 缺点 |
|------|------|
| 内存占用较低 | 需要全量训练聚类中心 |
| 支持 PQ 压缩 | 聚类边界附近的向量可能被漏搜 |
| 适合大规模数据 | 增量更新困难（聚类中心难动态更新） |

---

## 3. PQ / SQ：向量压缩原理

### Product Quantization (PQ)

- **思想**：将 D 维向量划分为 M 个子向量，每个子向量用一个“码本”（codebook）表示
- **压缩比**：原始 D 维 → M * log2(K) bits（K 为码本大小）
- **精度损失**：由于量化，距离计算有误差
- **加速比**：内存减少，可全部加载到内存，搜索更快

### Scalar Quantization (SQ)

- 对每个维度单独量化（如 32-bit float → 8-bit int）
- 压缩比低，但精度损失小

> 📚 **PQ 论文**：[Product Quantization for Nearest Neighbor Search](https://lear.inrialpes.fr/pubs/2011/JDS11/jegou_searching_with_quantizations.pdf)

## 4. 索引的构建、更新、合并与持久化全流程解析

### (1) 构建流程

1. 数据写入 → 存入临时段（Segment）
2. 达到阈值（如 100K 向量）→ 触发索引构建
3. 调用 HNSW/IVF 构建算法 → 生成索引文件
4. 索引注册到元数据层 → 标记为“可查询”

### (2) 更新机制

- **HNSW**：支持**增量插入**，新向量直接插入图中（但可能影响图质量）
- **IVF**：通常**不支持增量更新**，需定期全量重建聚类中心
- **混合策略**：新数据用 HNSW，老数据用 IVF+PQ

### (3) 合并与持久化

- 多个小段可合并为大段，减少索引碎片
- 索引文件通过 WAL 持久化到对象存储（S3/MinIO）
- 支持快照备份与恢复

---

## 5. 增量更新 vs 全量重建的成本对比

| 策略 | 延迟 | 精度 | 资源消耗 | 适用场景 |
|------|------|------|----------|----------|
| **增量更新** | 低（实时） | 中（图可能退化） | 低 | 写多读少，实时性要求高 |
| **全量重建** | 高（分钟级） | 高 | 高（CPU/内存） | 数据稳定，精度要求高 |

> ✅ **生产建议**：HNSW 适合增量，IVF 适合批量重建。
