# 第四部分：存储引擎与数据管理机制

本部分将深入剖析向量数据库的**底层存储设计**，涵盖向量数据的物理存储方式、写入持久化机制（WAL）、向量与元数据的联合存储策略、数据分片（Sharding）与负载均衡、以及垃圾回收与版本管理等关键系统机制。这些内容是理解向量数据库**可靠性、一致性与性能边界**的核心。

---

## 1. 向量数据如何存储？—— 内存映射、列式存储与分块机制

### (1) 存储抽象：Segment 与 Chunk

现代向量数据库（如 Milvus、Qdrant）普遍采用 **“Segment” 模型**作为数据组织单位：

- **Segment**：一个逻辑数据单元，包含一组向量及其元数据
- **Chunk**：Segment 的物理存储单元，通常对应一个文件或对象存储中的 blob

> 📌 **类比**：Segment ≈ 数据库中的“分区”，Chunk ≈ “数据文件”

#### Segment 的典型结构（以 Milvus 为例）

```
Segment
├── Vector Data (binlog)
├── Scalar Fields (binlog)
├── Index Files (HNSW/IVF)
├── Delta Logs (删除记录)
└── Checkpoint (WAL offset)
```

- 所有数据通过 **binlog（增量日志）** 持久化到对象存储（如 MinIO/S3）
- 索引文件独立存储，可异步构建

---

### (2) 存储格式：列式 vs 行式

| 存储方式 | 说明 | 适用场景 |
|--------|------|----------|
| **列式存储** | 每个字段（如向量、标签、时间戳）单独存储 | 向量数据库主流选择，便于独立加载和压缩 |
| **行式存储** | 每条记录的所有字段连续存储 | 传统数据库常见，不适合高维向量 |

> ✅ **优势**：
> - 向量列可单独加载到内存，元数据列按需读取
> - 支持不同压缩策略（如 PQ 压缩向量，Snappy 压缩元数据）

---

### (3) 分块机制（Chunking）

- 大向量集合被划分为多个 Segment，每个 Segment 包含 `chunk_size` 个向量（如 100K）
- 写入时先写入内存缓冲区，达到阈值后 flush 为只读 Segment
- 只读 Segment 可异步构建索引

> ⚙️ **参数控制**（Milvus）：
> - `segment.maxSize`：单个 Segment 最大尺寸（MB）
> - `chunk.rows`：每 chunk 行数

---

### (4) 内存映射（Memory-Mapped Files）

- 向量数据和索引文件通过 `mmap()` 映射到进程地址空间
- 无需一次性加载全部数据到内存，由操作系统按需分页加载
- 减少内存拷贝，提升 I/O 效率

> ⚠️ **M1 Mac 注意**：Docker Desktop 默认内存限制可能不足，建议调整至 8GB+。

---

## 2. 是否使用 WAL？如何保证写入持久性？

### (1) WAL（Write-Ahead Log）的作用

WAL 是向量数据库实现**持久性（Durability）** 和 **崩溃恢复（Crash Recovery）** 的核心机制。

#### 工作流程：

1. 客户端写入请求到达
2. 数据首先追加到 **WAL 日志**（顺序写，高性能）
3. 写入成功 → 返回 ACK
4. 后台线程异步将数据 flush 到 Segment 并持久化到对象存储

> ✅ **ACID 保证**：WAL 确保即使系统崩溃，未持久化的数据也可通过日志恢复。

---

### (2) Milvus 中的 WAL 实现

- 使用 **Raft + etcd** 或 **独立 WAL 服务** 记录所有写操作
- 每个 Segment 维护一个 `checkpoint`，记录已持久化的 WAL offset
- 节点重启时，从 checkpoint 恢复未完成的写入

```yaml
# docker-compose.yml 片段：WAL 依赖
services:
  etcd:
    image: quay.io/coreos/etcd:v3.5.10
    command: etcd -advertise-client-urls http://etcd:2379 -listen-client-urls http://0.0.0.0:2379
  minio:
    image: minio/minio:RELEASE.2023-08-16T18-35-56Z
    command: server /data
```

---

### (3) Qdrant 的 WAL 设计

- 使用 **RocksDB** 作为本地存储引擎，天然支持 WAL
- 所有写入先写入 RocksDB 的 WAL，再异步同步到其他节点
- 支持配置 `wal_capacity_mb` 和 `wal_segments` 控制日志大小

## 3. 向量与标量元数据的联合存储策略

### (1) 存储分离设计

| 数据类型 | 存储方式 | 说明 |
|--------|----------|------|
| **向量数据** | 列式存储，对象存储（S3/MinIO） | 大文件，冷热分离 |
| **标量元数据** | 列式存储，RocksDB 或 MySQL | 小数据，高频查询 |
| **索引文件** | 对象存储 + 内存缓存 | 构建耗时，需持久化 |

> ✅ **优势**：查询时可“过滤下推”（Pushdown），先用标量条件筛选，再对结果集做向量搜索。

---

### (2) 元数据索引优化

- 标量字段（如 `category`, `timestamp`）可建立传统索引（B+树、倒排）
- 查询时，QueryNode 先执行标量过滤，再在剩余向量上执行 ANN 搜索
- 减少不必要的向量距离计算

#### 示例：混合查询执行计划

```sql
-- 语义：在“科技”类文章中，找与“人工智能”最相关的 Top-5
SELECT * FROM articles 
WHERE category = 'tech' 
ORDER BY embedding SIMILARITY TO :query_vec 
LIMIT 5;
```

执行流程：
1. 标量过滤：`category = 'tech'` → 得到候选向量 ID 列表
2. 向量搜索：在候选向量上执行 HNSW 搜索
3. 排序返回 Top-5

> 📌 **优化关键**：避免“先搜再过滤”，应“先过滤再搜”。

---

## 4. 数据分片（Sharding）与负载均衡机制

### (1) 分片策略

向量数据库通过 **Sharding** 实现水平扩展，常见策略：

| 策略 | 说明 |
|------|------|
| **Hash-based Sharding** | 向量 ID 哈希 → 分配到不同 Segment | 均匀分布，但不支持范围查询 |
| **Range-based Sharding** | 按时间戳或 ID 范围分片 | 适合时间序列数据 |
| **Consistent Hashing** | 节点增减时最小化数据迁移 | 分布式系统常用 |

> ✅ Milvus 默认使用 Hash 分片，支持 `shard_num` 配置。

---

### (2) 负载均衡

- **写入负载均衡**：Proxy 将写请求均匀分发到多个 DataNode
- **查询负载均衡**：QueryCoord 将 Segment 分配给多个 QueryNode，支持并行搜索
- **热点检测**：监控各节点 QPS、内存使用，动态调整分片分布

#### 示例：Milvus 分片流程

```go
// Golang 客户端创建集合时指定分片数
collSchema := &milvuspb.CollectionSchema{
    Fields: []*schemapb.FieldSchema{
        {Name: "id", DataType: entity.FieldTypeInt64, IsPrimaryKey: true},
        {Name: "embedding", DataType: entity.FieldTypeFloatVector, TypeParams: map[string]string{"dim": "768"}},
    },
}

// 创建集合，指定 2 个分片
createReq := &milvuspb.CreateCollectionRequest{
    CollectionName: "docs",
    Schema:         collSchema,
    ShardNum:       2, // 分片数
}
```

## 5. 垃圾回收与版本管理（旧版本索引清理）

### (1) 版本控制模型

向量数据库通常采用 **多版本并发控制（MVCC）** 模型：

- 每次索引构建生成新版本
- 旧版本索引在无活跃查询后标记为可删除
- 支持快照读取（Snapshot Isolation）

---

### (2) 垃圾回收（GC）机制

#### 触发条件：

- Segment 被合并（compaction）
- 索引重建完成
- 删除操作积累到阈值

#### 回收流程：

1. 标记旧 Segment 为“待删除”
2. 等待所有查询完成（引用计数为 0）
3. 异步删除对象存储中的文件
4. 更新元数据，释放内存

> ⚠️ **风险**：GC 阻塞可能导致内存泄漏或查询延迟上升。

---

### (3) 删除操作的实现：Delta Logs

由于向量数据库通常**不支持原地更新**，删除操作通过 **Delta Log** 实现：

- 删除请求记录到 Delta Log（如 `delete_id=123`）
- 查询时，先查主数据，再查 Delta Log，过滤已删除 ID
- 后台定期 compact，物理删除数据

#### 为什么不能原地更新？

- HNSW 图结构不支持“删除节点”后高效重建连接
- IVF 聚类中心更新成本高
- 一致性模型复杂（需锁机制）

> ✅ **替代方案**：标记删除 + 异步重建。
