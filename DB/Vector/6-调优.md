# 第七部分：性能调优与稳定性保障

本部分将深入探讨向量数据库在**生产环境**中的核心挑战：如何通过**索引参数调优、资源监控、故障恢复、备份策略**等手段，确保系统在高并发、大数据量下的**高性能、高可用与数据安全**。我们将以 Qdrant 为例，结合 Milvus 的通用实践，提供可落地的优化方案。

---

## 1. 索引参数调优（HNSW、IVF、PQ）

### (1) HNSW 参数优化（Qdrant 默认索引）

HNSW 是 Qdrant 的默认索引，其性能由三个核心参数决定：

| 参数 | 说明 | 调优建议 |
|------|------|----------|
| `M` | 每个节点的最大连接数 | **越大越准，内存越高**。建议：`M=16~64`（M1 学习环境用 M=16，生产用 M=48） |
| `ef_construction` | 构建时的候选列表大小 | **越大索引质量越高，构建越慢**。建议：`ef_construction = 100~300` |
| `ef`（搜索时） | 搜索时的候选数 | **越大召回率越高，延迟越高**。建议：`ef=50~100`（平衡精度与延迟） |

#### Qdrant 配置示例（`docker-compose.yml`）

```yaml
environment:
  - QDRANT__SERVICE__HTTP_PORT=6333
  # 优化 HNSW 参数
  - QDRANT__STORAGE__OPTIMIZERS__DEFAULT_M=48
  - QDRANT__STORAGE__OPTIMIZERS__DEFAULT_EF_CONSTRUCTION=200
  - QDRANT__STORAGE__OPTIMIZERS__DEFAULT_EF=80
```

> ✅ **调优策略**：
> - **高精度场景**（如推荐系统）：提高 `ef` 和 `ef_construction`
> - **低延迟场景**（如实时搜索）：降低 `ef`，接受稍低召回率
> - **内存受限**：降低 `M`，或启用 PQ 压缩

---

### (2) PQ（Product Quantization）压缩

PQ 可显著降低内存占用，适合大规模部署。

#### 启用 PQ 压缩（Qdrant）

```go
// 创建集合时启用 PQ
req := &qdrant.CreateCollection{
    CollectionName: "compressed_docs",
    VectorsConfig: &qdrant.VectorsConfig{
        Config: &qdrant.VectorsConfig_Params{
            Params: &qdrant.VectorParams{
                Size:     768,
                Distance: qdrant.Distance_Cosine,
                HnswConfig: &qdrant.HnswConfigDiff{
                    M:              16,
                    EfConstruction: 100,
                    Ef:             50,
                },
            },
        },
    },
    OptimizersConfig: &qdrant.OptimizersConfigDiff{
        // 启用 PQ
        ProductQuantization: &qdrant.ProductQuantizationConfig{
            Compression: qdrant.CompressionType_Primary,
            M:           16, // 子向量数
        },
    },
}
```

> ✅ **效果**：
> - 内存减少 75%~90%（如 32-bit → 8-bit）
> - 搜索速度提升（因数据可全加载到内存）
> - 召回率略有下降（量化误差）

---

### (3) IVF 参数调优（Milvus 推荐）

| 参数 | 说明 | 建议 |
|------|------|------|
| `nlist` | 聚类数量 | `nlist ≈ sqrt(N)`，N 为向量总数 |
| `nprobe` | 搜索探查聚类数 | `nprobe = nlist / 10`，可动态调整 |
| `PQ` | 与 IVF 联用，进一步压缩 | `m = dim / 8`，如 768维 → m=96 |

> ✅ **IVF 适用场景**：数据量 > 1M，对内存敏感，可接受批量重建。

## 2. 资源监控与性能压测

### (1) 监控指标（Prometheus + Grafana）

| 指标 | 说明 | 告警阈值 |
|------|------|----------|
| `qdrant_collection_segments_count` | Segment 数量 | > 100（需 compact） |
| `qdrant_collection_points_count` | 向量总数 | 持续增长 |
| `qdrant_search_latency_ms` | 查询延迟 | P99 > 100ms |
| `qdrant_upsert_latency_ms` | 插入延迟 | P99 > 500ms |
| `process_resident_memory_bytes` | 内存使用 | > 80% 分配内存 |
| `go_grpc_server_handled_total` | gRPC 请求量 | 突增可能异常 |

#### 启用 Prometheus 监控（Qdrant）

```yaml
# docker-compose.yml
environment:
  - QDRANT__TELEMETRY__METRICS=true
  - QDRANT__TELEMETRY__METRICS_ADDRESS=0.0.0.0:6333
```

访问：`http://localhost:6333/metrics`

---

### (2) 性能压测工具

#### 使用 `hey` 进行 HTTP 压测

```bash
# 安装 hey
go install github.com/rakyll/hey@latest

# 压测搜索接口
hey -z 1m -c 10 -m POST -t 30 \
  -H "Content-Type: application/json" \
  -d '{"vector":[0.1,0.2,...],"limit":5}' \
  http://localhost:6333/collections/documents/points/search
```

> 参数说明：
> - `-z 1m`：持续 1 分钟
> - `-c 10`：10 个并发
> - `-t 30`：超时 30 秒

## 3. 故障恢复与高可用设计

### (1) Qdrant 集群模式（Raft + Replication）

Qdrant 支持 **peer-to-peer 复制**，通过 Raft 协议保证一致性。

#### 集群配置示例

```yaml
# docker-compose-cluster.yml
version: '3.7'
services:
  qdrant-1:
    image: qdrant/qdrant:v1.10.0
    ports: ["6333:6333"]
    environment:
      - QDRANT__CLUSTER__ENABLED=true
      - QDRANT__P2P__PORT=6335
      - QDRANT__HTTP__PORT=6333
    command: ["qdrant", "--bootstrap", "http://qdrant-1:6335"]

  qdrant-2:
    image: qdrant/qdrant:v1.10.0
    ports: ["6336:6333"]
    environment:
      - QDRANT__CLUSTER__ENABLED=true
      - QDRANT__P2P__PORT=6337
      - QDRANT__HTTP__PORT=6333
    command: ["qdrant", "--bootstrap", "http://qdrant-1:6335"]
```

> ✅ **优势**：
> - 自动故障转移（Leader Election）
> - 数据多副本，防止单点故障
> - 支持水平扩展读请求

---

### (2) Milvus 高可用架构

- **etcd**：多副本（3/5 节点），保证元数据高可用
- **MinIO/S3**：对象存储多副本，持久化保障
- **QueryNode/DataNode**：无状态，可多副本部署
- **Kubernetes**：结合 Operator 实现自动恢复

## 4. 备份与恢复策略

### (1) Qdrant 快照（Snapshot）

Qdrant 支持生成本地或远程快照。

#### 手动生成快照

```bash
# 创建快照
curl -X POST 'http://localhost:6333/collections/documents/snapshots'

# 列出快照
curl http://localhost:6333/collections/documents/snapshots

# 恢复快照（需重启服务）
# 将快照文件放入 `snapshots/` 目录，启动时自动恢复
```

#### 自动快照配置

```yaml
environment:
  - QDRANT__STORAGE__SNAPSHOTS__SCHEDULE_INTERVAL=3600  # 每小时
  - QDRANT__STORAGE__SNAPSHOTS__RETENTION_PERIOD=2592000  # 30天
```

---

### (2) Milvus 备份（通过对象存储）

- 所有 Segment 和索引文件已持久化到 S3/MinIO
- 直接备份对象存储中的 `by-dev/` 目录即可
- 恢复时，替换对象存储数据并重启服务

## 5. 生产环境稳定性 Checklist

| 项目 | 检查项 |
|------|--------|
| ✅ **资源分配** | Docker 分配 4GB+ 内存，CPU 2核+ |
| ✅ **监控告警** | Prometheus + Alertmanager，监控延迟、内存、错误率 |
| ✅ **日志收集** | 使用 ELK 或 Loki 收集容器日志 |
| ✅ **备份策略** | 每日快照 + 对象存储多区域复制 |
| ✅ **版本管理** | 固定版本号，避免 `latest` |
| ✅ **安全配置** | 启用认证（Qdrant 支持 API Key），防火墙限制端口 |
| ✅ **压测验证** | 上线前进行 1:1 流量压测 |
| ✅ **故障演练** | 定期模拟节点宕机，验证恢复能力 |
