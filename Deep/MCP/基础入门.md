# MCP 学习笔记：第一部分 基础入门

本笔记详细阐述了 MCP (Model Context Protocol) 的基础知识，旨在帮助初学者理解其核心价值、工作原理以及与现有技术的区别。

---

### 1. MCP 是什么？

#### 1.1. MCP 的官方定义与一句话解释

**官方定义：**
模型上下文协议（Model Context Protocol, MCP）是一个开源标准协议，旨在为 AI 应用（特别是大型语言模型 LLM）提供一个标准化的接口，用以连接和交互外部系统、数据源、工具和工作流。

**一句话解释（核心类比）：**
您可以把 MCP 理解为 **"AI 应用的 USB-C 端口"**。它让任何 AI 模型都能通过一个统一、标准的插口，方便地连接和使用各种外部工具与实时数据，而不需要为每个应用和工具都定制开发复杂的“胶水代码”。

**补充信息：**
该协议由 Anthropic 公司于 2024 年 11 月提出并开源，其底层通信主要基于 JSON-RPC 2.0 实现。

#### 1.2. MCP 不是什么？（与 HTTP, RPC, Pub/Sub 的区别）

为了更深刻地理解 MCP，我们需要将它与我们熟知的协议进行对比。

| 协议          | 核心特点                         | 主要用途                 | 与 MCP 的关系和区别                                                                           |
| :---------- | :--------------------------- | :------------------- | :------------------------------------------------------------------------------------- |
| **HTTP**    | **无状态 (Stateless)**          | Web 内容传输、RESTful API | HTTP 是 MCP 的常见载体，但 MCP 在其上层实现了**有状态**的交互。传统 HTTP API 每次请求都需携带完整上下文，而 MCP 允许上下文在服务端持久化。 |
| **RPC**     | **远程过程调用 (Action-oriented)** | 调用远程服务器上的函数          | MCP 底层使用 JSON-RPC，但其设计思想不同。RPC 关注“执行一个动作”，而 MCP 关注“**维护一个状态（上下文）**，并基于此状态执行动作”。        |
| **Pub/Sub** | **发布/订阅 (Event-driven)**     | 异步消息分发、事件广播          | Pub/Sub 是多对多的异步通信模式。MCP 通常是**点对点 (Client-Provider)** 的请求/响应模式，专注于构建和维护一个共享的、专用的上下文环境。  |

#### 1.3. 核心思想

MCP 的核心思想是：**将“上下文管理”从应用层解耦，使其成为一种独立、标准化的服务。**

这意味着：
*   **应用开发者（客户端）**：不再需要关心如何存储、截断、检索上下文。他们只需通过标准协议“更新”上下文（例如：“添加这个文件”、“记住这条用户消息”）。
*   **模型服务提供方（服务端）**：可以独立地对上下文管理进行深度优化，例如使用向量数据库、KV缓存、智能摘要等技术，而这些优化对客户端是完全透明的。

### 2. 为什么需要 MCP？(Problem Space)

#### 2.1. 传统大模型（LLM）应用开发的痛点

在没有 MCP 的世界里，用 HTTP API 构建一个能“记住”历史的 AI 应用（如多轮对话机器人、文档分析助手）通常会遇到以下痛点：

1.  **上下文丢失与重复传递 (Context Loss & Repetition)**
    *   由于 HTTP 无状态，客户端必须在**每次**请求中都附上完整的对话历史或相关文档，否则模型无法理解当前问题。
    *   **代码示例：典型的无状态 API 调用**
        ```python
        import openai

        # 第一次请求
        response1 = openai.chat.completions.create(
            model="gpt-4",
            messages=[
                {"role": "user", "content": "我的名字是李强。"}
            ]
        )
        print(response1.choices[0].message.content)
        # -> "你好，李强！很高兴认识你。"

        # 第二次请求，如果不传递历史，模型会“失忆”
        response2 = openai.chat.completions.create(
            model="gpt-4",
            messages=[
                {"role": "user", "content": "我叫什么名字？"}
            ]
        )
        print(response2.choices[0].message.content)
        # -> "抱歉，我不知道你的名字，因为我们之前的对话没有包含这个信息。"

        # 正确但低效的做法：每次都传递完整历史
        response3 = openai.chat.completions.create(
            model="gpt-4",
            messages=[
                {"role": "user", "content": "我的名字是李强。"},
                {"role": "assistant", "content": "你好，李强！很高兴认识你。"},
                {"role": "user", "content": "我叫什么名字？"} # 每次都要重复发送历史
            ]
        )
        print(response3.choices[0].message.content)
        # -> "你的名字是李强。"
        ```

2.  **重复计算与成本增加 (Repetitive Computation & High Cost)**
    *   模型在每次请求时，都需要重新阅读和处理一遍你发送的全部历史上下文，这造成了大量的 Token 浪费和计算资源的消耗，直接导致更高的费用和更慢的响应速度。

3.  **状态管理逻辑复杂 (Complex State Management)**
    *   开发者需要在客户端自己实现一套复杂的逻辑来管理上下文窗口：如何拼接历史、当历史太长时如何进行摘要或截断、如何注入外部文档等。这部分逻辑在每个 AI 应用中几乎都要重复造轮子。

#### 2.2. CaaS (Context-as-a-Service) 的理念与优势

为了解决上述痛点，CaaS（上下文即服务）的理念应运而生。它将上下文视为一种像数据库或缓存一样的、可远程管理和访问的资源。

*   **优势**：应用本身变得“轻量”，只关注业务逻辑，而将繁重的上下文管理工作外包给专业的 CaaS 服务。
*   **MCP 的角色**：MCP 就是实现 CaaS 的**标准通信协议**。它定义了应用该如何与 CaaS 服务进行对话。

#### 2.3. MCP 如何解决上述痛点

*   **实现有状态交互**：客户端只需发送一次上下文更新，服务端就会“记住”它。后续请求只需发送新的、增量的信息。
*   **提升效率与降低成本**：由于上下文存储在服务端，服务端可以采用高级缓存技术（如 KV Caching），避免重复计算，从而节省 Token、降低延迟。网络传输的数据量也大大减少。
*   **简化客户端逻辑**：开发者不再需要编写复杂的上下文管理代码，只需调用 MCP 提供的标准接口即可。

### 3. 核心概念 (Core Concepts)

*   **模型 (Model)**：指代 AI 模型本身，是执行推理的核心。
*   **上下文 (Context)**：模型进行推理所需的所有信息。它可以是对话历史、用户信息、外部文档、数据库记录、工具（API）的定义等等。它是模型的“记忆”和“知识库”。
*   **客户端 (Client)**：发起请求、管理和更新上下文的应用。例如，你的聊天机器人前端、VSCode 插件、AI Agent 程序。
*   **模型提供方 (Model Provider)**：接收并处理 MCP 消息的服务端。它负责安全地存储和管理上下文，并在接收到模型请求时，加载相关上下文并调用 AI 模型进行推理。
*   **消息 (Message)**：客户端和模型提供方之间通信的数据单元，通常是一个结构化的 JSON 对象，明确定义了操作类型（如`context_update`）和具体内容（Payload）。

### 4. 第一个 MCP "Hello, World"

让我们通过一个模拟的交互流程，看看 MCP 在实践中是如何工作的。

**场景**：我们想让 AI 分析一个文档，然后回答关于文档的问题。

#### 4.1. 一个最简单的 MCP 交互流程

**流程：** `Client` --(更新上下文)--> `Provider` --(请求模型)--> `Provider` --(响应)--> `Client`

#### 4.2. 模拟一次完整的对话

以下是模拟的 JSON 消息，展示了客户端和服务端的交互。

**第 1 步：客户端发送 `context_update` 消息，将文档内容添加到上下文中。**

```json
// Client -> Provider
{
  "protocol_version": "1.0",
  "message_id": "msg-001",
  "message_type": "context_update",
  "payload": {
    "add": [
      {
        "item_id": "doc-tesla-q3",
        "content_type": "text/plain",
        "content": "特斯拉2025年第三季度财报显示，公司营收达到500亿美元，净利润为80亿美元。"
      }
    ]
  }
}
```
*   **发生了什么？** 客户端告诉服务端：“请记住这个 ID 为 `doc-tesla-q3` 的文档。” 服务端收到后，会将这个文档存储起来，并与当前会话关联。

**第 2 步：服务端确认上下文更新成功（此步骤在实际协议中可能简化或合并）。**

**第 3 步：客户端发送 `model_request` 消息，提出问题。**

```json
// Client -> Provider
{
  "protocol_version": "1.0",
  "message_id": "msg-002",
  "message_type": "model_request",
  "payload": {
    "prompt": "根据财报，特斯拉的净利润是多少？",
    "context_item_ids": ["doc-tesla-q3"] // 明确指示模型应参考哪个上下文
  }
}
```
*   **发生了什么？** 客户端现在只发送了一个非常简短的问题。它通过 `context_item_ids` 告诉服务端：“请基于我们之前添加的那个文档来回答这个问题。” **注意：这里没有重复发送财报的完整内容！**

**第 4 步：服务端收到请求，执行推理，并返回 `model_response` 消息。**

```json
// Provider -> Client
{
  "protocol_version": "1.0",
  "message_id": "resp-to-msg-002",
  "message_type": "model_response",
  "payload": {
    "content": "根据财报，特斯拉2025年第三季度的净利润为80亿美元。",
    "usage": {
      "prompt_tokens": 15, // 只计算了新 prompt 的 token
      "completion_tokens": 25,
      "total_tokens": 40
    }
  }
}
```
*   **发生了什么？** 服务端在内部将存储的文档内容和用户的问题结合起来，送给 AI 模型。然后将模型生成的结果返回给客户端。注意 `usage` 字段，其成本远低于将整个文档和问题一起发送的传统方式。

通过这个简单的例子，我们可以清晰地看到 MCP 如何通过**分离上下文管理和模型请求**，实现更高效、简洁和经济的 AI 应用开发。
