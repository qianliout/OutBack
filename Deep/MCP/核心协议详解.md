# MCP 学习笔记：第二部分 核心协议详解

本笔记深入 MCP 协议的内部，详细解析其消息结构、核心消息类型和通信模式。掌握这部分是进行 MCP 开发和架构设计的基础。

---

### 1. MCP 消息结构

MCP 的所有通信都通过结构化的消息完成。这些消息遵循统一的顶层设计，通常使用 JSON 格式进行序列化。

#### 1.1. 通用消息格式

一个基础的 MCP 消息看起像这样：

```json
{
  "protocol_version": "1.0",
  "message_id": "msg-client-xyz-001",
  "message_type": "...",
  "payload": {
    "...": "..."
  }
}
```

#### 1.2. 关键字段解析

*   **`protocol_version`** (字符串, 必选)
    *   **作用**: 表明消息遵循的 MCP 协议版本。
    *   **目的**: 确保客户端和模型提供方之间的兼容性。如果未来协议有重大更新（例如 `2.0`），服务端可以根据版本号选择不同的处理方式，避免破坏性更改。
    *   **示例**: `"1.0"`

*   **`message_id`** (字符串, 必选)
    *   **作用**: 由消息发送方（通常是客户端）生成的唯一标识符。
    *   **目的**:
        1.  **请求追踪**: 用于将响应与原始请求对应起来，尤其是在异步通信中。
        2.  **幂等性**: 服务端可以利用 `message_id` 来识别和丢弃重复的请求，防止意外的重复操作。
    *   **示例**: `"msg-client-b7a9-4f12-8e0c-1c2b3d4e5f6a"`

*   **`message_type`** (字符串, 必选)
    *   **作用**: 消息的核心，定义了这条消息的**意图**。
    *   **目的**: 告诉接收方应该如何解析 `payload` 并执行何种操作。
    *   **核心类型**: `context_update`, `model_request`, `model_response`, `error`。

*   **`payload`** (对象, 必选)
    *   **作用**: 消息的“载荷”，包含了执行该消息类型所需的所有具体数据。
    *   **目的**: 其内部结构由 `message_type` 决定。

---

### 2. 核心消息类型 (Message Types)

下面我们逐一解析最重要的几种消息类型及其 `payload` 结构。

#### 2.1. `context_update`

这是 MCP 实现有状态交互的**关键**。客户端通过此消息来管理服务端上的上下文。

*   **Payload 结构**:
    *   `add` (数组, 可选): 用于**新增**上下文条目。
    *   `update` (数组, 可选): 用于**更新**已存在的上下文条目。
    *   `remove` (数组, 可选): 用于**删除**已存在的上下文条目。

*   **上下文条目 (Context Item) 结构**:
    *   `item_id` (字符串): 上下文条目的唯一标识符，由客户端指定和管理。
    *   `content_type` (字符串): 内容的 MIME 类型，如 `text/plain`, `text/markdown`, `application/json`。
    *   `content` (字符串/对象): 条目的具体内容。

*   **幂等性 (Idempotency)**:
    *   `context_update` 被设计为幂等的。重复发送同一个 `context_update` 消息（相同的 `message_id` 和 `payload`），服务端的最终状态应该是一致的。
    *   例如，使用 `add` 添加一个已存在的 `item_id`，其效果应等同于 `update`。

*   **代码示例**:
    ```json
    // 消息类型: context_update
    {
      "protocol_version": "1.0",
      "message_id": "msg-001",
      "message_type": "context_update",
      "payload": {
        "add": [
          {
            "item_id": "user_profile",
            "content_type": "application/json",
            "content": {
              "name": "李强",
              "role": "软件工程师",
              "interests": ["AI", "分布式系统"]
            }
          },
          {
            "item_id": "system_prompt",
            "content_type": "text/plain",
            "content": "你是一个乐于助人的 AI 助手。"
          }
        ],
        "remove": [
          "old_document_id"
        ]
      }
    }
    ```

#### 2.2. `model_request`

当上下文准备好后，客户端使用此消息向模型发起推理请求。

*   **Payload 结构**:
    *   `prompt` (字符串, 必选): 用户当前的输入或指令。
    *   `context_item_ids` (字符串数组, 可选): **核心字段**。明确指定本次推理需要使用哪些已存在的上下文条目。如果留空，服务端可能会使用会话中的全部上下文，或不使用任何上下文。
    *   `parameters` (对象, 可选): 控制模型生成行为的参数，如 `temperature`, `max_tokens`, `top_p` 等。
    *   `stream` (布尔值, 可选): 是否请求流式响应。默认为 `false`。

*   **代码示例**:
    ```json
    // 消息类型: model_request
    {
      "protocol_version": "1.0",
      "message_id": "msg-002",
      "message_type": "model_request",
      "payload": {
        "prompt": "根据我的兴趣，推荐一个周末可以学习的技术方向。",
        "context_item_ids": [
          "user_profile" // 明确告诉模型要参考 "user_profile" 这个上下文
        ],
        "parameters": {
          "temperature": 0.7,
          "max_tokens": 200
        },
        "stream": false
      }
    }
    ```

#### 2.3. `model_response`

服务端对 `model_request` 的成功响应。

*   **Payload 结构**:
    *   `content` (字符串): 模型生成的文本内容。
    *   `usage` (对象): 本次推理的 Token 使用情况，用于成本核算。
        *   `prompt_tokens`: 输入消耗的 Token。
        *   `completion_tokens`: 输出消耗的 Token。
    *   `finish_reason` (字符串): 模型停止生成的原因，如 `stop` (自然停止), `length` (达到 `max_tokens`), `tool_use` (需要调用工具)。

*   **代码示例**:
    ```json
    // 消息类型: model_response
    {
      "protocol_version": "1.0",
      "message_id": "resp-to-msg-002", // 对应请求的 message_id
      "message_type": "model_response",
      "payload": {
        "content": "考虑到您对 AI 和分布式系统的兴趣，可以研究一下“联邦学习”（Federated Learning）。它结合了机器学习和去中心化数据处理，非常有前景。",
        "usage": {
          "prompt_tokens": 50,
          "completion_tokens": 85
        },
        "finish_reason": "stop"
      }
    }
    ```

#### 2.4. `error`

当处理失败时，服务端返回错误消息。

*   **Payload 结构**:
    *   `code` (整数): 标准化的错误码（可参考 HTTP 状态码，如 400, 404, 500）。
    *   `message` (字符串): 人类可读的错误信息。
    *   `details` (对象, 可选): 提供更详细的错误上下文。

*   **代码示例**:
    ```json
    // 消息类型: error
    // 场景: model_request 引用了一个不存在的 context_item_id
    {
      "protocol_version": "1.0",
      "message_id": "err-resp-to-msg-003",
      "message_type": "error",
      "payload": {
        "code": 400,
        "message": "Bad Request: One or more context items not found.",
        "details": {
          "not_found_ids": ["non_existent_id"]
        }
      }
    }
    ```

### 3. 通信流程与状态管理

#### 3.1. 建立连接与会话 (Session)

*   MCP 的交互都发生在**会话 (Session)** 的概念中。一个会话就代表了一个独立的上下文环境。
*   会话可以通过多种方式实现：
    *   **长连接**: 如 WebSocket，连接本身就代表一个会话。断开即会话结束。
    *   **HTTP + Token**: 客户端在每个 HTTP 请求的 Header 中携带一个 `Session-ID`，服务端通过此 ID 来区分和恢复不同用户的上下文。

#### 3.2. 有状态的交互 (Stateful Interaction)

这是 MCP 最典型的使用模式，流程如下：
1.  **Client**: 发送 `context_update` 添加初始上下文（如用户身份、文档）。
2.  **Provider**: 存储上下文，并与当前会话关联。
3.  **Client**: 发送 `model_request`，引用已存在的上下文 ID。
4.  **Provider**: 加载指定上下文，结合 prompt 进行推理，返回 `model_response`。
5.  **Client**: 发送新的 `context_update` 添加新的对话历史（用户的新问题和模型的回答）。
6.  ...循环 3-5 ...

#### 3.3. 无状态的请求 (Stateless Interaction)

MCP 同样可以支持无状态的、一次性的请求，只需在 `model_request` 中不传递 `context_item_ids` 即可。这种用法等同于传统的 LLM API 调用，但好处是**格式统一**，应用无需为不同交互模式维护两套代码。

#### 3.4. 异步与流式处理 (Async & Streaming)

*   **异步 (Asynchronous)**:
    *   `message_id` 是实现异步的关键。客户端可以连续发送多个请求（例如，并行处理多个文档），而无需等待每个请求的响应。
    *   当服务端完成处理后，它会在响应中包含原始的 `message_id`，客户端据此就能将响应与正确的请求挂钩。

*   **流式 (Streaming)**:
    *   当 `model_request` 的 `stream` 标志为 `true` 时，服务端不会等到模型完全生成完再响应，而是会持续发送一系列的消息“块”。
    *   这些消息块可能是 `model_response` 的变体，例如 `model_response_chunk`，每个块包含一小段 `content`。这极大地改善了用户体验，因为用户可以立即看到文本开始出现，而不是长时间等待。
    *   流式响应的最后一个消息块会包含 `finish_reason` 和完整的 `usage` 统计。
