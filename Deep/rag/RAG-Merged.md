## 三、关键技术详解

### 🔹 1. Embedding 维度与 Transformer 的关系

- **Embedding 维度 = Transformer 的 `d_model` 参数**
- 在模型训练时即已确定，不可更改。
- 所有中间表示（token 向量、隐藏状态、句向量）均为 `[d_model]` 维。
- 示例：BERT 使用 `d_model=768`，输出向量长度为 768。

> ✅ **结论**：Embedding 维度是模型架构的一部分，由训练参数决定，不能随意变更。

---

### 🔹 2. 文本如何被向量化？六步流程

| 步骤 | 说明 |
|------|------|
| 1. 文本切片（Chunking） | 将长文档按语义边界或固定长度切分为小块（如 512 tokens） |
| 2. Tokenization | 使用 tokenizer 将文本转为 token ID 序列 |
| 3. 前向传播 | 输入 Transformer 模型得到每个 token 的上下文向量 |
| 4. Pooling | 通过 [CLS]、Mean Pooling 或 Max Pooling 得到句子/段落向量 |
| 5. 归一化 | L2 Normalization，便于计算余弦相似度 |
| 6. 存入向量库 | 存储向量 + 原文 + 元数据 到 PGVector / Qdrant / Faiss |

🧠 **训练方式**：采用对比学习（Contrastive Learning），如 Triplet Loss，使语义相近文本在向量空间中距离更近。

---

### 🔹 3. Embedding 与 Cross-Encoder 是否必须相同？

| 问题 | 回答 |
|------|------|
| 必须是同一个模型吗？ | ❌ 不必。推荐使用不同模型，发挥各自优势 |
| 它们的关系是什么？ | 协同工作：Embedding 负责召回，Cross-Encoder 负责精排 |

#### 功能对比表

| 特性 | Embedding 模型（Bi-Encoder） | Cross-Encoder（Reranker） |
|------|-------------------------------|-----------------------------|
| 输入形式 | 单文本独立编码 | 查询 + 文档联合输入 |
| 是否交互 | 否 | 是（深层注意力交互） |
| 速度 | ⚡️ 快（可预计算） | 🐢 慢（实时推理） |
| 精度 | 中等 | 高 |
| 输出 | 向量（如 [768]） | 相关性分数（scalar） |

✅ **最佳实践**：两段式检索 ——  
先用 Embedding 召回 top-50，再用 Cross-Encoder 精排 top-5。

## 四、三大核心组件选型建议

### ✅ 三大组件及其作用

| 组件 | 作用 | 关键要求 |
|------|------|----------|
| **Embedding 模型** | 向量检索，快速召回 | 高召回率、语义准确 |
| **Reranker 模型** | 对候选结果打分排序 | 高精度、强语义理解 |
| **LLM（生成模型）** | 结合知识生成回答 | 事实遵循强、支持引用标注 |

| 模型 | 语言 | 特点 | 推荐场景 |
|------|------|------|-----------|

### 🔹 2. Reranker 模型推荐

| 模型 | 参数量 | 特点 | 推荐场景 |
|------|--------|------|-----------|
| `BAAI/bge-reranker-large` | ~300M | 最强中文 reranker | 极致精度 |
| `BAAI/bge-reranker-base` | ~110M | 中文效果好 | 通用中文 |
| `ms-marco-MiniLM-L-6-v2` | ~28M | 轻量高效 | 快速原型 |

✅ **建议**：reranker 与 embedding 可不同源，但建议同系列（如 bge + bge-reranker）

### 🔹 3. LLM 生成模型推荐

| 类型 | 推荐模型 | 特点 | 适用场景 |
|------|---------|------|-----------|
| 开源小模型 | Qwen2-7B, Phi-3-mini | 可本地部署，成本低 | 内部系统 |

| 闭源 API | GPT-4-turbo, Claude-3 | 效果最好 | 高端客户支持 |

✅ **关键要求**：
- 良好的指令遵循能力
- 支持引用标注（citation）

## 五、系统功能全景（六大模块）

### 🔍 1. 检索前：知识预处理与增强

| 功能 | 描述 |
|------|------|
| **1.1 智能切片（Smart Chunking）** | 不再使用固定字符切分；采用语义边界切分（如 SemanticChunker）；保留标题层级结构（Markdown → 带路径 chunk）；代码按函数体切分，表格保持完整性 |
| **1.2 元数据注入** | 自动提取文件名、作者、创建时间、章节标题、页码；自动生成语义标签（如“退款政策”、“安装指南”）；添加权限标签（如 dept:sales, level:public），用于访问控制 |
| **1.3 知识图谱构建（可选）** | 从文本抽取实体与关系（如“产品A 支持 协议B”）；构建轻量级知识图谱，支持复杂推理（如“哪些产品支持 HTTPS？”） |
| **1.4 多模态支持** | 图像 OCR 提取文字；PDF 表格结构化处理；音视频内容转录并建立索引 |

---

### 🔎 2. 检索中：多策略混合检索

| 功能 | 描述 |
|------|------|
| **2.1 稠密检索（Dense Retrieval）** | 使用 BGE 等向量化模型生成 chunk 向量；存储于 PGVector；基于余弦相似度匹配 |
| **2.2 稀疏检索（Sparse Retrieval）** | 使用 Elasticsearch 进行关键词匹配；支持 BM25、布尔查询、模糊匹配；利用元数据字段过滤 |
| **2.3 混合检索与排序** | 粗排：合并稠密与稀疏结果，加权融合得分；精排：使用 Cross-Encoder 对 top-k 重排序；返回最终 top-5 最相关 chunk |
| **2.4 多向量检索（Multi-Vector Retrieval）** | 为每个 chunk 生成多个向量（全文、摘要、关键词）；检索时融合多视角匹配，提升召回率 |
| **2.5 查询重写（Query Rewriting）** | 同义词扩展：“打印机连不上” → “无法连接 wifi”；历史上下文重写：“它怎么用？” → “Phi-3 怎么用？”；问题分解：将复杂问题拆为子问题并行检索 |
| **2.6 查询路由（Query Routing）** | 判断问题类型：<br>• 知识库问答 → RAG<br>• 闲聊 → 纯 LLM<br>• 数据查询 → SQL 生成<br>可基于规则或轻量模型实现 |
| **2.7 分层检索（Hierarchical Retrieval）** | 先检索“文档”层级（如手册、政策），再在命中文档中检索“段落”或“章节”，减少噪声，提升精度 |

---

### 🧠 3. 生成阶段：对话理解与推理增强

| 功能 | 描述 |
|------|------|
| **3.1 多轮对话管理** | 维护对话历史上下文；支持长对话压缩与摘要；上下文感知，自动携带最近查询结果 |
| **3.2 指代消解** | 将“它”、“这个”、“上次说的”等代词替换为具体实体；基于对话历史与 NER 结果 |
| **3.3 命名实体识别（NER）** | 识别产品名、订单号、人名、时间、金额等；用于查询重写、意图识别、工具调用参数提取 |
| **3.4 意图识别 + 槽位提取** | 分类用户意图（咨询、投诉、技术支持、下单、退货等）；提取关键参数（槽位）：产品名、订单号、日期、原因 |
| **3.5 对话状态跟踪（DST）** | 跟踪当前对话目标（如“用户想退货”）；记录槽位填充状态（是否已提供订单号、原因等） |
| **3.6 可信度评估（Confidence Scoring）** | 判断生成回答是否基于可靠知识；低置信度时主动追问或返回“信息不足” |
| **3.7 引用溯源（Citation / Grounding）** | 生成回答时标注来源（“根据《用户手册》第3章…”）；返回引用的 chunk ID，前端可高亮原文 |
| **3.8 幻觉检测与拒答机制** | 检测回答是否超出知识范围；自动返回：“根据现有资料，无法确认…” 或 “我暂时无法回答” |

---

### 🗄️ 4. 存储与架构

| 功能 | 描述 |
|------|------|
| **4.1 向量存储：PGVector** | 使用 PostgreSQL 扩展 pgvector 存储向量；支持 HNSW 索引加速检索；支持向量压缩（PQ/SQ）与动态增删 |
| **4.2 元数据存储：Elasticsearch** | 存储 chunk 元数据（标题、页码、章节、标签、权限）；支持关键词检索与过滤 |
| **4.3 冷热数据分层** | 热数据 → 内存/Redis；冷数据 → 磁盘/对象存储 |
| **4.4 版本控制** | 支持知识库版本管理（v1.0 vs v2.0）；可按版本检索；支持回滚与对比 |

---

### 📊 5. 可观测性与运营体系

| 功能 | 描述 |
|------|------|
| **5.1 日志与监控** | 记录：用户问题、检索结果、生成回答、耗时；监控指标：检索命中率、回答满意度、延迟、错误率 |
| **5.2 用户反馈闭环** | 提供“有帮助/无帮助”按钮；收集 bad case，用于优化检索策略与知识库 |
| **5.3 A/B 测试** | 对比不同检索策略、模型、提示词的效果；数据驱动优化系统性能 |
| **5.4 自动化知识更新** | 监控 Confluence、数据库、文件系统变更；变更时自动触发加载、切片、向量化、索引更新 |

---

### 🤖 6. AI Agent 能力（未来演进方向）

| 功能 | 描述 |
|------|------|
| **6.1 工具调用（Function Calling / MCP）** | 支持 MCP 协议调用外部服务：<br>• `query_postgresql(query, params)`：查订单、用户数据<br>• `search_elasticsearch(index, keywords)`：搜日志或文档<br>所有调用记录日志，禁止写操作，SQL 参数化防注入 |
| **6.2 自主规划（Planning）** | 将复杂任务拆解为子任务：<br>“帮我退货” → 查订单 → 验证资格 → 生成退货单<br>支持多步推理与状态管理 |
| **6.3 自我反思（Self-Refine）** | 检查回答是否完整；主动补充信息或追问用户以获取缺失参数 |

## 九、评估与优化

### 🔍 评估指标

| 指标 | 说明 |
|------|------|
| Hit Rate@K | top-k 是否包含正确答案 |
| MRR | 正确答案的平均排名倒数 |
| 生成准确率 | 回答是否准确、无幻觉 |
| 端到端延迟 | 从提问到出答案的时间 |
| 幻觉率 | 回答中编造信息的比例 |

---

### 🛠️ 优化手段

- **领域微调**：在企业数据上微调 embedding 或 reranker
- **模型蒸馏**：将大模型知识迁移到小模型
- **混合检索**：稠密 + 稀疏 + 元数据过滤
- **动态 top-k**：根据问题复杂度调整检索范围
- **查询路由优化**：提升分类准确性，减少无效检索
