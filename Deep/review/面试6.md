# Agent 面试总结整理版

## 1. 面试官真正关注什么

这类 agent 面试，本质上通常围绕两条主线展开：

1. 这套东西在线上会不会出事
2. 你是否真的知道自己在用什么、为什么这么用、没用什么

换句话说，面试官不是想听框架名单，而是想看你是否具备：

- 把系统链路讲清楚的能力
- 对技术选型做取舍的能力
- 对线上稳定性、成本、边界、演进的理解

## 2. 知识点清单

这份笔记可以提炼成 8 组核心知识点：

1. 项目如何讲清楚
2. LangGraph 的价值、边界与工程细节
3. 上下文与记忆设计
4. Agent 形态与执行策略
5. 工具、Skill、MCP 的边界
6. RAG 的完整链路与优化点
7. 评测、监控、沙箱与数据闭环
8. 后端基础与线上链路意识

## 3. 详细讲解

### 3.1 项目如何讲清楚

项目介绍不要从框架开始，而要从业务链路开始。

推荐表达顺序：

1. 业务问题是什么
2. 输入输出边界是什么
3. 系统如何把自然语言转成可执行步骤
4. 谁负责工具调用
5. 谁负责汇总结果
6. 失败后状态落在哪一层
7. 最后再说为什么选 LangGraph、LangChain 或其他组件

面试官更想听的是因果链，而不是技术名词。

你应该能回答：

- 用户一句话进来后，第一步发生了什么
- 第一条日志写在哪里
- 哪一层做路由
- 哪一层做工具调用
- 哪一层做状态持久化
- 出错后如何恢复

一句话总结：

先讲系统如何工作，再讲你用了什么框架。

### 3.2 LangGraph 的价值、边界与工程细节

LangGraph 的核心价值不是“更高级”，而是把以下能力从业务代码里抽离出来：

- 分支控制
- 状态管理
- 可持久化执行
- 中断与恢复
- 人机协同

适合使用 LangGraph 的场景：

- 流程存在真实分支
- 需要 checkpoint
- 需要 interrupt
- 需要人工审批或补充信息
- 需要失败恢复和重放

不适合用重型图框架的场景：

- 整个流程只是线性三步
- 没有人机协同
- 没有持久化恢复需求
- 图结构与业务复杂度不匹配

判断是否过度设计，可以看三个问题：

1. 图上的边和条件是否对应真实业务分支
2. checkpoint 里存的状态是否真的需要长期存在
3. 引入框架后是否显著降低了业务代码复杂度

如果回答不上来，大概率就是用重了。

checkpoint 不是“存档”，而是可重放的状态机快照。

真正需要讲清的点有：

- 哪些 channel 的值会写入 checkpoint
- 恢复时 pending 边会不会重跑
- 外部副作用是否有幂等保护
- checkpoint 是否有 TTL、裁剪和脱敏策略

interrupt 的本质不是暂停，而是把流程挂起到一个安全点，等待人工输入、审批或补全信息。

thread_id 最好和业务主键分离：

- thread_id 用于编排会话
- 业务主键用于领域幂等和业务查询

这样可以避免把框架状态和领域模型搅在一起。

状态设计真正难的不是字段类型，而是状态演化策略：

- 哪些字段 append-only
- 哪些字段 merge
- 哪些字段在某条边后清空
- 并发写同一字段时 reducer 的语义是什么

图框架如果没有清晰的状态约定，半年后很容易变成没人敢动的黑箱。

### 3.3 上下文与记忆设计

长对话系统最难的不是“记住”，而是：

- 记对
- 不记爆
- 在需要时准确取回

常见问题包括：

- 早期约束被长上下文稀释
- 工具返回事实与模型幻觉混在一起
- 滚动摘要导致事实漂移
- 检索把不相关的历史聊天又拉回来

短期记忆适合保存：

- 当前任务闭环还需要的上下文
- 最近几轮对话
- 未完成的工具结果
- 路由用的标志位

长期记忆适合保存：

- 用户稳定偏好
- 跨 session 有效的结论
- 可检索知识
- 结构化事实

重要原则：

1. 不是每轮对话都要写入长期记忆
2. 长期记忆写入前要有触发条件和校验
3. 读取时要有 query 改写和 metadata 过滤
4. 记忆要支持时间戳、置信度和删除权

摘要不是无损压缩，所以滚动摘要一定会有事实漂移风险。

更稳的做法是：

- 关键约束结构化保存
- 工具原始结果不要过早丢弃
- 让模型显式引用记忆条目
- 用数据库或事实源做最终真相，而不是完全相信对话历史

### 3.4 Agent 形态与执行策略

ReAct 和 Plan-Execute 的区别，不只是“一个边想边做，一个先计划再执行”。

ReAct 更适合：

- 环境反馈密集
- 路径不可预见
- 需要边探索边修正

Plan-Execute 更适合：

- 步骤大体可枚举
- 工具调用成本高
- 希望计划先被人类确认
- 任务适合显式拆解

ReAct 的难点是如何防止空转。

常见控制手段：

- 最大步数
- token 上限
- wall-clock 超时
- 同参重复调用检测
- 语义重复检测

Plan-Execute 的难点是计划出错后的责任归属。

工程上通常有两种解法：

1. 计划阶段先做人机确认
2. 执行阶段允许局部重规划

否则计划第一步错了，后面整条链都会跟着错。

多智能体架构也不要只背名词。

重点是讲清：

- 角色如何分工
- 通过什么协议通信
- 如何做超时、重试、幂等
- 如何避免消息风暴和责任不清

如果被问到 A2A，不一定要把自己包装成分布式专家。只要能把问题降维成“协议、超时、失败语义、幂等”就已经很专业。

### 3.5 工具、Skill、MCP 的边界

这三个概念最容易被混着讲。

可以这样理解：

- Tool：可调用的原子能力
- Skill：一套可复用、可版本化的工作方法
- MCP：宿主与能力之间的传输和描述契约

进一步说：

- Tool 解决“能不能执行”
- Skill 解决“怎么更稳定地执行”
- MCP 解决“能力如何被发现、描述和调用”

Skill 化不是把 prompt 文档换个名字，而是把高频任务沉淀成：

- 清晰入口
- 明确边界
- 固定流程
- 可测试回归
- 可版本演进

如果系统里有很多 tool，真正的难点不是“写出来”，而是：

- 如何发现
- 如何按需加载
- 如何做权限控制
- 如何避免把全部 schema 一次性塞给模型

常见做法：

- 分层工具集
- meta-tool 做目录索引
- 检索式 tool selection
- 按租户或角色裁剪工具可见范围

工具失败处理要比“重试一下”更细：

- 读路径和写路径要分开设计
- 写操作必须有幂等键
- 重试要有退避和 jitter
- 返回给模型的错误信息要裁剪，避免泄露敏感堆栈

### 3.6 RAG 的完整链路与优化点

RAG 面试不只是问“你用了什么向量库”，真正想看的是你是否理解从建库到生成的完整链路。

核心链路包括：

1. 数据摄入 ingestion
2. chunk 切分
3. embedding
4. 索引构建
5. 检索召回
6. rerank
7. 上下文拼装
8. 生成与引用
9. 更新与回收

关于索引生命周期，必须能讲到：

- 全量重建和增量 upsert 的取舍
- 删除和更新如何处理
- embedding 模型升级后如何重嵌入

常见检索策略：

- hybrid：语义检索和关键词检索结合，通常是默认优选
- multi-query：适合用户表达多样、单 query 召回不稳
- HyDE：适合 query 很短、很口语
- parent-child：兼顾小块召回精度和大块上下文完整性

rerank 之所以重要，是因为召回目标和生成目标不完全一致。

把 top-k 召回出来，不代表顺序就是最优。cross-encoder 这类 reranker 能做更细粒度的相关性判断，通常比让生成模型顺手排序更稳定，也更可控。

RAG 线上问题常见排查方向：

- chunk 是否切坏了语义
- metadata 是否缺失
- query 是否需要改写
- 术语是否做了归一化
- 域内词是否没有进入词表
- 检索不到时是否应该拒答而不是硬编

如果是 Code-RAG，还可以加上：

- 符号级召回
- 调用关系感知
- 文件结构感知

### 3.7 评测、监控、沙箱与数据闭环

agent 系统不能只讲效果，必须讲闭环。

离线评测要关注：

- 数据集如何分层：简单、长尾、对抗
- 标注来自谁
- 是否存在训练泄漏
- 评分规则是否稳定

在线监控要关注：

- 成功率
- 延迟
- token 消耗
- 工具错误率
- 节点耗时
- trace id
- 失败是否可重放

沙箱隔离至少要说清楚边界：

- 网络是否隔离
- 文件系统是否隔离
- 进程权限如何控制
- 是否在容器级做隔离

准确率优化也不要只答“调 prompt”。

可以从四层讲：

- 数据层：难例挖掘、难例合成、bad case 入库
- 模型层：换更强模型、蒸馏、微调
- 系统层：结构化输出、后处理校验、低置信度转人工
- RAG 层：chunk、路由、rerank、query 改写

真正让 agent 越用越好，不靠玄学，靠的是数据闭环和评测驱动发布。

### 3.8 后端基础与线上链路意识

很多 agent 岗位虽然偏大模型，但落地时依然会考后端基础。

原因很简单：系统最终还是要在线上稳定运行。

大文件上传下载这类题，重点不是定义，而是整条链路：

- multipart 和 Content-Length
- 断点续传与校验
- 临时落盘
- 流式解析
- 异步扫描
- MQ 解耦
- 限流与背压
- 进度查询
- 清理与审计

HTTP 请求链路也要能从头讲到尾：

- DNS
- TCP/TLS
- 反向代理
- worker
- web 框架
- ORM
- 连接池
- view 返回

流式响应不要只会背 SSE 和 WebSocket。

最好还能讲到：

- chunked response
- nginx `proxy_buffering off`
- SSE 的 event 格式
- 心跳保活

这类细节很容易暴露出你到底是只会调 SDK，还是理解线上链路。

## 4. 面试时最值得记住的表达方式

### 4.1 回答技术选型

不要说：

- 我用了 LangGraph、LangChain、向量库、RAG、MCP

更好的说法是：

- 这个项目先解决的是某个业务问题
- 我们的输入是 X，输出是 Y
- 中间要经过路由、工具调用、状态持久化和结果汇总
- 因为流程里存在分支、人机协同和恢复需求，所以我选了 LangGraph
- 但如果只是线性流程，我不会强上图框架

### 4.2 回答稳定性

不要只说：

- 我们做了重试、降级、熔断

更好的说法是：

- 我会先区分读操作和写操作
- 网络抖动和代码 bug 的处理方式不同
- 写操作必须做幂等保护
- 错误信息回传给模型前要裁剪
- 所有步骤要能打结构化日志并支持重放

### 4.3 回答长期演进

不要只说：

- 后面还可以继续优化

更好的说法是：

- 新数据源接入要改几处
- bad case 是否能回流到评测集
- 新人接手是否能快速定位链路
- 线上状态有没有生命周期管理

## 5. 一页速记版

可以把整套思路记成下面 8 句话：

1. 先讲业务链路，再讲技术框架
2. 先讲为什么这样设计，再讲用了什么组件
3. LangGraph 的价值在分支、状态、持久化和人机协同
4. 记忆系统难点是记对、取准、控体积
5. Agent 设计重点是策略选择、循环控制和失败恢复
6. Tool 是能力，Skill 是方法，MCP 是契约
7. RAG 难点在索引生命周期、召回质量和引用可信度
8. 面试官最终看的是线上意识、边界意识和取舍能力

## 6. 我的复习重点

如果时间有限，优先准备这几个高频追问：

1. 为什么选 LangGraph，不选更轻的方案
2. checkpoint、interrupt、thread_id 怎么设计
3. 长短期记忆怎么区分，怎么防止记忆污染
4. ReAct 和 Plan-Execute 怎么选
5. Tool、Skill、MCP 分别解决什么问题
6. RAG 的召回、rerank、引用和更新怎么做
7. 线上如何观测、重试、限流、回放和审计
8. 你的系统哪里最容易出事故，怎么兜底
