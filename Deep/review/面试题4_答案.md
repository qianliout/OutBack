## 第一题：长文本摘要与待办提取

### 背景知识：为什么大模型无法直接处理长文本

现代大语言模型（LLM）都基于Transformer架构，其核心是自注意力机制（Self-Attention）。理解这个机制的限制，是理解长文本处理问题的关键。

Transformer通过计算序列中每个位置与所有其他位置的注意力权重来处理信息。对于长度为N的序列，注意力计算的复杂度是O(N²)，这意味着当文本长度翻倍时，计算量会增加四倍。

以GPT-4为例，其上下文窗口从8K到128K tokens不等。即使上下文窗口足够大，过长的文本会导致几个问题：首位置 token 难以承载全部关键信息（称为"丢失在中间"问题）、计算成本急剧上升、生成质量随上下文增长而下降。

2小时的会议录音转写文本通常在2-5万字，远超单次处理能力，且待办事项可能分散在不同的对话片段中。

### 核心挑战分析

处理长会议文本面临四个主要挑战：上下文窗口限制、时间依赖的信息遗漏、噪声干扰、隐式承诺的识别。

### Map-Reduce 方案

Map-Reduce是一种分而治之的思想。Map阶段将长文本切分为多个较短的片段，Reduce阶段将所有片段的摘要汇总。

Map-Reduce的优点是可以并行处理、扩展性强。缺点是由于各片段独立处理，可能丢失跨片段的信息关联。

### Refine 方案

Refine采用顺序处理文本片段，用前一个片段的处理结果来指导后续处理。核心优势是保持了上下文连贯性。

### 待办事项提取的信息抽取理论

待办事项提取融合了多个子任务：说话人角色识别、意图识别、语义角色标注、时间表达式识别。一个好的待办事项应该包含：任务内容、责任人、截止时间、相关上下文、优先级。

### 分块策略的理论考量

固定长度切分最简单，但可能切断句子。重叠切分在相邻块之间保留重叠内容，可以缓解边界信息丢失问题。实践中通常设置重叠和合适的块大小，配合重排序来平衡精确度和召回率。

```python
def map_reduce_summarize(text: str, chunk_size: int = 2000) -> str:
    # 1. 按语义分块（保留句子边界）
    chunks = split_by_sentences(text, chunk_size)

    # 2. Map：对每个chunk并行摘要
    partial_summaries = []
    for chunk in chunks:
        summary = llm.invoke(f"请简要概括以下内容：\n{chunk}")
        partial_summaries.append(summary)

    # 3. Reduce：汇总所有摘要
    combined = "\n".join(partial_summaries)
    final_summary = llm.invoke(f"整合以下摘要为一个连贯的总结：\n{combined}")
    return final_summary

def split_by_sentences(text: str, max_length: int) -> List[str]:
    sentences = re.split(r'[。！？\n]', text)
    chunks, current = [], ""

    for sent in sentences:
        if len(current) + len(sent) <= max_length:
            current += sent + "。"
        else:
            if current:
                chunks.append(current)
            current = sent + "。"

    if current:
        chunks.append(current)
    return chunks
```

```python
def normalize_time(time_expr: str, reference_date: datetime) -> datetime:
    weekday_map = {"周一": 0, "周二": 1, "周三": 2, "周四": 3, "周五": 4, "周六": 5, "周日": 6}
    modifier = 0

    if "下周" in time_expr:
        modifier = 7
    elif "上周" in time_expr:
        modifier = -7

    for day_name, day_num in weekday_map.items():
        if day_name in time_expr:
            current_weekday = reference_date.weekday()
            days_until = (day_num - current_weekday) % 7
            return reference_date + timedelta(days=days_until + modifier)

    return None
```

## 第二题：提示词工程高级应用

### Chain of Thought (CoT) 的理论基础

Chain of Thought（思维链）是一种让大语言模型进行显式推理的提示技术。其核心思想是：与其直接让模型输出答案，不如让它先展示推理过程。

为什么CoT有效？语言模型本质上是基于概率的文本补全工具，对于需要多步推理的复杂问题，模型需要中间步骤来"传播"信息。从认知科学的角度，CoT模仿了人类的"工作记忆"机制。

### CoT变体与进阶

CoT有多种进化形式。Zero-shot CoT不需要示例，只需在问题后加"请分步骤思考"。Few-shot CoT在Prompt中提供几个完整推理示例。Self-Consistency生成多个不同的推理路径，选择出现最频繁的答案。Tree of Thoughts（思维树）鼓励探索多条可能的推理路径。

### ReAct：推理与行动融合

ReAct让模型交替进行推理和外部动作。核心洞察是：纯粹的推理有时不足以完成任务，模型需要与外部世界交互获取信息。

### 推理链设计原则

设计有效的推理链需要遵循几个原则：原子化（每步只完成一个子目标）、有序性（步骤之间有逻辑依赖）、可验证性（中间步骤可以验证正确性）。

### 幻觉产生的原理

从信息论角度看，语言模型的目标是最大化生成文本的概率，而非保证信息的真实性。从认知偏差角度，模型可能会产生"接近记忆"的输出。从知识边界角度看，模型对自己知识的边界并不清楚。

### 幻觉抑制方法

基于不确定性的表达要求模型在不确定时明确表达。外部知识校验利用RAG框架，让模型基于检索到的证据回答。溯源机制要求模型在回答中标注信息来源。一致性检验让模型生成答案后检查自己的答案是否存在逻辑矛盾。

## 第三题：系统性能与并发处理

### 高并发系统的基本概念

5000人同时在线、1秒内响应，是一个典型的高并发低延迟场景。

并发指系统同时处理多个请求的能力。吞吐量指单位时间内系统能处理的请求数量，通常用QPS衡量。延迟指从请求发起到收到响应的时间。

对于5000人同时在线，假设峰值时段每个用户每分钟发起2-3次请求，系统需要支撑的QPS在150-250之间。如果80%的请求可以在1秒内从缓存返回，实际需要支撑的QPS约为50。

### 系统架构分层

高并发系统通常采用分层架构：接入层（限流、路由）、应用层（业务逻辑）、数据层（缓存、数据库）。

### 缓存理论

命中率是缓存返回结果的请求占总请求的比例。LRU淘汰最久未使用的条目。TTL为每个缓存条目设置有效期。

多级缓存是常见的架构模式：本地缓存（进程内，速度最快）、分布式缓存（如Redis）、向量缓存。

### 异步处理理论

同步处理中如果某步处理耗时很长，整个线程都被阻塞。异步处理的模型是：请求→入队→立即返回→后台处理。

消息队列是实现异步的核心组件。队列起到缓冲作用，平滑生产者和消费者之间的速度差异。

### CAP理论

分布式系统无法同时满足一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance）三个特性。对于AI应用，通常选择优先保证可用性，允许短暂的数据不一致。

### Python并发模型

asyncio是协程模型，通过事件循环调度协程任务，适合I/O密集型任务。threading受GIL限制，对CPU密集型任务无法提速。multiprocessing绕过GIL限制，实现真正的并行计算。

### Go并发模型

Go的并发模型基于轻量级线程Goroutine和通信顺序进程（CSP）。通道（Channel）是Goroutine之间的通信机制。

```python
import redis
from functools import lru_cache
from cachetools import TTLCache

class MultiLevelCache:
    def __init__(self):
        # L1: 进程内LRU缓存（1000条，5分钟TTL）
        self.l1 = TTLCache(maxsize=1000, ttl=300)
        # L2: Redis分布式缓存
        self.redis = redis.Redis(host='localhost', port=6379, db=0)

    def get(self, key: str) -> Optional[str]:
        # L1查找
        if key in self.l1:
            return self.l1[key]

        # L2查找
        value = self.redis.get(key)
        if value:
            self.l1[key] = value  # 回填L1
            return value

        return None

    def set(self, key: str, value: str, ttl: int = 3600):
        self.l1[key] = value
        self.redis.setex(key, ttl, value)

    def delete(self, key: str):
        self.l1.pop(key, None)
        self.redis.delete(key)
```

```python
import asyncio
from openai import AsyncOpenAI

class AsyncLLMWrapper:
    def __init__(self, max_concurrent: int = 100):
        self.semaphore = asyncio.Semaphore(max_concurrent)
        self.client = AsyncOpenAI()

    async def chat(self, messages: list) -> str:
        async with self.semaphore:
            response = await self.client.chat.completions.create(
                model="gpt-4",
                messages=messages
            )
            return response.choices[0].message.content

async def handle_request(user_input: str, llm: AsyncLLMWrapper):
    response = await llm.chat([{"role": "user", "content": user_input}])
    return response

async def main():
    llm = AsyncLLMWrapper(max_concurrent=50)

    # 模拟5000并发请求
    tasks = [handle_request(f"请求{i}", llm) for i in range(5000)]

    # 使用信号量控制并发不超过阈值
    results = await asyncio.gather(*tasks)
    return results
```

**限流器实现**：

```python
import time
from threading import Lock

class TokenBucket:
    def __init__(self, rate: int, capacity: int):
        self.rate = rate        # 每秒补充的token数
        self.capacity = capacity
        self.tokens = capacity
        self.last_update = time.time()
        self.lock = Lock()

    def acquire(self, tokens: int = 1) -> bool:
        with self.lock:
            now = time.time()
            # 补充token
            self.tokens = min(
                self.capacity,
                self.tokens + (now - self.last_update) * self.rate
            )
            self.last_update = now

            if self.tokens >= tokens:
                self.tokens -= tokens
                return True
            return False

# 使用示例
limiter = TokenBucket(rate=100, capacity=200)  # 每秒100QPS，突发容量200

def limited_request():
    if limiter.acquire():
        # 处理请求
        return do_request()
    else:
        # 拒绝或排队
        return {"error": "rate limited"}
```

## 第四题：评估体系建设

### 评估的基本概念

人工智能评估面临几个核心挑战：标准答案不存在、质量的多维性、分布漂移。

### RAG系统的评估维度

检索阶段的指标：精确率（检索回来的文档有多少是真正相关的）、召回率（所有相关文档中有多少被检索回来了）。

生成阶段的指标：忠实度（生成内容是否忠实于检索到的上下文）、答案正确性、答案相关性。

### 精确率和召回率的深入理解

以具体例子说明。假设用户问"谁负责项目A？"，知识库中有3篇相关文档。系统检索返回了5篇文档，其中3篇是真正相关的。

召回率 = 3 / 3 = 100%，精确率 = 3 / 5 = 60%。

### RAGAS评估框架

RAGAS的核心设计理念是用LLM自动评估。它定义了几种评估维度：Context Precision、Faithfulness、Answer Relevancy、Context Recall。

### LLM-as-Judge方法论

LLM-as-Judge是用强大的LLM来评估其他系统输出的质量。实现方式有评分制（1-5分）和对比制。局限包括Judge模型自身的偏见、无法评估事实正确性。

### 测试数据集构建

构建方法有人工标注（质量高但成本高）、合成数据（成本低但需要筛选）、真实数据（需要脱敏和标注）。对抗性测试数据专门设计用来"难倒"系统的案例。

## 第五题：数学基础与算法原理

### 向量空间模型

向量空间模型的核心思想是将文本表示为向量空间中的点。一个文档D可以表示为一个N维向量：D = (w₁, w₂, ..., wₙ)。TF-IDF是常见的权重计算方法：词在文档中出现越多越重要，但在整个语料库中出现越多越不重要。

### 词嵌入与语义向量

Word2Vec、GloVe等模型将词映射为稠密向量，相似的词在向量空间中距离较近。向量运算能捕捉语义关系：vec("king") - vec("man") + vec("woman") ≈ vec("queen")。

### 余弦相似度的数学原理

余弦相似度衡量两个向量在方向上的相似性：cos(A, B) = (A · B) / (||A|| × ||B||)。点积A·B = Σᵢ aᵢ × bᵢ。余弦值范围是[-1, 1]，实际应用中通常在0到1之间。

### 欧几里得距离的数学原理

欧几里得距离是直线距离：d(A, B) = ||A - B|| = sqrt(Σᵢ (aᵢ - bᵢ)²)。取值范围是[0, +∞)。

### 为什么高维文本向量首选余弦相似度

语义方向vs绝对位置——文本embedding捕捉的是语义方向，余弦相似度能忽略长度差异。维度灾难——随着维度增加，欧几里得距离的区分度下降。计算效率——余弦相似度只需计算点积。文本embedding通常经过归一化处理，模长信息无意义。

### 近似最近邻搜索（ANNS）问题

当数据规模达到百万级以上时，精确的最近邻搜索变得不切实际。ANNS通过允许一定程度的误差，换取搜索速度的大幅提升。

### HNSW算法理论

HNSW（Hierarchical Navigable Small World）的理论基础来自图论中的"小世界"现象。HNSW构建一个多层图结构：上层图的边更长，允许快速"跳跃"；下层图的边更短，允许精确搜索。

M（每个节点的最大连接数）：M越大，搜索精度越高，但内存占用也越大。efConstruction（构建时的搜索范围）：值越大，索引质量越好。efSearch（搜索时的搜索范围）：值越大，召回率越高。

### 其他ANNS算法

IVF基于聚类的思想。PQ将高维向量分割成多个子向量单独量化，内存占用极低。LSH使用多个哈希函数，增量友好但精度相对较低。

```python
import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def batch_cosine_similarity(query: np.ndarray, vectors: np.ndarray) -> np.ndarray:
    # query: (d,) vectors: (n, d)
    # 返回: (n,)
    return np.dot(vectors, query) / (
        np.linalg.norm(vectors, axis=1) * np.linalg.norm(query)
    )
```

**HNSW向量检索（使用faiss）**：

```python
import faiss
import numpy as np

class VectorStore:
    def __init__(self, dimension: int = 1536):
        self.dimension = dimension
        # 初始化HNSW索引
        self.index = faiss.IndexHNSWFlat(dimension, 16)  # M=16
        self.index.hnsw.efConstruction = 200
        self.index.hnsw.efSearch = 100

        self.documents = []

    def add(self, vectors: np.ndarray, documents: List[str]):
        # vectors: (n, dimension)
        vectors = vectors.astype('float32')
        self.index.add(vectors)
        self.documents.extend(documents)

    def search(self, query_vector: np.ndarray, k: int = 5) -> List[dict]:
        query_vector = query_vector.astype('float32').reshape(1, -1)

        # 搜索
        distances, indices = self.index.search(query_vector, k)

        results = []
        for dist, idx in zip(distances[0], indices[0]):
            results.append({
                "document": self.documents[idx],
                "distance": float(dist),
                "index": int(idx)
            })

        return results
```

## 第六题：场景故障排查

### 问题分析

"下周三"被错误识别为"本周三"是一个典型的时间实体识别错误。这类错误可能给用户造成严重困扰——日程安排错误一周。

从错误类型分析，这属于语义理解错误——模型理解了"周三"但没有正确理解"下"的修饰范围。或者是参考时间理解错误。

### 时间表达的语言学特征

时间表达有几种类型：绝对时间（如"2024年3月15日"）、相对时间（如"下周"、"三天后"，需要结合参考时间）、模糊时间（如"最近"）。

会议场景中的时间表达有其特点：大量使用相对时间，时间参照点不一定是说话时刻，而是会议召开的时间。

### 防御性编程理论

防御性编程假设任何外部输入都可能是错误的或恶意的。核心原则包括：不要信任任何外部输入、假设任何操作都可能失败、在关键决策点引入人工确认。

### 多层防御策略

针对时间识别错误，应该构建多层次的防御体系：输入层（Prompt引导谨慎处理）、解析层（结构化时间对象）、验证层（外部可信来源校验）、交互层（用户确认）。

### 人机回环（Human-in-the-Loop）理论

人机回环（HITL）是一种将人类智能融入自动化流程的设计模式。关键问题是：在哪些环节引入HITL？答案是计算预期损失——损失越大，越需要人工介入。

**时间解析器核心逻辑**：

```python
from datetime import datetime, timedelta
from dataclasses import dataclass
from typing import Optional

@dataclass
class TimeExpression:
    weekday: Optional[int] = None      # 0=周一, 6=周日
    modifier: Optional[str] = None     # "this_week", "next_week", "last_week"
    month_day: Optional[int] = None    # 月份中的某天
    relative_days: Optional[int] = None  # 相对天数，如+3表示3天后

    def to_absolute_date(self, reference: datetime) -> Optional[datetime]:
        if self.weekday is not None and self.modifier is not None:
            current_weekday = reference.weekday()
            days_until = (self.weekday - current_weekday) % 7

            if self.modifier == "next_week":
                days_until += 7
            elif self.modifier == "last_week":
                days_until -= 7

            return reference + timedelta(days=days_until)

        return None

class TimeParser:
    def __init__(self):
        self.weekday_map = {
            "周一": 0, "星期一": 0,
            "周二": 1, "星期二": 1,
            "周三": 2, "星期三": 2,
            "周四": 3, "星期四": 3,
            "周五": 4, "星期五": 4,
            "周六": 5, "星期六": 5,
            "周日": 6, "星期日": 6, "周末": 5
        }

    def parse(self, text: str, reference: datetime) -> TimeExpression:
        expr = TimeExpression()

        # 解析修饰词
        if "下周" in text:
            expr.modifier = "next_week"
        elif "本周" in text:
            expr.modifier = "this_week"
        elif "上周" in text:
            expr.modifier = "last_week"

        # 解析星期几
        for day_name, day_num in self.weekday_map.items():
            if day_name in text:
                expr.weekday = day_num
                break

        return expr
```

```python
class TimeValidator:
    def __init__(self, calendar_api):
        self.calendar = calendar_api

    async def validate_and_confirm(
        self,
        time_expr: TimeExpression,
        user_id: str,
        reference_date: datetime
    ) -> dict:
        # 1. 转换为绝对日期
        absolute_date = time_expr.to_absolute_date(reference_date)

        if absolute_date is None:
            return {
                "valid": False,
                "reason": "无法解析时间表达"
            }

        # 2. 合理性检查
        today = reference_date.date()
        target_date = absolute_date.date()
        days_diff = (target_date - today).days

        # 如果日期在过去或太远，标记为可疑
        if days_diff < 0:
            return {
                "valid": False,
                "reason": f"日期{absolute_date.strftime('%Y-%m-%d')}在过去"
            }

        if days_diff > 60:
            return {
                "valid": False,
                "reason": f"日期距离今天超过60天，请确认"
            }

        # 3. 日历冲突检查
        events = await self.calendar.get_events(
            user_id=user_id,
            start=absolute_date.replace(hour=0, minute=0),
            end=absolute_date.replace(hour=23, minute=59)
        )

        if events:
            return {
                "valid": True,
                "requires_confirmation": True,
                "date": absolute_date,
                "message": f"您选择的{absolute_date.strftime('%Y年%m月%d日')}有{len(events)}个会议，是否确认？",
                "conflicts": events
            }

        return {
            "valid": True,
            "requires_confirmation": False,
            "date": absolute_date,
            "message": f"确认安排在{absolute_date.strftime('%Y年%m月%d日')}"
        }
```

```python
class ConfirmationManager:
    def __init__(self):
        self.pending_confirmations = {}

    def request_confirmation(self, user_id: str, action: dict) -> str:
        confirmation_id = generate_uuid()

        self.pending_confirmations[confirmation_id] = {
            "user_id": user_id,
            "action": action,
            "created_at": datetime.now(),
            "expires_at": datetime.now() + timedelta(minutes=5)
        }

        return confirmation_id

    def confirm(self, confirmation_id: str, user_response: str) -> dict:
        pending = self.pending_confirmations.get(confirmation_id)

        if not pending:
            return {"success": False, "reason": "确认已过期"}

        if user_response in ["确认", "好的", "是", "ok"]:
            return {"success": True, "action": pending["action"]}
        elif user_response in ["取消", "否", "不对"]:
            return {"success": False, "reason": "用户取消"}
        else:
            # 可能是用户提供了修正信息
            return {"success": False, "reason": "需要进一步处理", "correction": user_response}
```
