## 1. 毫秒级启动与资源池化设计

### 题目本质

这道题考查的不是单一的冷启动优化，而是下面几个问题的综合平衡：

- 启动速度要快
- 成本不能失控
- 租户之间必须隔离
- 长连接和会话状态要可控
- 平台要能支撑流量波峰波谷

很多候选人会直接说“做预热池”。这只答对了 20%。真正的关键是：池化的层次是什么，池中的对象是什么，状态如何回收，如何避免脏实例复用。

### 基础原理

冷启动通常来自 6 个层次：

1. 镜像拉取
2. 容器或 Pod 创建
3. 运行时初始化
4. 语言解释器启动，比如 Python、Node.js
5. 依赖加载，比如模型、浏览器、插件
6. 业务会话初始化，比如登录态、长连接、工具握手

如果只优化 Pod 冷启动，通常只能从秒级降到几百毫秒；要做到“毫秒级可接单”，必须继续往进程级、会话级做池化。

### 总体架构

推荐做分层资源池，而不是单一资源池。

1. 容器池
- 预先拉起最小数量的 Worker Pod
- 解决镜像拉取和 Pod 调度延迟

2. 运行时池
- 在 Pod 内预先启动 Python/Node.js Runtime
- 提前加载公共依赖、SDK、证书、配置

3. 浏览器池
- 对浏览器自动化场景，预先拉起 Browser Process
- 请求到来时只创建 Browser Context 或 Page

4. 会话池
- 对终端、ADB、云手机等资源预先建立连接
- 请求到来时绑定租户上下文

5. 快照池
- 对于重型环境使用快照恢复，而不是完整启动
- 如 Firecracker snapshot、CRIU、内存快照恢复

### 为什么分层池化

不同资源初始化成本完全不同：

- Pod 启动通常是 100ms 到数秒
- Python 进程通常几十毫秒到几百毫秒
- Headless Chrome 完整启动可能几百毫秒到 2 秒以上
- 登录态恢复、插件加载、页面预热可能更慢

因此最优方案不是“一个大池子”，而是让不同层分别缓存最贵的启动阶段。

### 推荐方案

#### 1. 请求分级

根据任务类型做不同池化策略：

- 轻任务：终端命令、短时 Python 执行，走 Runtime Pool
- 中任务：Node.js + 工具调用，走 Runtime + Session Pool
- 重任务：浏览器、云手机、图形环境，走 Browser Pool 或 MicroVM Pool

#### 2. 预热策略

预热不能固定写死，要根据历史流量、时间分布和 SLA 动态调整。

常用做法：

- 固定基线池：保证最低 SLA
- 基于近期 QPS 的弹性池：最近 1 分钟、5 分钟的流量窗口
- 基于预测的提前预热：按小时、节假日、业务活动预测
- 分租户配额池：大客户保留池，小客户共享池

#### 3. 实例借还机制

池中的实例不是无限复用，必须有明确的生命周期：

- available：可借出
- assigned：已分配未开始
- running：执行中
- draining：等待回收
- resetting：清理中
- quarantined：疑似污染，隔离观察
- retired：销毁

#### 4. 状态清理

这是整道题最重要的部分之一。

必须清理：

- 进程环境变量
- 临时文件和下载目录
- 浏览器 cookie、localStorage、sessionStorage
- 页面进程、service worker、扩展残留
- shell 历史和后台进程
- 网络连接和端口占用
- 用户凭证和缓存

如果清不干净，就会产生跨租户数据泄露。

### 隔离模型

不能因为追求快启动就放弃隔离。推荐做“双层隔离”：

1. 租户级隔离
- 通过 Pod、MicroVM、gVisor、Firecracker 等提供强隔离边界

2. 会话级隔离
- 在同一基础实例上通过 Browser Context、Namespace、独立工作目录做轻量隔离

适用策略：

- 高安全租户：每任务独占 MicroVM
- 普通租户：共享 Worker Pod，但任务级独立进程和目录
- 浏览器任务：共享 Browser Process，但页面上下文必须独立

### 快照技术原理

#### CRIU

CRIU 可以将 Linux 进程的内存、文件描述符、网络连接等状态 checkpoint 到磁盘，再 restore 回来。

优点：

- 对进程级恢复很快
- 适合预加载了大量依赖的运行时

缺点：

- 与内核特性、文件描述符、网络状态兼容性相关
- 复杂浏览器进程恢复成本高，运维复杂

#### Firecracker Snapshot

Firecracker 是 MicroVM 技术。它的快照恢复本质上是恢复虚拟机的内存和设备状态。

优点：

- 隔离强
- 恢复速度快于完整启动 VM
- 适合高风险代码执行和云手机基础环境

缺点：

- 网络和设备恢复复杂
- 运维比容器更重

### 成本与延迟的平衡

可以用一个简单的目标函数来理解：

- 总成本 = 资源闲置成本 + 启动超时带来的 SLA 违约成本 + 调度复杂度成本

实践中常用三个控制参数：

1. min_pool_size
- 最低保留实例数，确保 SLA

2. max_warm_ratio
- 预热实例占峰值容量的比例，限制浪费

3. idle_ttl
- 实例闲置多久后回收

通常的经验做法：

- 轻量 Runtime Pool 保持较高预热比例
- 浏览器和云手机池保持小基线池 + 快照池
- 对突刺流量使用排队和优先级调度，而不是无限预热

```go
type WorkerState string

const (
    Available   WorkerState = "available"
    Assigned    WorkerState = "assigned"
    Running     WorkerState = "running"
    Resetting   WorkerState = "resetting"
    Quarantined WorkerState = "quarantined"
)

type Worker struct {
    ID          string
    Type        string
    TenantClass string
    State       WorkerState
    LastUsedAt  time.Time
    Dirty       bool
}

func AcquireWorker(pool []*Worker, taskType string, tenantClass string) *Worker {
    for _, w := range pool {
        if w.State == Available && w.Type == taskType && w.TenantClass == tenantClass && !w.Dirty {
            w.State = Assigned
            return w
        }
    }
    return nil
}

func ReleaseWorker(w *Worker, resetOK bool) {
    if !resetOK {
        w.State = Quarantined
        return
    }
    w.State = Resetting
    go func() {
        CleanupWorkspace(w.ID)
        CleanupBrowserContext(w.ID)
        CleanupNetworkNamespace(w.ID)
        w.State = Available
        w.LastUsedAt = time.Now()
        w.Dirty = false
    }()
}
```

可以这样回答：

## 2. 大规模并发下的任务调度系统

### 题目本质

这道题考查的是分布式调度系统设计，而不是单纯消息队列使用。

系统要解决的问题包括：

- 10 万并发任务如何接住
- 长短任务混跑如何避免相互拖垮
- 节点故障如何恢复
- 重试如何不重复执行
- 如何避免惊群效应和热点分区

### 基础原理

调度系统一般包含四个层次：

1. 接入层
- 接收任务提交请求

2. 控制层
- 做排队、优先级


3. 执行层
- 真正执行任务的 Worker 节点

4. 状态层
- 存储任务状态、租约、检查点、结果

高并发场景下，最重要的原则是：

- 状态外置
- 执行无状态化
- Worker 采用拉模型
- 用租约而不是强锁

### 为什么推荐拉模型

推模型的问题：

- 控制器会成为瓶颈
- 节点负载感知不实时
- 易出现惊群和热点

拉模型的思路：

- Worker 主动从队列领取任务
- 只有空闲 Worker 才会拉任务
- 更容易做背压控制

### 总体架构

推荐架构如下：

1. API Gateway
- 接收任务请求，生成 task_id

2. Task Manager
- 写任务元数据到数据库
- 按任务类型、优先级、租户分发到分片队列

3. Queue Layer
- Kafka、Pulsar、RabbitMQ 都可
- 更推荐支持分区和顺序控制的消息系统

4. Scheduler
- 不直接执行任务，而是维护分片、优先级、重试策略、租约策略

5. Worker Pool
- Worker 按资源标签订阅匹配队列
- 如 browser、python、mobile、gpu

6. State Store
- Redis 记录租约和短状态
- MySQL 或 PostgreSQL 记录任务主状态
- 对长任务额外存 checkpoint

### 调度算法

#### 1. 分层队列

建议按下面维度拆分：

- 任务类型分队列
- 优先级分队列
- 租户分队列
- 地域或机房分队列

这样可以避免浏览器长任务阻塞短终端任务。

#### 2. 拉取策略

Worker 拉取任务时采用：

- 先按资源标签匹配
- 再按优先级
- 再考虑公平性
- 再考虑租户配额

可以采用加权公平队列 WFQ 或 deficit round robin。

#### 3. 租约机制

任务不是“分配完成就结束”，而是：

- Worker 获取任务租约
- 周期性续租
- 如果租约过期，任务重新回到队列

这样能天然处理节点宕机。

### 惊群效应怎么解决

惊群效应本质是大量 Worker 同时竞争同一批任务。

解决手段：

1. 分片队列
- 每个 Worker 只关注一部分分区

2. 长轮询
- 队列空时阻塞等待，不做高频轮询

3. 本地令牌桶
- 控制单 Worker 的拉取速率

4. 预分配窗口
- 一次最多拉 N 个任务，执行完再拉

5. 分布式随机抖动
- 避免所有节点同频轮询

### 节点故障后如何无缝漂移

要做到无缝漂移，关键在于任务状态设计。

任务状态机示例：

- pending
- leased
- starting
- running
- checkpointing
- succeeded
- failed
- retry_wait
- cancelled

对于长任务，不要把所有状态放在内存里，而要周期性写 checkpoint：

- 浏览器任务记录 URL、cookie、最近操作步骤
- 代码执行任务记录中间文件、stdout offset、阶段结果
- 云手机任务记录设备状态和最近动作

这样节点挂掉后，新 Worker 可以从最近检查点恢复，而不是从头执行。

### 幂等与重试

重试风暴是调度系统的常见灾难。

必须做：

- task_id 全局唯一
- 每次执行 attempt_id 唯一
- 结果写入要幂等
- 外部副作用操作要有去重键

例如发消息、扣费、写数据库，都要带 idempotency key。

### 关键代码

任务领取和租约续约：

```python
from dataclasses import dataclass
from datetime import datetime, timedelta

@dataclass
class Lease:
    task_id: str
    worker_id: str
    expire_at: datetime

def acquire_task(task_queue, worker_id, now):
    task = task_queue.pop_ready_task(worker_id)
    if not task:
        return None
    lease = Lease(
        task_id=task["task_id"],
        worker_id=worker_id,
        expire_at=now + timedelta(seconds=30),
    )
    save_lease(lease)
    mark_task_state(task["task_id"], "leased")
    return task

def renew_lease(task_id, worker_id, now):
    lease = get_lease(task_id)
    if lease.worker_id != worker_id:
        raise RuntimeError("lease stolen")
    lease.expire_at = now + timedelta(seconds=30)
    save_lease(lease)

def requeue_expired_tasks(now):
    for lease in scan_expired_leases(now):
        mark_task_state(lease.task_id, "retry_wait")
        push_back_to_queue(lease.task_id)
```

### 面试中的高质量回答方式

“我会采用控制面和执行面分离的调度架构。执行节点使用拉模型从分片队列中领任务，而不是调度器主动推送，因为拉模型更容易做背压和容量感知。每个任务用租约管理执行权，节点通过心跳续租，租约过期后自动回收并重试。对于长任务会把进度、stdout offset 或浏览器步骤定期 checkpoint 到外部状态存储，节点故障后由新节点恢复。为避免惊群，我会做分区队列、长轮询、令牌桶限速和随机抖动。”

## 3. 多租户环境下的安全沙箱设计

### 题目本质

这题考查的是你是否真的理解“代码执行平台”的风险边界。

不要只回答 Docker 隔离。真正的风险是：

- 代码逃逸到宿主机
- 横向访问其他租户
- 滥用 CPU、内存、磁盘、网络
- 下载恶意负载
- 利用浏览器漏洞或内核漏洞提权
- 窃取凭证和环境变量

### 威胁模型

先做威胁建模，再谈防御。

攻击面主要包括：

1. 内核攻击面
- 利用系统调用触发内核漏洞

2. 文件系统攻击面
- 访问宿主机路径、挂载点、凭证文件

3. 网络攻击面
- 扫内网、访问元数据服务、发起 DDoS

4. 进程攻击面
- ptrace、共享进程空间、句柄继承

5. 浏览器攻击面
- 恶意网页利用 V8、GPU、沙箱漏洞

6. 供应链攻击面
- 镜像投毒、依赖投毒

### 基础原理

#### Namespace

Namespace 负责隔离可见性：

- pid namespace：隔离进程号
- mount namespace：隔离挂载点
- net namespace：隔离网络栈
- user namespace：隔离用户 ID 映射

它解决的是“看见谁”的问题，不解决“能做什么”的问题。

#### Cgroups

Cgroups 负责限制资源：

- CPU
- 内存
- IO
- pids

它解决的是“能吃多少资源”的问题。

#### Capabilities

Linux 把 root 权限拆成很多小能力，比如：

- CAP_SYS_ADMIN
- CAP_NET_ADMIN
- CAP_SYS_PTRACE

安全原则是默认全部去掉，只加必要能力。

#### Seccomp

Seccomp 用来过滤系统调用。

本质上是定义一个 allowlist 或 denylist，决定某些 syscall 是否允许执行。

对代码执行平台来说，推荐默认拒绝危险 syscall，如：

- mount
- ptrace
- clone3 某些模式
- bpf
- keyctl
- perf_event_open

#### AppArmor / SELinux

LSM 机制提供更细粒度的访问控制，如：

- 限制进程可访问哪些路径
- 限制进程可执行哪些文件
- 限制特定网络行为

#### eBPF

eBPF 不能替代隔离，但很适合做运行时观测和策略执行，例如：

- 网络出口审计
- 异常 syscall 监控
- DNS 行为审计
- 异常流量熔断

### 推荐安全架构

做纵深防御，不依赖单点安全。

#### 第 1 层：强隔离执行边界

高风险任务推荐：

- Firecracker MicroVM
- gVisor
- Kata Containers

普通风险任务可用：

- 容器 + user namespace + seccomp + LSM

#### 第 2 层：最小权限运行

- rootless container
- 只读根文件系统
- 临时可写目录挂载到独立 workspace
- 去掉所有默认 capabilities
- 禁止 privileged

#### 第 3 层：网络隔离

- 默认禁止出网
- 采用按域名或按服务白名单放行
- 禁止访问云厂商 metadata 地址
- 单租户独立 egress policy

#### 第 4 层：文件系统隔离

- `/tmp`、工作目录独立挂载
- 禁止挂载宿主机目录
- 下载文件单独隔离
- 所有工件上传后统一病毒扫描

#### 第 5 层：运行时审计和熔断

- eBPF 审计异常连接和 syscall
- CPU、内存、磁盘 IO 超阈值自动熔断
- 异常进程树自动隔离实例

### 浏览器自动化场景的特殊风险

浏览器不能简单看成普通进程，因为它本身就很复杂：

- 渲染进程多
- 有 GPU 相关能力
- 有下载能力
- 有 shared memory 使用
- 常涉及不可信网页

建议：

1. 浏览器进程运行在更强隔离环境中
- 如独立 Pod 或 MicroVM

2. 禁止无关能力
- 禁止宿主机设备访问
- 禁止共享主机网络

3. 下载目录单独挂载并扫描

## 4. 统一工具调用 API 的标准化与隔离

### 题目本质

这题考查的是平台抽象能力。

平台要支持：

- 浏览器
- 终端
- 云手机
- 文件系统
- HTTP 工具
- 数据库工具

如果上层 Agent 直接耦合每个工具的原生接口，系统会很快失控。

### 为什么必须做统一抽象

统一抽象的价值：

- 统一鉴权
- 统一超时
- 统一取消
- 统一审计
- 统一流式事件
- 统一错误码
- 统一会话生命周期

否则每个工具都会自己管理连接、流式输出、重试和超时，平台几乎无法治理。

### 建议抽象模型

核心对象建议如下：

1. ToolSpec
- 工具元信息和能力描述

2. ToolSession
- 一次长生命周期工具会话

3. ToolInvocation
- 一次具体调用

4. ToolEvent
- 流式事件输出

5. ToolArtifact
- 截图、录像、文件等产物

6. ToolResult
- 最终结果

### 统一事件流模型

不同工具本质上都可以抽象成事件流。

比如：

- 终端输出：stdout、stderr、exit_code
- 浏览器：dom_snapshot、console、screenshot、network_event
- 云手机：frame、touch_ack、device_log

统一后可以设计为：

- metadata
- chunk
- heartbeat
- artifact
- status
- error
- done

### 协议选择

#### gRPC / HTTP2

优点：

- 原生双向流
- Header 压缩
- 连接复用
- 适合内部服务间调用

#### WebSocket

适合：

- 对外前端控制台
- 浏览器实时调试

推荐做法：

- 服务内部：gRPC
- 面向控制台：WebSocket 或 SSE

### 超时模型设计

超时不是一个值，而是多个阶段：

1. queue_timeout
- 任务排队等待多久

2. start_timeout
- 工具实例多久内必须启动

3. exec_timeout
- 业务执行最长时长

4. idle_timeout
- 流式连接空闲多久断开

5. hard_timeout
- 最终强杀时间

### 隔离要求

统一接口不等于共享底层资源。需要支持：

- 会话隔离
- 租户鉴权
- 工具级别 ACL
- 参数校验
- 输出脱敏

例如 `terminal.exec` 和 `browser.navigate` 虽然都走统一网关，但底层执行资源不一定共享。

### 关键代码

gRPC 风格接口定义：

超时控制示例：

  }
}

## 5. 容器化、虚拟化与云手机的深度融合

### 题目本质

这题考查你是否真正理解容器和虚拟化的边界，以及 Kubernetes 在设备调度上的能力。

对于云手机、浏览器自动化这类重资源场景，单纯 Pod 化往往会遇到：

- 设备资源不可见
- GPU、声卡、虚拟显示资源难管理
- 网络拓扑复杂
- 安全隔离要求更高

### 基础原理

#### 容器和虚拟机区别

容器共享宿主机内核，优点是轻量和快；虚拟机有独立 Guest OS，优点是隔离强。

MicroVM 介于两者之间：

- 接近 VM 的隔离
- 接近容器的启动速度

#### Device Plugin

Kubernetes 默认只知道 CPU、内存等标准资源，不知道 GPU、FPGA、虚拟设备。

Device Plugin 的作用是：

1. 在节点上发现设备
2. 把设备资源注册给 kubelet
3. 在 Pod 调度时把设备分配给容器

它本质上是节点级设备资源的上报和分配协议。

#### RuntimeClass

用于告诉 K8s 某个 Pod 应该使用什么运行时，例如：

- runc
- gVisor
- kata

这对高隔离 Agent 很重要。

### 云手机场景的推荐架构

推荐分成三层：

1. 控制面
- 设备编排、状态管理、分配策略、回收策略

2. 计算面
- 运行 Android Emulator、浏览器、图形代理、音视频采集

3. 媒体与控制通道
- 视频流、触控指令、ADB 指令、日志回传

### 设备暴露方式

例如把 GPU 或虚拟显示设备暴露给容器：

- GPU：通过厂商 Device Plugin
- `/dev/kvm`：用于虚拟化加速
- 虚拟 framebuffer：通过自定义 Device Plugin 或挂载策略
- 声卡、摄像头等：按需暴露，默认不暴露

### 如果采用 MicroVM 运行云手机

重点问题是网络打通。

常见做法：

1. 宿主机 bridge + tap
- 每个 MicroVM 挂一个 tap 设备
- 通过 bridge 接入宿主机网络

2. CNI 集成
- 为 MicroVM 分配独立 IP
- 让其看起来像 K8s 中的一个可路由工作负载

3. Sidecar / Proxy
- 通过宿主机代理转发 ADB、视频流、控制流

### 为什么 MicroVM 网络复杂

容器直接复用宿主机网络 namespace 或 veth pair；MicroVM 则要模拟完整网卡设备，因此：

- 启动更复杂
- IP 管理更复杂
- 流量观测更复杂

但优点是隔离更强，适合高风险多租户环境。

## 6. 弹性伸缩策略与资源成本控制

### 题目本质

这题不是问你会不会配 HPA，而是问你能否设计出适合 Agent 业务的弹性系统。

Agent 业务的特点：

- 流量波动大
- 任务时长差异极大
- 有长连接
- 有状态
- 部分实例很贵，比如浏览器、云手机、GPU

### 基础知识

#### HPA

根据指标水平自动扩缩 Pod 副本数。

#### VPA

动态调整 Pod 的资源请求值。

#### Cluster Autoscaler

当 Pod 放不下时扩容节点。

这三者的职责不同，不能混用概念。

### 为什么 CPU 不是好指标

在 Agent 平台里，CPU 常常滞后于业务压力。

例如：

- 队列积压很多，但 CPU 还没打满
- 浏览器会话很多，但单个会话很空闲
- WebSocket 长连接占资源但 CPU 不高

因此必须用业务指标。

### 推荐指标体系

#### 通用指标

- queue_backlog：待执行任务数
- queue_latency_p95：任务排队延迟
- running_sessions：运行中会话数
- lease_utilization：执行槽位利用率

#### 浏览器场景指标

- active_browser_contexts
- page_load_p95
- screenshot_queue_depth

#### 云手机场景指标

- active_devices
- media_bandwidth_mbps
- frame_extract_backlog

#### 连接场景指标

- websocket_connections
- idle_session_ratio

### 防止伸缩震荡

震荡的本质是：

- 指标波动快
- 扩容生效有延迟
- 缩容太激进

常用抑制手段：

1. 扩容快、缩容慢

2. 冷却时间
- 如扩容后 1 到 3 分钟内不缩容

3. 指标滑动窗口
- 用 1 分钟平均值而不是瞬时值

4. 最小预热池
- 不能缩到 0，尤其是重资源服务

5. 分层伸缩
- 前台接入层、调度层、执行层分开扩缩

### 休眠-唤醒机制

这是 Agent 业务里非常重要的设计。

对于长时间无交互但要保留状态的 Agent，可以做：

1. 状态下沉
- 把上下文、变量、文件索引、浏览器快照写到外部存储

2. 计算释放
- 释放 Pod、浏览器实例、流媒体处理进程

3. 事件唤醒
- 新消息、新 Webhook、新定时器触发时恢复

4. 快照恢复
- 从保存的状态快速恢复到最近活跃状态

自定义指标 HPA 示例：

## 7. 全链路可观测性与调试系统

### 题目本质

这题考查你是否有能力排查复杂 AI Agent 系统的问题。

Agent 执行失败通常不是单点失败，而是链路失败：

- Prompt 问题
- 模型输出偏差
- 工具调用失败
- 浏览器页面变化
- 运行时异常
- 网络错误
- 超时与重试叠加

### 可观测性的四个支柱

推荐不要只讲日志，要讲完整观测体系：

1. Metrics
- 看整体趋势

2. Logs
- 看详细上下文

3. Traces
- 看跨服务调用链

4. Artifacts
- 截图、录像、网页快照、终端回放

对 Agent Infra 来说，Artifacts 非常关键，因为很多问题仅靠文本日志无法还原。

### OpenTelemetry 基础原理

#### Trace

一次完整请求链路。

#### Span

链路中的一个操作片段。

#### Context Propagation

在跨服务、跨线程、跨异步任务时把 trace 信息传下去。

对于 Agent 系统，可以这样切分 Span：

- 用户请求入口
- Planner 调用 LLM
- LLM token stream
- Tool Gateway 调用
- Browser Action
- Sandbox Exec
- Artifact Upload

### 如何串联 LLM 和底层工具

这是高质量设计的重点。

建议：

1. 给每次 Agent Run 分配 run_id

2. 给每个 tool invocation 分配 invocation_id

3. 所有日志、截图、录像、stdout、token stream 都打上：
- trace_id
- span_id
- run_id
- task_id
- tenant_id

4. 关键动作写结构化 Event

这样你才能从一次失败的用户反馈回溯到完整执行链路。

### 日志存储设计

文本日志和媒体日志不能混存。

推荐分层：

1. 结构化日志
- Elasticsearch、ClickHouse、Loki

2. Trace 数据
- Jaeger、Tempo、OTel Collector

3. 大对象工件
- S3、OSS、MinIO
- 如截图、录像、HAR 文件、DOM 快照

4. 索引元数据
- MySQL 或 PostgreSQL
- 用于把 artifact_id 映射到 trace_id、task_id

### 如何存储和检索大量截图与录像

建议不要把二进制媒体塞进日志系统。

正确做法：

- 二进制放对象存储
- 元数据进检索系统
- 按租户、时间、任务、trace 建索引
- 热数据保留低时延访问
- 冷数据归档到低成本存储

## 8. 数据流转与长期记忆存储

### 题目本质

这题不是单纯问你“向量库还是 KV”。真正考的是：

- 数据怎么分类
- 什么数据该实时读写
- 什么数据适合召回
- 敏感信息如何保护
- 成本如何控制

### 数据分类

在 Agent 平台里，建议至少分 5 类数据：

1. 短期上下文
- 当前对话窗口、临时变量、当前任务状态

2. 长期记忆
- 用户偏好、长期目标、历史行为摘要

3. 执行状态
- 任务进度、工具会话、检查点

4. 工件数据
- 文件、截图、录像、网页内容

5. 敏感数据
- 凭证、Token、Cookie、私密配置

### KV 和向量库的边界

#### KV 适合什么

- 精准 Key 查询
- 低延迟状态读写
- 会话状态
- 分布式锁
- 配置

例如 Redis、Etcd、DynamoDB。

#### 向量库适合什么

- 相似语义检索
- 长期知识召回
- 经验片段匹配

例如 Milvus、Weaviate、pgvector。

#### 为什么不能只用一种

因为二者解决的是不同问题：

- KV 解决“我知道 key，如何快速取值”
- 向量库解决“我不知道准确 key，但我想找语义相关内容”

### 推荐混合架构

1. 热数据层
- Redis / 内存缓存
- 当前会话状态、活跃任务状态

2. 温数据层
- PostgreSQL / MySQL / DynamoDB
- 用户画像、结构化记忆、索引元数据

3. 向量召回层
- pgvector / Milvus
- 摘要后的语义记忆

4. 冷数据层
- 对象存储
- 原始文档、网页快照、历史工件

### 记忆写入流程

推荐不要把全部原始对话直接写入向量库。

正确流程通常是：

1. 原始数据进入事件流
2. 先做清洗和敏感信息识别
3. 再做摘要、切片、标签化
4. 结构化字段入关系库
5. 语义片段计算 embedding 后入向量库
6. 原文入对象存储或冷数据层

### 热温冷分层

#### 热数据

- 最近 24 小时活跃会话
- 高频访问，要求毫秒级

#### 温数据

- 近 30 天摘要、结构化索引
- 秒级内可取回

#### 冷数据

- 历史归档、工件原文、原始对话
- 成本优先

### 敏感数据保护

敏感数据绝对不能简单进向量库。

建议：

1. 凭证和 Token 单独放 Secret Manager

2. 敏感字段加密
- 传输中 TLS
- 存储中 KMS envelope encryption

3. 检索前脱敏
- 向量化前先做 PII 检测

4. 最小可见范围
- 按租户和会话授权

5. 数据删除能力
- 满足审计和合规要求

## 9. 多模态 Agent 的流媒体处理架构

### 题目本质

这题考查的是实时媒体系统和 Agent 推理系统的结合能力。

多模态 Agent 要“看见”屏幕、视频或手机画面，就必须解决：

- 媒体低延迟传输
- 解码和抽帧
- 推理与控制的解耦
- 大量连接下的带宽和 CPU 成本

### 基础协议对比

#### WebRTC

特点：

- 超低延迟
- 支持双向实时通信
- 自带拥塞控制、NAT 穿透能力

适合：

- 云手机实时控制
- 浏览器实时预览
- 交互式视频场景

#### RTMP

特点：

- 生态成熟
- 延迟通常低于 HLS
- 但不如 WebRTC 低

适合：

- 推流到媒体服务器
- 兼容一些传统媒体链路

#### HLS

特点：

- 延迟高
- 分发稳定

不适合实时 Agent 控制主链路。

### 推流还是拉流

在“Agent 看屏幕”场景，通常建议：

- 设备端主动推流
- Agent 或分析服务按需订阅

原因：

1. 设备端更容易稳定输出

2. 多消费者场景更容易复用

3. 可以在媒体网关统一做转码、抽帧、录制

如果做拉流，设备端要暴露可访问流地址，控制复杂度更高。

### 推荐架构

1. Device Streamer
- 云手机或浏览器采集视频流并推送到媒体网关

2. Media Gateway
- 负责流接入、转发、订阅、鉴权

3. Frame Extractor
- 从流中按策略抽帧

4. Vision Inference Worker
- 对帧做 OCR、UI 元素检测、视觉理解

5. Control Plane
- 把分析结果反馈给 Agent Planner 或 Executor

### 为什么要异步解耦

如果主执行线程既做动作控制，又做视频解码和帧分析，会出现：

- 控制阻塞
- 帧积压
- 延迟漂移
- GPU 资源争抢

正确做法：

- 控制信令单独通道
- 媒体流单独通道
- 抽帧和推理异步队列化

### 帧提取策略

不应该每帧都送大模型。

常见优化：

- 固定采样，如 1fps 到 5fps
- 事件触发采样，如页面变化、点击后、动画结束后
- ROI 采样，只截取关键区域
- 轻模型预筛选，再决定是否调用大模型

## 10. 技术标准制定与代码质量控制

### 题目本质

这题考查的是架构师能力，而不只是编码能力。

重点是：

- 你是否能定义团队边界
- 是否能推动长期可维护性
- 是否能把快速迭代和稳定性统一起来

### SDK 向后兼容策略

AI Infra 经常变化快，但 SDK 不能跟着天天破坏兼容。

建议原则：

1. 遵守 SemVer
- major：不兼容修改
- minor：向后兼容新增
- patch：bugfix

2. 字段新增优先，字段删除慎用

3. 保留 deprecated 周期
- 例如两个小版本后再移除

4. 协议能力协商
- 客户端上报支持的 feature set

5. 保持错误码稳定

### API 设计原则

稳定的 API 一般具备这些特征：

- 字段可扩展
- 默认值明确
- 幂等
- 错误模型统一
- 分页、过滤、排序风格一致

### 代码审查与 CI/CD 体系

建议分层治理：

#### 应用代码

- 单元测试
- 集成测试
- e2e
- 静态检查
- 安全扫描

#### IaC 代码

- `terraform validate`
- `terraform plan`
- `tflint`
- `checkov` 或 `tfsec`

#### 容器与供应链

- 镜像漏洞扫描
- SBOM 生成
- 签名校验

#### API 与协议

- 契约测试
- 向后兼容检查

### 推荐流水线

1. pre-commit
- fmt、lint、secret scan

2. PR 阶段
- 单元测试
- 静态分析
- 依赖漏洞扫描
- API 兼容检查

3. merge 阶段
- 集成测试
- 镜像构建与签名
- IaC plan

## 总结：这 10 道题的统一答题思路

如果把这 10 道题放在一起看，其实它们都围绕一个核心：

- 如何构建一个高并发、强隔离、可观测、可扩展、低成本的 AI Agent Infra 平台

建议面试时始终围绕这 5 个关键词展开：

1. 控制面与执行面分离
2. 状态外置与检查点恢复
3. 分层隔离与最小权限
4. 流式事件统一抽象
5. 观测、治理与标准化先行

如果面试官继续深挖，你可以继续从下面几个角度展开：

- 为什么某些场景选容器，某些场景选 MicroVM
- 为什么 Agent 系统必须做事件流和状态机设计
- 为什么 AI 系统的可观测性比传统 Web 系统更复杂
- 为什么多租户代码执行平台一定要先做威胁模型
- 为什么平台化工作的本质是标准化，而不是功能堆叠

这份答案更适合作为高级岗位参考答案，而不是背诵稿。最好的准备方式是：

- 每题提炼 1 分钟版本
- 每题准备 3 分钟深入版本
- 每题准备 1 个实际项目案例映射

这样在面试里会显得既懂理论，也真正做过工程落地。
