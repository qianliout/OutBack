RAG系统数据处理流程详解

RAG（Retrieval-Augmented Generation）是一种结合检索系统和生成模型的技术架构，通过先从外部知识库检索相关信息，再让大语言模型基于检索结果生成答案，有效缓解大模型幻觉、知识时效性差等问题。RAG系统可分为**离线处理阶段**和**在线推理阶段**两大部分。

## 一、离线处理阶段（数据准备）

### 1.1 数据收集与清洗

**作用**：获取原始数据源并进行预处理，为后续处理奠定数据基础。

**核心组件**：爬虫工具、数据清洗脚本

**关键技术**：

- **HTML/XML解析**：BeautifulSoup、lxml、Playwright（处理JavaScript渲染页面）
- **正则表达式清洗**：去除特殊字符、HTML标签、脚本代码等噪声内容
- **去重算法**：
  - **MinHash**：基于Jaccard相似度的最小哈希签名，适用于大规模数据去重
  - **SimHash**：海明距离（Hamming Distance）快速判断近似重复
  - **Bloom Filter**：空间高效的存在性检测
- **文本规范化**：统一编码（UTF-8）、大小写转换、去除控制字符、标准化Unicode格式

**数据源类型**：
- 结构化数据（数据库、CSV、JSON）
- 半结构化数据（HTML、XML、Markdown）
- 非结构化数据（PDF、Word、TXT、PPT）

### 1.2 文本分块（Chunking）

**作用**：将长文档切分为语义连贯、适合检索的小片段，平衡信息完整性和检索粒度。

**核心组件**：文本分割器

**分块策略**：

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **固定长度分块** | 按token数或字符数硬切 | 简单高效、长度可控 | 可能打断语义 | 通用场景、快速原型 |
| **重叠固定分块** | 固定长度 + 重叠窗口 | 保留上下文连续性 | 冗余增加、存储成本高 | 连续性要求高的文档 |
| **递归分块** | 按层级分隔符递归切分 | 保持语义完整性 | 实现复杂 | 层级结构文档（Markdown、JSON） |
| **语义分块** | 按语义相似度自动聚类 | 块内语义连贯 | 计算成本高 | 高质量内容切分 |
| **句子边界分块** | 基于NLP句子识别切分 | 保持句子完整性 | 可能块大小不一 | 对话、演讲等自然语言 |
| **文档结构分块** | 利用标题、段落、列表结构 | 保留组织结构 | 依赖文档格式 | 技术文档、论文 |

**chunk size选择建议**：

- **通用场景**：256-512 tokens（短答案、FAQ）
- **复杂文档**：512-1024 tokens（技术文档、报告）
- **长文本分析**：1024-2048 tokens（书籍、论文）
- **重叠度**：通常15-25%重叠可获得较好的上下文连续性

**高级技巧**：

- **Late Chunking**：先对每个句子单独编码，再拼接所有句子编码取均值，保留位置信息
- **Small-to-Big**：小块用于检索，大块用于生成
- **Parent Document Retrieval**：维护父子文档层级关系

### 1.3 文本嵌入（Embedding）

**作用**：将文本转换为稠密向量表示，捕捉语义信息，支持语义相似度计算。

**核心组件**：嵌入模型

**主流模型对比**：

| 模型 | 维度 | 特点 | 适用场景 |
|------|------|------|----------|
| **OpenAI text-embedding-ada-002** | 1536 | 通用性强、易用 | 通用场景 |
| **OpenAI text-embedding-3-small/large** | 256-3072 | 最新一代、高性能 | 生产环境 |
| **Cohere Embed** | 1024 | 多语言支持好 | 多语言场景 |
| **BGE (BAAI)** | 768/1024 | 开源、中文优化 | 中文场景 |
| **M3E (Moka)** | 768 | 开源、中文优化 | 中文场景 |
| **Sentence-BERT (SBERT)** | 768 | 适合句子相似度 | 短文本 |
| **Dense Passage Retrieval (DPR)** | 768 | 适合问答检索 | 问答系统 |

**技术要点**：

- **维度选择**：维度越高表达力越强，但存储和计算成本也增加。768-1024是常见平衡点
- **归一化**：嵌入向量通常L2归一化，使余弦相似度等于点积
- **Matryoshka Representation Learning (MRL)**：支持可变维度嵌入，灵活权衡精度与效率
- **知识蒸馏**：将大模型的知识蒸馏到小模型，降低推理成本

**多语言与专业化**：
- 通用Embedding vs 领域特定Embedding（医疗、法律、金融）
- 多语言对齐：LaBSE、mBERT等支持跨语言检索

### 1.4 向量索引构建

**作用**：构建高效的向量检索结构，加速在高维空间中的最近邻搜索。

**核心组件**：向量数据库

**索引算法详解**：

| 算法 | 原理 | 优点 | 缺点 | 代表工具 |
|------|------|------|------|----------|
| **HNSW** | 构建多层可导航小世界图，类跳表结构 | 查询速度快、精度高 | 内存占用大、构建慢 | Faiss HNSW、Milvus |
| **IVF** | Inverted File Index，倒排索引 | 减少搜索范围 | 精度与速度需权衡 | Faiss IVF |
| **PQ** | Product Quantization，分块量化 | 大幅压缩存储 | 精度损失 | Faiss PQ |
| **HNSW+PQ** | HNSW +量化压缩 | 平衡精度与效率 | 调参复杂 | 生产常用 |
| **Annoy** | 随机投影树 | 内存友好、支持磁盘 | 精度一般 | Spotify Annoy |
| **ScaNN** | 异构剪枝量化 | Google出品、高性能 | 闭源 | Google ScaNN |
| **DiskANN** | 磁盘索引 | 支持十亿级数据 | 延迟较高 | Azure Vector Search |

**向量数据库选型**：

- **Pinecone**：托管服务、易用性好、适合快速启动
- **Milvus**：开源、功能全面、支持混合检索
- **Weaviate**：内置向量化、GraphQL接口
- **Chroma**：轻量级、开发友好、适合本地实验
- **Qdrant**：Rust实现、性能高、支持过滤
- **pgvector**：PostgreSQL扩展，适合已有PG栈的团队

**混合检索**：向量检索 + 关键词检索（BM25）组合使用，兼顾语义相似度和关键词匹配。

### 1.5 元数据存储与索引

**作用**：存储文档的附加信息，支持过滤检索、来源追溯等功能。

**存储组件**：关系型数据库（PostgreSQL、MySQL）或文档数据库（MongoDB）

**典型元数据**：

- 文档ID、来源URL、创建时间
- 作者、类别、标签
- 文档版本、有效期
- 访问权限、敏感等级

**高级特性**：

- **多向量索引**：同一文档支持多种嵌入模型
- **稀疏向量索引**：用于BM25等关键词检索
- **图索引**：实体关系图谱，支持知识图谱检索

## 二、在线推理阶段（查询处理）

### 2.1 查询理解

**作用**：对用户查询进行预处理和增强，提升检索效果。

**核心组件**：查询处理器

**关键技术**：

| 技术 | 描述 | 目的 |
|------|------|------|
| **查询重写（Query Rewriting）** | 改写查询为更利于检索的形式 | 消除歧义、补充隐含信息 |
| **查询扩展（Query Expansion）** | 添加相关同义词、上下位词 | 扩大召回 |
| **意图识别（Intent Classification）** | 分类查询类型（事实性/观点性/操作性） | 选择检索策略 |
| **实体识别（NER）** | 提取查询中的实体信息 | 精准检索、实体链接 |
| **HyDE（Hypothetical Document Embeddings）** | 让LLM生成假设性答案，再检索 | 弥合语义鸿沟 |
| **Step-back Prompting** | 先提炼高层概念再检索 | 处理抽象复杂查询 |
| **Query Decomposition** | 将复杂查询拆分为子查询 | 多跳推理、并行检索 |
| **Counterfactual Query** | 生成反面查询 | 提升检索鲁棒性 |

**Query分类与路由**：
- 根据查询类型选择不同的检索策略和prompt模板
- 高频简单查询可缓存结果

### 2.2 检索（Retrieval）

**作用**：在向量库中查找最相关的文档片段。

**核心组件**：向量检索引擎

**检索范式**：

| 范式 | 原理 | 特点 |
|------|------|------|
| **向量检索** | 最近邻搜索，找语义最相似的chunk | 语义匹配、泛化能力强 |
| **关键词检索** | BM25、TF-IDF匹配关键词 | 精确匹配、适合专有名词 |
| **混合检索** | 向量 + 关键词融合（RRF、则膨胀） | 兼顾语义与精确 |
| **知识图谱检索** | 图结构实体关系查询 | 关系推理、多跳查询 |
| **重排序检索** | 两阶段：粗排 + 精排 | 平衡精度与效率 |

**相似度计算**：
- **余弦相似度**：cosine similarity，衡量方向差异
- **点积**：dot product，归一化后等价于余弦
- **欧氏距离**：L2 distance，适合某些特定模型
- **Manhattan距离**：L1 distance，对异常值更鲁棒

**检索结果优化**：

- **Diversity Retrieval**：避免返回内容单一的相似结果
- **MMR（Maximum Marginal Relevance）**：平衡相关性与多样性
- **Context Window Compression**：压缩检索上下文长度
- **Citation/Source Tracking**：追踪文档来源和引用关系

### 2.3 重排序（Re-ranking）

**作用**：对初步检索结果进行精细排序，提升最终结果质量。

**核心组件**：重排序模型

**技术对比**：

| 方法 | 原理 | 优势 | 劣势 | 代表模型 |
|------|------|------|------|----------|
| **BM25重排** | 基于词频和文档长度的经典算法 | 可解释、无需训练 | 无法理解语义 | Elasticsearch |
| **Cross-Encoder重排** | query-doc配对输入模型输出相关性分数 | 精度高、考虑交互 | 计算慢、无法缓存 | BAAI/bge-reranker |
| **Bi-Encoder + Vector** | 分离编码、快速检索 | 效率高、可缓存 | 无法建模交互 | 常规向量检索 |
| **LLM重排** | 用大模型判断相关性 | 理解能力强 | 成本高、延迟大 | GPT-4、C商Rerank |
| **Learning to Rank** | 有监督学习排序 | 可定制、数据驱动 | 需要标注数据 | LambdaMART |

**主流重排模型**：

- **BAAI/bge-reranker-base/large**：开源中文优化，效果接近商业模型
- **Cohere Rerank**：商业API，多语言支持
- **Jina Reranker**：开源，支持长文档
- **M3E-Reranker**：中文优化

**实战技巧**：
- 重排后通常取Top 5-20个结果送入LLM
- 可使用句级别（passage-level）或文档级别（document-level）重排
- 长文档可先做段落级别检索，再在文档级别重排

### 2.4 上下文组装（Context Assembly）

**作用**：将检索到的文档片段与查询组合，构建完整的prompt上下文。

**核心组件**：上下文构建器

**组装策略**：

| 策略 | 方法 | 适用场景 |
|------|------|----------|
| **直接拼接** | 按相关性排序直接拼接 | 块数量少、长度短 |
| **上下文窗口组装** | 保留周围上下文形成窗口 | 需要更多背景信息 |
| **树状组装** | 按层级结构组织（摘要→细节） | 复杂文档、长文档 |
| **图状组装** | 实体关系图组织 | 关系复杂、多跳场景 |

**上下文压缩技术**：

- **LLMChainExtractor**：从每个检索块中提取关键信息
- **LLMChainFilter**：过滤掉不相关的检索块
- **ContextCompressor**：让LLM压缩上下文
- **Self-RAG adaptive retrieval**：根据需要动态决定是否检索

**提示模板设计**：

```
你是一个专业的AI助手。请根据以下参考资料回答用户的问题。
如果参考资料不足以回答问题，请如实说明。

参考资料：
{context}

用户问题：{question}

请基于参考资料给出回答，并在回答中注明所引用的参考资料编号。
```

### 2.5 生成回答（Generation）

**作用**：基于上下文和查询，让大语言模型生成最终回答。

**核心组件**：大语言模型

**生成策略**：

| 策略 | 描述 | 参数/技巧 |
|------|------|-----------|
| **贪婪解码** | 选择概率最高的token | 简单但可能重复 |
| **束搜索（Beam Search）** | 保留多个候选序列 | beam size通常3-5 |
| **Top-k采样** | 从top-k高概率中随机采样 | k值影响多样性 |
| **Top-p（Nucleus）采样** | 从累积概率达到p的词中采样 | 更自适应 |
| **温度调节** | 控制概率分布的平滑度 | 低温度=确定性，高温度=多样性 |
| **重复惩罚** | 惩罚已生成token的概率 | 减少重复 |
| **长度惩罚** | 惩罚序列长度 | 避免过短或过长回答 |

**LLM选型建议**：

| 场景 | 推荐模型 | 特点 |
|------|----------|------|
| **通用对话** | GPT-4o、Claude 3.5 | 效果好、成本高 |
| **中文场景** | GLM-4、通义千问 | 中文优化 |
| **开源自部署** | Llama 3.1、Qwen 2.5、Mistral | 成本可控、数据安全 |
| **轻量推理** | GPT-4o-mini、Claude 3-haiku | 成本低、速度快 |
| **长上下文** | Kimi、GPT-4-32k | 支持超长上下文 |

### 2.6 后处理（Post-processing）

**作用**：优化生成结果，提升输出质量和用户体验。

**核心组件**：后处理器

**后处理技术**：

| 技术 | 描述 | 示例 |
|------|------|------|
| **答案验证** | 检查答案是否基于参考资料 | 事实核查、一致性检查 |
| **引用标注** | 为答案中的claims标注来源 | [1][2]标注 |
| **格式化输出** | 结构化输出（JSON、Markdown） | {"answer": "", "sources": []} |
| **安全过滤** | 过滤敏感内容、越狱提示 | 关键词过滤、分类器 |
| **风格调整** | 调整回答风格、长度、格式 | 简洁版/详细版 |
| **置信度评估** | 评估答案的可靠程度 | 低置信度触发重检索 |
| **追问建议** | 生成可能的追问方向 | 提升交互体验 |

## 三、进阶架构与新技术

### 3.1 Agentic RAG（智能体RAG）

**核心思想**：将RAG与AI Agent结合，实现自主决策的检索-生成流程。

**典型架构**：

```
用户查询 → Agent → [判断是否检索] → [判断检索几次]
                      ↓
              知识库检索
                      ↓
              Agent判断答案质量
                      ↓
        [如需更多信息] → 再次检索/工具调用
                      ↓
              生成最终答案
```

**关键能力**：
- **自适应检索**：根据问题复杂度决定是否检索、检索多少次
- **多步推理**：分解复杂问题为多个子问题
- **工具调用**：结合计算器、搜索、代码执行等多种工具
- **自我纠正**：评估答案质量，不满意则重新生成

**代表框架**：
- **LangChain Agent**：支持多种RAG相关的Agent工具
- **LlamaIndex Agent**：专注于知识增强的Agent
- **AutoGPT/BabyAGI**：通用Agent框架

### 3.2 多模态RAG

**核心思想**：支持图像、音频、视频等多种模态的检索和生成。

**技术路线**：

| 路线 | 方法 | 代表模型 |
|------|------|----------|
| **图片→文本→向量** | 先将图片转为描述文本，再检索 | CLIP + LLM |
| **图片→向量** | 端到端多模态编码 | CLIP、LLaVA |
| **知识图谱多模态** | 构建多模态知识图谱 | 图谱 + RAG |

**应用场景**：
- 视频问答（视频切片 → 帧描述 → 索引）
- 文档图理解（PPT、PDF中的图表检索）
- 语音助手（语音→文本→RAG→语音）

### 3.3 RAG优化技术

| 技术 | 描述 | 效果 |
|------|------|------|
| **Self-RAG** | 自己生成 critique 反思是否需要检索 | 减少不必要的检索 |
| **RECOMP** | 从检索文档中提取压缩句子再输入LLM | 减少上下文长度 |
| **SUGAR** | 生成对抗性查询提升鲁棒性 | 提升检索多样性 |
| **Chain of Notation** | 中间推理步骤写入知识库 | 提升复杂推理能力 |
| **Memory Bank** | 维护会话级的记忆向量库 | 支持长期对话 |

## 五、性能优化与最佳实践

### 5.1 分块策略优化

**chunk size选择决策树**：

```
问题类型
    ├── 简单事实问答（"什么是X？"）→ 256-512 tokens
    ├── 技术文档解析 → 512-1024 tokens
    ├── 长文档总结 → 1024-2048 tokens
    └── 多跳推理 → 512-768 tokens（需要重叠）
```

**重叠度设置**：
- 重叠率 = 重叠token数 / 总token数
- 建议重叠15-25%，过高增加噪声，过低丢失上下文
- 对于有明确边界的文档（段落、章节），可减少重叠

### 5.2 检索效率优化

| 优化方向 | 具体措施 |
|----------|----------|
| **缓存** | 查询结果缓存（Redis）、嵌入向量缓存 |
| **异步处理** | 检索与生成并行、预取热数据 |
| **批量检索** | 合并多个查询的检索请求 |
| **量化压缩** | INT8/INT4量化，减少内存占用 |
| **分片策略** | 按业务分类分库，减少检索范围 |
| **预热** | 启动时预加载热点数据到内存 |

### 5.3 质量评估指标

| 阶段 | 指标 | 说明 |
|------|------|------|
| **检索阶段** | Precision@K、Recall@K、MRR、NDCG | 评估检索质量 |
| **生成阶段** | RAGAS（Faithfulness、Answer Relevance、Context Relevance）、BLEU、ROUGE | 评估生成质量 |
| **端到端** | 人工评估、任务完成率、用户满意度 | 业务指标 |

**RAGAS评估维度**：
- **Faithfulness**：生成答案是否忠实于检索上下文
- **Answer Relevance**：答案是否与问题相关
- **Context Relevance**：检索上下文是否与问题相关

### 5.4 成本优化策略

- **模型降级**：简单查询用小模型，复杂查询用大模型
- **缓存复用**：高频query结果缓存
- **批处理**：离线任务批量处理
- **混合部署**：本地小模型 + 云端大模型
- **智能路由**：根据query复杂度自动选择策略
