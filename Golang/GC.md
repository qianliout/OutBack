## Go GC 的完整运行流程 (V1.8+)

Go 的垃圾回收是一个并发过程，主要分为四个核心阶段，包含两次短暂的 STW (Stop The World)。

### 1. Sweep Termination (清理终止阶段 - STW)
这是垃圾回收的准备阶段，需要暂停所有用户协程 (STW)。
主要任务是等待并确保上一轮的并发清理工作已经彻底完成。
如果上一次 GC 还有未清理完的内存，会在此阶段强制完成清扫。

### 2. Mark (标记阶段 - 并发执行)
这个阶段是 GC 的核心，包含短暂的准备阶段和漫长的并发标记阶段。
在准备阶段 (STW) 中，会开启混合写屏障，并唤醒后台标记协程 (Mark Workers)。
随后进入并发标记阶段，此时恢复用户协程执行，GC 协程与用户协程并发运行。
GC 从根对象（如全局变量、当前存活的 Goroutine 栈）出发，使用三色标记法扫描并标记存活对象。
并发运行期间，混合写屏障会拦截并保护新分配或引用发生变更的对象，防止存活对象被误回收。

### 3. Mark Termination (标记终止阶段 - STW)
并发标记完成后，再次暂停所有用户协程 (STW)。
主要任务是处理并发标记期间遗留的极少量工作。
在此阶段会关闭混合写屏障。
计算下一次触发 GC 的目标内存大小等统计信息。

### 4. Sweep (清理阶段 - 并发执行)
恢复用户协程执行，进入后台并发清理阶段。
清理协程在后台并发运行，遍历并清扫未被标记的白色对象所在内存块。
被清理的内存会被回收到空闲链表 (Free List) 中，供后续分配使用。
这个过程完全在后台进行，不会阻塞用户程序的正常执行。

## Go GC核心问题：三色标记法与“对象丢失”

### 1. 背景：三色标记法
Go的并发GC采用**三色标记法（Tricolor Mark-Sweep）** 来追踪存活对象：
- **白色对象**：尚未被GC访问到的对象（回收周期开始时所有对象为白，结束时被回收）。
- **灰色对象**：已被GC访问，但其引用的子对象还未被检查。是标记阶段的工作队列。
- **黑色对象**：已被GC访问，且其所有子对象都已检查完毕。在本轮GC中不会再被处理。

**标记阶段的目标**：将所有从根对象（栈、全局变量等）可达的对象标记为黑色，剩余的白色对象即为垃圾。

### 2. 并发标记下的“对象丢失”问题
在GC并发标记期间，用户程序（Mutator）也在并行运行修改对象引用，这可能导致**本应存活的对象被错误回收**。该问题需要同时满足两个条件：

- **条件一（建立非法引用）**：一个黑色对象直接引用了一个白色对象（违反**强三色不变性**）。
- **条件二（切断救援路径）**：所有从灰色对象到达该白色对象的路径都被用户程序切断（违反**弱三色不变性**）。

#### 🎯 经典并发场景举例：
1. **初始状态**：
   - A: 灰色 (在GC扫描队列)
   - B: 黑色 (已扫描完成)
   - C: 白色
   - 引用关系： `A -> C` (C在灰色A的保护下)

2. **用户程序执行序列**（均为堆写入操作）：
   - `B.field = C`    // 操作1：黑色对象B引用白色对象C -> **满足条件一**
   - `A.field = nil`  // 操作2：断开灰色对象A到白色对象C的引用 -> **满足条件二**

3. **结果**：
   - C只被黑色B引用，且不再被任何灰色对象可达。
   - GC标记结束，C仍是白色，被错误回收。

## Go 1.8 之前的防御机制：插入写屏障 + STW栈重扫

### 1. 插入写屏障 (Dijkstra Barrier)
- **机制**：当发生指针写入操作 `*slot = ptr` 时，如果新指针 `ptr` 指向白色对象，则强制将其标记为灰色 (`shade(ptr)`)。
- **作用**：直接防止**条件一**的发生。在上例中，`B.field = C` 时，屏障会拦截并将C染灰，使得操作变为`B(黑)->C(灰)`，这是安全的。
- **优点**：有效防止对象丢失。
- **致命缺点**：出于性能考虑，**无法在栈的指针写入操作上开启屏障**（栈操作太频繁）。这留下了漏洞。

### 2. STW栈重新扫描 (Stack Rescan)
- **机制**：由于栈写入无屏障，并发标记结束后，必须**Stop The World (STW)**，然后将所有goroutine的栈作为根重新扫描一遍，以找出并保护那些在并发期间被“偷偷”写入栈的白色指针。
- **缺点**：此STW时间与**栈的数量和大小成正比**。对于高并发服务（goroutine极多），这次STW可达10-100ms，对延迟是致命打击。

**1.8之前的方案本质是**：用**插入屏障**解决堆的问题，用**STW重扫**补救栈的问题。它用一次长的、不可预测的STW停顿来换取并发标记期间栈操作的性能。

## Go 1.8 及之后的防御机制：混合写屏障 (Hybrid Write Barrier)

混合写屏障结合了插入屏障和删除屏障（Yuasa Barrier）的优点，其规则如下：

**在并发标记阶段，对任何指针写入操作 `*slot = ptr`：**
1.  **保护新值**：`shade(ptr)` // 如果`ptr`指向白对象，则将其标灰。（插入屏障思想）
2.  **条件性保护旧值**：如果当前Goroutine的栈**尚未被扫描**，则`shade(*slot)` // 保护旧指针指向的对象。（删除屏障思想）
3.  **执行写入**：`*slot = ptr`

### 🛡️ 混合屏障如何解决“对象丢失”？
沿用之前的危险场景，混合屏障会进行拦截：

- **当执行 `B.field = C` (操作1) 时**：
  - 屏障触发 `shade(C)`，**立即将白色C标记为灰色**。
  - 写入后，引用变为 `B(黑)->C(灰)`，**条件一被化解**。

- **当执行 `A.field = nil` (操作2) 时**：
  - 屏障会尝试 `shade(*slot)`（即保护A.field的旧值C），但发现C已是灰色，操作无效。
  - 此时C已是灰色，**条件二已无关紧要**。

**关键在于**：无论两个危险操作的执行顺序如何，**在第一个写操作发生时，屏障就会介入，确保对象C被标记为非白色**，从而彻底杜绝了两个条件同时成立的可能。

### ⚡ 混合屏障如何避免栈重扫？（核心贡献）

这是混合屏障最精妙的地方。它通过规则保证了**已被扫描的栈上永远不会出现指向白色对象的指针**。

1.  **对【堆->栈】写入的绝对保护**：
    - 当执行 `localVar = ptr` （从堆读指针写入栈）时，**总是触发 `shade(ptr)`**。
    - **结果**：任何能成功写入栈的指针，其指向的对象在写入瞬间就已不是白色。栈的内容永远是“安全”的。

2.  **对【栈->堆】写入的智能豁免**：
    - 当执行 `heapObj.field = localVar` （从栈读指针写入堆）时，屏障需要检查：
      - **`shade(localVar)`**：保护新值。
      - **`shade(*slot)`**：**仅在当前G的栈未被扫描时执行**。若栈**已被扫描**，则**豁免**此步骤。
    - **为何能豁免？** 因为规则1保证了已扫描栈上的指针不可能是白色的。因此，从这个栈拷贝指针到堆是安全的，无需再保护旧值。

**最终效果**：由于规则1这把“锁”，**GC可以确信，一个栈一旦被扫描完成，其状态就凝固了，永远不会再出现“黑引用白”的违规情况**。因此，标记结束后完全不需要再STW重新扫描所有栈。GC只需在开始时用一个极短的STW完成所有栈的初始扫描即可。

### ⚖️ 性能权衡：为何现在敢给栈加屏障？

- **1.8之前**：不在栈加屏障，是为了避免**全局性、持续性的性能开销**，但代价是**不可预测的长STW**。
- **1.8之后**：混合屏障选择了**承受可控的、较小的写入开销**，来换取**彻底消除长STW**这一更具价值的收益。
  - **开销**：指针写入操作有额外指令（检查、着色）。
  - **收益**：STW时间从**毫秒级（~10ms）** 降至**微秒级（<100μs）**，且**固定不变**。
  - **优化**：通过“栈扫描后豁免旧值保护”等优化，大幅降低了平均屏障开销。

**结论**：这是一种战略性的权衡。对于后端服务，**稳定、极低的延迟**远比少量的额外CPU开销重要得多。混合写屏障用智能的、局部化的屏障设计，实现了这一目标。

## 总结对比

| 特性/方面                | Go 1.8 之前                          | Go 1.8 及之后 (混合写屏障)     |
| :----------------------- | :----------------------------------- | :----------------------------- |
| **核心机制**             | 插入写屏障 (堆) + **STW栈重扫**        | **混合写屏障**                   |
| **防止条件一**           | 插入屏障：`shade(ptr)`               | 混合屏障：`shade(ptr)`         |
| **防止条件二**           | 依赖STW重扫补救                      | 混合屏障：条件性`shade(*slot)` |
| **栈上性能**             | 无屏障，写入极快                     | 有屏障（仅`shade(ptr)`），开销小  |
| **最大STW时间**          | **长** (与活跃Goroutine数相关，10+ms) | **极短** (固定，<100μs)        |
| **性能特点**             | 写入开销小，但延迟抖动大             | 写入有开销，但延迟极其稳定       |
| **设计哲学**             | 避免写入开销，代价是长停顿           | 接受小开销，换取确定性低延迟   |

Go 1.8的混合写屏障是GC技术的一次重大飞跃，它通过精巧的设计解决了并发准确性和低延迟之间的矛盾，是Go成为高性能系统首选语言的关键基石之一。

## GC 触发时机：GOGC 与 GOMEMLIMIT

了解 GC 如何运行之后，另一个关键问题是：**GC 何时触发？** Go 提供了两个核心参数来控制 GC 的触发频率。

### 1. GOGC（GC 百分比）

GOGC 决定了 GC 的内存-CPU 权衡。它的工作机制是：在每次 GC 周期结束后，设定下一次 GC 的**目标堆内存大小**。

**公式（Go 1.18+）**：

```
目标堆内存 = 存活堆内存 + (存活堆内存 + GC 根对象内存) × GOGC / 100
```

- `GOGC=100`（默认）：当新分配内存达到「存活堆 + GC 根对象」的 100% 时，触发下一次 GC。
- `GOGC=off` 或 `SetGCPercent(-1)`：关闭 GC（但仍受 GOMEMLIMIT 约束）。
- 增大 GOGC → 降低 GC 频率，减少 CPU 开销，但峰值内存更高；减小 GOGC → 反之。

**示例**：假设存活堆 8 MiB，goroutine 栈 1 MiB，全局变量指针 1 MiB（GC 根对象共 2 MiB），则 GOGC=100 时目标堆为 `8 + (8+2)×100% = 18 MiB`。

### 2. GOMEMLIMIT（内存上限，Go 1.19+）

GOGC 的问题在于它不感知物理内存上限 — 如果存活堆突然暴涨，GOGC 固定的比例可能导致 OOM。

Go 1.19 引入了 `GOMEMLIMIT`（或 `runtime/debug.SetMemoryLimit`），设定 Go runtime 整体内存的**软性上限**：

```
受控内存 = Sys - HeapReleased
```

- 当内存接近上限时，GC 会更频繁地运行以控制内存增长。
- 这是一个**软限制**：Go runtime 不保证绝不超出，防止 GC 过度运行导致**颠簸（thrashing）**。
- GC 的 CPU 时间被限制在约 50%（`2 × GOMAXPROCS` CPU-秒窗口内），避免程序因 GC 完全停滞。

**最佳实践**：在容器化部署中，通常同时设置 GOGC 和 GOMEMLIMIT，利用 GOGC 控制常态 GC 频率，利用 GOMEMLIMIT 兜底防止 OOM。

### 3. GC Pacer（步调控制器）

除了上述两个用户可配参数，Go runtime 内部还有一套 **GC Pacer** 机制，它持续追踪应用的内存分配速率和 GC 标记速率，动态调整 GC 的启动时机，确保 GC 能在目标堆内存被耗尽前完成标记。这是 Go GC 能够平滑运行、避免"突击式"GC 的关键基础设施。

## Go 1.25+ 实验性 GC 改进：Green Tea GC

在 Go 1.25 版本中，Go 官方引入了代号为 **Green Tea GC** 的全新实验性垃圾回收器。开发者可以通过设置环境变量 `GOEXPERIMENT=greenteagc` 显式开启。

这个新版本的 GC 并没有抛弃并发标记清除和三色标记法的基本面，而是专门针对现代 CPU 架构和**小对象分配密集型工作负载**进行了深度的性能优化，解决了传统 GC 在缓存局部性（Locality）和多核并行度上的瓶颈。

### 核心优化机制

1. **基于大小的对象分类 (Size-based Object Classification)**
   - 传统的 GC 扫描对内存块的处理较为统一，而 Green Tea GC 引入了更细粒度的按对象大小分类机制。
   - 针对大量短生命周期的小对象进行针对性扫描优化，减少了不必要的元数据访问开销。

2. **批量内存块扫描 (Batch Memory Block Scanning)**
   - **痛点**：以往 GC 扫描时内存访问比较随机，容易导致 CPU Cache Miss（缓存未命中），拖慢扫描速度。
   - **优化**：新 GC 会将内存块进行批处理扫描，大幅提升了内存访问的局部性（Locality），使得 CPU 缓存命中率显著提高，扫描效率大幅上升。

3. **增量标记优化 (Incremental Marking Optimization)**
   - 改进了标记阶段的内部调度机制，提升了标记阶段（Mark Phase）在多核环境下的**并行度**。
   - 标记协程（Mark Workers）能够更高效地分配工作队列，减少了协程间抢占和同步的损耗。

### 预期性能收益

开启 Green Tea GC 后，对于重度依赖 GC 的应用场景（例如：分配极速、小对象数量庞大、GC 耗时占比高的服务），预期可以获得显著的性能飞跃：
- **GC 整体开销降低 10% ~ 40%**。
- 应用程序的吞吐量（Throughput）得到明显提升。
- 进一步降低了由于缓存未命中带来的长尾延迟（Tail Latency）。

**注意**：Go 1.25 的 Green Tea GC 目前仍处于实验阶段。官方鼓励开发者在 Staging（测试）环境中使用并反馈，为未来版本将其转为默认 GC 机制做准备。
