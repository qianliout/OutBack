# Golang GPM 调度模型详解

本文详细探讨 Go 语言并发模型的核心，也就是 GPM 调度器，目标是整理出一份清晰、深入、适合学习和面试复习的笔记。

---

## 1. Go 协程与并发基础

### 1.1 什么是 Goroutine

Goroutine 是 Go 语言中实现并发的核心单元。它是一种极其轻量级、由 Go 运行时管理的执行体，常被描述为用户态线程。

通过 `go` 关键字，我们可以轻松地启动一个 Goroutine：

```go
package main

import (
    "fmt"
    "time"
)

func say(s string) {
    for i := 0; i < 3; i++ {
        fmt.Println(s)
        time.Sleep(100 * time.Millisecond)
    }
}

func main() {
    go say("Hello") // 启动一个新的 Goroutine
    say("World")    // main 函数自身也是一个 Goroutine
}
```

### 1.2 Goroutine 与线程的核心区别

| 特性 | Goroutine | 内核线程 |
| :--- | :--- | :--- |
| 内存占用 | 初始栈通常只有 2KB，并且支持按需增长和缩容 | 通常是 1MB 到 8MB，栈空间较大且相对固定 |
| 创建与销毁 | 由 Go 运行时直接管理，开销较小 | 需要操作系统参与，开销更大 |
| 调度方式 | 用户态调度，由 Go 调度器管理 | 内核态调度，由操作系统管理 |
| 数量规模 | 通常可以轻松创建数十万甚至上百万个 | 数量受操作系统和硬件资源限制，通常远少于 Goroutine |

## 2. Goroutine 的执行与调度

Go 的调度器采用 GPM 模型，这是一个典型的 M:N 调度模型，也就是用 M 个内核线程承载 N 个 Goroutine。

### 2.1 GPM 模型的核心组件

1. G，Goroutine。它表示一个具体的协程，内部保存执行栈、程序计数器和调度状态等信息。每个 `go` 语句最终都会创建一个新的 G。
2. P，Processor。它是 G 和 M 之间的中间层，负责维护本地可运行队列，并把 G 调度到 M 上执行。P 的数量决定了程序真正的并行度。
3. M，Machine。它对应操作系统线程，是真正执行 Go 代码的实体。一个 M 必须绑定一个 P 才能运行 Go 代码。

核心关系可以概括为：P 管理可运行的 G，M 绑定 P 之后执行这些 G。

### 2.2 调度策略与流程

1. 队列优先。P 会优先从自己的本地运行队列中获取 G，这条路径锁竞争最少，效率最高。
2. 全局队列。如果本地队列为空，调度器会尝试从全局运行队列中取一批 G。
3. 工作窃取。如果全局队列也为空，P 会尝试从其他 P 的本地队列中窃取一部分 G，以实现负载均衡。
4. 阻塞式系统调用。当某个 G 进入阻塞式系统调用，例如传统文件 I/O 或 CGO 调用时，当前 M 可能会被阻塞。此时调度器会把 P 从这个 M 上摘下来，交给其他空闲 M 或新创建的 M 继续执行剩余任务。
5. 网络 I/O。如果阻塞来自网络 I/O，Go 会通过 Netpoll 机制处理。G 会被挂起并注册到操作系统的 I/O 多路复用器中，M 和 P 则可以继续执行其他 G。等网络事件就绪后，对应的 G 会被重新唤醒并加入调度体系。

### 2.3 协作式调度与抢占式调度

#### Go 1.14 之前

Go 主要依赖协作式调度。Goroutine 通常只有在发生阻塞，例如 I/O、channel 操作、系统调用，或者主动调用 `runtime.Gosched()` 时，才会让出 CPU。这样会带来一个问题：如果某个 G 是纯计算任务，且长期没有阻塞点，它就可能长时间占着 M 不放，导致其他 G 得不到运行机会。

#### Go 1.14 及之后

Go 引入了基于信号的异步抢占机制。如果一个 Goroutine 运行时间过长，调度器可以向对应的 M 发送信号，打断当前 G 的继续执行，并把它重新放回调度队列。这样可以显著提升调度公平性，避免长时间独占 CPU 的情况。

## 3. Goroutine 间通信：Channel

Go 提倡不要通过共享内存来通信，而要通过通信来共享内存。Channel 正是这一思想的核心实现。

### 3.1 Channel 的工作原理

Channel 的底层实现是 `hchan` 结构体。理解它时，可以重点关注以下字段：

1. `qcount`：当前缓冲区中的元素数量。
2. `dataqsiz`：缓冲区容量。无缓冲 channel 的这个值为 0。
3. `buf`：底层环形缓冲区。
4. `sendx` 和 `recvx`：发送和接收在环形队列中的索引位置。
5. `recvq` 和 `sendq`：等待队列，分别保存因接收或发送而阻塞的 Goroutine。
6. `lock`：互斥锁，用于保护 `hchan` 的内部状态。

发送流程可以这样理解：

1. 如果接收队列 `recvq` 不为空，说明已经有 G 在等待接收，此时可以直接把数据交给对方并唤醒它。
2. 如果没有等待接收的 G，但缓冲区还有空间，就把数据写入缓冲区。
3. 如果既没有等待接收的 G，缓冲区又已经满了，当前发送方就会被挂起，并进入 `sendq`。

接收流程与之对应：

1. 如果发送队列 `sendq` 不为空，说明已经有 G 在等待发送，此时可以直接取走对方的数据并唤醒它。
2. 如果没有等待发送的 G，但缓冲区里还有数据，就直接从缓冲区读取。
3. 如果既没有等待发送的 G，缓冲区里也没有数据，当前接收方就会被挂起，并进入 `recvq`。

### 3.2 无缓冲与有缓冲 Channel

#### 无缓冲 Channel

`make(chan T)` 创建的是无缓冲 channel。它的核心特征是发送和接收必须同时准备好，否则一方就会阻塞。因此它天然带有同步语义。

#### 有缓冲 Channel

`make(chan T, N)` 创建的是有缓冲 channel。只要缓冲区未满，发送操作通常不会阻塞；只要缓冲区非空，接收操作通常不会阻塞。因此它更偏向异步通信。

## 4. Goroutine 间同步：sync.Mutex

在必须使用共享内存的场景下，`sync.Mutex` 是保证并发安全、防止数据竞争的重要工具。

### 4.1 `sync.Mutex` 的基本原理

`sync.Mutex` 的核心是一个名为 `state` 的整数字段。它通过位运算来表示锁的不同状态。

1. `mutexLocked`，第 0 位，表示锁当前是否被持有。
2. `mutexWoken`，第 1 位，表示是否已经有等待者被唤醒。
3. `mutexStarving`，第 2 位，表示锁是否进入饥饿模式。
4. `waiter`，剩余位，表示等待这把锁的 Goroutine 数量。

### 4.2 `Mutex` 的两种工作模式

#### 正常模式

在正常模式下，锁释放之后，等待中的 Goroutine 和新到来的 Goroutine 会一起竞争锁。由于新到来的 G 往往已经在 CPU 上运行，它可能更容易连续抢到锁。这样有利于吞吐量，但也可能导致老的等待者长期拿不到锁。

#### 饥饿模式

如果某个 G 等待锁的时间超过 1ms，`Mutex` 可能切换到饥饿模式。在这个模式下，锁释放后会更倾向于直接交给等待队列前面的 Goroutine，而不是继续让新来的 G 参与激烈竞争。这样做是为了保证公平性，防止队首等待者长期饥饿。

这种双模式设计，本质上是在吞吐量和公平性之间做权衡。正常模式更强调性能，饥饿模式更强调等待者不会被饿死。

## 5. G、P、M 的关系与调优

### 5.1 G、P、M 的动态关系

G、P、M 的关系不是静态的，理解它们时要同时区分两个视角：某一时刻的绑定关系，以及整个生命周期中的流转关系。

这里有两个核心原则：

1. `GOMAXPROCS` 决定了 P 的数量，也就决定了程序的最大并行度。
2. M 必须绑定 P 才能执行 Go 代码。M 是执行者，P 是执行上下文和调度许可。

### 5.2 一个 P 能否对应多个 M

答案是：在同一时刻不可以，但从时间维度看，一个 P 可能先后和多个 M 建立过绑定关系。

在某一个精确时刻，一个 P 只能绑定一个 M，形成一个具体的执行单元。但是在程序生命周期内，如果绑定它的 M 因系统调用而阻塞，调度器就会把这个 P 转交给其他 M。

典型过程如下：

1. 初始状态下，P1 绑定 M1，M1 正在执行 G1。
2. G1 发起阻塞式系统调用，导致 M1 被操作系统挂起。
3. 调度器为了不让 P1 空转，会把 P1 从 M1 上摘下来。
4. 接着调度器会寻找一个空闲的 M，例如 M2；如果没有空闲 M，也可能新建一个 M2。
5. P1 转而绑定到 M2 上，继续调度其他可运行的 G。
6. 等 M1 的系统调用结束后，M1 会尝试重新获取一个可用的 P；如果没有拿到，它就进入休眠等待。

因此，P 和 M 在瞬时关系上是 1:1，在生命周期视角上则可能呈现 1:N 的先后绑定关系。

### 5.3 一个 M 能否对应多个 P

答案是不可以。

一个 M 在任何时刻都只能绑定一个 P。原因很简单：M 是执行者，而 P 持有自己的调度上下文和本地运行队列。一个执行线程不可能同时携带两个不同的 P 并并行消费两套本地队列。

### 5.4 G、P、M 关系总结

1. G 与 P 的关系可以理解为多对一。一个 P 的本地运行队列中可以挂很多等待执行的 G。
2. P 与 M 在某一时刻是 1:1，但在整个程序生命周期内，一个 P 可能先后绑定多个 M。
3. G 与 M 的整体关系是 M:N，这也是 Go 调度模型常被称为 M:N 调度的原因。

### 5.5 如何调整 GPM

1. `runtime.GOMAXPROCS(n)` 用于设置 P 的数量。
2. 从 Go 1.5 开始，`GOMAXPROCS` 默认通常等于机器的逻辑 CPU 核心数。
3. 在绝大多数场景下，不需要手动修改它。只有在非常特殊的部署环境中，例如多租户资源限制场景，才需要刻意调整。

## 6. 常见面试题

### 6.1 什么是 GPM 模型

GPM 是 Go 运行时调度器的核心模型。G 表示 Goroutine，P 表示逻辑处理器，M 表示内核线程。Go 通过 P 这个中间层，把大量 G 有效地分配到少量 M 上执行，因此整体上形成了 M:N 调度模型。

### 6.2 Goroutine 为什么比线程更轻量

主要原因有三点：

1. Goroutine 的初始栈很小，通常只有 2KB，并且支持动态增长。
2. Goroutine 的调度发生在用户态，切换成本通常低于线程的内核态切换。
3. Goroutine 的创建和销毁由 Go 运行时管理，不需要像线程那样频繁依赖操作系统。

### 6.3 Go 的调度器是抢占式的吗

从 Go 1.14 开始，调度器支持基于信号的异步抢占。如果某个 Goroutine 运行时间过长，调度器可以打断它，把它重新放回队列，让其他 G 获得执行机会。

### 6.4 Channel 的底层是什么

Channel 的底层是 `hchan` 结构体。它包含缓冲区、发送和接收索引、等待队列以及锁。发送和接收时，运行时会根据当前是否有等待者、缓冲区是否为空或已满，决定是直接交换数据、访问缓冲区，还是挂起当前 Goroutine。

### 6.5 `sync.Mutex` 为什么需要饥饿模式

因为如果始终使用高吞吐量的竞争策略，某些等待时间很长的 Goroutine 可能一直抢不到锁。饥饿模式的作用就是在必要时优先照顾等待已久的 Goroutine，避免长期饥饿。

### 6.6 `runtime.GOMAXPROCS` 设置过大有什么影响

`GOMAXPROCS` 控制的是 P 的数量，也就是 Go 程序可并行执行 Go 代码的上限。把它设置得明显大于 CPU 核心数，通常不会提升性能，反而可能因为调度和上下文切换成本上升而让程序变慢。

## 7. 新创建的协程会去哪里

当我们写下 `go myFunction()` 时，Go 运行时并不是立刻让它执行，而是先完成创建和入队。

### 7.1 创建过程

1. 编译器会把 `go myFunction()` 转换成对运行时函数 `runtime.newproc` 的调用。
2. `newproc` 会创建一个新的 G。如果存在可复用的 G，就从 `gFree` 里取；否则就分配新的 G 对象。
3. 新建的 G 会完成初始化，包括分配初始栈、设置入口 PC，并把状态设为 `_Grunnable`。

### 7.2 新 G 的优先放置位置

新创建的 G 并不会直接进入全局队列。调度器优先考虑当前 P 的本地执行上下文。

#### 首选：`runnext` 与本地运行队列

调度器会优先尝试把新 G 放入当前 P 的 `runnext` 槽位，也就是“下一个优先执行的 G”。如果这个位置已经有 G，原来的 G 会被挪到当前 P 的本地运行队列尾部。

这样设计的原因是为了更好地利用 CPU 缓存局部性。父协程刚创建子协程时，二者往往共享上下文或数据，让子协程尽快在当前 P 上继续执行，通常更高效。P 的本地运行队列默认容量通常是 256。

#### 次选：全局运行队列

如果本地运行队列已经满了，新创建的 G 才会被放入全局运行队列。

全局队列是所有 P 共享的，需要加锁访问，开销高于本地队列。不过它也承担了全局负载均衡的作用，让其他空闲 P 有机会拿到这些任务。

### 7.3 队列分配的总结

1. `go myFunction()` 最终触发 `runtime.newproc`。
2. `newproc` 创建并初始化一个新的 G。
3. 调度器优先把它放到当前 P 的 `runnext` 或本地运行队列。
4. 只有当本地队列放不下时，它才会进入全局运行队列。

## 8. 调度循环与工作窃取

一个 M 在执行完当前 G 之后，会进入调度循环。这个过程的核心逻辑主要体现在 `schedule` 和 `findrunnable` 等函数中。

可以把寻找下一个可执行 G 的过程理解为下面几步：

1. 周期性检查全局队列。为了避免全局队列中的任务长期得不到调度，运行时会定期优先看一下 GRQ。
2. 从当前绑定 P 的本地队列中取任务。通常会先看 `runnext`，再看 LRQ。这是最常见、也是效率最高的路径。
3. 如果本地队列没有任务，再尝试从全局队列批量取一部分 G 到自己的本地队列，然后执行其中一个。
4. 如果暂时没有现成的 runnable G，调度器会在合适时机尝试 `netpoll`，看是否有因为网络 I/O 已经就绪、可以重新运行的 G。
5. 如果前面的路径都没有拿到工作，再进入工作窃取流程，从其他 P 的本地队列尾部偷取一部分 G。

### 8.1 如何理解 Netpoll

Netpoll 不是像 LRQ 或 GRQ 那样长期保存 runnable G 的普通队列。它本质上是 Go 运行时对操作系统 I/O 多路复用机制的封装，例如 Linux 的 `epoll` 和 macOS 的 `kqueue`。

当某个 Goroutine 因网络 I/O 暂时不能继续运行时，它不会一直霸占 M，而是先被挂起，并和对应的 fd 关联起来。等到底层 fd 的读写事件就绪后，运行时才会把这个 G 重新标记为 runnable，再交回调度器。

### 8.2 Linux 下的 `eventfd` 唤醒机制

在 Linux 上，Go runtime 会把一个专门的 `eventfd` 注册到 `epoll` 中。当某个线程阻塞在 `epoll_wait` 内，而运行时又需要打断这次等待、让它重新参与调度时，就会调用 `netpollBreak`。

`netpollBreak` 会向这个 `eventfd` 写入 8 字节数据，从而人为制造一个 `epoll` 就绪事件。这样阻塞中的 `epoll_wait` 就会立刻返回，等待中的线程也就被唤醒了。

### 8.3 如何理解工作窃取

如果一个 P 的本地队列已经空了，而其他 P 还有大量待执行 G，那么空闲 P 就会尝试去别人的本地队列尾部偷任务。这样做的目标是让各个 P 的负载尽可能均衡，避免部分线程很忙而另一些线程空转。

通过这一整套机制，Go 调度器才能在较少的操作系统线程之上，高效地并发执行大量 Goroutine。
