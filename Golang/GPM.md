# Golang GPM 调度模型详解

本文详细探讨 Go 语言并发模型的核心——GPM 调度器，旨在提供一份清晰、深入的学习笔记和面试参考。

---

### 1. Go 协程 (Goroutine)：并发的基石

#### 1.1 什么是 Goroutine？

Goroutine 是 Go 语言中实现并发的核心单元。它是一种极其轻量级的、由 Go 运行时（Runtime）管理的执行体，常被描述为“用户态线程”。

通过 `go` 关键字，我们可以轻松地启动一个 Goroutine：

```go
package main

import (
    "fmt"
    "time"
)

func say(s string) {
    for i := 0; i < 3; i++ {
        fmt.Println(s)
        time.Sleep(100 * time.Millisecond)
    }
}

func main() {
    go say("Hello") // 启动一个新的 Goroutine
    say("World")    // main 函数自身也是一个 Goroutine
}
```

#### 1.2 Goroutine 与线程 (Thread) 的核心区别

| 特性        | Goroutine                              | 内核线程 (Thread)                    |
| :-------- | :------------------------------------- | :------------------------------- |
| **内存占用**  | **小**，初始栈大小仅为 2KB，按需增长,按需缩容。           | **大**，通常为 1-8MB，固定大小。            |
| **创建/销毁** | **开销小**，由 Go 运行时直接创建和管理。               | **开销大**，需要陷入内核，由操作系统管理。          |
| **调度**    | **用户态调度**，由 Go 调度器（GPM）管理，切换不涉及内核，成本低。 | **内核态调度**，由操作系统调度，切换涉及上下文切换，成本高。 |
| **数量**    | 可以轻松创建**数十万甚至上百万**个。                   | 数量受限于操作系统和硬件，通常为**数千**个。         |

### 2. Goroutine 的执行与调度

Go 的调度器采用 GPM 模型，这是一个高效的 M:N 调度模型，即 M 个内核线程承载 N 个 Goroutine。

#### 2.1 GPM 模型核心组件

- **G (Goroutine)**：代表一个 Goroutine。它存储了 Goroutine 的执行栈、指令指针以及其他用于调度的信息。每个 `go` 语句都会创建一个 G。
- **P (Processor)**：逻辑处理器。P 是 G 和 M 之间的“中间层”，它维护了一个可运行的 Goroutine 队列（LRQ, Local Runnable Queue），并负责将 G 调度到 M 上执行。P 的数量决定了真正的并发度。
- **M (Machine)**：内核线程。M 是操作系统线程的抽象，是真正执行 Go 代码的实体。一个 M 必须绑定一个 P 才能执行 G。

**核心关系**：P 管理着一个 G 的本地队列，而 M 则从 P 的队列中取出 G 来执行。

#### 2.2 调度策略与流程

1.  **队列优先**：P 优先从自己的本地队列（LRQ）中获取 G。这减少了锁的竞争，提高了效率。
2.  **全局队列**：如果 P 的本地队列为空，它会尝试从全局队列（GRQ, Global Runnable Queue）中获取一批 G。
3.  **工作窃取 (Work-Stealing)**：如果全局队列也为空，P 会变成一个“小偷”，随机从其他 P 的本地队列中“窃取”一半的 G 来执行。这保证了所有 P 都有任务可做，提高了 M 的利用率。
4.  **系统调用 (Syscall)**：当一个 G 在 M 上执行时发生系统调用，M 会被阻塞。此时，调度器会将 P 与该 M 分离，并寻找一个空闲的 M（或新建一个 M）来接管这个 P，使其能够继续调度其他 G。当系统调用结束后，原来的 G 会被放回可运行队列，等待再次被调度。

#### 2.3 抢占式调度 vs. 协作式调度

- **协作式调度 (Go 1.14 之前)**：Goroutine 只有在发生阻塞（如 IO、channel 操作、系统调用）或主动调用 `runtime.Gosched()` 时才会出让 CPU。一个纯计算、无阻塞的 Goroutine 会一直霸占 M，导致其他 G “饥饿”。
- **抢占式调度 (Go 1.14 及之后)**：Go 引入了**基于信号的抢占机制**。编译时，编译器会在函数入口插入一段代码，检查 Goroutine 是否需要被抢占。如果一个 Goroutine 运行时间过长（超过一个时间片），Go 调度器会向该 M 发送一个信号，M 接收到信号后会中断当前 G 的执行，将其重新放入队列，然后执行其他 G。这确保了调度的公平性。

### 3. Goroutine 间通信：Channel

Go 提倡“**不要通过共享内存来通信，而要通过通信来共享内存**”。Channel 就是这一哲学的核心实践。

#### 3.1 Channel 工作原理

Channel 的底层实现是 `hchan` 结构体，其核心组成部分包括：

- **`qcount`**: 环形队列中当前元素的数量。
- **`dataqsiz`**: 环形队列的容量（对于有缓冲 channel）。
- **`buf`**: 用于存储数据的环形队列。
- **`sendx` / `recvx`**: 发送和接收操作在环形队列中的索引位置。
- **`recvq` / `sendq`**: 两个等待队列，分别存储因接收或发送阻塞的 Goroutine（`sudog` 结构体）。
- **`lock`**: 互斥锁，用于保护 `hchan` 的各个字段在并发访问时的一致性。

**工作流程**：
- **发送**：
    - 如果接收队列 `recvq` 不为空（有 G 在等待接收），直接将数据交给等待的 G，并唤醒它。
    - 如果 `recvq` 为空且缓冲区 `buf` 未满，将数据存入缓冲区。
    - 如果 `recvq` 为空且缓冲区已满，将当前 G 加入发送等待队列 `sendq` 并挂起。
- **接收**：
    - 如果发送队列 `sendq` 不为空（有 G 在等待发送），从等待的 G 中取数据，并唤醒它。
    - 如果 `sendq` 为空且缓冲区 `buf` 不为空，从缓冲区取数据。
    - 如果 `sendq` 为空且缓冲区为空，将当前 G 加入接收等待队列 `recvq` 并挂起。

#### 3.2 有缓冲 vs. 无缓冲 Channel

- **无缓冲 Channel (`make(chan T)`)**: `dataqsiz` 为 0。发送和接收必须**同时准备好**，否则一方会阻塞。它是一种强同步机制，确保了发送和接收的瞬间同步。
- **有缓冲 Channel (`make(chan T, N)`)**: `dataqsiz` 为 N > 0。在缓冲区未满前，发送不会阻塞；在缓冲区非空前，接收不会阻塞。它实现了异步通信。

### 4. Goroutine 间同步：sync.Mutex

当必须使用共享内存时，`sync.Mutex` 是保证数据同步、防止数据竞争（Data Race）的关键工具。

#### 4.1 `sync.Mutex` 原理

`sync.Mutex` 的核心是一个名为 `state` 的整数字段，通过位操作来表示锁的不同状态：

- **`mutexLocked` (第 0 位)**: 表示锁是否被锁定。
- **`mutexWoken` (第 1 位)**: 表示是否有 Goroutine 被唤醒。
- **`mutexStarving` (第 2 位)**: 表示锁是否处于饥饿模式。
- **`waiter` (剩余的位数)**: 表示等待锁的 Goroutine 数量。

`Mutex` 包含两种工作模式：

1.  **正常模式 (Normal Mode)**
    - 当锁被释放时，所有等待的 Goroutine（被唤醒的旧 G 和刚来请求的新 G）会一起竞争锁。
    - 这种模式下，新来的 G 有优势，因为它正在 CPU 上运行，可以连续多次获取锁。这可能导致等待队列中的 G 长时间无法获取锁，即“饥饿”。

2.  **饥饿模式 (Starvation Mode)**
    - 当一个 G 等待锁的时间超过 1ms，`Mutex` 会切换到饥饿模式。
    - 在饥饿模式下，锁被释放后会**直接交给等待队列头部的 Goroutine**，新来的 G 不会参与竞争，只能乖乖排到队尾。
    - 当一个 G 获得锁时，如果它是队列中最后一个等待者，或者它的等待时间小于 1ms，锁会切换回正常模式。

这种设计兼顾了性能（正常模式）和公平性（饥饿模式）。

### 5. GPM 关系与调优

#### 5.1 G, P, M 的动态关系详解

G, P, M 之间的关系不是静态的，而是动态变化的。理解它们的对应关系，关键在于区分“某一时刻”和“整个生命周期”。

**核心原则：**
- **P 的数量 (`GOMAXPROCS`) 决定了真正的并行度**。有多少个 P，就最多有多少个 G 可以同时（并行）执行。
- **一个 M 必须与一个 P 绑定才能执行 G**。M 是执行的动力，P 是执行的许可和上下文（持有 G 队列）。

#### 5.2 P 和 M 的关系：一对一还是多对多？

这是一个常见的误区。让我们来澄清：

**1. 一个 P 可以对应多个 M 吗？**

**答案：不可以，但在时间维度上，一个 P 会和多个 M 发生关联。**

在**任何一个确切的时间点**，一个 P 只能与**一个** M 绑定，形成一个执行单元 `P-M`。

但是，在一个 Go 程序的**整个生命周期**中，一个 P 可能会与**多个** M 先后进行绑定。这种情况最典型的场景就是**系统调用（Syscall）**：

1.  **初始状态**：P1 与 M1 绑定，正在执行一个 G1。
2.  **发生阻塞**：G1 发起了一个阻塞式的系统调用（例如，文件 IO）。这会导致 M1 线程被操作系统挂起，M1 将会阻塞。
3.  **P 的“移情别恋”**：Go 调度器不希望 P1 因为 M1 的阻塞而闲置（因为 P1 的本地队列里可能还有其他待运行的 G）。于是，调度器会执行以下操作：
    *   将 P1 与阻塞的 M1 **解绑**。
    *   寻找一个空闲的 M（比如 M2），或者**新建一个 M2**。
    *   将 P1 与 M2 **绑定**，形成新的 `P1-M2` 执行单元。
4.  **继续执行**：P1 现在可以在 M2 上继续调度和执行其本地队列中的其他 G。
5.  **阻塞结束**：一段时间后，M1 的系统调用完成，M1 恢复运行。此时 M1 会尝试重新获取一个 P。如果能找到空闲的 P，它就绑定并开始工作；如果找不到，它就会进入休眠状态，等待被调度器唤醒。

**结论**：P 和 M 在某一瞬间是 `1:1` 的关系，但从时间线上看，一个 P 会因为 M 的阻塞而与多个 M 发生过 `1:N` 的关系。

**2. 一个 M 可以对应多个 P 吗？**

**答案：绝对不可以。**

一个 M（内核线程）在任何时候都**只能与一个 P 绑定**。M 是执行者，P 提供了待执行的任务队列（G 队列）。一个执行者无法同时处理两个不同的任务列表。如果 M 没有绑定 P，那么它就是一个休眠或等待任务的线程。

#### 5.3 G, P, M 关系总结

- **G 与 P**：**多对一**。一个 P 的本地队列中可以有多个 G 等待被调度。
- **P 与 M**：
    - **某一瞬间是 1:1**：一个 P 绑定一个 M 执行。
    - **生命周期是 1:N**：一个 P 可能因为 M 的阻塞而先后与多个 M 绑定过。
- **G 与 M**：**多对多 (M:N)**。M 个 M 承载着 N 个 G 的执行。这是 Go 调度模型被称为 M:N 模型的原因。

#### 5.4 如何调整 GPM

- **`runtime.GOMAXPROCS(n)`**: 这个函数用于设置 P 的数量。
- **默认值**: 从 Go 1.5 开始，`GOMAXPROCS` 默认等于机器的 CPU 逻辑核心数。
- **何时调整**: 在绝大多数情况下，**不需要手动调整**。默认值对于 CPU 密集型和 IO 密集型应用通常都是最优的。只有在非常特殊的场景下，例如在多租户环境中需要限制某个 Go 程序使用的 CPU 核心数时，才考虑修改它。

### 6. 常见面试题及解析

1.  **Q: 请简述 Go 的 GPM 模型是什么？**
    **A:** GPM 是 Go 语言调度器的核心模型。G 代表 Goroutine，是 Go 的并发执行单元；P 代表逻辑处理器，负责调度 G；M 代表内核线程，是真正执行代码的实体。GPM 是一个 M:N 调度模型，即用 M 个线程执行 N 个 Goroutine，通过 P 作为中间层来高效地分发和调度任务，实现了低成本的并发。

2.  **Q: Goroutine 和线程有什么区别？为什么它更轻量？**
    **A:** 主要区别在于：1) **内存占用**：Goroutine 初始栈只有 2KB，而线程是 MB 级别。2) **调度开销**：Goroutine 在用户态由 Go 调度器管理，切换成本低；线程由操作系统在内核态调度，切换成本高。3) **创建和销毁**：Goroutine 由 Go 运行时管理，非常廉价，可以轻松创建百万个。

3.  **Q: Go 的调度器是抢占式的吗？它如何实现抢占？**
    **A:** 从 Go 1.14 开始是抢占式的。它采用**基于信号的异步抢占**。如果一个 Goroutine 运行时间过长，调度器会向它所在的 M 发送一个信号，中断当前 G 的执行，将其放回队列，从而让其他 G 有机会运行，保证了调度的公平性。

4.  **Q: 谈谈你对 Channel 的理解，它的底层实现是怎样的？**
    **A:** Channel 是 Go 的核心通信机制，用于在 Goroutine 之间安全地传递数据。其底层是 `hchan` 结构体，包含一个环形队列（缓冲区）、用于保护数据一致性的锁、以及两个等待队列（分别用于阻塞的发送者和接收者）。发送和接收操作都伴随着加锁和一系列条件检查，以确定是直接传递数据、将数据放入缓冲区，还是将当前 Goroutine 挂起并放入等待队列。

5.  **Q: `sync.Mutex` 有哪些工作模式？为什么需要饥饿模式？**
    **A:** `sync.Mutex` 有**正常模式**和**饥饿模式**。正常模式下，所有等待者公平竞争锁，性能高但可能导致饥饿。当一个 Goroutine 等待锁超过 1ms，会切换到饥饿模式。饥饿模式下，锁会直接交给等待队列的头部，保证了公平性，避免了队首的 Goroutine 被饿死。

6.  **Q: `runtime.GOMAXPROCS` 是什么？把它设置成 CPU 核心数的两倍会有什么效果？**
    **A:** `GOMAXPROCS` 用于设置 P 的数量，即 Go 程序可以同时运行的 CPU 核心数。默认值就是 CPU 核心数。设置为核心数的两倍通常**不会带来性能提升，反而可能因为过于频繁的线程调度和上下文切换而导致性能下降**。因为当 P 的数量大于 CPU 核心数时，操作系统需要花费额外的精力在多个 P（内核线程）之间进行切换，这些切换是有成本的。


## 新创建的协程会去哪里？(队列分配)


当我们使用 `go` 关键字启动一个函数时，例如 `go myFunction()`，Go 的运行时系统会执行以下操作：

1.  **调用 `newproc`:** 在编译层面，`go myFunction()` 会被转换为对运行时函数 `runtime.newproc` 的调用。
2.  **创建 G 对象:** `newproc` 函数的主要职责是创建一个新的 G 对象。它会从一个 G 对象的池（`gFree` 列表）中尝试获取一个可复用的 G，如果池为空，则会分配一个新的 G 对象。
3.  **初始化 G:** 新的 G 对象会被初始化，包括：
    *   分配一个小的执行栈（通常为 2KB）。
    *   设置其起始指令指针（PC），使其指向待执行函数的入口。
    *   设置 G 的状态为 `_Grunnable`，表示它已经准备好，可以被执行了。

G 对象创建并初始化完成后，调度器需要决定将它放在哪里，以便未来的某个时刻被 M 执行。这个决策遵循以下优先级顺序：

### 1. P 的本地运行队列 (Local Run Queue - LRQ)

**首选目标。**

调度器会首先尝试将这个新的、可运行的 G 放入**当前 G 所在的 P** 的本地运行队列（LRQ）中。

- **为什么？** 这是最高效的方式。因为创建 G 的代码本身正在一个 M 和 P 的组合上运行，将新的 G 放入同一个 P 的队列中，可以避免不同 P 之间的锁竞争，并且利用了 CPU 缓存的局部性原理。后续该 P 上的 M 可以很快地从自己的队列中取出并执行这个新的 G。

### 2. 全局运行队列 (Global Run Queue - GRQ)

**次选目标。**

如果 P 的本地运行队列（LRQ）已满（默认容量为 256），调度器会将这个新的 G 放入全局运行队列（GRQ）中。

- **为什么？** GRQ 是所有 P 共享的队列，需要通过互斥锁来保护，访问开销比 LRQ 更高。当 LRQ 满了，说明当前的 P 已经有足够多的任务，将新的 G 放入 GRQ 可以让其他空闲的 P（通过工作窃取机制）来领取并执行它，从而实现负载均衡。

### 总结队列分配流程：

1.  `go myFunction()` 触发 `newproc` 创建一个新的 G。
2.  尝试将 G 放入当前 P 的 LRQ。
3.  如果 LRQ 已满，则将 G 放入 GRQ。

## 调度循环与工作窃取 (Work-Stealing)

一个 M 在执行完一个 G 后，会进入一个调度循环（`schedule` 函数），它会按照以下顺序为自己寻找新的 G 来执行：

1.  **从绑定的 P 的 LRQ 中查找:** 这是最常见的路径。
2.  **从 GRQ 中查找:** 如果 LRQ 为空，M 会尝试从 GRQ 中获取一批 G（例如 `GOMAXPROCS` 个）并放到自己的 LRQ 中，然后取一个执行。
3.  **工作窃取 (Work Stealing):** 如果 GRQ 也为空，M 会变成一个“小偷”。它会随机选择另一个 P，并尝试从那个 P 的 LRQ 中“偷”走一半的 G 放到自己的 LRQ 中。这个机制极大地提高了调度效率和 CPU 利用率，避免了某些 P 很忙而另一些 P 却空闲的情况。
4.  **轮询网络:** 如果上述方法都找不到 G，M 可能会去检查网络轮询器（netpoller）中是否有因网络 I/O 而就绪的 G。

通过这个精巧的 GPM 模型和多级队列机制，Go 调度器实现了在少量操作系统线程上高效地并发执行成千上万个 goroutine。
