这是一份基于前面讨论整理而成的 **Go `sync.Mutex` 深度解析笔记**，涵盖了数据结构、加解锁流程、饥饿模式、底层调度原语、信号量实现，以及与 netpoller 的对比。

---

## 1. Mutex 的结构

`sync.Mutex` 位于 `src/sync/mutex.go`，只包含两个字段：

```go
type Mutex struct {
    state int32
    sema  uint32
}
```

- **`state`**：一个 32 位整数，用于表示锁的当前状态，划分为四个部分：
  - **最低位（`mutexLocked`）**：1 表示已锁定，0 表示空闲。
  - **第二位（`mutexWoken`）**：标记是否有 goroutine 被唤醒并正在尝试获取锁。
  - **第三位（`mutexStarving`）**：标记锁是否处于饥饿模式。
  - **剩余 29 位**：记录当前在该锁上等待的 goroutine 数量。
- **`sema`**：一个 `uint32` 值，作为运行时信号量的**标识符**。它本身不存储任何队列信息，而是由 Go 运行时以它的地址为键，维护独立的等待链表。

---

## 2. 加锁过程（`Lock`）

调用 `mu.Lock()` 时，依据竞争程度和模式，会依次尝试以下策略：

### 2.1 快速路径（CAS）

如果 `state` 为 0（完全无竞争），goroutine 使用原子 `Compare-And-Swap` 将 `state` 从 0 设为 `mutexLocked`。成功则直接获得锁并返回。整个过程**仅在用户态执行几条指令，无系统调用**。

### 2.2 自旋阶段

如果快速路径失败，说明锁已被其他 goroutine 持有。在满足条件时（多核 CPU、普通模式、自旋次数未超限），当前 goroutine 会进入**自旋**：
- 循环执行 `PAUSE` 指令，降低 CPU 功耗。
- 反复检查 `state` 中的锁位是否被释放，一旦发现空闲，立即尝试用原子操作抢占。
- 自旋时间很短（约 30 个时钟周期），若依然失败，则转入等待队列。

自旋的目的是乐观忙等，避免频繁陷入内核挂起。

### 2.3 信号量阻塞

如果自旋仍无法获得锁，或者不满足自旋条件（如单核、饥饿模式），goroutine 会：
1. 原子地将 `state` 中的**等待者计数加 1**。
2. 调用运行时信号量 `runtime.SemacquireMutex(&m.sema, ...)`，将自己挂入等待队列。
3. 此后 goroutine 被移出调度器的运行队列，真正阻塞，直到被 `Unlock` 唤醒。

---

## 3. “另一个 goroutine 去获取锁”发生了什么

设 goroutine A 已持有锁，goroutine B 调用 `Lock()`：
- B 快速路径 CAS 失败。
- 若允许自旋，B 在极短时间内忙等，期望 A 快速释放。
- 自旋无果后，B 通过 `SemacquireMutex` 挂到 `sema` 关联的等待链表上，并调用 `gopark` 让出 CPU。B 对应的线程（M）会继续执行其他 goroutine，完全无阻塞。
- 当 A 调用 `Unlock` 时，A 从链表头部取出一个等待者（可能是 B），调用 `goready(B)` 将其唤醒。B 重新被调度后从 `gopark` 返回，争夺锁。

整个流程确保**同时只有一个 goroutine 能成功设置 `mutexLocked` 位**，实现互斥。

---

## 4. 解锁过程（`Unlock`）

1. 原子清除 `state` 中的 `mutexLocked` 标志：`state &^= mutexLocked`。
2. 如果 `state` 中等待者计数 > 0，调用 `runtime.Semrelease(&m.sema, ...)` 唤醒**一个**等待者。
   - 被唤醒的 goroutine 从 `SemacquireMutex` 中返回，进入锁竞争。
   - 在**正常模式**下，新到达的 goroutine 与刚被唤醒的 goroutine 同时竞争，刚唤醒的可能失败（不公平）。
   - 在**饥饿模式**下，直接将锁移交给队首等待者。

---

## 5. 正常模式与饥饿模式

为解决尾延迟，Go 1.9 引入饥饿模式：

| 模式 | 特点 | 触发条件 |
|------|------|----------|
| **正常模式** | 新到达的 goroutine 可能通过自旋抢走锁，优先级高，吞吐量大 | 默认模式 |
| **饥饿模式** | 释放锁时直接将所有权交给队首等待者，新来的 goroutine 不自旋，直接排到队尾 | 一个等待者等待时间超过 **1 ms** |

退出饥饿模式：当队首等待者获得锁后，如果发现自己的等待时间小于 1 ms，或等待队列为空，则切回正常模式。

## 6. 底层实现：goroutine 的挂起与唤醒

Go 中锁的阻塞**直接挂起的是 goroutine，而非操作系统线程**。这是通过调度器原语实现的。

### 6.1 `gopark` 与 `goready`

- **`gopark(reason)`**：将当前 goroutine 状态从 `_Grunning` 变为 `_Gwaiting`，并记录原因；将其与等待事件关联（如加入信号量链表）；接着调用 `mcall` 切换到 `g0` 栈执行 `schedule`，当前 M 拾取其他 goroutine 继续运行。线程不会因此而阻塞。
- **`goready(gp)`**：将 `gp` 状态从 `_Gwaiting` 置为 `_Grunnable`，并将其放入某个 P 的运行队列；必要时唤醒或创建新的 M 来执行它。

整个 M:N 调度模型的核心就是：**一个 goroutine 阻塞，线程仍然可以干别的活**。

### 6.2 线程何时真正挂起？

当某个 M 上所有 goroutine 都阻塞，且全局队列无可用任务时，M 才会进入空闲状态，并可能通过 `futex` 在内核中挂起。这是**系统空闲的兜底行为**，不是每个锁等待直接导致的。

### 6.3 锁的信号量实现细节

`runtime.sema` 是 Go 运行时封装的一套信号量机制，为 `Mutex`、`channel` 等提供阻塞/唤醒服务：

- 以 `sema` 字段的**地址**为键，维护一个 `semaRoot` 平衡树。每个键下挂着一个由 `sudog` 构成的双向链表，`sudog` 中保存了被挂起的 goroutine 指针。
- `SemacquireMutex`：将当前 goroutine 包装成 `sudog` 插入链表尾部，然后调用 `gopark`。
- `Semrelease`：从链表头部摘取一个 `sudog`，取出 `g` 调用 `goready`。

因此，**`state` 中的等待者计数只是快速判断“是否有人等”用的；真正的队列由运行时根据 `sema` 地址维护**，两者各司其职。

---

## 7. state 与等待队列的关系总结

- `state` 字段**只存计数和标志位**，不存储任何 goroutine 标识。
- `sema uint32` 通过其地址作为 key，在运行时内部映射到一个 `sudog` 链表，这里才是真正的等待者队列。
- 加锁时计数加 1，解锁时计数减 1，唤醒时直接从链表取走一个 `sudog`。这样既保持了状态位的原子性，又实现了高效排队。

---

## 8. 与 Netpoller 的对比

Netpoller 处理网络 I/O，底层依赖 epoll/kqueue，但它复用了与锁相同的 `gopark/goready` 原语。

| 对比维度 | 锁的信号量 | Netpoller |
|----------|------------|-----------|
| **等待条件** | 其他 goroutine 释放锁 | 内核通知 fd 可读/写 |
| **唤醒触发者** | 另一个 goroutine 调用 `Semrelease` | 调度器或 sysmon 调用 `netpoll` 检测到就绪事件 |
| **底层事件监测** | 无，纯用户态原子操作 + 链表 | 内核 epoll/kqueue |
| **挂起函数** | `gopark`（相同） | `gopark`（相同） |
| **线程阻塞** | 仅在系统整体空闲时通过 futex 休眠 | 同理，线程不被单个 I/O 挂起 |
| **公平性** | FIFO 链表，支持饥饿模式强制移交 | 由 epoll 就绪顺序和调度决定，不保证严格 FIFO |

**核心区别**：锁等待是“自驱动”的（一个 goroutine 直接唤醒另一个），网络等待是“他驱动”的（必须有一个统一的监控器轮询内核并批量唤醒）。两者都在 goroutine 层面阻塞，充分利用了 M:N 调度的优势。

## 9. 总结

- **互斥根源**：`state` 最低位通过原子 CAS 操作保证互斥。
- **等锁行为**：先自旋（用户态），失败后通过信号量挂起 goroutine（`gopark`），让出 CPU，线程继续运行其他任务。
- **队列实现**：`sema` 作为 key，运行时维护 `sudog` 链表，与 `state` 计数协作。
- **模式切换**：正常模式关注吞吐，饥饿模式确保公平，自动切换阈值 1 ms。
- **高性能关键**：无竞争时仅几条原子指令；有竞争时只阻塞 goroutine 不阻塞线程，与 netpoller 等协同构建了 Go 高并发的基石。

这份笔记可帮助你从数据结构到底层系统调用，完整理解 `sync.Mutex` 的工作原理。

`sync.RWMutex` 是读写互斥锁，核心原则是**读写互斥、写写互斥，读读不互斥**。它的实现建立在 `Mutex` 之上，但通过引入额外的计数器和信号量，实现了多读者并发、写者优先的语义。

---

## 1. 数据结构

```go
type RWMutex struct {
    w           Mutex    // 内部互斥锁，用于写者间互斥
    writerSem   uint32   // 写者等待信号量
    readerSem   uint32   // 读者等待信号量
    readerCount int32    // 当前活跃读者数（或特殊值表示有写者等待）
    readerWait  int32    // 写者等待时，已进入的读者需要完成的数量
}
```

- **`w`**：一把标准的 `Mutex`，**写者通过获取此锁保证写 - 写互斥**。
- **`writerSem` / `readerSem`**：运行时信号量，用于挂起和唤醒等待的写者和读者，与 `Mutex.sema` 用途相同。
- **`readerCount`**：
  - 正常情况：记录当前持有读锁的 goroutine 数量。
  - 当写者尝试加锁时，写者会将其减去一个极大的常数 `rwmutexMaxReaders`（1<<30），使其变为负数，**作为“有写者等待”的标志**，阻止后续读者进入。
- **`readerWait`**：写者加锁时，记录在它之前已经进入的读者数量（即写者需要等待这些读者全部释放后，才能真正获得写锁）。

---

## 2. 读锁（`RLock` 与 `RUnlock`）

### 加读锁
1. 原子地将 `readerCount` **加 1**。
2. 若加 1 后的值**< 0**（说明有写者正在等待或已持有写锁），则调用 `runtime.SemacquireMutex(&rw.readerSem, ...)` 将自己挂起，等待写者唤醒。
3. 若加 1 后 >= 0，直接获得读锁，继续执行。

*注意：读锁路径无自旋，一旦检测到写者等待，立刻挂起。*

### 解读锁
1. 原子地将 `readerCount` **减 1**。
2. 若减 1 后的值**< 0**（说明有写者在等待），则进一步检查此时是否所有读者都已释放（即 `readerWait` 是否为 0），若是，则通过 `runtime.Semrelease(&rw.writerSem, ...)` 唤醒**一个**等待的写者。
3. 若减 1 后 >= 0，直接返回。

---

## 3. 写锁（`Lock` 与 `Unlock`）

### 加写锁
1. **获取内部互斥锁 `rw.w`**：保证同一时刻只有一个写者执行后续逻辑。
2. **阻止新读者**：原子地将 `readerCount` 减去 `rwmutexMaxReaders`，使其变为负数。此时新来的 `RLock` 会因 `readerCount < 0` 而阻塞。
3. **等待现有读者完成**：若当前仍有活跃读者（即原 `readerCount > 0`），则记录需要等待的读者数量到 `readerWait`，然后调用 `runtime.SemacquireMutex(&rw.writerSem, ...)` 挂起自己。  
   - 若原 `readerCount == 0`，则直接获得写锁，无需等待。
4. 当写者被 `RUnlock` 唤醒后，再次检查 `readerCount`，确认所有读者已退出，此时写者真正持有写锁。

### 解写锁
1. 原子地将 `readerCount` 加上 `rwmutexMaxReaders`（恢复为非负值），允许后续读者继续获取读锁。
2. 通过 `runtime.Semrelease(&rw.readerSem, ...)` 唤醒所有因该写锁而阻塞的读者。
3. 释放内部互斥锁 `rw.w`，允许其他写者竞争。

---

## 4. 写优先策略

`RWMutex` 实现的是**写优先**，避免写者饥饿：
- 当写者调用 `Lock()` 并成功将 `readerCount` 变为负数后，**所有后续读者都将阻塞**。
- 已持有读锁的读者会继续运行，直到全部释放，写者才能被唤醒。
- 写者释放后，一次性唤醒所有等待的读者。

这种设计保证：只要写者到来，就不会有新的读者插队，写者只需等待在它之前的读者完成。

---

## 5. 与 Mutex 实现的区别

| 特性 | `sync.Mutex` | `sync.RWMutex` |
|------|-------------|----------------|
| **并发度** | 完全互斥，同时只允许一个 goroutine | 允许多个读者并发，写者互斥 |
| **内部锁** | 自身即为互斥锁 | 包含一个 `Mutex`（`w`）用于写者互斥，读者通过计数器与信号量管理 |
| **自旋** | 有自旋阶段（普通模式） | 写锁因内部 `Mutex` 可能自旋；读锁**无自旋**，直接挂起 |
| **饥饿模式** | 支持，由内部 `state` 位控制 | 写锁继承自 `w` 的饥饿模式；读者无独立饥饿模式，依赖写优先策略防饿 |
| **信号量** | 一个 `sema` | 两个信号量：`writerSem` 和 `readerSem` |
| **状态维护** | 单原子整数 `state` 包含锁位、唤醒、饥饿、等待计数 | 多个原子变量：`readerCount`（正数为读者数，负数为写锁标志）、`readerWait`（写者需等待的读者数） |
| **唤醒粒度** | 释放锁时唤醒**一个**等待者 | 写锁释放时唤醒**所有**等待的读者；读者释放时可能唤醒**一个**写者 |
| **公平性** | 先到先服务（FIFO），饥饿模式强制移交 | 写优先，写者一旦等待，新读者必须排队；读者间不保证顺序 |

---

## 6. 深度总结

`RWMutex` 巧妙地复用了 `Mutex`：
- **写 - 写互斥**完全委托给内部 `w Mutex`，享受着 `Mutex` 的自旋、饥饿模式等优化。
- **读 - 写互斥**则通过 `readerCount` 的正负符号位实现：`readerCount >= 0` 意味着“正常模式，读者可进入”，`< 0` 意味着“写者已就位，读者必须等待”。
- **挂起与唤醒**沿用与 `Mutex` 完全相同的运行时信号量 `Semacquire/Semrelease`，底层依旧是 `gopark/goready` 不阻塞线程。

这种分层设计使得 `RWMutex` 无需从零实现互斥，而是在 `Mutex` 之上构建了更灵活的读写语义，既保证了正确性，又最大化了并发度。
