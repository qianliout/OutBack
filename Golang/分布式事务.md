# 分布式事务：从理论到实战 (MySQL + Kafka)

本文档旨在系统性地讲解分布式事务的核心理论，并结合一个真实的电商下单场景，展示如何在 `MySQL` 和 `Kafka` 技术栈中进行工程实践。

---

## 第一部分：分布式事务核心理论

### 1. 什么是分布式事务？

在分布式系统中，一个业务操作通常由多个独立的服务（或数据库）共同完成。分布式事务（Distributed Transaction）是指事务的参与者、支持事务的服务器、资源服务器以及事务管理器分别位于分布式系统的不同节点之上。

简单来说，就是一次大的操作由不同节点上的多个小操作共同组成，这些小操作要么全部成功，要么全部失败。

#### 1.1 挑战：CAP 与 BASE 理论

- **CAP 定理**: 一个分布式系统最多只能同时满足以下三项中的两项：
  - **一致性 (Consistency)**: 所有节点在同一时间的数据完全一致。
  - **可用性 (Availability)**: 每个请求都能接收到一个响应，无论成功或失败。
  - **分区容错性 (Partition Tolerance)**: 系统在网络分区（节点间通信中断）的情况下，仍能继续运行。
  在现代分布式系统中，网络分区是必然要面对的（P），因此架构师必须在一致性（C）和可用性（A）之间进行权衡。

- **BASE 理论**: 是对 CAP 中一致性和可用性权衡的结果，是最终一致性方案的基石。
  - **基本可用 (Basically Available)**: 系统在出现故障时，允许损失部分可用性，保证核心功能可用。
  - **软状态 (Soft State)**: 允许系统中的数据存在中间状态。
  - **最终一致性 (Eventually Consistent)**: 系统中的所有数据副本，在经过一段时间的同步后，最终能够达到一个一致的状态。

### 2. 二阶段提交 (Two-Phase Commit, 2PC)

2PC 是一种经典的**强一致性**、中心化的原子提交协议。

- **实现步骤**:
  1.  **准备阶段 (Prepare Phase)**: 协调者询问所有参与者是否可以提交，参与者执行本地事务并锁定资源，但不提交。
  2.  **提交阶段 (Commit Phase)**: 如果所有参与者都回复“可以”，协调者发送 `COMMIT` 指令；否则发送 `ROLLBACK` 指令。

- **优缺点**:
  - **优点**: 原理简单，提供了强一致性保证。
  - **缺点**: 同步阻塞（性能差）、协调者单点故障、存在数据不一致风险。

### 3. 三阶段提交 (Three-Phase Commit, 3PC)

3PC 是 2PC 的改进版，引入了 `CanCommit` 阶段和超时机制，试图解决 2PC 的问题。

- **实现步骤**:
  1.  **CanCommit**: 协调者询问是否可以提交。
  2.  **PreCommit**: 参与者执行事务，写 Redo/Undo Log。
  3.  **DoCommit**: 协调者发送提交或回滚指令。参与者若超时未收到指令，会自动提交。

- **优缺点**:
  - **优点**: 相比 2PC 降低了阻塞，减少了单点故障风险。
  - **缺点**: 依然存在数据不一致的可能，且实现更复杂。

### 4. TCC (Try-Confirm-Cancel)

TCC 是一种**补偿型**的最终一致性方案，业务侵入性强。

- **实现步骤**:
  1.  **Try**: 尝试执行阶段。完成所有业务检查，并**预留**业务资源。
  2.  **Confirm**: 确认执行阶段。真正执行业务，**使用**预留的资源。
  3.  **Cancel**: 取消执行阶段。如果失败，则调用 `Cancel` 接口**释放**预留的资源。

- **优缺点**:
  - **优点**: 性能好，并发高，不依赖底层数据库的事务。
  - **缺点**: 业务侵入性强，开发成本高，需要保证 `Confirm` 和 `Cancel` 的幂等性。

### 5. Saga 模式

Saga 是一种流行的**长事务**解决方案，核心思想是将长事务拆分为多个本地短事务，失败时通过补偿事务来恢复。

- **实现步骤**: 一个 Saga 由一系列子事务 `T1, T2, ..., Tn` 和对应的补偿事务 `C1, C2, ..., Cn` 组成。如果 `Ti` 失败，则反向执行 `C(i-1), ..., C1`。

- **优缺点**:
  - **优点**: 系统吞吐量高，易于实现，适合长流程业务。
  - **缺点**: 无法保证隔离性，会暴露中间状态，补偿逻辑开发有挑战。

### 6. 本地消息表 (Transactional Outbox)

这是一种基于消息队列实现的最终一致性方案，核心思想是将业务操作和发送消息这两个步骤放在同一个**本地事务**中。

- **实现步骤**:
  1.  在本地事务中，同时完成业务数据处理和消息数据写入（到一个特殊的消息表）。
  2.  通过一个独立的任务，轮询该消息表，将消息发送到消息队列（MQ）。
  3.  消息发送成功后，更新或删除消息表中的记录。

- **优缺点**:
  - **优点**: 可靠性高，将业务与通知解耦，是一种非常可靠的最终一致性方案。
  - **缺点**: 依赖本地事务，消息发送存在延迟，需要保证消费者幂等。

## 第二部分：方案实战 - 基于MySQL+Kafka的下单支付场景

现在，我们将理论付诸实践。对于高并发的电商系统，其技术栈通常为 `MySQL + Kafka`，我们将演示如何应用**本地消息表**模式来解决“下单并通知支付”的分布式事务问题。

### 场景回顾

- **订单服务 (Order Service)**: 使用 `MySQL`，负责创建订单。
- **支付服务 (Payment Service)**: 负责处理支付，需要接收订单创建成功的通知。
- **挑战**: 保证“创建订单”的DB操作和“通知支付”的Kafka消息发送，这两个动作的原子性。

### 实现步骤详解

**步骤一：在订单服务中，创建本地消息表**

在订单服务的数据库中，创建一张 `message_outbox` 表。

```sql
CREATE TABLE `message_outbox` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `aggregate_id` VARCHAR(255) NOT NULL, -- 通常是订单ID，用于Kafka消息分区
  `topic` VARCHAR(255) NOT NULL,        -- 目标 Kafka Topic
  `payload` JSON NOT NULL,              -- 消息体
  `status` TINYINT NOT NULL DEFAULT 0,  -- 消息状态: 0-待发送, 1-已发送
  `created_at` TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  `sent_at` TIMESTAMP(6) NULL DEFAULT NULL,
  PRIMARY KEY (`id`),
  INDEX `idx_status_created_at` (`status`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**步骤二：在Go代码中，将业务和消息写入包裹在同一事务中**

```go
// 以下为伪代码，展示核心逻辑
func createOrder(db *sql.DB, orderDetails Order, kafkaTopic string) error {
    tx, err := db.Begin() // 1. 开始MySQL本地事务
    if err != nil { return err }
    defer tx.Rollback()

    orderID, err := insertOrder(tx, orderDetails) // 2. 插入订单
    if err != nil { return err }

    messagePayload, _ := json.Marshal(orderDetails) // 3. 插入消息到outbox表
    err = insertMessage(tx, orderID, kafkaTopic, messagePayload)
    if err != nil { return err }

    return tx.Commit() // 4. 提交事务，保证原子性
}
```

**步骤三：创建消息中继服务 (Message Relay) 并配置高可靠 Kafka 生产者**

该服务负责将 `message_outbox` 表中的消息推送到 Kafka。为保证可靠性，Kafka Producer 需做如下关键配置：

- `enable.idempotence=true`: **开启幂等性**。这是最重要的配置，可以防止因网络重试等原因造成的重复消息。它会自动将 `acks` 设为 `all`，并将 `retries` 设为大于0的值。
- `acks=all`: **最高持久化等级**。Leader副本必须等待所有ISR（In-Sync Replicas）都收到消息后，才认为写入成功。
- `max.in.flight.requests.per.connection=1`: **保证消息顺序**。在单个连接上，同一时间只发送一个请求，防止消息乱序。

**步骤四：支付服务进行幂等消费**

支付服务作为消费者，必须**关闭自动提交offset** (`enable.auto.commit=false`)，并在业务逻辑处理成功后，**手动提交offset**。同时，消费逻辑必须是**幂等的**，以防止消息重发导致业务重复执行（例如，通过查询支付记录是否已存在来判断）。

**改进措施：使用 Debezium/Canal 替代轮询**

为避免轮询给数据库带来的压力，并降低延迟，可以引入 CDC (Change Data Capture) 工具（如 `Debezium`）监听 `MySQL` 的 `binlog`，一旦 `message_outbox` 表有新纪录，就将其准实时地推送到 Kafka。

## 第三部分：方案对比与选型建议

| 方案 | 一致性 | 实现复杂度 | 业务侵入 | 性能/并发 | 推荐用于下单支付场景? |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **2PC/3PC** | 强一致性 | 中 | 低 | 差 | **不推荐** |
| **TCC** | 最终一致性 | 高 | 高 | 好 | **不推荐 (过度设计)** |
| **Saga** | 最终一致性 | 中 | 中 | 好 | **不推荐 (过度设计)** |
| **本地消息表** | 最终一致性 | 低 | 低 | **极好** | **强烈推荐** |

### 总结

- 对于需要**强一致性**、低并发的内部系统，可以考虑 **2PC/3PC**。
- 对于需要编排**多个（3个以上）服务**的复杂业务流程，可以考虑 **Saga** 或 **TCC**。
- 对于绝大多数涉及**核心DB操作 + 可靠异步通知**的业务场景（如本文的下单支付），**本地消息表**模式是兼具可靠性、高性能和低成本的最佳实践。
