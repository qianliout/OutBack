## 一、为什么需要分布式锁？—— 核心痛点

在单机系统中，我们用 `synchronized` 或 `ReentrantLock` 解决并发问题。但**分布式系统**（多节点、多进程）面临新挑战：

- **竞争条件**：多个节点同时操作共享资源（如库存扣减、订单生成），导致数据不一致。
- **无共享内存**：节点间无法通过内存锁同步，必须依赖**外部协调服务**。

> ✅ **本质**：分布式锁 = 一种**分布式协调机制**，确保在分布式环境下，同一时间只有一个客户端能持有锁，安全访问共享资源。

## 二、分布式锁的核心原理

### 1. 必须满足的三大特性

| 特性           | 说明                    | 不满足的后果          |
| ------------ | --------------------- | --------------- |
| **互斥性**      | 任意时刻仅有一个客户端能持有锁       | 并发操作导致数据错误（如超卖） |
| **可重入性**（可选） | 同一线程可多次获取锁（避免死锁）      | 重复加锁导致业务阻塞      |
| **锁超时**（必须）  | 锁自动过期（防死锁），客户端需在过期前续期 | 节点宕机后锁永久持有，系统挂起 |

### 2. 关键设计挑战

- **网络分区**：节点间通信延迟/失败，导致锁状态不一致。
- **时钟漂移**：不同节点时钟不同步，影响锁超时判断。
- **原子性**：加锁/解锁必须是原子操作（避免中间状态）。

> 💡 **核心思想**：用**外部存储**（如Redis、ZooKeeper）作为“锁的仲裁者”，通过原子操作实现互斥。

## 三、主流实现方式深度对比

### 方式1：基于Redis（最常用，性能优先）

#### 实现原理

- 利用 `SET key value NX PX ttl` 命令（Redis 2.6+）：
    
    ```bash
    SET lock_key "client_id:123" NX PX 3000
    ```
    
    - `NX`：仅当key不存在时设置
    - `PX 3000`：锁过期时间3秒（防死锁）
    - `client_id`：唯一标识（防误释放）

#### 为什么这样用？

|优势|劣势|
|---|---|
|✅ 高性能（10万+ QPS）|❌ 单点故障风险（Redis主节点宕机）|
|✅ 语法简单，易集成|❌ 需处理锁续期（业务执行时间>3秒）|
|✅ 支持可重入（通过客户端库）|❌ Redlock算法争议大（见下文）|

#### 为什么不用“简单SET”？

- **错误示例**：`SET lock_key "value"` + `DEL lock_key`  
    → 问题：`DEL` 可能删除其他客户端的锁（无唯一标识）。
- **正确做法**：用 `client_id` 标识持有者，释放锁时校验：
    
    ```java
    if (redis.get("lock_key").equals(client_id)) {
        redis.del("lock_key");
    }
    ```
    

#### Redlock算法（争议点）

- **设计初衷**：解决Redis单点故障（多Redis实例集群）
- **实现**：向5个独立Redis节点加锁，需3个节点成功才生效。
- **为什么被质疑**？
    
    > Redis作者Antirez指出：**在大多数生产环境，单Redis实例已足够**。  
    > 问题：网络分区时，可能同时获得多个锁（违反互斥性），且实现复杂。  
    > ✅ **结论**：除非对高可用要求极高（如金融级系统），否则**避免用Redlock**，改用单Redis+合理过期时间。
    

---

### 方式2：基于ZooKeeper（强一致性，容错优先）

#### 实现原理

- 利用ZooKeeper的**临时顺序节点**：
    1. 客户端在`/locks`下创建临时节点（如`lock_0000000001`）。
    2. 获取所有子节点，按序号排序，**最小序号的节点持有锁**。
    3. 当前持有锁的客户端退出时，ZooKeeper自动删除节点，触发下一位客户端获得锁。

#### 为什么这样用？

|优势|劣势|
|---|---|
|✅ 强一致性（ZooKeeper保证）|❌ 性能低（1000+ QPS，Redis 10倍）|
|✅ 自动处理节点故障（临时节点）|❌ 依赖ZooKeeper集群，运维复杂|
|✅ 无锁过期问题（ZK会话管理）|❌ 无原生可重入支持|

#### 适用场景

- 需要**强一致性**的场景（如配置中心、注册中心）。
- 业务对性能要求不高，但对数据一致性要求极高。

> 💡 **对比Redis**：ZooKeeper适合“低频、高一致性”场景；Redis适合“高频、高性能”场景。

---

### 方式3：基于数据库（简单但不推荐）

#### 实现原理

- 用数据库行锁（如MySQL `SELECT ... FOR UPDATE`）：
    
    ```sql
    -- 创建锁表
    CREATE TABLE lock (id INT PRIMARY KEY, lock_key VARCHAR(255) UNIQUE);
    
    -- 加锁
    INSERT INTO lock (id, lock_key) VALUES (1, 'order_lock') ON DUPLICATE KEY UPDATE id=id;
    
    -- 解锁
    DELETE FROM lock WHERE lock_key = 'order_lock';
    ```
    

#### 为什么不用？

|问题|后果|
|---|---|
|❌ 数据库成为性能瓶颈|业务吞吐量下降50%+|
|❌ 无法实现锁续期|业务执行超时导致锁提前释放|
|❌ 事务回滚可能残留锁|锁泄漏，系统卡死|

> ✅ **结论**：**仅用于简单场景**（如单机测试），生产环境**绝对不推荐**。

## 四、典型使用场景与避坑指南

### 场景1：秒杀系统（高并发、强一致性）

- **需求**：防止超卖（如100件商品被10万用户抢）
    
- **正确实现**：
    
    ```java
    // 使用Redisson（封装了续期）
    RLock lock = redisson.getLock("seckill:product:1001");
    if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
        try {
            // 扣减库存逻辑
        } finally {
            lock.unlock();
        }
    }
    ```
    
- **为什么这样用？**  
    Redisson自动处理锁续期（每10秒续期），避免业务执行超时导致锁失效。
    
- **不这样用的坏处**：  
    ❌ 未设置过期时间 → 节点宕机后锁永久持有，库存永远无法扣减。  
    ❌ 业务执行时间>3秒 → 锁提前释放，导致超卖（如100件卖120件）。
    

---

### 场景2：分布式任务调度（避免重复执行）

- **需求**：同一任务（如每日数据汇总）只在一台机器执行
    
- **正确实现**：用ZooKeeper的`Ephemeral Sequential`节点
    
    ```java
    // 创建临时节点，自动排序
    String lockPath = zk.create("/schedules/lock-", new byte[0], Ids.OPEN_ACL_UNSAFE, CreateMode.EPHEMERAL_SEQUENTIAL);
    // 检查是否最小序号节点
    List<String> children = zk.getChildren("/schedules", false);
    if (lockPath.equals("/schedules/lock-0000000001")) { // 最小序号
        executeTask();
    }
    ```
    
- **为什么用ZooKeeper？**  
    任务失败后，ZooKeeper自动清理节点，下个节点自动接管（无脑挂）。
    
- **不这样用的坏处**：  
    ❌ 用Redis实现 → 任务执行中Redis故障，任务未完成但锁失效，导致重复执行。

## 五、高频错误与致命陷阱

|错误类型|案例|后果|解决方案|
|---|---|---|---|
|**锁未设置过期时间**|`SET lock_key "value"`|节点宕机后锁永久持有|必须用 `PX` 或 `EX` 设置过期|
|**锁过期时间过短**|`PX 1000`（1秒）|业务执行时间>1秒 → 锁提前释放|过期时间 = 业务执行时间×2|
|**锁释放未校验持有者**|`DEL lock_key`（直接删除）|误释放其他客户端的锁|用 `client_id` 校验后删除|
|**未处理锁续期**|单次加锁，业务执行10秒|锁在5秒后失效，导致并发|使用Redisson等自动续期库|
|**单Redis无容灾**|仅用单台Redis|Redis宕机 → 全链路锁失效|用Redis Sentinel或Cluster|

> 💡 **血泪教训**：某电商在双11因Redis锁过期时间设为5秒（业务需10秒），导致超卖1000+订单，损失千万。

## 六、最佳实践总结

1. **首选Redis（用Redisson）**
    
    - 适用场景：高并发、高性能要求（秒杀、订单系统）。
    - 必做：设置过期时间 + 自动续期（Redisson `tryLock` + `lockWatchdogTimeout`）。
2. **次选ZooKeeper**
    
    - 适用场景：强一致性、低频任务（调度中心、配置管理）。
    - 必做：用临时顺序节点 + 监听节点变化。
3. **绝对避免**
    
    - 数据库实现、单Redis无容灾、无锁过期。
4. **通用原则**
    
    - **过期时间** = 业务执行时间 × 2（预留缓冲）。
    - **锁标识** = `UUID.randomUUID().toString()`（避免客户端ID冲突）。
    - **释放锁** = 先校验持有者，再删除（避免误释放）。

## 七、总结：分布式锁的本质

> **分布式锁不是“锁”，而是“分布式共识”**。
> 
> - 用Redis解决“性能问题”，用ZooKeeper解决“一致性问题”。
> - **核心不是实现锁，而是设计容错机制**：
>     - 用过期时间防死锁，
>     - 用唯一ID防误释放，
>     - 用自动续期防超时。

## 八、可重入 Redis 分布式锁实现（Go + Lua）

这一节补一套可以直接落地的实现，目标是同时满足下面几个要求：

- 首次加锁必须原子成功
- 同一 `owner` 可以重复进入同一把锁
- 解锁时必须校验 `owner`，并按 `count` 递减
- 业务执行时间超过 `ttl` 时，锁可以自动续期

先说明一个容易混淆的点：

- Java 里常说“同一线程可重入”
- Go 没有可靠的“线程本地身份”可直接用于业务锁
- 在 Go + Redis 场景里，一般用“同一请求 / 同一调用链 / 同一业务 owner”来表达可重入身份
- 这个 `owner` 必须在整条调用链中保持稳定，例如 `requestID`、`traceID` 或 `serviceInstanceID + requestID`

### 1. 业务例子

下面继续用前面讨论过的例子。外层方法和内层方法都操作同一个订单，都需要同一把分布式锁。

```go
func HandleOrder(ctx context.Context, locker *ReentrantLocker, orderID string) error {
	owner, err := LockOwnerFromContext(ctx)
	if err != nil {
		return err
	}

	lockKey := "order:" + orderID
	if err := locker.Lock(ctx, lockKey, owner); err != nil {
		return err
	}
	defer func() {
		unlockErr := locker.Unlock(context.Background(), lockKey, owner)
		if unlockErr != nil {
			log.Printf("unlock order lock failed: key=%s owner=%s err=%v", lockKey, owner, unlockErr)
		}
	}()

	return updateOrder(ctx, locker, orderID)
}

func updateOrder(ctx context.Context, locker *ReentrantLocker, orderID string) error {
	owner, err := LockOwnerFromContext(ctx)
	if err != nil {
		return err
	}

	lockKey := "order:" + orderID
	if err := locker.Lock(ctx, lockKey, owner); err != nil {
		return err
	}
	defer func() {
		unlockErr := locker.Unlock(context.Background(), lockKey, owner)
		if unlockErr != nil {
			log.Printf("unlock order lock failed: key=%s owner=%s err=%v", lockKey, owner, unlockErr)
		}
	}()

	// 这里执行真正的订单更新逻辑
	return nil
}
```

如果这把锁不支持可重入，会发生下面的流程：

- `HandleOrder()` 首次加锁成功
- `updateOrder()` 再次申请同一个 `lockKey`
- Redis 发现 key 已存在，于是拒绝本次加锁
- 客户端进入重试 / 等待逻辑
- 但当前持锁人其实就是自己，所以变成“自己等自己”

如果支持可重入，流程会变成这样：

- `HandleOrder()` 首次加锁成功，Redis 记录 `owner=request-abc`，`count=1`
- `updateOrder()` 再次加锁时，Redis 发现 `owner` 还是 `request-abc`
- Redis 不再拒绝，而是把 `count` 从 `1` 增加到 `2`
- `updateOrder()` 解锁时只做 `count--`，变成 `1`
- `HandleOrder()` 最后解锁时再做一次 `count--`
- 当 `count=0` 时，才真正删除 Redis 中的锁 key

### 2. Redis 中如何存锁

推荐把锁存在一个 Hash 中，`ttl` 挂在 key 本身上：

| 字段 | 作用 |
| --- | --- |
| `owner` | 当前锁持有者，防止误删别人的锁 |
| `count` | 当前重入次数 |
| `PTTL` | 锁剩余过期时间，防止死锁 |

例如：

```text
key   = distlock:order:123
type  = hash
owner = request-abc
count = 2
ttl   = 30000ms
```

为什么用 Hash：

- 一个 key 就能同时保存 `owner` 和 `count`
- `ttl` 仍然可以直接挂在 key 上
- Lua 脚本里读写字段比较清晰

### 3. 三个核心 Lua 脚本

这里的设计目标非常明确：

- 加锁脚本负责“首次加锁”与“同 owner 重入”
- 解锁脚本负责“校验 owner”与“递减 count”
- 续期脚本负责“只有 owner 正确时才能延长 ttl”

#### 3.1 加锁脚本

返回值约定如下：

- `1`：首次加锁成功
- `2`：同一 `owner` 重入成功
- `0`：锁已被其他 `owner` 持有

```lua
-- KEYS[1]: lock key
-- ARGV[1]: owner
-- ARGV[2]: ttl milliseconds

local key = KEYS[1]
local owner = ARGV[1]
local ttl = tonumber(ARGV[2])

if redis.call("EXISTS", key) == 0 then
    redis.call("HSET", key, "owner", owner, "count", 1)
    redis.call("PEXPIRE", key, ttl)
    return 1
end

local currentOwner = redis.call("HGET", key, "owner")
if currentOwner == owner then
    redis.call("HINCRBY", key, "count", 1)
    redis.call("PEXPIRE", key, ttl)
    return 2
end

return 0
```

这里有两个关键点：

- 首次加锁与设置过期时间必须在同一个 Lua 脚本里完成，避免“加锁成功但没来得及设置过期时间”
- 同一 `owner` 重入时顺便刷新一次 `ttl`，避免刚重入就接近过期

#### 3.2 解锁脚本

返回值约定如下：

- `0`：已完全释放，Redis key 已删除
- `>0`：还存在外层持有者，返回剩余 `count`
- `-1`：锁不存在
- `-2`：`owner` 不匹配，禁止释放

```lua
-- KEYS[1]: lock key
-- ARGV[1]: owner

local key = KEYS[1]
local owner = ARGV[1]

if redis.call("EXISTS", key) == 0 then
    return -1
end

local currentOwner = redis.call("HGET", key, "owner")
if currentOwner ~= owner then
    return -2
end

local count = redis.call("HINCRBY", key, "count", -1)
if count > 0 then
    return count
end

redis.call("DEL", key)
return 0
```

这个脚本解决的是两个生产问题：

- 防止旧请求在锁过期后误删新请求的锁
- 防止重入层级还没退出完，就提前删掉 key

#### 3.3 续期脚本

返回值约定如下：

- `1`：续期成功
- `0`：锁已不存在
- `-1`：`owner` 不匹配，不能续期

```lua
-- KEYS[1]: lock key
-- ARGV[1]: owner
-- ARGV[2]: ttl milliseconds

local key = KEYS[1]
local owner = ARGV[1]
local ttl = tonumber(ARGV[2])

if redis.call("EXISTS", key) == 0 then
    return 0
end

local currentOwner = redis.call("HGET", key, "owner")
if currentOwner ~= owner then
    return -1
end

redis.call("PEXPIRE", key, ttl)
return 1
```

续期不是“可重入性的定义”，但它是生产环境必须具备的能力。否则即使锁支持可重入，只要业务执行时间超过 `ttl`，锁仍然会过期并被别人抢走。

### 4. Go 实现

下面给出一版完整的 Go 核心实现。为了保持代码清晰，这里使用 `github.com/redis/go-redis/v9` 作为 Redis 客户端。

```go
import (
	"context"
	"errors"
	"fmt"
	"io"
	"log"
	"sync"
	"time"

	// ErrLockBusy 表示锁当前被其他 owner 占用。

	// ErrLockNotFound 表示解锁时锁已经不存在。
	ErrLockNotFound = errors.New("distributed lock is not found")
	// ErrLockNotOwned 表示当前 owner 不是锁持有者。
	ErrLockNotOwned = errors.New("distributed lock is not owned by caller")

// Config 定义可重入分布式锁的配置。
type Config struct {
	KeyPrefix     string
	LockTTL       time.Duration
	RetryInterval time.Duration
	MaxRetries    int
	RenewInterval time.Duration
	Logger        *log.Logger
}

// ReentrantLocker 提供基于 Redis 的可重入分布式锁能力。
type ReentrantLocker struct {
	client redis.UniversalClient
	cfg    Config

	acquireScript *redis.Script
	unlockScript  *redis.Script
	renewScript   *redis.Script

	mu       sync.Mutex
	renewers map[string]context.CancelFunc
}

// NewReentrantLocker 创建一个可重入 Redis 分布式锁实例。
func NewReentrantLocker(client redis.UniversalClient, cfg Config) (*ReentrantLocker, error) {
	if client == nil {
		return nil, errors.New("redis client is nil")
	}

	if cfg.LockTTL <= 0 {
		return nil, errors.New("lock ttl must be greater than zero")
	}
	if cfg.RetryInterval <= 0 {
		cfg.RetryInterval = 100 * time.Millisecond
	}
	if cfg.RenewInterval <= 0 {
		cfg.RenewInterval = cfg.LockTTL / 3
	}
	if cfg.RenewInterval >= cfg.LockTTL {
		return nil, errors.New("renew interval must be less than lock ttl")
	}
	if cfg.Logger == nil {
		cfg.Logger = log.New(io.Discard, "", 0)
	}

	return &ReentrantLocker{
		client:        client,
		cfg:           cfg,
		acquireScript: redis.NewScript(acquireLua),
		unlockScript:  redis.NewScript(unlockLua),
		renewScript:   redis.NewScript(renewLua),
		renewers:      make(map[string]context.CancelFunc),
	}, nil
}

// Lock 尝试获取锁；若锁被其他 owner 占用，则按配置重试。
func (l *ReentrantLocker) Lock(ctx context.Context, resourceKey, owner string) error {
	if err := validateArgs(resourceKey, owner); err != nil {
		return err
	}

	key := l.redisKey(resourceKey)
	ttlMS := l.cfg.LockTTL.Milliseconds()

	for attempt := 0; attempt <= l.cfg.MaxRetries; attempt++ {
		code, err := l.evalInt(ctx, l.acquireScript, []string{key}, owner, ttlMS)
		if err != nil {
			return fmt.Errorf("acquire lock: %w", err)
		}

		switch code {
		case 1:
			l.ensureRenewer(resourceKey, owner)
			return nil
		case 2:
			return nil
		case 0:
			if attempt == l.cfg.MaxRetries {
				return ErrLockBusy
			}
			if err := sleepWithContext(ctx, l.cfg.RetryInterval); err != nil {
				return err
			}
		default:
			return fmt.Errorf("acquire lock: unexpected result %d", code)
		}
	}

	return ErrLockBusy
}

// Unlock 释放锁；当 count 归零时才真正删除 Redis key。
func (l *ReentrantLocker) Unlock(ctx context.Context, resourceKey, owner string) error {
	if err := validateArgs(resourceKey, owner); err != nil {
		return err
	}

	key := l.redisKey(resourceKey)
	code, err := l.evalInt(ctx, l.unlockScript, []string{key}, owner)
	if err != nil {
		return fmt.Errorf("unlock lock: %w", err)
	}

	switch {
	case code == 0:
		l.stopRenewer(resourceKey, owner)
		return nil
	case code > 0:
		return nil
	case code == -1:
		return ErrLockNotFound
	case code == -2:
		return ErrLockNotOwned
	default:
		return fmt.Errorf("unlock lock: unexpected result %d", code)
	}
}

func (l *ReentrantLocker) redisKey(resourceKey string) string {
	if l.cfg.KeyPrefix == "" {
		return resourceKey
	}
	return l.cfg.KeyPrefix + resourceKey
}

func (l *ReentrantLocker) sessionID(resourceKey, owner string) string {
	return resourceKey + "::" + owner
}

func (l *ReentrantLocker) ensureRenewer(resourceKey, owner string) {
	sessionID := l.sessionID(resourceKey, owner)

	l.mu.Lock()
	if _, ok := l.renewers[sessionID]; ok {
		l.mu.Unlock()
		return
	}

	renewCtx, cancel := context.WithCancel(context.Background())
	l.renewers[sessionID] = cancel
	l.mu.Unlock()

	go l.runRenewLoop(renewCtx, resourceKey, owner)
}

func (l *ReentrantLocker) stopRenewer(resourceKey, owner string) {
	sessionID := l.sessionID(resourceKey, owner)

	l.mu.Lock()
	cancel, ok := l.renewers[sessionID]
	if ok {
		delete(l.renewers, sessionID)
	}
	l.mu.Unlock()

	if ok {
		cancel()
	}
}

func (l *ReentrantLocker) runRenewLoop(ctx context.Context, resourceKey, owner string) {
	ticker := time.NewTicker(l.cfg.RenewInterval)
	defer ticker.Stop()

	key := l.redisKey(resourceKey)
	ttlMS := l.cfg.LockTTL.Milliseconds()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			renewCtx, cancel := context.WithTimeout(context.Background(), l.cfg.RetryInterval)
			code, err := l.evalInt(renewCtx, l.renewScript, []string{key}, owner, ttlMS)
			cancel()

			if err != nil {
				l.cfg.Logger.Printf("renew lock failed: key=%s owner=%s err=%v", key, owner, err)
				continue
			}

			switch code {
			case 1:
				continue
			case 0:
				l.cfg.Logger.Printf("renew lock stopped because key is missing: key=%s owner=%s", key, owner)
				l.stopRenewer(resourceKey, owner)
				return
			case -1:
				l.cfg.Logger.Printf("renew lock stopped because owner changed: key=%s owner=%s", key, owner)
				l.stopRenewer(resourceKey, owner)
				return
			default:
				l.cfg.Logger.Printf("renew lock returned unexpected code: key=%s owner=%s code=%d", key, owner, code)
			}
		}
	}
}

func (l *ReentrantLocker) evalInt(ctx context.Context, script *redis.Script, keys []string, args ...interface{}) (int64, error) {
	cmd := script.Run(ctx, l.client, keys, args...)
	if err := cmd.Err(); err != nil {
		return 0, err
	}
	return cmd.Int64()
}

func validateArgs(resourceKey, owner string) error {
	if resourceKey == "" {
		return errors.New("resource key is empty")
	}
	if owner == "" {
		return errors.New("owner is empty")
	}
	return nil
}

func sleepWithContext(ctx context.Context, d time.Duration) error {
	timer := time.NewTimer(d)
	defer timer.Stop()

	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-timer.C:
		return nil
	}
}
```

### 5. 把 owner 放到调用链里

可重入锁有一个前提：同一条调用链里的每次加锁，都必须使用同一个 `owner`。下面给一个简单做法。

```go
package distlock

import (
	"context"
	"errors"
)

type lockOwnerKey struct{}

// WithLockOwner 把锁 owner 放入上下文，供整条调用链复用。
func WithLockOwner(ctx context.Context, owner string) (context.Context, error) {
	if owner == "" {
		return nil, errors.New("owner is empty")
	}
	return context.WithValue(ctx, lockOwnerKey{}, owner), nil
}

// LockOwnerFromContext 从上下文中提取锁 owner。
func LockOwnerFromContext(ctx context.Context) (string, error) {
	value := ctx.Value(lockOwnerKey{})
	owner, ok := value.(string)
	if !ok || owner == "" {
		return "", errors.New("lock owner is missing in context")
	}
	return owner, nil
}
```

例如在 HTTP 中间件里，可以把 `requestID` 放到上下文中：

```go
requestID := "req-20260611-0001"
ctx, err := WithLockOwner(r.Context(), requestID)
if err != nil {
	return err
}
```

这样 `HandleOrder()` 和 `updateOrder()` 都能拿到同一个 `owner`，重入才有意义。

### 6. 初始化与使用方式

下面是一个完整的使用示例：

```go
package main

import (
	"context"
	"log"
	"os"
	"time"

	"github.com/redis/go-redis/v9"

	"example.com/project/distlock"
)

func main() {
	logger := log.New(os.Stdout, "", log.LstdFlags)

	rdb := redis.NewClient(&redis.Options{
		Addr: "127.0.0.1:6379",
	})

	locker, err := distlock.NewReentrantLocker(rdb, distlock.Config{
		KeyPrefix:     "distlock:",
		LockTTL:       30 * time.Second,
		RetryInterval: 100 * time.Millisecond,
		MaxRetries:    50,
		RenewInterval: 10 * time.Second,
		Logger:        logger,
	})
	if err != nil {
		logger.Fatalf("create locker failed: %v", err)
	}

	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
	defer cancel()

	ctx, err = distlock.WithLockOwner(ctx, "req-20260611-0001")
	if err != nil {
		logger.Fatalf("inject lock owner failed: %v", err)
	}

	if err := HandleOrder(ctx, locker, "123"); err != nil {
		logger.Fatalf("handle order failed: %v", err)
	}
}
```

这段代码的真实执行顺序如下：

1. `HandleOrder()` 调用 `Lock("order:123", "req-20260611-0001")`
2. Redis 中还没有这把锁，于是写入 `owner=req-20260611-0001`，`count=1`
3. `locker` 在本地启动续期协程，每隔 `10s` 刷新一次 `ttl`
4. `HandleOrder()` 调用 `updateOrder()`
5. `updateOrder()` 再次调用同一把锁
6. Lua 发现 `owner` 相同，于是把 `count` 从 `1` 改成 `2`
7. `updateOrder()` 执行完成，调用 `Unlock()`
8. Lua 把 `count` 从 `2` 改成 `1`，此时不删除 key
9. `HandleOrder()` 最终执行完成，再次调用 `Unlock()`
10. Lua 把 `count` 从 `1` 改成 `0`，删除 key
11. `locker` 停止本地续期协程

这就是“可重入 + 续期 + 按层释放”的完整链路。

### 7. 这套实现解决了什么问题

它至少解决了下面几类高频问题：

- 外层方法和内层公共方法重复加同一把锁时，不会自己阻塞自己
- 旧请求在锁过期后执行 `unlock` 时，不会误删新请求的锁
- 长事务或慢 SQL 导致业务执行时间超过 `ttl` 时，锁不会意外过期
- 多次进入临界区时，不会因为提前 `DEL` 导致其他请求错误进入

### 8. 这套实现还不负责什么

即使做到这里，也不要把它理解为“万能分布式锁”。这份示例没有覆盖下面这些能力：

- Redis 主从切换时的强一致性保证
- 多 Redis 节点仲裁
- 进程崩溃后本地续期协程的恢复
- 公平锁、读写锁、可中断锁等高级语义

如果业务已经进入复杂阶段，建议直接使用成熟库，例如：

- Java 用 `Redisson`
- Go 评估成熟的 Redis 锁库或直接用 `etcd` 的租约锁

### 9. 一句话总结

- 可重入分布式锁的核心不是“把 key 存进去”这么简单
- 它至少要保证 `首次加锁`、`同 owner 重入`、`释放时 owner 校验并递减 count`
- 在生产环境里，还要补上 `续期`
- 否则业务一旦变深、变慢、变复杂，就会出现自阻塞、误删锁、锁提前过期这三类问题

## 九、Go 中使用 etcd 实现分布式锁

如果说上一节是“自己手写一把 Redis 可重入锁”，那这一节讲的是 Go 生态里更成熟的现成方案：

- 官方客户端：`go.etcd.io/etcd/client/v3`
- 官方并发库：`go.etcd.io/etcd/client/v3/concurrency`

在 Go 项目里，如果系统本身已经依赖 etcd，那么分布式锁通常优先考虑官方 `concurrency` 包，而不是自己重新手写一套锁协议。

先给结论：

- Go 中最成熟的 etcd 分布式锁方案，就是官方 `concurrency.Mutex`
- 它底层依赖 `lease` 与 `session`
- 进程正常时会自动续租
- 进程崩溃或会话失效时，锁会自动释放
- 它更偏“强一致 + 工程可靠”，而不是 Redis 那种“性能优先”

同时要注意一个非常重要的区别：

- `concurrency.Mutex` 默认不是可重入锁
- 同一请求如果重复对同一把 etcd 锁调用 `Lock()`，仍然可能把自己等住
- 所以 etcd 官方锁更适合“单层互斥”“任务抢占”“调度执行”“主节点选举”这类场景

### 1. 官方现成用法

etcd 分布式锁最常见的写法，就是下面这个组合：

- 先创建 `client`
- 再创建 `session`
- 然后基于 `session` 创建 `mutex`
- 最后使用 `Lock()` 和 `Unlock()`

完整示例如下：

```go
package main

import (
	"context"
	"errors"
	"log"
	"os"
	"time"

	clientv3 "go.etcd.io/etcd/client/v3"
	"go.etcd.io/etcd/client/v3/concurrency"
)

func main() {
	logger := log.New(os.Stdout, "", log.LstdFlags)

	cli, err := clientv3.New(clientv3.Config{
		Endpoints:   []string{"127.0.0.1:2379"},
		DialTimeout: 5 * time.Second,
	})
	if err != nil {
		logger.Fatalf("create etcd client failed: %v", err)
	}
	defer func() {
		if closeErr := cli.Close(); closeErr != nil {
			logger.Printf("close etcd client failed: %v", closeErr)
		}
	}()

	session, err := concurrency.NewSession(cli, concurrency.WithTTL(10))
	if err != nil {
		logger.Fatalf("create etcd session failed: %v", err)
	}
	defer func() {
		if closeErr := session.Close(); closeErr != nil {
			logger.Printf("close etcd session failed: %v", closeErr)
		}
	}()

	mutex := concurrency.NewMutex(session, "/locks/order/123")

	lockCtx, lockCancel := context.WithTimeout(context.Background(), 8*time.Second)
	defer lockCancel()

	if err := mutex.Lock(lockCtx); err != nil {
		logger.Fatalf("acquire etcd lock failed: %v", err)
	}
	defer func() {
		unlockCtx, unlockCancel := context.WithTimeout(context.Background(), 3*time.Second)
		defer unlockCancel()

		if unlockErr := mutex.Unlock(unlockCtx); unlockErr != nil {
			logger.Printf("release etcd lock failed: %v", unlockErr)
		}
	}()

	logger.Printf("lock acquired: %s", "/locks/order/123")

	if err := handleOrder(context.Background(), logger); err != nil {
		logger.Printf("handle order failed: %v", err)
		return
	}

	logger.Printf("business finished")
}

func handleOrder(ctx context.Context, logger *log.Logger) error {
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-time.After(2 * time.Second):
		logger.Printf("handle order success")
		return nil
	}
}
```

这段代码里最关键的 3 行是：

```go
session, err := concurrency.NewSession(cli, concurrency.WithTTL(10))
mutex := concurrency.NewMutex(session, "/locks/order/123")
err = mutex.Lock(lockCtx)
```

可以把它理解成：

- `client` 负责连接 etcd
- `session` 负责创建并维护租约
- `mutex` 负责在指定锁路径上竞争所有权

### 2. 如果抢不到锁怎么办

`Lock()` 会等待直到获取到锁，或者直到传入的 `context` 超时 / 被取消。

这意味着：

- 如果你想“最多等 8 秒”，就给 `Lock()` 传一个带超时的 `context`
- 如果你想“立即尝试一次，不行就返回”，可以用 `TryLock()`

例如：

```go
lockCtx, lockCancel := context.WithTimeout(context.Background(), 2*time.Second)
defer lockCancel()

if err := mutex.TryLock(lockCtx); err != nil {
	if errors.Is(err, concurrency.ErrLocked) {
		log.Printf("lock is already held by another session")
		return
	}
	log.Printf("try lock failed: %v", err)
	return
}
defer func() {
	unlockCtx, unlockCancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer unlockCancel()

	if unlockErr := mutex.Unlock(unlockCtx); unlockErr != nil {
		log.Printf("release etcd lock failed: %v", unlockErr)
	}
}()
```

这种写法很适合“任务调度抢占”场景：

- 抢到锁的实例执行业务
- 没抢到的实例直接退出或下次再试

### 3. 更贴近实际业务的例子

下面用“多实例定时任务”举一个更贴近生产的例子。

假设有 3 个服务实例都在执行“每分钟汇总订单”这项任务，但同一时间只允许一个实例真正执行。

```go
package scheduler

import (
	"context"
	"log"
	"time"

	clientv3 "go.etcd.io/etcd/client/v3"
	"go.etcd.io/etcd/client/v3/concurrency"
)

type JobRunner struct {
	client *clientv3.Client
	logger *log.Logger
}

func NewJobRunner(client *clientv3.Client, logger *log.Logger) *JobRunner {
	return &JobRunner{
		client: client,
		logger: logger,
	}
}

func (r *JobRunner) RunDailySummary(ctx context.Context) error {
	session, err := concurrency.NewSession(r.client, concurrency.WithTTL(15))
	if err != nil {
		return err
	}
	defer func() {
		closeErr := session.Close()
		if closeErr != nil {
			r.logger.Printf("close etcd session failed: %v", closeErr)
		}
	}()

	mutex := concurrency.NewMutex(session, "/jobs/daily-summary")

	lockCtx, lockCancel := context.WithTimeout(ctx, 3*time.Second)
	defer lockCancel()

	if err := mutex.TryLock(lockCtx); err != nil {
		if errors.Is(err, concurrency.ErrLocked) {
			r.logger.Printf("skip daily summary because another instance owns the lock")
			return nil
		}
		return err
	}
	defer func() {
		unlockCtx, unlockCancel := context.WithTimeout(context.Background(), 3*time.Second)
		defer unlockCancel()

		unlockErr := mutex.Unlock(unlockCtx)
		if unlockErr != nil {
			r.logger.Printf("release daily summary lock failed: %v", unlockErr)
		}
	}()

	r.logger.Printf("run daily summary start")

	if err := r.aggregateOrders(ctx); err != nil {
		return err
	}

	r.logger.Printf("run daily summary done")
	return nil
}

func (r *JobRunner) aggregateOrders(ctx context.Context) error {
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-time.After(5 * time.Second):
		return nil
	}
}
```

这个例子里，真正有价值的点不是“代码能跑”，而是下面这个语义：

- 只有拿到 `/jobs/daily-summary` 这把锁的实例才会执行汇总
- 其他实例看到锁已被持有，就直接退出
- 如果正在执行的实例崩溃，锁会在租约失效后自动释放
- 下一轮调度时，其他实例就有机会接管任务

### 4. `lease` 是什么

理解 etcd 分布式锁，第一步必须搞清楚 `lease`。

可以把 `lease` 理解为“带有效期的租约”：

- 创建一个 `lease`
- 给它配置 `ttl`
- 把一个或多个 key 绑定到这个 `lease`
- 只要 `lease` 还活着，这些 key 就继续存在
- 一旦 `lease` 过期，这些 key 会被 etcd 自动删除

这和 Redis 里的 key 过期有一点像，但 etcd 的 `lease` 是一等对象，而不是“单个 key 自带一个过期时间”这么简单。

对于锁来说，这意味着：

- 锁 key 不是永久存在的
- 它跟着租约一起生效和失效
- 不需要业务自己额外维护“过期后删锁”的逻辑

### 5. `session` 是什么

官方 `concurrency.Session` 本质上是对 `lease` 的一层封装。

它主要做了 3 件事：

- 创建一个租约
- 在后台自动 keepalive
- 对外暴露一个适合并发原语使用的会话对象

也就是说：

- `session` 活着，底层 `lease` 就会不断续命
- `session` 关闭，底层 `lease` 就会被撤销或最终过期
- `mutex`、`election` 等并发原语，都是建立在 `session` 之上的

这就是为什么 etcd 锁的代码里通常不是直接操作 `lease`，而是先创建 `session`。

### 6. etcd 锁为什么能自动释放

这一点是 etcd 锁最强的工程价值之一。

自动释放的根本原因不是 `Unlock()`，而是：

- 锁 key 绑定在 `session` 对应的 `lease` 上
- `session` 持续 keepalive 时，锁就一直有效
- 一旦进程崩溃、网络中断太久、Pod 被杀、keepalive 停止，`lease` 到期
- `lease` 一到期，绑定的锁 key 就会被 etcd 自动删除

所以即使业务没有来得及执行 `Unlock()`，锁也不会永久残留。

这也是 etcd 锁在调度系统、选主系统里特别受欢迎的原因：

- 它天然适合处理“进程挂了怎么办”
- 它不需要你自己再写一套 watchdog 续期线程

### 7. etcd 锁为什么不容易误删别人的锁

这是 etcd 相对手写 Redis 锁的另一个明显优势。

在手写 Redis 锁里，最危险的情况通常是：

- 请求 A 拿到锁
- A 的锁过期
- 请求 B 又拿到同一个锁
- A 这时才跑来执行 `DEL`
- 结果把 B 的锁误删了

而 etcd 官方 `Mutex` 不容易出现这个问题，原因在于它不是“所有人都去争同一个公共 key”。

更准确地说：

- 每个竞争者都会在锁前缀下创建属于自己的锁记录
- 这些锁记录都绑定到各自的 `session`
- 解锁时删除的是“当前 session 自己创建的那条记录”
- 不是简单粗暴地把整个公共锁路径删掉

因此：

- A 释放时不会直接删除 B 的那条锁记录
- A 的会话失效后，也只是清理 A 自己绑定的 key
- 不会把后续持有者的锁一起删掉

你可以把它类比成排队取号：

- 每个请求先拿自己的号码
- 谁排在前面谁先执行
- 执行完只把自己的号码牌拿走
- 不会把后面人的号码牌一起撕掉

这就是 etcd 锁“不容易误删锁”的核心原因。

### 8. `concurrency.Mutex` 底层竞争流程

这一块不要求记住源码细节，但建议理解流程。

大致过程可以理解为：

1. 每个竞争者先基于当前 `session` 在锁前缀下创建一个自己的键
2. 这个键会绑定到当前 `lease`
3. etcd 用 revision 表示创建先后顺序
4. revision 更小的竞争者排在前面
5. 排在第一位的获得锁
6. 后面的竞争者监听前一个竞争者的删除事件
7. 当前一个释放锁或租约失效后，下一个竞争者继续尝试进入

所以 etcd 锁不是单纯“谁先 `Put` 成功谁就赢”，而更像“一个有序等待队列”。

这带来两个结果：

- 竞争流程更清晰
- 互斥关系更容易建立在一致性之上

### 9. etcd 锁和 Redis 手写锁的差异

如果把这一节和上一节放在一起看，差异会很明显。

Redis 手写锁更关注：

- `owner`
- `count`
- `ttl`
- `Lua` 原子脚本
- 自己管理续期逻辑

etcd 官方锁更关注：

- `lease`
- `session`
- 自动 keepalive
- 自动释放
- 基于锁前缀的有序竞争

所以一般可以这样理解：

- Redis 更适合高频、轻量、性能优先的场景
- etcd 更适合一致性优先、调度优先、可靠性优先的场景

### 10. etcd 锁的使用建议

如果你准备在 Go 项目里正式使用 etcd 锁，建议遵守下面这些规则：

- `Lock()` 一定传带超时的 `context`
- `Unlock()` 最好使用独立的短超时 `context`
- `session.Close()` 必须显式调用
- 锁路径要稳定可读，例如 `/locks/order/123`
- 不要把 `concurrency.Mutex` 当成可重入锁来用
- 如果业务调用链会重复申请同一把锁，优先重构代码，而不是假设 etcd 官方锁支持重入

最后收成一句话：

- 在 Go 生态里，用 etcd 做分布式锁，最成熟的方案就是官方 `client/v3/concurrency`
- 它依靠 `lease + session + mutex` 提供锁语义
- 核心优势是自动续租、自动释放、不容易误删锁
- 核心限制是默认不支持可重入
