### **1. 设计一个支持千万级用户的社交平台（如微博）**

#### **如何实现高并发发布/订阅？**

对于微博这类社交平台，核心是“发布/订阅”模式，即一个用户（发布者）发布动态，其所有粉丝（订阅者）都能收到。

**挑战:**
- **写扩散 vs 读扩散:**
    - **写扩散 (Push):** 发布者发布动态后，系统立即将动态ID推送给所有粉丝的“收件箱”。
        - **优点:** 粉丝读取动态时速度快，因为收件箱是预计算好的。
        - **缺点:** 对于大V（拥有千万级粉丝），一次发布会导致千万次的写操作，对存储和消息系统造成巨大压力。
    - **读扩散 (Pull):** 粉丝登录或刷新时，主动拉取其关注的所有用户的最新动态。
        - **优点:** 发布动态时开销小，只需写入一次。
        - **缺点:** 粉丝读取动态时延迟高，需要多次查询，且可能导致数据库“热点”问题。

**架构设计 (推拉结合):**

为了兼顾性能和延迟，业界普遍采用“推拉结合”的混合模式：

1.  **普通用户 (粉丝数 < 阈值，如 10000):** 采用**写扩散 (Push)**模式。
    - 用户发布动态后，通过异步任务（如MQ）将动态ID写入其所有粉丝的Redis `Sorted Set` 收件箱中，`score`为时间戳，`value`为动态ID。
    - 粉丝拉取动态时，直接从自己的收件箱中分页获取动态ID列表，再去查询动态详情。

2.  **大V用户 (粉丝数 >= 阈值):** 采用**读扩散 (Pull)**模式。
    - 大V发布动态后，只将动态写入自己的“发件箱”。
    - 粉丝拉取动态时，除了读取自己的“收件箱”，还需要额外拉取其关注的大V的“发件箱”中的最新动态。
    - 将两部分动态在业务层进行聚合、排序后返回。

**技术选型与优化:**

- **消息队列 (MQ):** 使用Kafka或RocketMQ进行发布操作的异步解耦。发布动态的请求写入MQ后即可返回，由后台消费者处理后续的“写扩散”逻辑。
- **缓存 (Redis):**
    - **收件箱/发件箱:** 使用Redis的`Sorted Set`或`List`存储，`Sorted Set`便于按时间排序和分页。
    - **动态内容缓存:** 使用Redis `Hash`或`String`缓存动态的具体内容，减轻数据库压力。
    - **用户关系缓存:** 缓存用户的关注列表和粉丝列表。
- **数据库:**
    - 使用MySQL或PostgreSQL等关系型数据库存储动态内容、用户信息、用户关系等。
    - 对动态表进行**分库分表**，例如按用户ID或时间进行哈希分片。
- **服务拆分:**
    - **发布服务:** 处理动态发布请求。
    - **订阅服务:** 管理用户关系。
    - **时间线服务 (Timeline Service):** 聚合生成用户的主页时间线。

### **2. 设计一个分布式电商系统（如淘宝）**

#### **如何保证高并发下单（库存、订单、支付）？**

高并发下单的核心挑战在于**数据一致性**和**性能**的平衡。

**流程拆解:**
下单操作可分解为：创建订单 -> 扣减库存 -> 请求支付 -> 更新订单状态。

**架构设计:**

1.  **流量削峰:**
    - **前端:** 在秒杀等场景，按钮点击后置灰，防止用户重复提交。
    - **Nginx/Gateway:** 限制单用户请求频率和总并发数。
    - **消息队列 (MQ):** 将下单请求写入MQ，后端服务按自身处理能力消费。这是最核心的削峰手段，将同步的下单流程异步化。

2.  **库存扣减:**
    - **“拍下减库存” vs “付款减库存”:**
        - **拍下减库存:** 用户体验好，但恶意用户可能只拍不付，导致库存被无效占用。需要有**订单自动取消机制**（如30分钟后未支付则取消，并回补库存）。
        - **付款减库存:** 资金安全，但用户支付时可能发现库存不足，体验较差。
    - **技术方案:**
        - **Redis预扣减:** 将库存放在Redis中，利用其原子操作（如`DECR`）进行快速预扣减。如果Redis扣减成功，再通过MQ通知数据库进行最终扣减。
        - **Lua脚本:** 将“读库存 -> 判断 -> 减库存”三个操作封装在Lua脚本中，由Redis原子执行，避免并发问题。
        - **分布式锁:** 针对单个SKU（商品最小库存单位）加锁，但性能较差，不适用于高并发主流程。

3.  **订单系统:**
    - **订单号生成:** 保证全局唯一。可采用**雪花算法 (Snowflake)**或基于Redis自增ID的方案。
    - **分库分表:** 订单表是增长最快的表之一，必须按用户ID或时间进行分库分表。
    - **状态机:** 订单有“待支付”、“已支付”、“已发货”、“已完成”、“已取消”等多种状态，使用状态机模型进行管理，确保状态流转的正确性。

4.  **支付环节:**
    - 见问题5的支付系统设计。下单服务只需调用支付网关，并接收异步回调通知即可。

**数据一致性保证:**

- **最终一致性:** 采用**可靠消息最终一致性**方案。
    - 例如，订单服务在本地事务中完成订单创建，并向MQ发送“订单创建成功”的消息。
    - 库存服务和支付服务订阅此消息，完成各自的操作。
    - 使用**本地消息表**或**事务消息 (如RocketMQ)**确保“业务操作”和“发送消息”这两个步骤的原子性。
    - 设置**定时任务**对账，处理因网络问题或服务宕机导致的暂时不一致。

### **3. 设计一个实时竞价广告系统（如Google Ads）**

#### **如何实现毫秒级广告竞价？**

**核心要求:** 低延迟（通常要求在100ms内完成）和高并发。

**架构设计:**

1.  **技术栈选型:**
    - **语言:** 选择C++或Go等高性能编译型语言。
    - **网络模型:** 使用epoll (Linux) / kqueue (BSD) / IOCP (Windows) 等I/O多路复用技术，结合非阻塞I/O。

2.  **竞价流程优化:**
    - **请求解析:** 使用高效的序列化协议，如Protobuf或FlatBuffers，代替JSON。
    - **广告检索 (Ad Retrieval):**
        - **倒排索引:** 建立关键词、用户标签、地域等维度的倒排索引。当一个请求到来时，根据请求特征（如用户画像、媒体位置），快速从索引中筛选出符合条件的广告候选集。
        - **索引预加载:** 将广告索引数据全量加载到内存中，避免磁盘I/O。可以使用mmap等技术。
    - **广告排序 (Ad Ranking):**
        - **精排模型:** 使用预先训练好的机器学习模型（如LR, GBDT, DNN）对候选广告进行点击率（CTR）和转化率（CVR）预估。
        - **模型优化:** 模型要轻量化，推理速度快。可以使用模型蒸馏、量化等技术。
        - **并行计算:** 对多个候选广告的排序计算可以并行处理。
    - **竞价与计费:**
        - **计费模型:** 通常采用**广义第二价格（GSP）**计费，即第一名按第二名的出价+0.01元付费。
        - **计算:** 排序和计费逻辑纯内存计算，速度极快。

#### **如何保证高可用和低延迟？**

- **高可用:**
    - **多地域部署:** 在全球多个数据中心部署服务，通过DNS或Anycast实现流量的就近访问和故障转移。
    - **负载均衡:** 使用LVS/Nginx等进行四/七层负载均衡。
    - **无状态服务:** 竞价服务器本身不存储状态，所有状态（如广告索引、模型）都从外部加载，便于快速扩缩容和故障恢复。
    - **熔断与降级:** 当下游服务（如用户画像服务）超时或不可用时，可以执行降级策略（如使用默认画像或直接放弃该次请求），保证核心竞价流程不受影响。
- **低延迟:**
    - **CDN:** 将静态资源（如广告素材）缓存在CDN。
    - **就近接入:** 用户流量接入最近的边缘节点。
    - **内存计算:** 核心流程全内存操作。
    - **代码优化:** 减少锁竞争、使用对象池（如`sync.Pool`）减少GC压力、CPU绑定等。

#### **如何存储和分析海量广告点击数据？**

- **数据收集:**
    - **日志服务器集群:** 前端通过“埋点”将曝光和点击日志发送到专门的日志服务器集群。
    - **消息队列:** 日志服务器将数据清洗、格式化后，推送到Kafka中。Kafka作为数据总线，供下游的实时和离线系统消费。
- **数据存储:**
    - **离线存储:**
        - 使用**HDFS**作为海量日志的永久存储。
        - 数据仓库可构建在**Hive**或**Spark SQL**之上。
    - **实时/近实时查询:**
        - **ClickHouse:** 列式存储，对于聚合查询性能极高，非常适合广告数据的OLAP分析。
        - **Druid/Kylin:** 预聚合的OLAP引擎，提供亚秒级的多维分析能力。
- **数据处理:**
    - **实时计算 (流处理):**
        - 使用**Flink**或**Spark Streaming**消费Kafka中的数据，进行实时的数据统计（如实时CTR/CVR计算）、反作弊识别等。
    - **离线计算 (批处理):**
        - 使用**Spark**或**MapReduce**定期（如每天）对HDFS上的数据进行批处理，生成报表、训练模型等。

### **5. 设计一个高可用的支付系统（如支付宝）**

#### **如何保证支付事务的ACID特性？**

支付事务的核心是“钱”的转移，必须严格保证ACID。

- **Atomicity (原子性):** 用户的账户扣款和商家的账户收款，必须同时成功或同时失败。
    - **两阶段提交 (2PC):** 理论上可行，但同步阻塞，性能差，且存在协调者单点问题和数据不一致风险，在互联网场景下很少使用。
    - **TCC (Try-Confirm-Cancel):**
        - **Try:** 预留资源。例如，冻结用户的支付金额。
        - **Confirm:** 确认执行。如果Try成功，则执行实际的扣款和收款。
        - **Cancel:** 取消执行。如果Try失败或后续步骤失败，则解冻之前冻结的金额。
        - **优点:** 性能优于2PC，由业务层实现，灵活性高。
        - **缺点:** 编码复杂，对业务侵入性强。
    - **可靠消息最终一致性:** (更常用)
        - 见问题2中的方案。支付系统内部的账户A扣款和账户B收款，可以通过消息队列实现最终一致。
        - 关键是保证消息的可靠投递和消费的幂等性。

- **Consistency (一致性):** 事务前后，系统的总金额（或其他约束）保持不变。这主要由业务逻辑和数据库约束（如`CHECK`）来保证。

- **Isolation (隔离性):**
    - 使用数据库的**乐观锁**。在更新账户余额时，增加一个`version`字段。
    - `UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE user_id = 'A' AND version = 1;`
    - 如果更新的行数为0，说明在此期间有其他事务修改了数据，本次操作失败，需要重试。
    - 相比悲观锁（如`SELECT ... FOR UPDATE`），乐观锁在高并发下性能更好。

- **Durability (持久性):**
    - 依赖数据库的持久化能力。只要事务提交成功，数据就必须被持久化到磁盘。
    - 使用高可用的数据库集群（如MySQL主从+MGR/Galera，或分布式数据库如TiDB）。

#### **如何设计对账系统？**

对账是保证资金安全的最后一道防线。

- **对账目标:** 发现并修正因系统异常（网络、宕机、Bug）导致的数据不一致。
- **对账方:**
    - **内部对账:** 支付系统自身各模块（如交易、会计）之间的对账。
    - **外部对账:** 与银行、第三方支付渠道的对账。
- **对账流程:**
    1.  **数据拉取:** 定期（如T+1日凌晨）从银行或第三方渠道获取对账文件（通常是CSV或TXT格式）。
    2.  **数据标准化:** 将外部文件和内部数据库中的订单记录，转换为统一的格式。
    3.  **数据核对:**
        - 以一方为基准（如银行），遍历每一条记录，在另一方查找对应的记录。
        - **核对维度:** 订单号、金额、时间、状态等。
        - **结果:**
            - **平账:** 双方记录完全一致。
            - **不平账:**
                - **长款 (我方有，渠道无):** 可能是我方单方面成功，需要确认是否需要退款。
                - **短款 (渠道有，我方无):** 可能是我方漏单，需要补单。
                - **金额不一致:** 需要人工介入调查。
    4.  **差错处理:**
        - 将不平账的记录存入“差错表”。
        - 通过**运营后台**展示差错信息，由财务或运营人员进行人工处理（补单、退款、挂账等）。
        - 部分简单的差错（如明确的漏单）可以设计自动化处理流程。

#### **如何防止重复支付和超卖？**

- **防止重复支付:**
    - **唯一支付请求号:**
        - 调用方（如业务系统）在发起支付时，生成一个全局唯一的请求号（`request_id`）。
        - 支付系统在创建支付订单时，将此`request_id`与支付订单关联，并在`request_id`上建立唯一索引。
        - 当收到重复的`request_id`时，数据库会因唯一性约束而插入失败，从而阻止创建重复的支付订单。
    - **幂等性控制:** 支付接口需要实现幂等性。收到相同的支付请求时，如果已经处理过，则直接返回之前处理成功的结果，而不是再次执行扣款操作。

- **防止超卖:**
    - **核心:** 保证“扣库存”操作的原子性和正确性。
    - **方案 (同问题2):**
        1.  **数据库乐观锁:** `UPDATE products SET stock = stock - 1 WHERE product_id = 'X' AND stock > 0;`
            - 利用`stock > 0`作为前置条件，保证不会卖出负数库存。
            - 这是最简单直接的方式，但并发高时性能瓶颈在数据库。
        2.  **Redis原子操作:**
            - 将库存放在Redis中，利用`DECR`或Lua脚本进行原子扣减。
            - `IF redis.call('GET', 'stock:X') > 0 THEN redis.call('DECR', 'stock:X') ... END`
            - 这是目前互联网架构中最主流的方案，性能极高。

### **6. 设计一个实时大数据分析平台（如实时风控系统）**

#### **如何实现低延迟的流式计算？**

- **计算引擎:**
    - **Apache Flink:** 是业界公认的下一代流计算引擎。
        - **优点:**
            - **高吞吐、低延迟:** 基于原生的流式模型，延迟可达毫秒级。
            - **强大的状态管理:** 提供多种State Backend（内存、文件系统、RocksDB），可以支持复杂的有状态计算（如窗口、聚合）。
            - **精确一次 (Exactly-Once) 语义:** 通过Checkpoint机制保证。
- **架构设计:**
    1.  **数据源:** 用户行为日志、交易数据等通过Flume或Logstash收集，注入到Kafka。
    2.  **流处理:** Flink集群消费Kafka中的数据流。
    3.  **计算逻辑:**
        - **规则引擎:** 对于风控系统，可以加载一系列预设的规则（如“1分钟内异地登录3次”）。Flink作业根据这些规则进行实时匹配。
        - **机器学习模型:** 可以加载在线学习或预训练好的模型，对数据流进行实时预测（如判断一笔交易是否为欺诈）。
    4.  **结果输出 (Sink):**
        - **触发告警:** 将高风险事件写入另一个Kafka Topic或直接调用告警服务。
        - **更新用户画像:** 将分析结果写回HBase或Redis，用于更新用户的实时风险标签。
        - **实时大盘:** 将统计指标写入ClickHouse或Elasticsearch，用于实时监控和展示。

#### **如何存储和查询PB级数据？**

- **存储:**
    - **HDFS (Hadoop Distributed File System):** 作为大数据生态的基石，提供高吞- 吐、高容错的PB级数据存储能力。适合存储原始日志和中间计算结果。
    - **对象存储 (如S3, OSS):** 成本更低，与计算分离，弹性更好，是现代数据湖架构的趋势。
- **查询/分析引擎:**
    - **离线分析 (OLAP):**
        - **Hive/Spark SQL:** 将HDFS上的结构化数据映射为表，提供SQL查询能力。适合大规模的批处理和探索性分析，延迟较高（分钟到小时级）。
        - **Presto/Trino:** 高性能的分布式SQL查询引擎，可以跨多种数据源（HDFS, MySQL, Kafka等）进行联邦查询，延迟在秒级到分钟级。
    - **实时分析 (OLAP):**
        - **ClickHouse:** 面向列的数据库管理系统，为在线分析处理（OLAP）而设计。在聚合查询场景下，性能远超传统行式数据库，可达亚秒级响应。
        - **Apache Doris/StarRocks:** 新一代的MPP（大规模并行处理）分析型数据库，兼容MySQL协议，易于使用，性能优异。
        - **Apache Kylin/Druid:** 预聚合技术，通过空间换时间，对固定的多维分析场景可以提供毫秒级的查询响应。

#### **如何保证数据处理的Exactly-Once语义？**

Exactly-Once意味着端到端的数据处理流程中，每一条记录既不重复，也不丢失。

- **Flink的实现 (两阶段提交 + Checkpoint):**
    1.  **Source端:** Source Connector需要是可重放的（如Kafka），并且能记录消费的偏移量（offset）。
    2.  **Flink内部:**
        - **Checkpoint:** Flink定期将所有算子（operator）的当前状态（包括Source的offset）制作一个快照（Snapshot），并持久化到分布式存储（如HDFS）中。这个过程被称为Checkpoint。
        - **Barrier:** Flink在数据流中插入一种特殊的消息——Barrier。当一个算子收到所有上游的Barrier后，才会对自己进行快照，并向下游广播Barrier。这保证了快照的一致性。
    3.  **Sink端:** Sink Connector需要支持**事务**或**幂等写入**。
        - **两阶段提交Sink (TwoPhaseCommitSinkFunction):**
            - **Pre-commit (预提交):** 在Checkpoint开始时，Sink开启一个事务，并将接下来收到的数据写入这个事务，但不提交。
            - **Commit (提交):** 当Flink的JobManager收到所有算子的Checkpoint完成通知后，它会通知Sink去提交之前开启的事务。
            - **Abort (中止):** 如果Checkpoint失败，则通知Sink中止事务。
- **端到端Exactly-Once的条件:**
    - **Source:** 必须是可重置/可重放的（如Kafka）。
    - **Flink:** 开启Checkpoint机制。
    - **Sink:** 必须是事务性的或支持幂等写入的（如Kafka 0.11+，或自己实现的幂等写入Sink）。

通过以上设计，即使在发生故障并从上一个Checkpoint恢复时，Flink也能保证数据不多不少，恰好被处理一次。
