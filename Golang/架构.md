### 1. 设计一个支持千万级用户的社交平台（如微博）

#### 如何实现高并发发布/订阅？

对于微博这类社交平台，核心是“发布/订阅”模式，即一个用户发布动态后，其所有粉丝都能收到。

挑战

1. 写扩散（Push）
发布者发布动态后，系统立即将动态 ID 推送给所有粉丝的“收件箱”。
优点：粉丝读取动态时速度快，因为收件箱是预计算好的。
缺点：对于大 V，一次发布可能导致千万次写操作，对存储和消息系统造成巨大压力。

2. 读扩散（Pull）
粉丝登录或刷新时，主动拉取其关注用户的最新动态。
优点：发布动态时开销小，只需写入一次。
缺点：粉丝读取动态时延迟较高，需要多次查询，还可能造成数据库热点问题。

架构设计（推拉结合）

为了兼顾性能和延迟，业界通常采用“推拉结合”的混合模式。

1. 普通用户（粉丝数低于阈值，如 10000）
采用写扩散模式。
用户发布动态后，通过异步任务或消息队列将动态 ID 写入所有粉丝的 Redis `Sorted Set` 收件箱中，`score` 为时间戳，`value` 为动态 ID。
粉丝拉取动态时，直接从自己的收件箱分页获取动态 ID，再查询动态详情。

2. 大 V 用户（粉丝数高于等于阈值）
采用读扩散模式。
大 V 发布动态后，只将动态写入自己的“发件箱”。
粉丝拉取动态时，除了读取自己的“收件箱”，还需要额外读取所关注大 V 的“发件箱”。
两部分动态在业务层聚合并排序后返回。

技术选型与优化

1. 消息队列（MQ）
使用 Kafka 或 RocketMQ 进行发布操作的异步解耦。发布请求写入 MQ 后即可返回，由后台消费者处理后续的写扩散逻辑。

2. 缓存（Redis）
收件箱和发件箱可使用 Redis `Sorted Set` 或 `List` 存储，其中 `Sorted Set` 更便于按时间排序和分页。
动态内容可使用 Redis `Hash` 或 `String` 缓存，以减轻数据库压力。
用户关系也可以缓存，包括关注列表和粉丝列表。

3. 数据库
使用 MySQL 或 PostgreSQL 等关系型数据库存储动态内容、用户信息和用户关系。
动态表通常需要分库分表，例如按用户 ID 或时间进行哈希分片。

4. 服务拆分
发布服务负责处理动态发布请求。
订阅服务负责管理用户关系。
时间线服务负责聚合生成用户主页时间线。

### 2. 设计一个分布式电商系统（如淘宝）

#### 如何保证高并发下单（库存、订单、支付）？

高并发下单的核心挑战在于数据一致性和性能之间的平衡。

流程拆解

下单操作通常可分解为：创建订单、扣减库存、请求支付、更新订单状态。

架构设计

1. 流量削峰
前端在秒杀等场景中可在点击后将按钮置灰，防止用户重复提交。
网关层可通过 Nginx 或 Gateway 限制单用户请求频率和总并发数。
消息队列是最核心的削峰手段，可以将下单请求写入 MQ，由后端服务按自身处理能力消费，把同步流程异步化。

2. 库存扣减
常见思路有两种。
拍下减库存：用户体验较好，但恶意用户可能只拍不付，导致库存被无效占用，因此通常要配合订单自动取消机制。
付款减库存：资金安全性更高，但用户可能在支付时才发现库存不足，体验较差。

库存技术方案

1. Redis 预扣减
将库存放在 Redis 中，利用 `DECR` 等原子操作进行快速预扣减。如果 Redis 扣减成功，再通过 MQ 通知数据库做最终扣减。

2. Lua 脚本
将“读库存、判断库存、扣减库存”封装为一个 Lua 脚本，由 Redis 原子执行，避免并发问题。

3. 分布式锁
针对单个 SKU 加锁也能保证正确性，但性能较差，不适合作为高并发主流程方案。

订单系统
订单号需要保证全局唯一，通常采用雪花算法或基于 Redis 的自增 ID 方案。
订单表增长极快，通常要按用户 ID 或时间进行分库分表。
订单状态建议使用状态机模型管理，例如待支付、已支付、已发货、已完成、已取消等，确保状态流转正确。

支付环节
下单服务只需调用支付网关，并接收异步回调通知即可，支付系统设计可参考后文相关章节。

数据一致性保证

推荐采用可靠消息最终一致性方案。
例如，订单服务在本地事务中完成订单创建，再向 MQ 发送“订单创建成功”消息。
库存服务和支付服务订阅消息后完成各自处理。
可以使用本地消息表或事务消息（如 RocketMQ）保证“业务操作”和“发送消息”的原子性。
同时应设置定时对账任务，处理因网络抖动或服务宕机导致的暂时不一致。

### 3. 设计一个实时竞价广告系统（如 Google Ads）

#### 如何实现毫秒级广告竞价？

核心要求是低延迟和高并发，通常需要在 100ms 内完成一次竞价请求。

架构设计

1. 技术栈选型
语言通常选择 C++ 或 Go 等高性能编译型语言。
网络模型通常采用 epoll、kqueue 或 IOCP 这类 I/O 多路复用机制，并配合非阻塞 I/O。

2. 竞价流程优化

请求解析
建议使用 Protobuf 或 FlatBuffers 等高效序列化协议，尽量避免 JSON 带来的额外开销。

广告检索
通常会建立关键词、用户标签、地域等维度的倒排索引。
当请求到来时，根据用户画像、媒体位置等特征，快速筛出候选广告集合。
索引数据通常全量预加载到内存中，避免磁盘 I/O，也可结合 `mmap` 等技术。

广告排序
可使用预训练的模型对候选广告做 CTR 和 CVR 预估，例如 LR、GBDT、DNN。
模型需要尽量轻量化，以保证推理速度，可结合模型蒸馏和量化。
多个候选广告的排序计算通常可以并行执行。

竞价与计费
常见计费模型是广义第二价格（GSP），即第一名按第二名出价加一个最小增量付费。
排序和计费逻辑通常放在内存中完成，以降低延迟。

#### 如何保证高可用和低延迟？

高可用设计

1. 多地域部署
在多个数据中心部署服务，通过 DNS 或 Anycast 实现流量就近接入和故障转移。

2. 负载均衡
可使用 LVS 或 Nginx 实现四层或七层负载均衡。

3. 无状态服务
竞价服务器本身尽量不存储状态，广告索引和模型等状态由外部加载，便于快速扩缩容和故障恢复。

4. 熔断与降级
当下游服务，如用户画像服务，出现超时或不可用时，可使用默认画像或直接放弃该次请求，确保主链路可用。

低延迟设计

1. CDN
将广告素材等静态资源缓存到 CDN。

2. 就近接入
用户流量接入离自己最近的边缘节点。

3. 内存计算
核心流程尽量全部在内存中完成。

4. 代码优化
减少锁竞争，必要时使用对象池降低 GC 压力，并结合 CPU 绑定等手段进一步优化。

#### 如何存储和分析海量广告点击数据？

数据收集

1. 日志服务器集群
前端通过埋点将曝光和点击日志发送到日志服务器集群。

2. 消息队列
日志服务器将数据清洗和格式化后写入 Kafka，Kafka 作为数据总线供实时和离线系统消费。

数据存储

1. 离线存储
可使用 HDFS 存储海量日志。
数据仓库一般构建在 Hive 或 Spark SQL 之上。

2. 实时或近实时查询
ClickHouse 适合高性能聚合查询，是广告数据 OLAP 分析的常见选择。
Druid 或 Kylin 通过预聚合提供亚秒级多维分析能力。

数据处理

1. 实时计算
可使用 Flink 或 Spark Streaming 消费 Kafka 中的数据，完成实时统计和反作弊识别。

2. 离线计算
可使用 Spark 或 MapReduce 定期处理 HDFS 上的数据，用于生成报表和训练模型。

### 5. 设计一个高可用的支付系统（如支付宝）

#### 如何保证支付事务的 ACID 特性？

支付事务的核心是“钱”的转移，因此必须严格保证 ACID。

1. Atomicity（原子性）
用户账户扣款和商家账户收款必须同时成功或同时失败。

常见实现方案如下。

两阶段提交（2PC）
理论上可行，但同步阻塞严重，性能较差，还存在协调者单点和数据不一致风险，因此在互联网场景中较少直接使用。

TCC
Try：预留资源，例如冻结用户支付金额。
Confirm：如果 Try 成功，则正式执行扣款和收款。
Cancel：如果 Try 失败或后续步骤失败，则解冻之前冻结的金额。
优点是性能通常优于 2PC，且由业务层控制，灵活性较高。
缺点是编码复杂，对业务侵入较强。

可靠消息最终一致性
这是更常用的方案。
支付系统内部的账户 A 扣款和账户 B 收款，可以通过消息队列实现最终一致。
关键点在于保证消息可靠投递，以及消费过程具备幂等性。

2. Consistency（一致性）
事务前后系统总金额或其他约束必须保持不变，这主要通过业务逻辑和数据库约束来保证。

3. Isolation（隔离性）
通常使用数据库乐观锁。
例如，在更新账户余额时增加一个 `version` 字段：
`UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE user_id = 'A' AND version = 1;`
如果更新行数为 0，说明该记录已被其他事务修改，需要重试。
相比悲观锁，乐观锁在高并发场景下通常表现更好。

4. Durability（持久性）
只要事务提交成功，数据就必须被持久化到磁盘。
这依赖数据库自身的持久化能力，以及高可用数据库集群，例如 MySQL 主从加 MGR、Galera，或 TiDB 这类分布式数据库。

#### 如何设计对账系统？

对账是保障资金安全的最后一道防线。

对账目标

发现并修正因网络异常、服务宕机或程序 Bug 导致的数据不一致问题。

对账方

1. 内部对账
支付系统内部各模块之间的对账，例如交易模块与会计模块。

2. 外部对账
支付系统与银行、第三方支付渠道之间的对账。

对账流程

1. 数据拉取
定期从银行或第三方渠道获取对账文件，通常在 T+1 日凌晨执行，文件格式一般为 CSV 或 TXT。

2. 数据标准化
将外部文件和内部订单记录统一转换为标准格式，便于后续比对。

3. 数据核对
通常以一方数据为基准，例如银行流水，逐条在另一方查找对应记录。
核对维度通常包括订单号、金额、时间和状态。

核对结果一般有两类。
平账：双方记录完全一致。
不平账：双方记录存在差异。

不平账又常见为以下几种情况。
长款：我方有记录，渠道无记录，可能是我方单边成功，需要确认是否退款。
短款：渠道有记录，我方无记录，可能是我方漏单，需要补单。
金额不一致：通常需要人工介入调查。

4. 差错处理
将不平账记录写入差错表。
通过运营后台展示差错信息，由财务或运营人员执行补单、退款、挂账等操作。
对于规则明确的差错，也可以设计自动化处理流程。

#### 如何防止重复支付和超卖？

防止重复支付

1. 唯一支付请求号
调用方在发起支付时生成全局唯一的 `request_id`。
支付系统在创建支付订单时，将 `request_id` 与订单绑定，并对该字段建立唯一索引。
这样当重复请求到来时，数据库会因唯一约束拒绝重复插入。

2. 幂等性控制
支付接口本身必须具备幂等性。
对于相同请求，如果已经处理成功，则应直接返回上一次的结果，而不是再次执行扣款。

防止超卖

核心是保证扣库存操作的原子性和正确性。

1. 数据库乐观锁
可使用如下语句：
`UPDATE products SET stock = stock - 1 WHERE product_id = 'X' AND stock > 0;`
其中 `stock > 0` 作为前置条件，确保不会卖出负库存。
这种方式实现简单，但高并发下瓶颈通常在数据库。

2. Redis 原子操作
可将库存放在 Redis 中，使用 `DECR` 或 Lua 脚本做原子扣减。
例如：
`IF redis.call('GET', 'stock:X') > 0 THEN redis.call('DECR', 'stock:X') ... END`
这是互联网高并发场景中非常主流的方案，性能较高。

### 6. 设计一个实时大数据分析平台（如实时风控系统）

#### 如何实现低延迟的流式计算？

计算引擎

Apache Flink 是当前业界非常主流的流计算引擎。

它的主要优势包括：
高吞吐、低延迟，基于原生流式模型，延迟可达毫秒级。
状态管理能力强，支持多种 State Backend，例如内存、文件系统和 RocksDB。
支持 Exactly-Once 语义，可通过 Checkpoint 机制保证。

架构设计

1. 数据源
用户行为日志、交易数据等可通过 Flume 或 Logstash 收集，再注入 Kafka。

2. 流处理
Flink 集群消费 Kafka 中的数据流。

3. 计算逻辑
可以通过规则引擎加载一系列预设规则，例如“1 分钟内异地登录 3 次”。
也可以加载在线学习模型或离线训练模型，对数据流进行实时预测，例如判断交易是否欺诈。

4. 结果输出（Sink）
高风险事件可写入另一个 Kafka Topic，或直接调用告警服务。
分析结果可写回 HBase 或 Redis，以更新用户实时画像。
统计指标也可写入 ClickHouse 或 Elasticsearch，用于实时看板展示。

#### 如何存储和查询 PB 级数据？

存储

1. HDFS
HDFS 是大数据生态的基础设施之一，具备高吞吐和高容错能力，适合存储原始日志和中间计算结果。

2. 对象存储
例如 S3、OSS。其成本更低，并且天然支持存储与计算分离，是现代数据湖架构的重要方向。

查询与分析引擎

1. 离线分析
Hive 或 Spark SQL 可以将 HDFS 上的结构化数据映射为表，适合批处理和探索性分析，延迟通常在分钟到小时级。
Presto 或 Trino 是高性能分布式 SQL 查询引擎，可以跨 HDFS、MySQL、Kafka 等多种数据源做联邦查询，延迟通常为秒级到分钟级。

2. 实时分析
ClickHouse 是典型的列式 OLAP 数据库，聚合查询性能极强，可达到亚秒级响应。
Apache Doris 和 StarRocks 是新一代 MPP 分析型数据库，兼容 MySQL 协议，易用性较好，性能也很强。
Apache Kylin 和 Druid 通过预聚合，用空间换时间，在固定多维分析场景下可做到毫秒级响应。

#### 如何保证数据处理的 Exactly-Once 语义？

Exactly-Once 表示端到端的数据处理流程中，每条记录既不重复，也不丢失。

Flink 的实现机制

1. Source 端
Source Connector 必须是可重放的，例如 Kafka，并且能够记录消费偏移量。

2. Flink 内部
Flink 会定期对所有算子的状态做快照，并将其持久化到分布式存储中，这个过程称为 Checkpoint。
Flink 还会在数据流中插入 Barrier。一个算子收到所有上游 Barrier 后才会对自身做快照，并继续向下游传播，以此保证快照一致性。

3. Sink 端
Sink Connector 需要支持事务，或者至少支持幂等写入。

两阶段提交 Sink

Pre-commit：在 Checkpoint 开始时，Sink 开启事务并写入数据，但暂不提交。
Commit：当 JobManager 确认所有算子的 Checkpoint 都完成后，再通知 Sink 提交事务。
Abort：如果 Checkpoint 失败，则通知 Sink 中止事务。

端到端 Exactly-Once 的条件

1. Source 必须可重置或可重放，例如 Kafka。
2. Flink 必须开启 Checkpoint。
3. Sink 必须支持事务性写入或幂等写入。

通过以上设计，即使系统故障并从上一个 Checkpoint 恢复，Flink 也能保证数据恰好处理一次。
