# 🚀 高并发秒杀系统架构与防超卖实战指南（高级架构师视角）

> **场景基准**：“100件库存，10万并发”
> **核心思想**：防超卖本质是一个**漏斗模型**。架构设计的原则是“尽量将请求拦截在上游”，绝不能让10万并发直接击穿到数据库。秒杀系统本质上是“极高并发下的读写冲突问题”，解决它的核心思路是：**分层过滤、异步解耦、削峰填谷、缓存兜底**。
>
> 秉承 Go 语言哲学：简单、直接、显式错误处理、善用并发原语。

---

## 🛡️ 第一部分：系统整体架构与流量漏斗模型

高并发系统绝不能把所有请求都放到数据库层去抗，必须在每个层级尽可能地拦截无效或超载请求，形成一个“漏斗状”的防御体系。

### 1.1 宏观分层架构职责

- **客户端层（H5/App）**：提供良好交互体验。按钮防重复点击（点击后置灰）、**答题/验证码机制**（将集中在 0.1 秒内的请求分散到 3-5 秒的时间窗口内，极大降低瞬时峰值）。
- **CDN 节点与边缘计算层**：秒杀商品详情页全面静态化推送 CDN，结合边缘计算进行简单的 IP 黑名单拦截。
- **接入层（API Gateway / Nginx）**：
  - **算法拦截**：使用令牌桶（Token Bucket）或漏桶算法，限制单节点 QPS（如 `limit_req_zone` 限制单 IP 请求频率）。
  - **黑名单风控**：基于 IP、User-ID 进行访问频率限制，识别并拦截羊毛党。直接丢弃超额请求，返回"排队中"。
- **应用层（Microservices in Go）**：无状态设计核心业务逻辑（用户校验、库存预扣、订单生成）。
- **缓存层（Redis Cluster / 本地缓存）**：利用 Redis 单线程原子操作预扣库存。L1 本地缓存（如 Go `freecache`）拦截售罄后的无效流量。
- **消息队列层（RocketMQ / Kafka）**：削峰填谷，异步化耗时操作。Redis 扣减成功后即发 MQ 并向前端返回成功。
- **数据库层（MySQL）**：最终数据落盘。依靠数据库层的乐观锁（`stock > 0`）与唯一索引做最后的兜底防超卖。

### 1.2 流量漏斗量化图（每层拦截效果）

```
┌─────────────────────────────────────────────────────────────────┐
│                    10万并发请求涌入                               │
├─────────────────────────────────────────────────────────────────┤
│ 客户端层（答题验证码）        → 过滤 60%，剩 4万                    │

│     ↓                                                               │
│ 网关限流（令牌桶/黑名单）   → 过滤 70%，剩 1万                      │
│     ↓                                                               │
│ Redis Lua 原子扣减         → 过滤 99%，剩 ~100                     │
│     ↓                                                               │
│ MQ 异步下单（削峰填谷）     → 平滑处理，无瞬时压力                   │
│     ↓                                                               │
│ MySQL 落盘（乐观锁兜底）    → 最终一致，零超卖                       │

核心原则：尽量将请求拦截在上游，绝不能让 10 万并发直接击穿到数据库。
```

### 1.2 核心业务流程时序

1. **抢购开始**：前端向网关获取**动态秒杀 Token/隐藏 URL**（防抓包机刷），携带 Token 发起请求。
2. **预扣减库存**：请求到达 Redis，执行 **Lua 脚本**进行原子性库存检查与扣减（同时记录用户已参与防重）。
   - 若库存不足：直接返回"已售罄"，应用层本地缓存标记售罄。
3. **异步下单（MQ）**：Redis 扣减成功后，应用层生成唯一订单号（雪花算法），发送至 MQ，并向前端返回"抢购成功，排队中..."。
4. **消费者落盘与支付**：MQ 消费者平滑拉取消息，在 MySQL 创建订单记录并真实扣减 DB 库存。
5. **超时未支付处理**：利用 MQ 延迟队列（如 15 分钟），检查订单未支付则取消，回加 DB 和 Redis 库存。

### 1.3 下单结果通知方案（前端如何获取最终状态）
前端获得"抢购成功"后，需要知道最终下单是否完成。两种主流方案：

**方案一：前端轮询（简单直接）**
```go
// 前端每 2 秒轮询订单状态接口
// GET /api/seckill/order/status?orderID=xxx
func (s *SeckillService) GetOrderStatus(ctx context.Context, orderID string) (string, error) {
    order, err := s.repo.FindOrderByID(ctx, orderID)
    if err != nil {
        return "", err
    }
    // 返回状态：PENDING（排队中）/ CONFIRMED（已确认）/ CANCELLED（已取消）/ PAID（已支付）
    return order.Status, nil
}
```

**方案二：WebSocket 实时推送（实时性更好）**
```go
// 消费者落盘后，主动推送 WebSocket 通知用户
func (s *SeckillService) OnOrderCreated(ctx context.Context, order *SeckillOrder) error {
    // 查询用户的 WebSocket 连接
    conn, ok := s.wsPool.Get(order.UserID)
    if !ok {
        return nil // 用户不在线，轮询兜底
    }
    message := &_ws.Message{
        Type:    "seckill_result",
        OrderID: order.OrderID,
        Status:  order.Status,
    }
    return conn.WriteJSON(message)
}
```

> 💡 **建议**：优先使用轮询方案（实现简单，易于维护）。高并发场景下 WebSocket 会有连接管理开销，需要额外的 sticky session 或全局广播机制。

## ⚡ 第二部分：Redis 极速扣减层（抗压核心）

在“10 万并发”打入时，Redis 是真正抗下读写冲突的核心。利用 Redis 内存型单线程特性抗住高并发流量，核心是**原子性**。

### 1. 架构反模式与最佳实践
- **反模式（分布式锁扣库存）**：`加锁 -> 查询库存 -> 判断 -> 扣减 -> 解锁`。这种方式存在多次网络 I/O 损耗，且将 Redis 退化成了串行处理，并发度极低。
- **最佳实践（Lua 脚本）**：直接使用 **Lua 脚本**。将查和扣合并为一次操作，Redis 单线程执行 Lua 脚本天生具备原子性。

### 2. Go + Redis Lua 实战代码
```go
// 依赖注入，显式传递 context
type SeckillService struct {
    rdb *redis.Client
}

// Lua 脚本：DECR 后判断 -> 回补库存 -> 记录用户下单标记 (防止重复抢购)
// 核心原则：必须用 DECR 后判断，不能先 GET 再 DECR（不原子）
const deductScript = `
    local stockKey = KEYS[1]
    local userRecordKey = KEYS[2]
    local uid = ARGV[1]
    
    -- 1. 检查是否已经抢过（使用 SISMEMBER 精确防重）
    if redis.call("SISMEMBER", userRecordKey, uid) == 1 then
        return -1 -- 重复抢购
    end
    
    -- 2. 直接 DECR，然后判断结果（原子操作）
    local stock = redis.call("DECR", stockKey)
    if stock < 0 then
        -- 库存不够，回补 DECR 造成的减量
        redis.call("INCR", stockKey)
        return 0 -- 库存不足
    end
    
    -- 3. 记录用户下单（原子扣减成功后才能记录）
    redis.call("SADD", userRecordKey, uid)
    return 1 -- 成功
`

func (s *SeckillService) PreDeductStock(ctx context.Context, goodsID, userID int64) error {
    stockKey := fmt.Sprintf("{sk:%d}:stock", goodsID)
    userKey := fmt.Sprintf("{sk:%d}:users", goodsID)

    result, err := s.rdb.Eval(ctx, deductScript, []string{stockKey, userKey}, userID).Result()
    if err != nil {
        log.Printf("[PreDeductStock] Redis eval failed, goodsID: %d, userID: %d, err: %v", goodsID, userID, err)
        return fmt.Errorf("redis execution error: %w", err)
    }

    resCode := result.(int64)
    switch resCode {
    case 1:
        return nil
    case 0:
        return ErrStockNotEnough
    case -1:
        return ErrDuplicateOrder
    default:
        return ErrUnknown
    }
}
```

> ⚠️ **常见错误**：先 `GET stock` 再 `DECR` 是两步操作，不是原子的。在高并发下会出现超卖。

### 3. 热点数据隔离（库存分桶）
单 key 热点问题是 Redis 面临的最大挑战。10万并发全部打到同一个 `{sk:goods_id}:stock` key 上，即便 Lua 脚本原子操作再快，也会产生严重锁竞争。

**解决方案：库存分桶 + 用户 ID Hash 路由**

```go
const bucketScript = `
    local stockKeyPrefix = KEYS[1]
    local userRecordKey = KEYS[2]
    local uid = ARGV[1]
    local bucketCount = tonumber(ARGV[2])

    -- 1. 检查是否已经抢过
    if redis.call("SISMEMBER", userRecordKey, uid) == 1 then
        return -1
    end

    -- 2. 根据用户 ID Hash 取模选择桶
    local bucketIndex = (uid % bucketCount) + 1
    local stockKey = stockKeyPrefix .. ":" .. bucketIndex

    -- 3. DECR 并判断
    local stock = redis.call("DECR", stockKey)
    if stock < 0 then
        redis.call("INCR", stockKey)
        return 0
    end

    -- 4. 记录用户（注意：这里用户只能在一个桶有记录即可）
    redis.call("SADD", userRecordKey, uid)
    return 1
`

func (s *SeckillService) PreDeductStockWithBucket(ctx context.Context, goodsID, userID int64, bucketCount int) error {
    stockKeyPrefix := fmt.Sprintf("{sk:%d}:stock", goodsID)
    userKey := fmt.Sprintf("{sk:%d}:users", goodsID)

    result, err := s.rdb.Eval(ctx, bucketScript,
        []string{stockKeyPrefix, userKey},
        userID, bucketCount).Result()
    if err != nil {
        return fmt.Errorf("redis error: %w", err)
    }

    resCode := result.(int64)
    switch resCode {
    case 1:
        return nil
    case 0:
        return ErrStockNotEnough
    case -1:
        return ErrDuplicateOrder
    default:
        return ErrUnknown
    }
}
```

> 💡 **分桶数量建议**：一般设为 `CPU 核心数 * 2` 即可（如 16 核机器设 32 桶）。桶数过多会增加 Lua 脚本复杂度。

### 4. 极端场景应对（主从架构陷阱）
- **主从延迟导致少卖**：Master 执行 Lua 扣减成功，但未 Sync 到 Slave 时 Master 宕机。Sentinel 切换后，新的 Master 库存比实际多，导致“少卖”。
- **架构解法**：
  1. 核心库存采用 Redis Standalone（单机独立部署），利用高配机器硬抗，舍弃高可用换取强一致性。
  2. 接受短暂少卖，依赖后置的**异步对账**修复。

## 🔒 第三部分：分布式锁与并发控制的正确姿势

在秒杀中，如果业务不仅是扣库存，还包含复杂校验前置逻辑，需要用到分布式锁时，必须规避**商品级加锁**和**羊群效应**。

### 1. 锁设计原则与羊群效应
- **原则**：分布式锁主要用于**防止用户恶意重复提交**或**支付回调防重**。锁的粒度应精确到 `userID + goodsID`，**绝不对商品级加锁**。
- **羊群效应 (Thundering Herd)**：锁释放瞬间，大量阻塞客户端同时被唤醒抢锁，打爆 Redis/ZK。
- **解法**：使用 ZK 的临时顺序节点（链式唤醒），或在 Redis 中采用**随机退避策略 (Random Backoff)**错峰重试。

### 2. 锁续期与看门狗 (Watchdog) 机制
解决“业务执行时间超过了锁的过期时间（TTL）”导致的**并发混乱**。
利用 Go 原生并发特性实现 Watchdog 的架构思路：
```go
// LockWithWatchdog 带看门狗的分布式锁实现
// 返回释放函数，业务层 defer unlock() 调用
func (s *SeckillService) LockWithWatchdog(ctx context.Context, key string, ttl time.Duration) (func(), error) {
    // 1. 尝试获取锁 (SET NX PX)
    ok, err := s.rdb.SetNX(ctx, key, "locked", ttl).Result()
    if err != nil {
        return nil, fmt.Errorf("redis error: %w", err)
    }
    if !ok {
        return nil, ErrLockFailed
    }

    // 2. 创建 context 用于停止 watchdog
    watchdogCtx, cancel := context.WithCancel(ctx)

    // 3. 启动 Goroutine 作为守护线程，自动续期
    go func() {
        ticker := time.NewTicker(ttl / 3) // 续期周期为 TTL/3
        defer ticker.Stop()
        for {
            select {
            case <-ticker.C:
                // 仅当锁还存在时才续期（防止业务提前释放后误续期）
                if s.rdb.Exists(ctx, key).Val() == 1 {
                    s.rdb.Expire(ctx, key, ttl)
                }
            case <-watchdogCtx.Done():
                // 业务逻辑执行完毕，watchdog 退出
                return
            }
        }
    }()

    // 4. 返回释放函数
    unlock := func() {
        cancel()
        s.rdb.Del(ctx, key)
    }
    return unlock, nil
}

// 业务层使用示例
func (s *SeckillService) ProcessPayment(ctx context.Context, orderID int64) error {
    key := fmt.Sprintf("order:lock:%d", orderID)
    unlock, err := s.LockWithWatchdog(ctx, key, 30*time.Second)
    if err != nil {
        return err
    }
    defer unlock() // 业务完成后释放锁

    // 业务逻辑：支付处理、防重校验等
    return nil
}
```

> ⚠️ **关键点**：
> - 续期周期建议为 TTL/3，避免业务执行时间接近 TTL 时锁已过期
> - `unlock` 函数必须是原子操作（Lua 脚本或 Redis Del）

### 3. 什么情况下需要分布式锁？

分布式锁并非银弹，只有在**跨进程/跨实例需要互斥访问共享资源**时才有必要使用。以下是分布式锁的典型适用场景：

| 场景 | 说明 | 典型用例 |
| :--- | :--- | :--- |
| **防止重复操作** | 同一用户对同一资源的重复提交（如重复下单、重复支付） | 支付回调防重、订单确认 |
| **任务抢领** | 多个 Worker 竞争执行同一任务（如秒杀优惠券发放） | 优惠券领用、红包分发 |
| **资源协调** | 分布式环境下对共享设备/配置的独占访问 | 配置更新、Leader 选举 |
| **库存锁定（复杂场景）** | 业务逻辑无法简单用 Lua 原子脚本完成，需要更长的临界区 | 预售订单、限时活动的前置校验 |

> ⚠️ **高并发秒杀的核心观点**：如果可以用 **Redis Lua 原子操作** 完成（如库存扣减），**绝不** 使用分布式锁。Lua 脚本原子操作性能比分布式锁高 10 倍以上。分布式锁应作为复杂业务逻辑的最后手段。

### 4. 分布式锁的原理

#### 4.1 Redis 分布式锁实现原理

**核心命令**：`SET key value NX PX milliseconds`

```
┌─────────────────────────────────────────────────────────────────┐
│                     分布式锁获取流程                               │
├─────────────────────────────────────────────────────────────────┤
│  客户端 A                 Redis                                  │
│     │                                                               │
│     │──── SET lock:order:123 "uuid-a" NX PX 30000 ────▶           │
│     │                         │                                   │
│     │                         │  返回 OK（获取成功）                │
│     │◀─────────────────────────┤                                   │
│     │                                                               │
│     │  [执行业务逻辑...]                                             │
│     │                                                               │
│     │──── DEL lock:order:123 ─────────────────────────▶            │
│     │◀─────────────────────────┤                                   │
└─────────────────────────────────────────────────────────────────┘
```

**关键点**：
- `NX`（Not eXists）：仅当 key 不存在时才设置，保证互斥性
- `PX milliseconds`：设置过期时间，防止锁持有者崩溃后锁无法释放（死锁）
- `value` 必须唯一：使用 UUID 或snowflake ID，用于安全释放（只能释放自己的锁）

**安全释放（防误删）**：
```go
// 错误示范：直接 DEL 会误删他人持有的锁
func wrongUnlock(ctx context.Context, rdb *redis.Client, key string) {
    rdb.Del(ctx, key) // 可能删掉别人刚获取的锁！
}

// 正确做法：用 Lua 脚本原子检查 + 删除
const unlockScript = `
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
`

func safeUnlock(ctx context.Context, rdb *redis.Client, key, value string) error {
    _, err := rdb.Eval(ctx, unlockScript, []string{key}, value).Result()
    return err
}
```

#### 4.2 ZooKeeper 分布式锁实现原理

ZK 基于 **临时顺序节点** 和 **Watch 机制** 实现分布式锁：

```
┌─────────────────────────────────────────────────────────────────┐
│                     ZK 临时顺序节点锁原理                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│  /locks                                                          │
│    ├── lock-000001  [客户端 A 创建]  ←──── 当前持有锁              │
│    ├── lock-000002  [客户端 B 创建]                              │
│    └── lock-000003  [客户端 C 创建]                              │
│                                                                   │
│  客户端 A 解锁后删除 lock-000001                                  │
│  ZK 通知等待 lock-000002 的客户端 B：你是最小的，可以获取锁了        │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

**优势**：
- **链式唤醒**：ZK 自动将等待队列转为链表，按顺序唤醒，避免羊群效应
- **Session 临时节点**：客户端崩溃时，临时节点自动删除，锁自动释放
- **强一致性**：ZK 是 CP 系统，保证锁的线性一致性

**劣势**：
- 性能低于 Redis（每次锁操作需要 ZK Leader 协调）
- 需要额外部署 ZK 集群

#### 4.3 Redisson 分布式锁（Redis 封装）

Redisson 是 Java 生态最成熟的分布式锁库，其 Go 等价实现为 `Reds`：

### 5. 分布式锁的常见问题与解决方案

| 问题 | 原因 | 解决方案 |
| :--- | :--- | :--- |
| **死锁** | 锁持有者崩溃未释放锁 | 必须设置 TTL（过期时间） |
| **锁过期，业务未完成** | TTL 设置过短 | 使用 Watchdog 自动续期 |
| **误删他人锁** | 直接 DEL 不检查 value | 用 Lua 脚本原子检查 + 删除 |
| **羊群效应** | 锁释放时大量客户端同时抢锁 | ZK 临时顺序节点链式唤醒 / Redis 随机退避重试 |
| **主从切换丢锁** | Master 加锁后未同步到 Slave 就挂了 | 使用 RedLock（多数派投票）或 Redis Standalone |
| **可重入性** | 同一客户端递归获取同一锁 | 锁 value 包含计数器和线程 ID，支持重入 |

### 6. Redis Standalone vs RedLock vs ZK 对比

| 维度 | Redis Standalone | RedLock | ZooKeeper |
| :--- | :--- | :--- | :--- |
| **性能** | 极高 | 高 | 中等 |
| **一致性** | AP（可能丢锁） | CP（多数派强一致） | CP（线性一致） |
| **可靠性** | 依赖 Redis 持久化 | 需要多个独立 Redis 实例 | 依赖 ZK 集群 |
| **复杂度** | 低 | 高（需 5 个独立实例） | 中（需部署 ZK） |
| **适用场景** | 普通分布式锁 | 对可靠性要求极高 | 需要临时顺序节点特性 |
| **Go 支持** | go-redis 原生支持 | 需自行实现或用第三方库 | 第三方库如 `go-zookeeper` |

> 💡 **架构建议**：高并发秒杀场景下，**Redis Standalone** 是最佳选择（舍弃高可用换取极致性能）。如果对锁的可靠性有极致要求且能接受复杂度，再考虑 RedLock。

### 7. 分布式锁最佳实践 Checklist

```go
// 分布式锁实现检查清单
type LockUsage struct {
    // ✅ 1. 锁的 key 必须精确到最小竞争单元（userID + goodsID，避免商品级锁）
    // ✅ 2. value 必须唯一（UUID），用于安全释放
    // ✅ 3. 必须设置 TTL，防止死锁
    // ✅ 4. 业务执行时间不确定时，必须实现 Watchdog 自动续期
    // ✅ 5. 解锁必须原子（Lua 脚本），防止误删他人锁
    // ✅ 6. 获取锁失败必须有重试机制，且重试时使用随机退避避免羊群效应
    // ✅ 7. 优先使用 Redis Lua 原子操作，而非分布式锁（性能差距 10 倍+）
}
```

> 📌 **架构师核心结论**：分布式锁是**不得已而为之**的兜底方案。在高并发系统中，首先应该通过**分层过滤**（验证码、限流、Redis Lua 原子扣减）将并发压低到可控范围，再考虑分布式锁。记住：**最好的锁是根本不加锁**。

## 🧱 第四部分：数据库层面的终极防线（兜底控制）

即便上游缓存全挂，数据库作为最终的 Source of Truth，必须严防死守不超卖。

### 1. 乐观锁与库存分段优化
- **经典 SQL 防超卖**：依靠 `stock > 0` 这一条件作为乐观锁，而不是依赖版本号（高并发下版本号冲突率极高）。
  ```sql
  UPDATE seckill_goods SET stock = stock - 1 WHERE goods_id = 100 AND stock > 0;
  ```
- **关键优化点：库存分段 (Inventory Segmentation)**
  - **痛点**：库存仅剩 1 件时，千个线程更新同一行，导致严重的 InnoDB 行锁竞争。
  - **方案**：将 100 件库存拆分为 10 条记录（如 `goods_1` 到 `goods_10`）。扣减时通过 UserID Hash 路由到特定分段，分散单行热点，提升 10 倍 DB 吞吐量。

### 2. 数据库唯一索引防重
- `seckill_order` 表必须建立 `UNIQUE KEY uk_user_goods (user_id, goods_id)`。
- **作用**：网络重发或 MQ At-Least-Once 机制会导致消息重复消费。即使 MQ 重复投递，DB 也会抛出 `Duplicate Key` 异常，Consumer 捕获异常并直接 Ack 即可，保障绝对的幂等。

## 📨 第五部分：异步削峰与最终一致性对账

"10万并发"秒杀中，**同步写数据库订单是必死无疑的**，必须转为"异步排队"。

### 1. Outbox Pattern（发件箱模式）保证消息不丢失
不能依赖单纯的 `redis.call` 之后直接 `mq.send`，若应用在中间宕机会导致库存扣了但没发 MQ（严重少卖）。
- **流程**：
  1. 开启数据库本地事务。
  2. 插入业务数据（如需落库）+ 插入一条 `outbox_message` 表记录（状态为 `SENT`）。
  3. 提交事务。
  4. 异步线程将 `outbox` 投递到 MQ，成功后更新状态为 `CONFIRMED`。
  5. **定时对账任务**：扫描超时仍为 `SENT` 的记录进行补偿重发。

### 2. 分布式事务的高级解法（RocketMQ 事务消息）
若不使用 Outbox 表，可使用 RocketMQ 的事务消息：
1. 应用层发送 Half 消息到 MQ。
2. 执行本地 Redis 扣减。
3. 根据本地执行结果向 MQ 提交 Commit 或 Rollback。
4. 若半途应用宕机，MQ 主动回调应用层检查接口，确认事务状态。

### 3. MQ 消费端幂等性保障（重要）
MQ 的 At-Least-Once 机制会导致消息重复投递，必须在消费端做幂等：

```go
type SeckillService struct {
    rdb *redis.Client
    repo *OrderRepository
}

type OrderMessage struct {
    OrderID   string
    UserID    int64
    GoodsID   int64
    Timestamp int64
}

// ConsumeSeckillOrder 消费 MQ 消息创建订单
func (s *SeckillService) ConsumeSeckillOrder(ctx context.Context, msg *OrderMessage) error {
    // 1. 利用 Redis 做幂等标记（24小时有效）
    idempotentKey := fmt.Sprintf("seckill:processed:%s", msg.OrderID)
    exists, err := s.rdb.SetNX(ctx, idempotentKey, 1, 24*time.Hour).Result()
    if err != nil {
        return fmt.Errorf("redis error: %w", err)
    }
    if !exists {
        // 已处理过，直接返回成功（幂等）
        return nil
    }

    // 2. 执行真正的下单逻辑（MySQL 唯一索引兜底）
    order := &SeckillOrder{
        OrderID:   msg.OrderID,
        UserID:    msg.UserID,
        GoodsID:   msg.GoodsID,
        Status:    OrderStatusConfirmed,
        CreatedAt: time.Now(),
    }
    if err := s.repo.CreateOrder(ctx, order); err != nil {
        // 唯一索引冲突，说明重复，直接忽略
        if strings.Contains(err.Error(), "Duplicate") {
            return nil
        }
        return err
    }

    // 3. 回补用户购买记录（用于查询）
    s.rdb.SAdd(ctx, fmt.Sprintf("{sk:%d}:purchased", msg.GoodsID), msg.UserID)
    return nil
}
```

### 4. 库存回滚定时对账任务（补偿机制）
支付超时（15分钟）未支付，需要回滚库存：

```go
// ReconcileTimeoutOrders 定时扫描超时未支付订单，回滚库存
func (s *SeckillService) ReconcileTimeoutOrders(ctx context.Context) error {
    // 1. 查询超时未支付的订单（状态 PENDING 且创建时间 > 15分钟）
    orders, err := s.repo.FindTimeoutPendingOrders(ctx, 15*time.Minute)
    if err != nil {
        return fmt.Errorf("query timeout orders failed: %w", err)
    }

    for _, order := range orders {
        // 2. 回滚 Redis 库存
        stockKey := fmt.Sprintf("{sk:%d}:stock", order.GoodsID)
        if _, err := s.rdb.Incr(ctx, stockKey).Result(); err != nil {
            log.Printf("[Reconcile] Failed to rollback stock, orderID: %s, err: %v", order.OrderID, err)
            continue
        }

        // 3. 标记订单已取消
        if err := s.repo.UpdateOrderStatus(ctx, order.OrderID, OrderStatusCancelled); err != nil {
            log.Printf("[Reconcile] Failed to cancel order, orderID: %s, err: %v", order.OrderID, err)
        }

        // 4. 移除用户购买标记（允许重新抢购）
        userKey := fmt.Sprintf("{sk:%d}:users", order.GoodsID)
        s.rdb.SRem(ctx, userKey, order.UserID)

        log.Printf("[Reconcile] Order cancelled, orderID: %s, goodsID: %d, userID: %d", order.OrderID, order.GoodsID, order.UserID)
    }
    return nil
}
```

> 💡 **建议**：对账任务每分钟执行一次，使用分布式锁保证单节点执行，避免多实例重复处理。

## 📊 架构师总结：超卖与少卖的权衡

| 维度                 | 策略与底线               | 架构应对方案                                                         |
| :----------------- | :------------------ | :------------------------------------------------------------- |
| **超卖 (Oversell)**  | **🔴 绝对不可接受（红线）**   | 损害信誉。需通过 Redis Lua 原子扣减 + 数据库唯一索引/乐观锁（`stock > 0`）严防死守。        |
| **少卖 (Undersell)** | **🟡 可接受（需修复）**     | Redis 主从切换丢数据、支付超时取消等。通过 MQ 延迟队列回退库存、异步定时对账补偿解决。               |
| **架构原则**           | **🟢 最终一致性 (BASE)** | 放弃强一致性（ACID）。优先保证核心可用性（快速失败、前置拦截），允许状态短暂不一致，通过 MQ 和对账任务保证最终一致。 |
