- **安全性**: HTTP 是超文本传输协议，信息是明文传输，存在安全风险。HTTPS 在 TCP 和 HTTP 网络层之间加入了 SSL/TLS 安全协议，对报文进行加密传输，解决了 HTTP 不安全的缺陷。
- **连接过程**: HTTP 连接建立相对简单，TCP 三次握手之后便可进行报文传输。而 HTTPS 在 TCP 三次握手之后，还需进行 SSL/TLS 的握手过程，才可进入加密报文传输。
- **默认端口**: 两者的默认端口不一样，HTTP 默认端口号是 80，HTTPS 默认端口号是 443。
- **证书要求**: HTTPS 协议需要向 CA（证书权威机构）申请数字证书，来保证服务器的身份是可信的。

### 2. 简述HTTP/1.1, HTTP/2, HTTP/3的主要演进和区别。

- **HTTP/1.1**:
    - **长连接**: 引入了持久连接（Keep-Alive），多个HTTP请求可以复用同一个TCP连接，减少了连接建立和断开的开销。
    - **管道化 (Pipeline)**: 允许客户端在收到上一个响应前发送下一个请求，但响应必须按顺序返回，存在队头阻塞（HOLB）问题。
    - **缺点**: 头部未经压缩，内容冗长；请求-响应模式导致队头阻塞。

- **HTTP/2**:
    - **二进制分帧**: 将所有传输的信息分割为更小的消息和帧，并对它们采用二进制格式编码。
    - **多路复用**: 在一个TCP连接上可以并行处理多个请求和响应，解决了HTTP/1.1的队头阻塞问题。
    - **头部压缩 (HPACK)**: 使用HPACK算法压缩请求和响应头，减少了传输开销。
    - **服务器推送 (Server Push)**: 服务器可以主动向客户端推送资源，减少了请求的延迟。
    - **缺点**: 基于TCP协议，TCP层的队头阻塞问题依然存在。如果一个TCP报文丢失，会阻塞该连接上的所有HTTP请求。

- **HTTP/3**:
    - **基于QUIC协议**: 将传输层协议从TCP替换为UDP，并在UDP之上实现了可靠传输、流量控制、多路复用等功能。
    - **解决了TCP队头阻塞**: QUIC实现了流级别的多路复用，一个流的丢包不会影响其他流。
    - **更快的连接建立**: QUIC将TCP握手和TLS握手合并，只需要1个RTT即可建立连接和密钥协商，甚至可以实现0-RTT。
    - **连接迁移**: 使用连接ID来标识连接，而不是TCP的四元组（源IP、源端口、目的IP、目的端口）。当网络切换（如从4G到WiFi）时，IP地址改变，连接依然可以维持，不会中断。

### 3. HTTP协议的无状态性是什么意思？如何解决？

- **无状态性**: 指的是协议对于事务处理没有记忆能力。服务器不知道客户端是什么状态，即服务器不会保留之前请求或响应的任何信息。每个请求都被视为独立的事务。
- **优点**: 服务器不需要额外的资源来记录状态信息，减轻了服务器的负担。
- **缺点**: 在处理需要关联性的操作（如网上购物）时会非常麻烦，每次都需要重新验证身份。
- **解决方案**: 通常使用 **Cookie** 技术来解决。服务器在第一次响应时通过 `Set-Cookie` 头部向客户端下发一个包含用户信息的唯一标识。客户端会保存这个Cookie，并在后续的请求中通过 `Cookie` 头部将其带上，这样服务器就能识别用户身份，维持会话状态。


### 8. HTTP状态码有哪些类别？列举5个常见的状态码。

HTTP状态码分为五大类：
- **1xx (信息性状态码)**: 表示请求已接收，继续处理。
- **2xx (成功状态码)**: 表示请求已成功被服务器接收、理解、并接受。
- **3xx (重定向状态码)**: 表示要完成请求，需要进一步操作。
- **4xx (客户端错误状态码)**: 表示客户端请求有语法错误或请求无法实现。
- **5xx (服务器错误状态码)**: 表示服务器未能实现合法的请求。

**5个常见的状态码**:
1.  **200 OK**: 请求成功。
2.  **301 Moved Permanently**: 永久重定向。
3.  **304 Not Modified**: 资源未修改，客户端可以使用缓存。
4.  **404 Not Found**: 请求的资源在服务器上未找到。
5.  **500 Internal Server Error**: 服务器内部错误。

### 9. 301和302重定向有什么区别？

- **301 Moved Permanently (永久重定向)**:
    - 表示请求的资源已永久移动到新的URL。
    - 浏览器会缓存这个重定向，下次请求会自动访问新的URL。
    - 对SEO友好，搜索引擎会将权重从旧地址转移到新地址。

- **302 Found (临时重定向)**:
    - 表示请求的资源临时从不同的URL响应。
    - 浏览器不会缓存这个重定向，每次都会请求原始URL。
    - SEO不友好，搜索引擎不会更新其索引。

### 10. 列举5个常见的HTTP请求头和响应头。

**常见请求头 (Request Headers)**:
1.  `Host`: 指定服务器的域名。
2.  `User-Agent`: 客户端的身份标识（浏览器信息）。
3.  `Accept`: 客户端可接受的内容类型。
4.  `Cookie`: 客户端携带的Cookie信息。
5.  `Content-Type`: 请求体的媒体类型（用于POST/PUT请求）。

**常见响应头 (Response Headers)**:
1.  `Content-Type`: 响应体的媒体类型。
2.  `Content-Length`: 响应体的长度。
3.  `Cache-Control`: 控制缓存策略。
4.  `Set-Cookie`: 服务器向客户端下发Cookie。
5.  `Location`: 指定重定向的目标URL（用于3xx状态码）。


### 11. 什么是HTTP持久连接(Keep-Alive)？

HTTP持久连接（也称HTTP长连接）是HTTP/1.1引入的特性。它允许在一次TCP连接上发送和接收多个HTTP请求/响应，而不是为每个请求/响应对都建立一个新的TCP连接。这减少了TCP连接建立（三次握手）和断开（四次挥手）的开销，提高了性能。HTTP/1.1默认开启持久连接。

### 12. 什么是HTTP队头阻塞(Head-of-line blocking)问题？如何解决？

- **HTTP/1.1的队头阻塞**: 在一个持久连接上，请求是顺序发送的，服务器也必须按接收请求的顺序返回响应。如果第一个响应因为处理时间长而延迟，那么后续的响应即使已经处理完毕，也必须等待它发送完成后才能发送。这就阻塞了后续的响应。
- **HTTP/2的队头阻塞**: HTTP/2通过多路复用解决了HTTP层的队头阻塞，但它基于TCP协议，TCP本身存在队头阻塞。TCP是一个可靠的、按序的协议，如果一个TCP报文段丢失，TCP会等待该报文段重传，这会阻塞该TCP连接上的所有HTTP/2流。
- **解决方案**: HTTP/3使用QUIC协议代替TCP。QUIC基于UDP，实现了自己的可靠传输和多路复用机制。QUIC的流是独立的，一个流的丢包不会阻塞其他流，从而彻底解决了队头阻塞问题。

### 13. HTTP/3为什么使用QUIC协议？它解决了什么问题？

HTTP/3使用QUIC协议主要是为了解决HTTP/2中存在的基于TCP的队头阻塞问题，并提升性能。

**QUIC解决的问题**:
1.  **队头阻塞**: QUIC基于UDP，其多路复用是在协议内部实现的，多个流之间相互独立。一个流的数据包丢失不会影响其他流的传输。
2.  **连接建立延迟**: QUIC将TCP握手和TLS握手（基于TLS 1.3）结合在一起，大部分情况下只需要1个RTT就可以完成连接建立和密钥协商，甚至可以实现0-RTT快速重连。
3.  **连接迁移**: TCP连接由四元组（源IP、源端口、目的IP、目的端口）标识。当网络切换时（如手机从Wi-Fi切换到4G），IP地址改变，TCP连接会中断。QUIC使用一个64位的连接ID来标识连接，即使IP地址改变，只要连接ID不变，连接就可以继续，实现了无缝的连接迁移。

### 14. 什么是CDN？简述其工作原理。

- **CDN (Content Delivery Network, 内容分发网络)**: 是一个由分布在不同地理位置的服务器组成的网络，用于更快速、可靠地将静态内容（如图片、CSS、JS文件、视频）分发给用户。
- **工作原理**:
    1.  当用户首次请求一个资源时，请求会发送到源服务器。
    2.  源服务器将资源响应给用户的同时，也会将资源缓存到离用户最近的CDN边缘节点服务器上。
    3.  当其他用户或同一用户再次请求相同资源时，用户的请求会被DNS解析到最近的CDN边缘节点。
    4.  如果边缘节点有该资源的缓存，则直接从边缘节点返回给用户，无需再请求源服务器。这大大减少了延迟，并减轻了源服务器的负载。


### 15. HTTPS是如何保证数据传输安全的？请描述其核心流程。

HTTPS通过在HTTP和TCP之间加入SSL/TLS协议层来保证数据传输安全。它主要解决了三大风险：窃听、篡改和冒充。

**核心保障机制**:
1.  **机密性 (防窃听)**: 使用**混合加密**。在TLS握手阶段，使用非对称加密来安全地协商出一个对称加密的“会话密钥”。握手结束后，所有应用数据都使用这个会话密钥进行对称加密，保证了传输效率和安全性。
2.  **完整性 (防篡改)**: 使用**消息认证码 (MAC)**，通常是基于哈希算法（如SHA-256）实现的。发送方对数据计算一个摘要并与数据一同发送，接收方用同样的方法计算摘要并进行比对，确保数据未被篡改。
3.  **真实性 (防冒充)**: 使用**数字证书**。服务器持有一个由受信任的CA（证书颁发机构）签发的数字证书。证书中包含了服务器的公钥和身份信息。客户端在握手时会验证证书的有效性（通过证书链和CA签名），从而确认服务器的身份是真实可信的。

### 16. 简述SSL/TLS的握手过程。

以TLS 1.2的RSA握手为例，过程主要分为四步（2个RTT）：

1.  **ClientHello**: 客户端向服务器发送问候。包含：支持的TLS版本、一个客户端随机数`Client Random`、支持的密码套件列表。
2.  **ServerHello & Certificate & ServerHelloDone**: 服务器响应。
    - `ServerHello`: 确认TLS版本、一个服务器随机数`Server Random`、从客户端列表中选择一个密码套件。
    - `Certificate`: 发送服务器的数字证书（包含公钥）。
    - `ServerHelloDone`: 告知客户端，服务器的初始信息发送完毕。
3.  **ClientKeyExchange & ChangeCipherSpec & Finished**: 客户端响应。
    - 客户端验证服务器证书。
    - `ClientKeyExchange`: 生成第三个随机数`Pre-Master Secret`，用服务器的公钥加密后发送给服务器。
    - 客户端和服务器使用`Client Random`、`Server Random`和`Pre-Master Secret`各自生成对称的“会话密钥”。
    - `ChangeCipherSpec`: 通知服务器，后续通信将使用加密。
    - `Finished`: 发送一个加密的握手摘要，供服务器验证。
4.  **ChangeCipherSpec & Finished**: 服务器响应。
    - `ChangeCipherSpec`: 通知客户端，后续通信将使用加密。
    - `Finished`: 发送一个加密的握手摘要，供客户端验证。

握手完成后，双方使用协商好的会话密钥进行加密通信。

### 17. 对称加密和非对称加密在HTTPS中是如何应用的？

HTTPS采用的是**混合加密**的策略，结合了两者的优点：

- **非对称加密**: 用于在TLS握手阶段安全地协商密钥。
    - **作用**: 解决密钥交换问题。客户端用服务器的公钥加密一个随机数（Pre-Master Secret），只有拥有私钥的服务器才能解密。
    - **优点**: 安全性高，可以安全地在不安全的信道上传输密钥。
    - **缺点**: 计算速度慢，不适合加密大量数据。

- **对称加密**: 用于在握手结束后的实际数据传输阶段。
    - **作用**: 加密/解密HTTP请求和响应的报文内容。
    - **优点**: 计算速度快，适合加密大量数据。
    - **缺点**: 密钥分发困难，如果密钥泄露则加密失效。

通过混合加密，HTTPS既保证了密钥交换的安全性，又保证了数据传输的高效性。

### 18. 什么是数字证书和证书链？

- **数字证书**: 是一个由权威的、受信任的第三方机构——证书颁发机构（CA）签发的电子文件。它将一个公钥与一个实体（如网站域名）的身份信息绑定在一起。
    - **内容**: 包含公钥、持有者信息、CA信息、有效期、CA的数字签名等。
    - **作用**: 证明公钥的归属，防止中间人攻击者用自己的公钥冒充服务器。

- **证书链 (Certificate Chain)**: 是一个证书的层级结构，用于验证一个证书的有效性。
    - **结构**: `终端实体证书 -> 中间CA证书 -> ... -> 根CA证书`。
    - **验证过程**: 客户端收到服务器的证书（终端实体证书）后，会用其颁发者（中间CA）的公钥来验证其签名。如果中间CA证书不是根证书，客户端会继续查找中间CA证书的颁发者，直到找到一个客户端操作系统或浏览器内置的、无条件信任的**根CA证书**为止。通过这样一层层向上验证，构成了一条信任链。只要链条上的所有证书都有效，最终的服务器证书就被认为是可信的。

### 19. 什么是中间人攻击？HTTPS如何防范？

- **中间人攻击 (Man-in-the-Middle Attack, MITM)**: 攻击者介入客户端和服务器的通信链路中，截获并可能篡改双方的通信内容。在HTTP中，攻击者可以轻易地窃听和修改数据。在HTTPS场景下，攻击者会尝试用自己的证书替换服务器的证书。

- **HTTPS的防范机制**:
    1.  **数字证书**: HTTPS的核心防范手段。当客户端与服务器建立TLS连接时，服务器会提供其数字证书。
    2.  **证书验证**: 客户端（浏览器）会严格验证该证书：
        - **检查有效期**: 确保证书未过期。
        - **检查域名**: 确保证书中的域名与正在访问的网站域名匹配。
        - **检查证书链**: 验证证书是否由一个受信任的CA签发。浏览器会使用内置的根CA公钥来验证证书链，直到根CA。
    3.  **警告用户**: 如果证书验证失败（例如，证书是自签名的，或由不受信任的CA签发），浏览器会向用户显示一个非常醒目的安全警告，阻止用户继续访问。

因此，只要用户不忽略浏览器的安全警告，HTTPS就能有效地防范中间人攻击。



### 21. Cookie和Session的区别与联系是什么？

Cookie和Session都是用来在无状态的HTTP协议中维持会话状态的机制。

- **存储位置**:
    - **Cookie**: 数据存储在**客户端**（浏览器）中。
    - **Session**: 数据存储在**服务器端**。

- **工作原理**:
    - **Cookie**: 服务器通过`Set-Cookie`响应头将少量数据发送到客户端，浏览器将其保存。之后每次请求，浏览器都会通过`Cookie`请求头将这些数据发回服务器。
    - **Session**: 服务器为每个用户创建一个Session对象，并生成一个唯一的`Session ID`。服务器将这个`Session ID`通过Cookie发送给客户端。客户端后续请求只需带上这个`Session ID`，服务器根据ID找到对应的Session数据。

- **安全性**:
    - **Cookie**: 数据存储在客户端，相对不安全，容易被篡改或窃取。
    - **Session**: 数据存储在服务器端，只在客户端保存一个无意义的ID，相对更安全。

- **存储大小与类型**:
    - **Cookie**: 大小受限（通常4KB），只能存储字符串。
    - **Session**: 理论上无大小限制，可以存储任意类型的对象。

- **对服务器的压力**:
    - **Cookie**: 无压力，状态由客户端维护。
    - **Session**: 会占用服务器的内存资源，用户量大时压力较大。

**联系**: Session机制通常依赖于Cookie来实现`Session ID`的传递。

### 22. Cookie有哪些安全问题？如何防范？

**安全问题**:
1.  **跨站脚本攻击 (XSS)**: 攻击者通过注入恶意脚本，可以利用`document.cookie`窃取用户的Cookie。
2.  **跨站请求伪造 (CSRF)**: 攻击者诱导用户在登录状态下访问一个恶意网站，该网站可以利用用户的Cookie向被攻击网站发送伪造的请求。
3.  **会话固定 (Session Fixation)**: 攻击者在用户登录前，先获取一个合法的Session ID，并诱导用户使用这个ID进行登录，从而劫持用户的会话。
4.  **信息泄露**: Cookie在HTTP下是明文传输的，容易被中间人窃听。

**防范措施**:
1.  **`HttpOnly`属性**: 设置此属性后，Cookie不能通过JavaScript的`document.cookie` API访问，可以有效防止XSS攻击窃取Cookie。
2.  **`Secure`属性**: 设置此属性后，Cookie只在HTTPS连接中被发送，防止在HTTP连接中被窃听。
3.  **`SameSite`属性**: 控制Cookie在跨站请求中是否被发送，是防御CSRF攻击的有效手段。
    - `Strict`: 完全禁止第三方Cookie。
    - `Lax`: 允许导航到目标网站时发送Cookie。
    - `None`: 允许第三方Cookie，但必须同时设置`Secure`属性。
4.  **设置合理的`Expires`或`Max-Age`**: 减少Cookie的生命周期，降低被盗用的风险。
5.  **对敏感信息加密**: 不要在Cookie中存储明文的敏感信息。

### 23. Token认证(如JWT)和Session认证有什么区别？

- **状态**:
    - **Session**: 是**有状态的**。服务器需要存储Session信息，通常在内存或数据库中。
    - **Token**: 是**无状态的**。服务器不需要存储Token信息。Token本身包含了所有需要验证的信息（如用户信息、权限、过期时间），服务器只需验证Token的签名即可。

- **可扩展性**:
    - **Session**: 在分布式系统中，需要处理Session共享问题，例如使用粘性Session、Session复制或集中式Session存储（如Redis），扩展性较差。
    - **Token**: 由于无状态，天然适用于分布式系统和微服务架构，服务器之间无需共享任何状态。

- **安全性**:
    - **Session**: `Session ID`存储在Cookie中，面临CSRF等攻击。
    - **Token (JWT)**: Token可以存储在任何地方（如`localStorage`），如果存储在Cookie中，同样面临CSRF风险。JWT本身通过签名来防止篡改。

- **性能**:
    - **Session**: 每次请求都需要查询服务器端的Session存储，有一定开销。
    - **Token**: 服务器只需进行签名验证，通常是CPU密集型操作，无需IO查询，性能较好。

- **适用场景**:
    - **Session**: 适用于单体应用或状态管理不复杂的场景。
    - **Token**: 适用于移动应用（App）、单页应用（SPA）、API接口、微服务等无状态、跨域的场景。

### 24. 描述HTTP的缓存机制（强缓存与协商缓存）。

HTTP缓存是提升Web性能的重要机制，分为**强缓存**和**协商缓存**。浏览器在发起请求时，会先检查强缓存，如果命中则直接使用缓存；如果强缓存失效，则进入协商缓存阶段。

- **强缓存 (Strong Cache)**:
    - 浏览器判断缓存是否过期，如果未过期，则**不向服务器发送请求**，直接从本地缓存读取资源，HTTP状态码为`200 (from disk cache/memory cache)`。
    - 控制字段：
        - **`Expires` (HTTP/1.0)**: 一个绝对时间的GMT格式字符串，表示资源的过期时间。缺点是依赖于客户端本地时间，可能不准确。
        - **`Cache-Control` (HTTP/1.1)**: 一个相对时间，通过`max-age=秒`指令指定资源的有效时长。优先级高于`Expires`。

- **协商缓存 (Negotiation Cache)**:
    - 强缓存失效后，浏览器向服务器发送一个请求，服务器根据请求中的缓存标识来判断资源是否更新。
    - 如果资源**未更新**，服务器返回`304 Not Modified`状态码，响应体为空，浏览器继续使用本地缓存。
    - 如果资源**已更新**，服务器返回`200 OK`状态码和新的资源内容。
    - 控制字段（成对出现）：
        - **`Last-Modified` / `If-Modified-Since`**:
            - 服务器在响应头中通过`Last-Modified`告知资源的最后修改时间。
            - 浏览器在下次请求时通过`If-Modified-Since`将这个时间发回服务器，服务器进行比对。
        - **`ETag` / `If-None-Match`**:
            - 服务器在响应头中通过`ETag`提供一个资源的唯一标识（类似指纹）。
            - 浏览器在下次请求时通过`If-None-Match`将这个标识发回服务器，服务器进行比对。`ETag`比`Last-Modified`更精确。

### 25. `Cache-Control`有哪些常用指令？

`Cache-Control`是控制缓存行为的核心指令，可以用于请求和响应。

**常用指令**:
- **`public`**: 表示响应可以被任何对象（包括浏览器、代理服务器等）缓存。
- **`private`**: 表示响应只能被单个用户（通常是浏览器）缓存，不能被共享缓存（如代理服务器）缓存。
- **`no-cache`**: 强制进行协商缓存。浏览器在使用缓存前，必须向服务器发送请求验证资源是否过期。
- **`no-store`**: 完全禁止缓存。浏览器和代理服务器都不能缓存该响应的任何部分。
- **`max-age=<seconds>`**: 设置缓存的最大有效时间（秒）。在此时间内，浏览器可直接使用强缓存。
- **`s-maxage=<seconds>`**: 类似于`max-age`，但仅适用于共享缓存（如CDN、代理）。
- **`must-revalidate`**: 一旦缓存过期，必须向源服务器验证其有效性，验证失败则不能使用。

### 28. 从浏览器地址栏输入URL到页面加载完成，中间发生了什么？

这是一个宏大的过程，可以概括为以下几个主要步骤：

1.  **URL解析**: 浏览器解析用户输入的URL，判断协议、域名、端口、路径等。
2.  **缓存检查**: 浏览器检查本地缓存（强缓存和协商缓存），如果命中且有效，则直接从缓存加载页面，过程结束。
3.  **DNS解析**: 如果缓存未命中，浏览器发起DNS请求，将域名解析为对应的IP地址。过程包括：浏览器缓存 -> 系统缓存 -> 路由器缓存 -> ISP DNS缓存 -> 根DNS服务器 -> ... 递归或迭代查询。
4.  **建立TCP连接**: 浏览器根据IP地址和端口号，与服务器进行TCP三次握手，建立TCP连接。
5.  **发起HTTPS握手**: 如果是HTTPS协议，在TCP连接建立后，进行TLS握手，协商加密参数，建立安全连接。
6.  **发起HTTP请求**: 浏览器构建HTTP请求报文，通过建立的连接发送给服务器。
7.  **服务器处理请求并响应**: 服务器接收并处理请求，生成HTTP响应报文（包含状态码、响应头、响应体），发送给浏览器。
8.  **浏览器接收响应并解析**: 浏览器接收HTTP响应。
9.  **断开连接**: 根据`Connection`头的值（`keep-alive`或`close`），决定是保持连接还是进行TCP四次挥手断开连接。
10. **渲染页面**:
    - 浏览器解析HTML，构建DOM树。
    - 解析CSS，构建CSSOM树。
    - 将DOM和CSSOM合并，构建渲染树（Render Tree）。
    - **布局 (Layout/Reflow)**: 根据渲染树计算每个节点的位置和大小。
    - **绘制 (Paint)**: 将节点绘制到屏幕上。
    - **处理JavaScript**: 解析和执行JavaScript代码，可能会修改DOM和CSSOM，导致重排（Reflow）和重绘（Repaint）。
### 31. 什么是WebSocket？它与HTTP有什么关系？

- **WebSocket**: 是一种在单个TCP连接上进行**全双工通信**的协议。它允许服务器主动向客户端推送数据，也允许客户端主动向服务器发送数据。
- **与HTTP的关系**:
    1.  **依赖关系**: WebSocket的**握手阶段是基于HTTP协议**的。客户端发起一个特殊的HTTP请求（包含`Upgrade: websocket`和`Connection: Upgrade`等头部），请求将连接从HTTP升级到WebSocket。
    2.  **协议切换**: 如果服务器同意升级，会返回一个`101 Switching Protocols`状态码的HTTP响应。此后，该TCP连接的通信协议就从HTTP切换到了WebSocket。
    3.  **独立性**: 一旦握手成功，后续的数据传输就完全按照WebSocket的协议格式进行，与HTTP再无关系。
- **主要区别**:
    - **通信方式**: HTTP是半双工的（客户端请求，服务器响应）。WebSocket是全双工的（双方可以随时互相发送数据）。
    - **协议开销**: HTTP请求包含冗长的头部。WebSocket连接建立后，数据帧的头部非常小，开销低。
    - **适用场景**: HTTP适用于一次性的请求-响应场景。WebSocket适用于需要实时、高频、双向通信的场景，如在线游戏、聊天室、实时数据推送等。

### 32. 什么是HTTP代理？正向代理和反向代理的区别是什么？

- **HTTP代理**: 是一个位于客户端和服务器之间的服务器，它接收客户端的请求，并将其转发给目标服务器，然后将服务器的响应返回给客户端。

- **正向代理 (Forward Proxy)**:
    - **为客户端服务**: 代理的是**客户端**。客户端明确知道要访问的目标服务器，但通过代理服务器来发起请求。
    - **作用**:
        1.  **访问限制资源**: 突破防火墙或访问内部网络（俗称“翻墙”）。
        2.  **隐藏客户端身份**: 服务器只知道是代理服务器在访问，不知道真实的客户端是谁。
        3.  **缓存**: 缓存资源，加速访问。
    - **例子**: 公司的上网网关、VPN。

- **反向代理 (Reverse Proxy)**:
    - **为服务器服务**: 代理的是**服务器**。客户端只知道反向代理服务器的地址，并认为它就是目标服务器。至于请求最终由哪个后端服务器处理，由反向代理决定。
    - **作用**:
        1.  **负载均衡**: 将请求分发到多个后端服务器，分担压力。
        2.  **隐藏服务器身份和结构**: 保护后端服务器不被直接暴露。
        3.  **安全防护**: 作为防火墙，抵御网络攻击。
        4.  **缓存**: 缓存静态内容，提升性能。
    - **例子**: Nginx、HAProxy。

### 33. RESTful API的设计原则是什么？

REST (Representational State Transfer) 是一种软件架构风格，而不是一个标准。RESTful API是遵循REST原则设计的API。

**主要设计原则 (约束)**:
1.  **客户端-服务器 (Client-Server)**: 客户端和服务器的角色是分离的。
2.  **无状态 (Stateless)**: 服务器不保存客户端的会话状态。每个请求都必须包含所有必要的信息，以便服务器能够理解和处理它。
3.  **可缓存 (Cacheable)**: 响应必须能够被标记为可缓存或不可缓存。
4.  **统一接口 (Uniform Interface)**: 这是REST的核心原则，包含四个子约束：
    - **资源标识**: 通过URI来标识资源。
    - **通过表述来操作资源**: 客户端通过获取资源的表述（如JSON、XML）来操作资源。
    - **自描述消息**: 每个消息都包含足够的信息来描述如何处理它。
    - **超媒体作为应用状态的引擎 (HATEOAS)**: 响应中应包含链接，指导客户端可以进行哪些下一步操作。
5.  **分层系统 (Layered System)**: 客户端通常不知道它是否与最终服务器直接连接，或者与中间的代理、负载均衡器等连接。
6.  **按需代码 (Code on Demand)**: 可选约束。服务器可以临时扩展或自定义客户端的功能，通过传输可执行代码（如JavaScript）的方式。

### 34. 简述XSS和CSRF攻击的原理和防范方法。

- **XSS (Cross-Site Scripting, 跨站脚本攻击)**:
    - **原理**: 攻击者向Web页面注入恶意的JavaScript脚本。当其他用户浏览该页面时，这些脚本会在用户的浏览器中执行，从而窃取用户信息（如Cookie）、劫持会话或执行其他恶意操作。
    - **类型**:
        - **存储型XSS**: 恶意脚本被存储在服务器数据库中。
        - **反射型XSS**: 恶意脚本作为URL参数，诱导用户点击后在浏览器中执行。
        - **DOM型XSS**: 通过修改DOM来触发的XSS。
    - **防范**:
        1.  **输入验证**: 对用户输入进行严格的过滤和验证。
        2.  **输出转义**: 在将数据显示到HTML页面时，对特殊字符（如`<`, `>`, `&`, `"`）进行HTML实体转义。
        3.  **内容安全策略 (CSP)**: 使用HTTP头`Content-Security-Policy`来限制页面可以加载和执行的资源。
        4.  **HttpOnly Cookie**: 设置Cookie的`HttpOnly`属性，防止脚本窃取。

- **CSRF (Cross-Site Request Forgery, 跨站请求伪造)**:
    - **原理**: 攻击者诱导已登录的用户在不知情的情况下，访问一个包含伪造请求的恶意页面。浏览器会自动携带用户的Cookie等凭证去请求被攻击的网站，从而以用户的名义执行非预期的操作（如转账、修改密码）。攻击者只“伪造请求”，而不“窃取数据”。
    - **防范**:
        1.  **验证Referer**: 检查HTTP请求头中的`Referer`字段，判断请求来源是否合法。
        2.  **使用CSRF Token**: 在用户访问表单页面时，服务器生成一个随机的Token并嵌入表单中。提交时，服务器验证该Token是否匹配。攻击者无法获取这个Token。
        3.  **SameSite Cookie属性**: 将Cookie的`SameSite`属性设置为`Strict`或`Lax`，可以阻止浏览器在跨站请求中发送Cookie。
        4.  **二次验证**: 对于关键操作，要求用户输入密码或验证码进行二次确认。



### 8. HTTP状态码有哪些类别？列举5个常见的状态码。

HTTP状态码分为五大类：
- **1xx (信息性状态码)**: 表示请求已接收，继续处理。
- **2xx (成功状态码)**: 表示请求已成功被服务器接收、理解、并接受。
- **3xx (重定向状态码)**: 表示要完成请求，需要进一步操作。
- **4xx (客户端错误状态码)**: 表示客户端请求有语法错误或请求无法实现。
- **5xx (服务器错误状态码)**: 表示服务器未能实现合法的请求。

**5个常见的状态码**:
1.  **200 OK**: 请求成功。
2.  **301 Moved Permanently**: 永久重定向。
3.  **304 Not Modified**: 资源未修改，客户端可以使用缓存。
4.  **404 Not Found**: 请求的资源在服务器上未找到。
5.  **500 Internal Server Error**: 服务器内部错误。

### 9. 301和302重定向有什么区别？

- **301 Moved Permanently (永久重定向)**:
    - 表示请求的资源已永久移动到新的URL。
    - 浏览器会缓存这个重定向，下次请求会自动访问新的URL。
    - 对SEO友好，搜索引擎会将权重从旧地址转移到新地址。

- **302 Found (临时重定向)**:
    - 表示请求的资源临时从不同的URL响应。
    - 浏览器不会缓存这个重定向，每次都会请求原始URL。
    - SEO不友好，搜索引擎不会更新其索引。

### 10. 列举5个常见的HTTP请求头和响应头。

**常见请求头 (Request Headers)**:
1.  `Host`: 指定服务器的域名。
2.  `User-Agent`: 客户端的身份标识（浏览器信息）。
3.  `Accept`: 客户端可接受的内容类型。
4.  `Cookie`: 客户端携带的Cookie信息。
5.  `Content-Type`: 请求体的媒体类型（用于POST/PUT请求）。

**常见响应头 (Response Headers)**:
1.  `Content-Type`: 响应体的媒体类型。
2.  `Content-Length`: 响应体的长度。
3.  `Cache-Control`: 控制缓存策略。
4.  `Set-Cookie`: 服务器向客户端下发Cookie。
5.  `Location`: 指定重定向的目标URL（用于3xx状态码）。


### 11. 什么是HTTP持久连接(Keep-Alive)？

HTTP持久连接（也称HTTP长连接）是HTTP/1.1引入的特性。它允许在一次TCP连接上发送和接收多个HTTP请求/响应，而不是为每个请求/响应对都建立一个新的TCP连接。这减少了TCP连接建立（三次握手）和断开（四次挥手）的开销，提高了性能。HTTP/1.1默认开启持久连接。

### 12. 什么是HTTP队头阻塞(Head-of-line blocking)问题？如何解决？

- **HTTP/1.1的队头阻塞**: 在一个持久连接上，请求是顺序发送的，服务器也必须按接收请求的顺序返回响应。如果第一个响应因为处理时间长而延迟，那么后续的响应即使已经处理完毕，也必须等待它发送完成后才能发送。这就阻塞了后续的响应。
- **HTTP/2的队头阻塞**: HTTP/2通过多路复用解决了HTTP层的队头阻塞，但它基于TCP协议，TCP本身存在队头阻塞。TCP是一个可靠的、按序的协议，如果一个TCP报文段丢失，TCP会等待该报文段重传，这会阻塞该TCP连接上的所有HTTP/2流。
- **解决方案**: HTTP/3使用QUIC协议代替TCP。QUIC基于UDP，实现了自己的可靠传输和多路复用机制。QUIC的流是独立的，一个流的丢包不会阻塞其他流，从而彻底解决了队头阻塞问题。

### 13. HTTP/3为什么使用QUIC协议？它解决了什么问题？

HTTP/3使用QUIC协议主要是为了解决HTTP/2中存在的基于TCP的队头阻塞问题，并提升性能。

**QUIC解决的问题**:
1.  **队头阻塞**: QUIC基于UDP，其多路复用是在协议内部实现的，多个流之间相互独立。一个流的数据包丢失不会影响其他流的传输。
2.  **连接建立延迟**: QUIC将TCP握手和TLS握手（基于TLS 1.3）结合在一起，大部分情况下只需要1个RTT就可以完成连接建立和密钥协商，甚至可以实现0-RTT快速重连。
3.  **连接迁移**: TCP连接由四元组（源IP、源端口、目的IP、目的端口）标识。当网络切换时（如手机从Wi-Fi切换到4G），IP地址改变，TCP连接会中断。QUIC使用一个64位的连接ID来标识连接，即使IP地址改变，只要连接ID不变，连接就可以继续，实现了无缝的连接迁移。

### 14. 什么是CDN？简述其工作原理。

- **CDN (Content Delivery Network, 内容分发网络)**: 是一个由分布在不同地理位置的服务器组成的网络，用于更快速、可靠地将静态内容（如图片、CSS、JS文件、视频）分发给用户。
- **工作原理**:
    1.  当用户首次请求一个资源时，请求会发送到源服务器。
    2.  源服务器将资源响应给用户的同时，也会将资源缓存到离用户最近的CDN边缘节点服务器上。
    3.  当其他用户或同一用户再次请求相同资源时，用户的请求会被DNS解析到最近的CDN边缘节点。
    4.  如果边缘节点有该资源的缓存，则直接从边缘节点返回给用户，无需再请求源服务器。这大大减少了延迟，并减轻了源服务器的负载。


### 15. HTTPS是如何保证数据传输安全的？请描述其核心流程。

HTTPS通过在HTTP和TCP之间加入SSL/TLS协议层来保证数据传输安全。它主要解决了三大风险：窃听、篡改和冒充。

**核心保障机制**:
1.  **机密性 (防窃听)**: 使用**混合加密**。在TLS握手阶段，使用非对称加密来安全地协商出一个对称加密的“会话密钥”。握手结束后，所有应用数据都使用这个会话密钥进行对称加密，保证了传输效率和安全性。
2.  **完整性 (防篡改)**: 使用**消息认证码 (MAC)**，通常是基于哈希算法（如SHA-256）实现的。发送方对数据计算一个摘要并与数据一同发送，接收方用同样的方法计算摘要并进行比对，确保数据未被篡改。
3.  **真实性 (防冒充)**: 使用**数字证书**。服务器持有一个由受信任的CA（证书颁发机构）签发的数字证书。证书中包含了服务器的公钥和身份信息。客户端在握手时会验证证书的有效性（通过证书链和CA签名），从而确认服务器的身份是真实可信的。

### 16. 简述SSL/TLS的握手过程。

以TLS 1.2的RSA握手为例，过程主要分为四步（2个RTT）：

1.  **ClientHello**: 客户端向服务器发送问候。包含：支持的TLS版本、一个客户端随机数`Client Random`、支持的密码套件列表。
2.  **ServerHello & Certificate & ServerHelloDone**: 服务器响应。
    - `ServerHello`: 确认TLS版本、一个服务器随机数`Server Random`、从客户端列表中选择一个密码套件。
    - `Certificate`: 发送服务器的数字证书（包含公钥）。
    - `ServerHelloDone`: 告知客户端，服务器的初始信息发送完毕。
3.  **ClientKeyExchange & ChangeCipherSpec & Finished**: 客户端响应。
    - 客户端验证服务器证书。
    - `ClientKeyExchange`: 生成第三个随机数`Pre-Master Secret`，用服务器的公钥加密后发送给服务器。
    - 客户端和服务器使用`Client Random`、`Server Random`和`Pre-Master Secret`各自生成对称的“会话密钥”。
    - `ChangeCipherSpec`: 通知服务器，后续通信将使用加密。
    - `Finished`: 发送一个加密的握手摘要，供服务器验证。
4.  **ChangeCipherSpec & Finished**: 服务器响应。
    - `ChangeCipherSpec`: 通知客户端，后续通信将使用加密。
    - `Finished`: 发送一个加密的握手摘要，供客户端验证。

握手完成后，双方使用协商好的会话密钥进行加密通信。

### 17. 对称加密和非对称加密在HTTPS中是如何应用的？

HTTPS采用的是**混合加密**的策略，结合了两者的优点：

- **非对称加密**: 用于在TLS握手阶段安全地协商密钥。
    - **作用**: 解决密钥交换问题。客户端用服务器的公钥加密一个随机数（Pre-Master Secret），只有拥有私钥的服务器才能解密。
    - **优点**: 安全性高，可以安全地在不安全的信道上传输密钥。
    - **缺点**: 计算速度慢，不适合加密大量数据。

- **对称加密**: 用于在握手结束后的实际数据传输阶段。
    - **作用**: 加密/解密HTTP请求和响应的报文内容。
    - **优点**: 计算速度快，适合加密大量数据。
    - **缺点**: 密钥分发困难，如果密钥泄露则加密失效。

通过混合加密，HTTPS既保证了密钥交换的安全性，又保证了数据传输的高效性。

### 18. 什么是数字证书和证书链？

- **数字证书**: 是一个由权威的、受信任的第三方机构——证书颁发机构（CA）签发的电子文件。它将一个公钥与一个实体（如网站域名）的身份信息绑定在一起。
    - **内容**: 包含公钥、持有者信息、CA信息、有效期、CA的数字签名等。
    - **作用**: 证明公钥的归属，防止中间人攻击者用自己的公钥冒充服务器。

- **证书链 (Certificate Chain)**: 是一个证书的层级结构，用于验证一个证书的有效性。
    - **结构**: `终端实体证书 -> 中间CA证书 -> ... -> 根CA证书`。
    - **验证过程**: 客户端收到服务器的证书（终端实体证书）后，会用其颁发者（中间CA）的公钥来验证其签名。如果中间CA证书不是根证书，客户端会继续查找中间CA证书的颁发者，直到找到一个客户端操作系统或浏览器内置的、无条件信任的**根CA证书**为止。通过这样一层层向上验证，构成了一条信任链。只要链条上的所有证书都有效，最终的服务器证书就被认为是可信的。

### 19. 什么是中间人攻击？HTTPS如何防范？

- **中间人攻击 (Man-in-the-Middle Attack, MITM)**: 攻击者介入客户端和服务器的通信链路中，截获并可能篡改双方的通信内容。在HTTP中，攻击者可以轻易地窃听和修改数据。在HTTPS场景下，攻击者会尝试用自己的证书替换服务器的证书。

- **HTTPS的防范机制**:
    1.  **数字证书**: HTTPS的核心防范手段。当客户端与服务器建立TLS连接时，服务器会提供其数字证书。
    2.  **证书验证**: 客户端（浏览器）会严格验证该证书：
        - **检查有效期**: 确保证书未过期。
        - **检查域名**: 确保证书中的域名与正在访问的网站域名匹配。
        - **检查证书链**: 验证证书是否由一个受信任的CA签发。浏览器会使用内置的根CA公钥来验证证书链，直到根CA。
    3.  **警告用户**: 如果证书验证失败（例如，证书是自签名的，或由不受信任的CA签发），浏览器会向用户显示一个非常醒目的安全警告，阻止用户继续访问。

因此，只要用户不忽略浏览器的安全警告，HTTPS就能有效地防范中间人攻击。

### 20. 什么是HTTP严格传输安全(HSTS)？

HTTP Strict Transport Security (HSTS) 是一个Web安全策略机制。它通过一个HTTP响应头 (`Strict-Transport-Security`) 告诉浏览器，该网站在未来的一段时间内（由`max-age`指定）**必须且只能**通过HTTPS进行访问。

- **工作流程**:
    1.  用户首次通过HTTPS访问一个启用了HSTS的网站。
    2.  服务器响应时包含`Strict-Transport-Security`头。
    3.  浏览器记录下这个策略。
    4.  在`max-age`有效期内，即使用户尝试通过HTTP（如在地址栏输入`http://`或点击一个HTTP链接）访问该网站，浏览器也会在内部自动将请求转换为HTTPS请求，而不会真正发出HTTP请求。
- **作用**:
    - 防止协议降级攻击。
    - 防止中间人攻击者在用户首次访问时将会话从HTTPS劫持到HTTP。
    - 提升安全性，强制全程使用HTTPS。


### 21. Cookie和Session的区别与联系是什么？

Cookie和Session都是用来在无状态的HTTP协议中维持会话状态的机制。

- **存储位置**:
    - **Cookie**: 数据存储在**客户端**（浏览器）中。
    - **Session**: 数据存储在**服务器端**。

- **工作原理**:
    - **Cookie**: 服务器通过`Set-Cookie`响应头将少量数据发送到客户端，浏览器将其保存。之后每次请求，浏览器都会通过`Cookie`请求头将这些数据发回服务器。
    - **Session**: 服务器为每个用户创建一个Session对象，并生成一个唯一的`Session ID`。服务器将这个`Session ID`通过Cookie发送给客户端。客户端后续请求只需带上这个`Session ID`，服务器根据ID找到对应的Session数据。

- **安全性**:
    - **Cookie**: 数据存储在客户端，相对不安全，容易被篡改或窃取。
    - **Session**: 数据存储在服务器端，只在客户端保存一个无意义的ID，相对更安全。

- **存储大小与类型**:
    - **Cookie**: 大小受限（通常4KB），只能存储字符串。
    - **Session**: 理论上无大小限制，可以存储任意类型的对象。

- **对服务器的压力**:
    - **Cookie**: 无压力，状态由客户端维护。
    - **Session**: 会占用服务器的内存资源，用户量大时压力较大。

**联系**: Session机制通常依赖于Cookie来实现`Session ID`的传递。

### 22. Cookie有哪些安全问题？如何防范？

**安全问题**:
1.  **跨站脚本攻击 (XSS)**: 攻击者通过注入恶意脚本，可以利用`document.cookie`窃取用户的Cookie。
2.  **跨站请求伪造 (CSRF)**: 攻击者诱导用户在登录状态下访问一个恶意网站，该网站可以利用用户的Cookie向被攻击网站发送伪造的请求。
3.  **会话固定 (Session Fixation)**: 攻击者在用户登录前，先获取一个合法的Session ID，并诱导用户使用这个ID进行登录，从而劫持用户的会话。
4.  **信息泄露**: Cookie在HTTP下是明文传输的，容易被中间人窃听。

**防范措施**:
1.  **`HttpOnly`属性**: 设置此属性后，Cookie不能通过JavaScript的`document.cookie` API访问，可以有效防止XSS攻击窃取Cookie。
2.  **`Secure`属性**: 设置此属性后，Cookie只在HTTPS连接中被发送，防止在HTTP连接中被窃听。
3.  **`SameSite`属性**: 控制Cookie在跨站请求中是否被发送，是防御CSRF攻击的有效手段。
    - `Strict`: 完全禁止第三方Cookie。
    - `Lax`: 允许导航到目标网站时发送Cookie。
    - `None`: 允许第三方Cookie，但必须同时设置`Secure`属性。
4.  **设置合理的`Expires`或`Max-Age`**: 减少Cookie的生命周期，降低被盗用的风险。
5.  **对敏感信息加密**: 不要在Cookie中存储明文的敏感信息。

### 23. Token认证(如JWT)和Session认证有什么区别？

- **状态**:
    - **Session**: 是**有状态的**。服务器需要存储Session信息，通常在内存或数据库中。
    - **Token**: 是**无状态的**。服务器不需要存储Token信息。Token本身包含了所有需要验证的信息（如用户信息、权限、过期时间），服务器只需验证Token的签名即可。

- **可扩展性**:
    - **Session**: 在分布式系统中，需要处理Session共享问题，例如使用粘性Session、Session复制或集中式Session存储（如Redis），扩展性较差。
    - **Token**: 由于无状态，天然适用于分布式系统和微服务架构，服务器之间无需共享任何状态。

- **安全性**:
    - **Session**: `Session ID`存储在Cookie中，面临CSRF等攻击。
    - **Token (JWT)**: Token可以存储在任何地方（如`localStorage`），如果存储在Cookie中，同样面临CSRF风险。JWT本身通过签名来防止篡改。

- **性能**:
    - **Session**: 每次请求都需要查询服务器端的Session存储，有一定开销。
    - **Token**: 服务器只需进行签名验证，通常是CPU密集型操作，无需IO查询，性能较好。

- **适用场景**:
    - **Session**: 适用于单体应用或状态管理不复杂的场景。
    - **Token**: 适用于移动应用（App）、单页应用（SPA）、API接口、微服务等无状态、跨域的场景。


### 28. 从浏览器地址栏输入URL到页面加载完成，中间发生了什么？

这是一个宏大的过程，可以概括为以下几个主要步骤：

1.  **URL解析**: 浏览器解析用户输入的URL，判断协议、域名、端口、路径等。
2.  **缓存检查**: 浏览器检查本地缓存（强缓存和协商缓存），如果命中且有效，则直接从缓存加载页面，过程结束。
3.  **DNS解析**: 如果缓存未命中，浏览器发起DNS请求，将域名解析为对应的IP地址。过程包括：浏览器缓存 -> 系统缓存 -> 路由器缓存 -> ISP DNS缓存 -> 根DNS服务器 -> ... 递归或迭代查询。
4.  **建立TCP连接**: 浏览器根据IP地址和端口号，与服务器进行TCP三次握手，建立TCP连接。
5.  **发起HTTPS握手**: 如果是HTTPS协议，在TCP连接建立后，进行TLS握手，协商加密参数，建立安全连接。
6.  **发起HTTP请求**: 浏览器构建HTTP请求报文，通过建立的连接发送给服务器。
7.  **服务器处理请求并响应**: 服务器接收并处理请求，生成HTTP响应报文（包含状态码、响应头、响应体），发送给浏览器。
8.  **浏览器接收响应并解析**: 浏览器接收HTTP响应。
9.  **断开连接**: 根据`Connection`头的值（`keep-alive`或`close`），决定是保持连接还是进行TCP四次挥手断开连接。
10. **渲染页面**:
    - 浏览器解析HTML，构建DOM树。
    - 解析CSS，构建CSSOM树。
    - 将DOM和CSSOM合并，构建渲染树（Render Tree）。
    - **布局 (Layout/Reflow)**: 根据渲染树计算每个节点的位置和大小。
    - **绘制 (Paint)**: 将节点绘制到屏幕上。
    - **处理JavaScript**: 解析和执行JavaScript代码，可能会修改DOM和CSSOM，导致重排（Reflow）和重绘（Repaint）。

### 29. 什么是跨域？列举至少三种解决跨域问题的方法。

- **跨域**: 指的是浏览器的**同源策略 (Same-Origin Policy)** 所施加的限制。当一个请求的URL的**协议、域名、端口**三者中任意一个与当前页面的URL不同时，就被视为跨域。同源策略限制了从一个源加载的文档或脚本如何与来自另一个源的资源进行交互，这是浏览器的一个核心安全功能，主要为了防止CSRF等攻击。

- **三种解决方法**:
    1.  **CORS (Cross-Origin Resource Sharing, 跨域资源共享)**:
        - 这是**W3C标准**，也是目前最主流和推荐的解决方案。
        - 服务器通过设置HTTP响应头（如`Access-Control-Allow-Origin`）来告知浏览器，允许哪些源的请求访问其资源。
    2.  **JSONP (JSON with Padding)**:
        - 一种利用`<script>`标签没有跨域限制的“漏洞”来实现的旧技术。
        - 只能用于**GET**请求。
        - 客户端定义一个回调函数，并通过URL参数传递给服务器。服务器返回一段执行该回调函数的JavaScript代码，并将数据作为参数传入。
        - 安全性较差，现在已不推荐使用。
    3.  **代理 (Proxy)**:
        - 在同源的服务器端设置一个代理服务，由该代理去请求跨域的资源，然后将结果返回给前端。
        - 对于前端来说，它请求的是同源的代理服务器，不存在跨域问题。跨域的请求由服务器端完成。
        - 在开发环境中，Webpack的`devServer`就提供了代理功能。在生产环境中，可以通过Nginx等反向代理服务器实现。


### 31. 什么是WebSocket？它与HTTP有什么关系？

- **WebSocket**: 是一种在单个TCP连接上进行**全双工通信**的协议。它允许服务器主动向客户端推送数据，也允许客户端主动向服务器发送数据。
- **与HTTP的关系**:
    1.  **依赖关系**: WebSocket的**握手阶段是基于HTTP协议**的。客户端发起一个特殊的HTTP请求（包含`Upgrade: websocket`和`Connection: Upgrade`等头部），请求将连接从HTTP升级到WebSocket。
    2.  **协议切换**: 如果服务器同意升级，会返回一个`101 Switching Protocols`状态码的HTTP响应。此后，该TCP连接的通信协议就从HTTP切换到了WebSocket。
    3.  **独立性**: 一旦握手成功，后续的数据传输就完全按照WebSocket的协议格式进行，与HTTP再无关系。
- **主要区别**:
    - **通信方式**: HTTP是半双工的（客户端请求，服务器响应）。WebSocket是全双工的（双方可以随时互相发送数据）。
    - **协议开销**: HTTP请求包含冗长的头部。WebSocket连接建立后，数据帧的头部非常小，开销低。
    - **适用场景**: HTTP适用于一次性的请求-响应场景。WebSocket适用于需要实时、高频、双向通信的场景，如在线游戏、聊天室、实时数据推送等。

### 32. 什么是HTTP代理？正向代理和反向代理的区别是什么？

- **HTTP代理**: 是一个位于客户端和服务器之间的服务器，它接收客户端的请求，并将其转发给目标服务器，然后将服务器的响应返回给客户端。

- **正向代理 (Forward Proxy)**:
    - **为客户端服务**: 代理的是**客户端**。客户端明确知道要访问的目标服务器，但通过代理服务器来发起请求。
    - **作用**:
        1.  **访问限制资源**: 突破防火墙或访问内部网络（俗称“翻墙”）。
        2.  **隐藏客户端身份**: 服务器只知道是代理服务器在访问，不知道真实的客户端是谁。
        3.  **缓存**: 缓存资源，加速访问。
    - **例子**: 公司的上网网关、VPN。

- **反向代理 (Reverse Proxy)**:
    - **为服务器服务**: 代理的是**服务器**。客户端只知道反向代理服务器的地址，并认为它就是目标服务器。至于请求最终由哪个后端服务器处理，由反向代理决定。
    - **作用**:
        1.  **负载均衡**: 将请求分发到多个后端服务器，分担压力。
        2.  **隐藏服务器身份和结构**: 保护后端服务器不被直接暴露。
        3.  **安全防护**: 作为防火墙，抵御网络攻击。
        4.  **缓存**: 缓存静态内容，提升性能。
    - **例子**: Nginx、HAProxy。
