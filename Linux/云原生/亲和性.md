# Kubernetes 调度进阶：亲和性与反亲和性 (Affinity & Anti-Affinity)

## 1. 核心认知与背景

在 Kubernetes 中，默认的 kube-scheduler 调度器会通过一系列算法（过滤、打分）为 Pod 选择最合适的 Node。
最初级的定向调度手段是 `nodeSelector`，但它具有明显的局限性：
- 只能实现**硬性匹配**（必须满足，否则 Pending）。
- 表达能力有限，只支持等值匹配。
- 只能基于 Node 的标签进行调度，无法感知集群中**其他 Pod** 的分布情况。

为了应对更复杂的微服务架构和高可用需求，K8s 引入了**亲和性（Affinity）**和**反亲和性（Anti-Affinity）**机制。它们极大地增强了调度的表达能力，是构建企业级高可用架构的基石。

从高级开发的架构视角来看，亲和性不仅仅是“把 Pod 放到哪”，更是**资源隔离、故障域（Fault Domain）打散、降低网络延迟**的核心策略。

---

## 2. 节点亲和性 (Node Affinity)

Node Affinity 是 `nodeSelector` 的升级版，用于限制 Pod 只能被调度到具备某些标签的 Node 上。

### 2.1 两种调度策略（硬/软限制）

K8s 调度语义非常严谨，目前节点亲和性包含两种规则：

1. **`requiredDuringSchedulingIgnoredDuringExecution` (硬亲和性)**：
   - **语义**：“必须满足”。如果找不到符合条件的 Node，Pod 将一直处于 Pending 状态。
   - **适用场景**：强依赖特定硬件（如 GPU 节点、SSD 磁盘）、数据合规性要求（必须在国内机房）。
2. **`preferredDuringSchedulingIgnoredDuringExecution` (软亲和性)**：
   - **语义**：“尽量满足”。调度器会尝试寻找匹配的 Node 并为其加分（权重 `weight` 1-100），如果没有符合的，也会退而求其次调度到其他 Node。
   - **适用场景**：优化类需求（如尽量调度到高主频 CPU 节点以加速计算，但没有也能跑）。

> **💡 提示**：`IgnoredDuringExecution` 意味着如果 Pod 已经调度成功，后续你修改了 Node 的 Label 导致其不再满足规则，系统**不会**驱逐（Evict）该 Pod。

### 2.2 操作符 (Operators)

支持比 `nodeSelector` 更丰富的逻辑判断：
- `In`, `NotIn`：标签值在/不在列表中。
- `Exists`, `DoesNotExist`：是否存在该标签的 Key（不关心 Value）。
- `Gt`, `Lt`：标签值大于/小于指定的数值（用于比较 CPU/内存等级）。

### 2.3 实操演练：节点亲和性

**场景**：我们有一个核心数据库 Pod，**必须**调度到带有 `disktype=ssd` 标签的节点，同时**优先**调度到区域 `zone=us-east-1` 的节点。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: node-affinity-pod
spec:
  affinity:
    nodeAffinity:
      # 1. 硬亲和性：必须是 SSD
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values:
            - ssd
      # 2. 软亲和性：尽量在 us-east-1，权重为 80
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - us-east-1
  containers:
  - name: db-container
    image: mysql:8.0
```

## 3. Pod 亲和性与反亲和性 (Pod Affinity & Anti-Affinity)

这是解决**服务间拓扑关系**的核心能力。它允许 Pod 根据**已经运行在集群上的其他 Pod 的标签**来决定自己的调度位置，而不是根据 Node 的标签。

- **Pod Affinity (亲和)**：“我和你关系好，我要和你部署在同一个地方”。（降低网络延迟，如 Web 与 Cache）
- **Pod Anti-Affinity (反亲和)**：“我们是同一个服务的多个副本，不能把鸡蛋放在同一个篮子里”。（高可用容灾打散）

### 3.1 核心概念：拓扑域 (Topology Domain)

在使用 Pod 亲/反亲和性时，必须指定一个极其重要的字段：`topologyKey`。
它定义了“同一个地方”的边界（范围）：
- `topologyKey: kubernetes.io/hostname`：以**单一 Node** 为边界。
- `topologyKey: topology.kubernetes.io/zone`：以**可用区 (Zone)** 为边界。
- `topologyKey: topology.kubernetes.io/region`：以**地域 (Region)** 为边界。

### 3.2 实操演练：Pod 亲和性 (紧密协作)

**场景**：前端 Web 服务需要极其频繁地访问 Redis 缓存，为了降低网络延迟，要求 Web Pod **必须**和包含标签 `app=redis` 的 Pod 调度到**同一台物理机（Node）**上。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        podAffinity:
          # 硬亲和：必须和 Redis 在同一个 Node
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - redis
            # 拓扑域：Node 级别
            topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx:alpine
```

### 3.3 实操演练：Pod 反亲和性 (高可用打散)

**场景**：为了保证高可用，同一个 Web 服务的 3 个副本，**绝对不能**部署在同一台机器上，防止单机宕机导致服务全挂。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-ha
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-ha
  template:
    metadata:
      labels:
        app: web-ha
    spec:
      affinity:
        podAntiAffinity:
          # 硬反亲和：不能和带 app=web-ha 标签的 Pod 呆在一起
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web-ha
            # 拓扑域：Node 级别
            topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: nginx:alpine
```

## 4. 架构设计考量与高级实践 (Senior Perspective)

作为高级开发/架构师，在应用这些规则时，需要考虑以下工程挑战和最佳实践：

### 4.1 大规模集群的调度器性能陷阱
在大规模集群（数百上千个 Node）中，**Pod 反亲和性（特别是配合 hostname 级别）会极大地消耗 kube-scheduler 的 CPU 资源**。
调度器需要遍历所有 Node，并检查其上的所有 Pod 标签来计算冲突，时间复杂度急剧上升。
- **最佳实践**：如果仅仅是为了将 Deployment 的副本打散以实现高可用，**在 K8s v1.19+ 版本后，强烈建议使用 `TopologySpreadConstraints` (拓扑分布约束)** 来代替 Pod Anti-Affinity。它在语义上更贴合“均匀打散”的需求，且调度算法优化得更好。

### 4.2 亲和性 vs 污点与容忍度 (Taints and Tolerations)
面试或架构设计中常问：这两者有何区别？
- **Node Affinity** 是 Pod 的主动选择（Pod 喜欢去哪里）。这不能阻止其他不需要这些特性的普通 Pod 也被调度到这个 Node 上。
- **Taints (污点)** 是 Node 的主动排斥（Node 拒绝没有对应 Toleration 的 Pod）。
- **结合使用**：如果要实现**专属节点组**（例如 10 台高配 GPU 机器只给 AI 训练组用，不接业务流量），必须结合两者：
  1. Node 打 Taint，拒绝普通业务 Pod。
  2. AI 训练 Pod 加上 Toleration 容忍污点。
  3. AI 训练 Pod 再加上 Node Affinity，确保它一定调度到这批 GPU 节点（防止它漂移到其他恰好没有打污点的普通节点）。

### 4.3 命名空间隔离限制
`podAffinity` 和 `podAntiAffinity` 默认只在 Pod 所在的 Namespace 内生效。如果需要基于其他 Namespace 的 Pod 进行亲和性调度，可以通过设置 `namespaces` 字段来跨命名空间匹配（但这增加了集群耦合度，需谨慎使用）。

## 5. 深度解析：topologyKey 的本质与作用

在配置 Pod 亲和性与反亲和性时，`topologyKey` 是一个**必填且极为核心**的字段。理解它，是构建高可用、高性能和成本优化的分布式架构的关键。

### 5.1 什么是 topologyKey？
从字面上看，它是“拓扑键”。在 K8s 底层，`topologyKey` 就是 **Node 上的一个 Label（标签）的 Key**。

K8s 集群中的每个节点都会携带描述自身物理或逻辑位置的标签（例如主机名、所在机房、所在可用区等）。调度器通过比对节点上这个特定 Label Key 的 Value 是否相同，来判断两个节点是否属于同一个**“拓扑域（Topology Domain）”**。

### 5.2 核心作用：划定“距离”与“边界”
我们在谈论“亲和（靠拢）”或“反亲和（远离）”时，必须先定义**边界**。`topologyKey` 的核心作用就是**划定这个生效边界的范围**。

- **亲和性场景**：`topologyKey` 定义了两个 Pod 靠得“有多近”算满足条件。
- **反亲和场景**：`topologyKey` 定义了两个 Pod 离得“有多远”才能实现故障隔离。

> **💡 一句话总结**：没有 `topologyKey`，调度器就不知道所谓的“在一起”或“不在一起”到底是指在同一台机器上，还是在同一个机房里。

### 5.3 常见取值与架构场景 (Senior Perspective)

作为高级开发/架构师，选择不同的 `topologyKey` 直接决定了系统的**容灾级别（RTO/RPO）**与**网络成本**：

#### 1. 机器级隔离：`kubernetes.io/hostname`
- **语义边界**：单台 Node（物理机或虚拟机）。只要两台 Node 的 hostname 标签值不同，它们就不在一个拓扑域。
- **反亲和场景（最常见）**：**防单机故障**。确保同一个微服务的多个副本绝对不会落在同一台机器上。如果机器宕机，最多只损失一个副本。
- **亲和场景**：**极致的低延迟通信**。如 Web 和本地 Redis 缓存必须在同一台机器上，以实现微秒级延迟。

#### 2. 机房/可用区级隔离：`topology.kubernetes.io/zone`
- **语义边界**：云厂商的可用区（Availability Zone，如北京一区 `cn-beijing-a`）。
- **反亲和场景**：**防机房级故障（同城多活架构）**。强制将应用副本打散分布到不同的可用区。即使整个 A 机房断电停摆，B 机房的副本依然能对外提供服务。
- **亲和场景**：**平衡延迟与云厂商流量费**。微服务跨可用区调用通常会产生 1-2ms 的网络延迟，且云厂商通常会收取**跨可用区内网流量费**。通过配置 zone 级别的亲和性，可以让核心调用链路上的微服务尽量保持在同一个可用区，从而显著降低延迟并节约成本。

#### 3. 地域级隔离：`topology.kubernetes.io/region`
- **语义边界**：云厂商的地域（Region，如北京、上海）。
- **反亲和场景**：**异地灾备（两地三中心架构）**。确保核心系统（如全局 DNS 或控制面）的不同实例分布在完全不同的城市，抵御城市级自然灾害。

### 5.4 调度器的底层计算逻辑
假设你设置了**反亲和性**，要求新调度的 Pod A 不能和带有 `app=web` 的老 Pod 处于同一个 `zone`。调度器是这样工作的：
1. **拿候选节点**：调度器评估一个候选 Node (比如 Node-X)。
2. **读拓扑标签**：读取 Node-X 上的 `topology.kubernetes.io/zone` 标签的值（假设为 `cn-beijing-a`）。
3. **找同域节点**：调度器去寻找集群中所有带有 `topology.kubernetes.io/zone=cn-beijing-a` 标签的 Node。
4. **查冲突 Pod**：检查这些同域的 Node 上，有没有运行带 `app=web` 标签的 Pod。
5. **裁决**：如果发现了匹配的 Pod，说明当前候选 Node-X 所在的 zone 已经有该服务了，违背了反亲和策略，候选失败。

通过这种标签匹配和范围查找，K8s 优雅地将物理世界的网络拓扑映射到了调度逻辑中。
