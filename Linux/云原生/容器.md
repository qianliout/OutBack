# 容器核心原理详解

## 容器本质：一种特殊的进程

容器技术的核心理解是：**容器是一种沙盒技术，本质上是一个运行在宿主机上的特殊进程**。

### 进程与容器的区别

传统的进程运行在宿主机上，拥有真实的 PID，由操作系统统一管理。而容器内的进程虽然"看似"拥有独立的 PID=1（容器内），但实际上在宿主机上仍然是普通的进程，由宿主机操作系统统一管理。

```
宿主机视角：
PID 100: dockerd (Docker 守护进程)
PID 101: containerd (容器运行时)
PID 25686: python app.py (容器内的应用进程)

容器视角（通过 Namespace 隔离后看到的）：
PID 1: python app.py
```

**关键理解**：Docker 项目本身并不创建任何"实体容器"，它只是在创建进程时为进程添加了 Namespace 参数，让这些进程"以为"自己运行在独立的环境中。

## 一、Linux Namespace：创造"障眼法"

### 1.1 什么是 Namespace？

Linux Namespace 是 Linux 内核提供的一种内核级别隔离机制，通过修改进程的"视图"，让进程只能看到特定范围内的资源。

形象理解：就像给进程戴上了一副"VR眼镜"，让它只能看到设定好的"虚拟世界"，而实际上它仍然在真实的物理机上运行。

### 1.2 Namespace 的类型

Linux 提供了多种类型的 Namespace：

| Namespace 类型 | 隔离内容 | 内核参数 |
|---------------|---------|---------|
| PID | 进程编号 | CLONE_NEWPID |
| Network | 网络设备、端口等 | CLONE_NEWNET |
| Mount | 挂载点、文件系统 | CLONE_NEWNS |
| UTS | 主机名、域名 | CLONE_NEWUTS |
| IPC | 信号量、消息队列、共享内存 | CLONE_NEWIPC |
| User | 用户ID、组ID | CLONE_NEWUSER |

### 1.3 Namespace 的实现原理

#### clone() 系统调用

Linux 创建新进程的系统调用是 `clone()`：

```c
int pid = clone(main_function, stack_size, SIGCHLD, NULL);
```

这个系统调用创建一个新进程，并返回其进程号。

当使用 `clone()` 创建进程时，可以通过参数指定开启哪些 Namespace：

```c
int pid = clone(main_function, stack_size, 
                CLONE_NEWPID | SIGCHLD, NULL);
```

此时，新创建进程的 PID 在容器内显示为 1，但在宿主机上仍然是真实的 PID 值。

#### 容器内查看 Namespace 文件

每个容器的 Namespace 信息都存储在 `/proc/[进程号]/ns/` 目录下：

```bash
$ ls -l /proc/25686/ns/
total 0
lrwxrwxrwx 1 root root 0 Aug 13 14:05 cgroup -> cgroup:[4026531835]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 ipc -> ipc:[4026532278]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 mnt -> mnt:[4026532276]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 net -> net:[4026532281]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 pid -> pid:[4026532279]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 pid_for_children -> pid:[4026532279]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 user -> user:[4026531837]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 uts -> uts:[4026532277]
```

每种 Namespace 都有一个虚拟文件，指向真实的 Namespace 对象。

## 二、Linux Cgroups：资源的"紧箍咒"

### 2.1 问题的提出

仅仅通过 Namespace 创建"障眼法"是不够的。考虑以下场景：

- 容器内的 PID=1 进程虽然在"视图"上被隔离
- 但它仍然是宿主机上的普通进程，可以占用任何资源
- 这个进程可以把宿主机的 CPU、内存全部吃光

**这就是"限制"的必要性。**

### 2.2 什么是 Cgroups？

Linux Cgroups它的核心作用是：**限制一个进程组能够使用的资源上限**。

支持的资源限制包括：
- CPU
- 内存
- 磁盘 I/O
- 网络带宽

### 2.3 Cgroups 的使用方式

Cgroups 通过文件系统暴露接口，位于 `/sys/fs/cgroup/`：

```bash
$ ls /sys/fs/cgroup/
cpuset  cpu    cpuacct  memory  blkio  ...
```

#### 实践：为进程设置 CPU 限制

1. 创建控制组（目录）：
```bash
$ mkdir /sys/fs/cgroup/cpu/container
```

2. 查看默认配置：
```bash
$ cat /sys/fs/cgroup/cpu/container/cpu.cfs_quota_us
-1  # -1 表示无限制
$ cat /sys/fs/cgroup/cpu/container/cpu.cfs_period_us
100000  # 默认周期 100ms
```

3. 设置 20% CPU 限制：
```bash
$ echo 20000 > /sys/fs/cgroup/cpu/container/cpu.cfs_quota_us
```

4. 将进程加入控制组：
```bash
$ echo 226 > /sys/fs/cgroup/cpu/container/tasks
```

这意味着在每 100ms 周期内，该进程只能使用 20ms 的 CPU 时间。

### 2.4 Docker 中的 Cgroups

Docker 启动容器时，会在对应子系统的控制组下创建新目录：

```bash
$ docker run -it --cpu-period=100000 --cpu-quota=20000 ubuntu /bin/bash
```

对应的 Cgroups 文件：
```
/sys/fs/cgroup/cpu/docker/[容器ID]/cpu.cfs_quota_us = 20000
/sys/fs/cgroup/cpu/docker/[容器ID]/cpu.cfs_period_us = 100000
```

## 三、容器的"边界"：rootfs 与文件系统

### 3.1 什么是 rootfs？

容器需要自己的文件系统视图。rootfs 是容器启动时挂载的根文件系统，提供了容器内的"完整"操作系统视图。

但这个 rootfs 是由多个层（layer）组成的：

```
联合文件系统（UnionFS）结构：
├── 只读层 1（来自镜像）
├── 只读层 2（来自镜像）
├── ...
├── Init 层（Docker 添加的初始化配置）
└── 可读写层（容器内修改的复制）
```

### 3.2 Init 层

Init 层是 Docker 添加的特殊层，用于存放被临时修改的配置文件（如 /etc/hosts），确保这些修改不会被 `docker commit` 提交。

### 3.3 可读写层（Copy-on-Write）

容器运行过程中对文件系统的一切修改，都会在可读写层进行。这就是 Copy-on-Write 机制：

- 读取时：直接读取只读层
- 写入时：先从只读层复制到可读写层，再修改

## 四、docker exec 的实现原理

### 4.1 用户疑问

> 既然容器是一个进程，那 docker exec 是怎么"进入"容器并执行命令的呢？

### 4.2 Namespace 的跨进程共享

理解 docker exec 的关键在于：**一个进程可以加入另一个进程的 Namespace**。

这是通过 `setns()` 系统调用实现的。

### 4.3 setns() 的使用

假设我们要进入容器（PID=25686）的 Network Namespace：

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <sched.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    int fd = open(argv[1], O_RDONLY);  // 打开 Namespace 文件
    setns(fd, 0);                       // 加入该 Namespace
    execvp(argv[2], &argv[2]);         // 在该 Namespace 中执行命令
}
```

编译并使用：
```bash
$ gcc -o set_ns set_ns.c
$ ./set_ns /proc/25686/ns/net /bin/bash
```

执行后，当前 shell 进程就加入到了容器的 Network Namespace 中，**看到的网络设备与容器一致**。

### 4.4 验证 Namespace 共享

```bash
# 容器进程
$ ls -l /proc/25686/ns/net
net:[4026532281]

# exec 后的进程
$ ls -l /proc/28499/ns/net
net:[4026532281]  # 与容器进程指向相同的 Namespace 对象
```

两个进程共享同一个 Network Namespace，这就是 docker exec 的本质。

### 4.5 Docker 的 --net 参数

Docker 提供了 `--net` 参数来控制网络 Namespace 的共享方式：

```bash
$ docker run -it --net=container:<容器ID> ubuntu /bin/bash
```

新容器会加入指定容器的 Network Namespace。

而 `--net=host` 则不为容器创建 Network Namespace，直接使用宿主机网络。

## 五、容器内新进程的管理机制

### 5.1 用户疑问

> 进入容器后执行的命令或启动的新进程，是怎么管理的？

### 5.2 容器的"单进程模型"

**核心概念**：容器是一个"单进程"模型。

容器的 PID=1 进程是 ENTRYPOINT 指定的进程（如 python app.py），这个进程是容器内所有其他进程的父进程。

```
容器内进程树：
PID 1: python app.py (父进程)
  └── PID 10: /bin/bash (docker exec 创建)
        └── PID 11: ps (子进程)
```

### 5.3 容器内进程的管理

**容器内的进程管理依赖于容器的 PID Namespace**：

1. **PID=1 进程**（ENTRYPOINT）负责管理和回收子进程
   - 类似于传统 Linux 系统中的 init 进程
   - 处理孤儿进程（父进程退出的子进程）
   - 响应 SIGCHLD 信号

2. **所有新进程都继承 PID Namespace**
   - 在容器内执行 `python new_app.py`，该进程会在容器内显示为新 PID
   - 在宿主机上，该进程的 PID 是真实值（如 30000）

3. **Namespace 视图隔离**
   - 容器内的 `ps` 命令只能看到同一 PID Namespace 内的进程
   - 容器外的 `ps` 命令加上适当的过滤器可以看到容器进程

### 5.4 容器进程与宿主机进程的关系

```
宿主机视角：
PID 25686: python app.py (容器主进程)
PID 28499: /bin/bash (docker exec 创建)
PID 28500: ps aux (docker exec 创建)

容器内视角（Namespace 隔离后）：
PID 1: python app.py
PID 10: /bin/bash
PID 11: ps aux
```

### 5.5 为什么容器通常只运行一个进程？

由于 PID=1 进程负责管理子进程，如果运行多个应用，需要选择一个通用的 PID=1 进程（如 systemd 或 supervisord），这增加了复杂性。

**最佳实践**：一个容器运行一个进程。

## 六、Volume 的挂载原理

### 6.1 问题背景

容器使用 rootfs 后，容器内的修改不会影响宿主机。但需要：
- 宿主机向容器传递文件
- 容器向宿主机暴露文件

### 6.2 Docker Volume 机制

两种 Volume 声明方式：
```bash
$ docker run -v /test ...           # Docker 自动创建临时目录
$ docker run -v /home:/test ...     # 指定宿主机目录
```

### 6.3 绑定挂载（bind mount）

Docker 使用 Linux 的绑定挂载机制：

```bash
mount --bind /home /test
```

这将 `/test` 的目录项（dentry）重定向到 `/home` 的索引节点（inode）。

**关键点**：由于此时 Mount Namespace 已经开启，这个挂载只在容器内可见，不影响宿主机。

### 6.4 Volume 与 docker commit

- Volume 内的文件修改发生在宿主机对应目录
- 执行 `docker commit` 时，Volume 内容不会被提交
- 因为 Mount Namespace 隔离，宿主机看不到 Volume 挂载点内的真实内容

## 七、综合总结：容器的全景图

一个运行中的 Docker 容器，可以用以下结构描述：

```
容器进程 (python app.py)
│
├── Linux Namespace（隔离）
│   ├── PID Namespace：进程编号隔离
│   ├── Network Namespace：网络隔离
│   ├── Mount Namespace：文件系统视图隔离
│   ├── UTS Namespace：主机名隔离
│   ├── IPC Namespace：进程间通信隔离
│   └── User Namespace：用户ID隔离
│
├── Linux Cgroups（限制）
│   ├── CPU限制
│   ├── 内存限制
│   ├── I/O限制
│   └── ...
│
└── rootfs（文件系统）
    ├── 只读层（来自镜像）
    ├── Init 层（Docker 配置）
    └── 可读写层（Copy-on-Write）
```

## 八、容器与虚拟机的核心区别

| 特性 | 虚拟机 | 容器 |
|-----|-------|-----|
| 隔离层级 | 硬件虚拟化 | 操作系统级 |
| Guest OS | 需要完整 Guest OS | 不需要（共享宿主机内核） |
| 资源消耗 | 100-200MB 内存 | 几乎忽略不计 |
| 启动速度 | 慢（分钟级） | 快（秒级） |
| 性能损耗 | 虚拟化拦截开销 | 无（直接运行在宿主机） |
| 隔离程度 | 彻底 | 不够彻底（共享内核） |

## 九、K8s Pod 与 Docker 容器的区别

### 9.1 Docker 容器的本质

```
宿主机：
dockerd → containerd → shim → 容器进程 (PID 在宿主机上是真实值)

容器内：
PID 1: 你的应用进程
```

**每个 Docker 容器是独立的进程，拥有自己隔离的 Namespace。**

### 9.2 K8s Pod 的本质

**Pod 是 K8s 的最小调度单位，一个 Pod 可以包含多个容器。**

```
┌─────────────────────────────────────────┐
│              K8s Pod                     │
│  ┌─────────────┐  ┌─────────────┐      │
│  │  Container A │  │  Container B │      │
│  │  (nginx)     │  │  (app)       │      │
│  └─────────────┘  └─────────────┘      │
│                                         │
│  ════════════════════════════════════   │
│       共享 Network + PID + IPC          │
│  ════════════════════════════════════   │
│                                         │
│  ┌─────────────┐                       │
│  │ Pause 容器  │  ← 共享的 PID Namespace │
│  │  (PID=1)    │    所有容器都加入这个    │
│  └─────────────┘    Namespace           │
└─────────────────────────────────────────┘
```

### 9.3 核心区别对比

| 特性 | Docker 容器 | K8s Pod |
|-----|------------|---------|
| 最小单位 | 单进程 | 一组容器 |
| 进程关系 | 独立 PID Namespace | 共享 PID Namespace |
| 网络 | 独立网络栈 | 共享 localhost |
| 进程可见性 | 只能看到自己 | 可以看到同 Pod 其他容器 |
| 调度 | 进程级别 | Pod 级别 |

**关键理解**：同一个 Pod 内的容器共享 PID=1（Pause 容器），所以它们能看到彼此的进程。

## 十、K8s 多容器与 Init 容器

### 10.1 同一 Pod 内的多容器

同一个 Pod 内的容器**共享 Network 和 PID Namespace**：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 80
  - name: app
    image: myapp
```

在这个 Pod 里：
- **nginx** 和 **app** 共享网络 → 可以用 `localhost:80` 互相访问
- **共享 PID Namespace** → 在 nginx 容器里 `ps aux` 能看到 app 容器的进程
- **共享挂载** → 可以通过 Volume 共享文件

### 10.2 Init 容器（初始化容器）

**Init 容器是在主应用容器启动之前运行的特殊容器。**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  initContainers:
  - name: init-myservice
    image: busybox
    command: ['sh', '-c', 'echo Init container ran']
  
  containers:
  - name: myapp
    image: myapp
```

**特点**：
1. **按顺序执行** - 所有 Init 容器必须完成，下一个才执行
2. **必须成功退出** - 如果 Init 容器失败，主容器不会启动
3. **可重复执行** - 每次 Pod 启动都会执行

**用途**：
- 等待依赖服务（如数据库）ready
- 预先拉取配置或凭证
- 准备数据目录

## 十一、容器内运行程序的进程结构

### 11.1 直接运行程序

执行 `docker run ubuntu python main.py`：

```
容器内视角（隔离后看到的）：
PID 1: python main.py  ← 你是 PID=1

宿主机视角（真实情况）：
PID 30000: python main.py  ← docker exec 创建的新进程
```

**你运行的就是 PID=1 进程本身。**

### 11.2 先启动容器再运行程序

```bash
docker run -it ubuntu /bin/bash
# 容器内执行：
python main.py
```

```
容器内进程树：
PID 1: /bin/bash           ← 你的 bash 是 PID=1
  └── PID 10: python main.py  ← python 是 bash 的子进程

宿主机进程树：
PID 20000: /bin/bash (容器主进程)
  └── PID 20001: python main.py (bash 的子进程)
```

**Python 进程是容器 ENTRYPOINT 进程的子进程。**

### 11.3 关键理解

无论哪种方式：
- **容器内**看到的 PID 是 Namespace 后的"障眼法"
- **宿主机上**看到的是真实的 PID
- **所有容器内进程都是宿主机进程的子进程或孙进程**

## 十二、Volume 数据持久化

### 12.1 绑定挂载（Bind Mount）

```bash
docker run -v /home:/container/data ubuntu
```

**挂载的是宿主机目录，容器退出后数据不会丢失！**

```
宿主机：/home 目录
     ↓ mount --bind 挂载
容器内：/container/data
```

即使容器删除，宿主机的 `/home` 目录完好无损。

### 12.2 Docker 管理的 Volume（匿名卷）

```bash
docker run -v /data ubuntu
```

Docker 会在 `/var/lib/docker/volumes/` 下创建临时目录。

**容器删除后，这个临时目录会被 Docker 自动清理。**

### 12.3 命名卷（Named Volume）

```bash
docker run -v mydata:/data ubuntu
```

**容器删除后，命名卷的数据仍然保留。**

### 12.4 Volume 类型对比

| 挂载方式 | 容器删除后数据 | 命令示例 |
|---------|--------------|---------|
| 绑定宿主机目录 | **保留** | `-v /home:/data` |
| 匿名卷 | 删除 | `-v /data` |
| 命名卷 | **保留** | `-v mydata:/data` |

### 12.5 查看 Volume 信息

```bash
# 查看 Volume 列表
docker volume ls

# 查看容器挂载信息
docker inspect <container_id> -f '{{.Mounts}}'
```

## 十三、常见问题解答

### Q1: 为什么容器内的 top 命令显示的是宿主机信息？

这是因为 `/proc` 文件系统不了解 Cgroups 限制的存在。解决方案是使用 `lxcfs` 等工具来提供容器内正确的资源视图。

### Q2: cgroup Namespace 是什么？

Linux 4.6+ 新增的 cgroup Namespace，用于隔离 cgroup 文件系统的视图，让容器内的进程看到自己独立的 cgroup 层级结构。

### Q3: docker run -v /home:/test 时，容器内 /test 原有的内容去哪了？

绑定挂载会**隐藏**原有的内容。由于挂载点重定向到 `/home`，原本挂载点的内容被隐藏了，这就是 bind mount 的特性。

## 十四、知识回顾与思考

### 核心要点

1. **容器是进程**：容器本身不是实体，是通过 Namespace 和 Cgroups 隔离和限制的进程
2. **Namespace 是视图隔离**：修改进程看到的资源视图，但资源本身是共享的
3. **Cgroups 是资源限制**：防止进程占用过多资源
4. **rootfs 是文件系统**：提供容器内独立的文件系统视图
5. **docker exec 是 Namespace 加入**：通过 setns() 加入容器的 Namespace
6. **容器内新进程由 PID=1 管理**：容器是单进程模型
7. **K8s Pod 是容器组**：同 Pod 容器共享 PID 和 Network Namespace
8. **Init 容器先于主容器执行**：用于初始化准备工作
9. **Volume 数据持久化**：绑定挂载和命名卷在容器删除后数据保留

### 深入思考

1. 如果容器内 PID=1 的进程退出，容器会怎样？（容器也会退出）
2. 如果使用 `--net=host`，容器的网络隔离会发生什么变化？（隔离被移除）
3. 为什么容器不能完全替代虚拟机？（隔离不彻底、安全性问题）
4. K8s 中同一个 Pod 的两个容器如何通信？（通过 localhost 或者共享的 Volume）
5. Init 容器和应用容器谁先启动？（Init 容器先启动，必须全部成功才会启动应用容器）
