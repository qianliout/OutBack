# 容器核心原理详解

## 容器本质：一种特殊的进程

容器技术的核心理解是：**容器是一种沙盒技术，本质上是一个运行在宿主机上的特殊进程**。

### 进程与容器的区别

传统的进程运行在宿主机上，拥有真实的 PID，由操作系统统一管理。而容器内的进程虽然"看似"拥有独立的 PID=1（容器内），但实际上在宿主机上仍然是普通的进程，由宿主机操作系统统一管理。

```
宿主机视角：
PID 100: dockerd (Docker 守护进程)
PID 101: containerd (容器运行时)
PID 25686: python app.py (容器内的应用进程)

容器视角（通过 Namespace 隔离后看到的）：
PID 1: python app.py
```

**关键理解**：Docker 项目本身并不创建任何"实体容器"，它只是在创建进程时为进程添加了 Namespace 参数，让这些进程"以为"自己运行在独立的环境中。

---

## 八、补充说明：挂载可见性与数据可见性

在理解 Mount Namespace 时，最容易混淆的是“挂载关系是否可见”和“写入的数据是否可见”其实不是一回事。

- Mount Namespace 隔离的是挂载视图，而不是底层存储本身。
- 所谓“挂载只在容器内可见”，意思是容器内新增的挂载关系只出现在容器自己的挂载表中，宿主机的挂载表不会因此改变。
- 例如容器内执行 `mount --bind /home /test`，容器内看到的 `/test` 会指向 `/home`，但宿主机不会因为这次操作也自动出现同样的挂载效果。

但这并不等于容器内对文件的写入一定对宿主机不可见。文件内容是否能被宿主机看到，取决于挂载背后是否对应同一份底层存储：

- 如果容器挂载的是宿主机上的真实目录，那么容器内写入文件后，宿主机通常也能在对应目录中看到这些修改。
- 如果写入发生在容器自己的可写层中，那么这些数据虽然最终仍落在宿主机磁盘上，但宿主机通常不会通过容器内相同的路径直接看到它，而是由容器运行时负责管理。

因此，更严谨的理解方式是：

- 挂载关系的可见性，看的是 Mount Namespace。
- 文件内容的可见性，看的是底层是否共享同一份存储。

一句话总结：Mount Namespace 主要隔离“怎么看文件系统”，不直接决定“底层文件数据会不会被其他环境看到”。

## 一、Linux Namespace：创造"障眼法"

### 1.1 什么是 Namespace？

Linux Namespace 是 Linux 内核提供的一种内核级别隔离机制，通过修改进程的"视图"，让进程只能看到特定范围内的资源。

形象理解：就像给进程戴上了一副"VR眼镜"，让它只能看到设定好的"虚拟世界"，而实际上它仍然在真实的物理机上运行。

### 1.2 Namespace 的类型

Linux 提供了多种类型的 Namespace：

| Namespace 类型 | 隔离内容 | 内核参数 |
|---------------|---------|---------|
| PID | 进程编号 | CLONE_NEWPID |
| Network | 网络设备、端口等 | CLONE_NEWNET |
| Mount | 挂载点、文件系统 | CLONE_NEWNS |
| UTS | 主机名、域名 | CLONE_NEWUTS |
| IPC | 信号量、消息队列、共享内存 | CLONE_NEWIPC |
| User | 用户ID、组ID | CLONE_NEWUSER |

### 1.3 Namespace 的实现原理

#### clone() 系统调用

Linux 创建新进程的系统调用是 `clone()`：

```c
int pid = clone(main_function, stack_size, SIGCHLD, NULL);
```

这个系统调用创建一个新进程，并返回其进程号。

当使用 `clone()` 创建进程时，可以通过参数指定开启哪些 Namespace：

```c
int pid = clone(main_function, stack_size, 
                CLONE_NEWPID | SIGCHLD, NULL);
```

此时，新创建进程的 PID 在容器内显示为 1，但在宿主机上仍然是真实的 PID 值。

#### 容器内查看 Namespace 文件

每个容器的 Namespace 信息都存储在 `/proc/[进程号]/ns/` 目录下：

```bash
$ ls -l /proc/25686/ns/
total 0
lrwxrwxrwx 1 root root 0 Aug 13 14:05 cgroup -> cgroup:[4026531835]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 ipc -> ipc:[4026532278]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 mnt -> mnt:[4026532276]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 net -> net:[4026532281]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 pid -> pid:[4026532279]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 pid_for_children -> pid:[4026532279]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 user -> user:[4026531837]
lrwxrwxrwx 1 root root 0 Aug 13 14:05 uts -> uts:[4026532277]
```

#### 1.3.1 理解 `/proc/[pid]/ns/` 下的"虚拟文件"

上面 `ls -l` 的输出中，每一行看起来像是符号链接：

```
net -> net:[4026532281]
```

但这里的 `net:[4026532281]` **不是常规的文件路径**，而是一个内核内部标识。要理解它，需要拆成三层：

---

**第一层：这不是普通文件，是 procfs 暴露的"句柄"**

`/proc/[pid]/ns/` 是 Linux 内核通过 proc 文件系统暴露的一组特殊条目。它们**不是存储在磁盘上的真实文件**，而是内核在用户态开的一扇"窗"——每次你 `ls` 或 `open` 它，内核动态生成内容。

可以把它们理解为**指向内核 Namespace 对象的"指针"**。虽然 `ls -l` 显示为符号链接，但它的行为更像是一个**文件描述符入口**：打开它，你就拿到了通往内核中那个 Namespace 对象的"钥匙"（file descriptor）。

---

**第二层：`[4026532281]` 是什么？—— Namespace 的"身份证号"**

方括号里的数字是该 Namespace 在内核中的 **inode 号**。它有两个关键作用：

1. **唯一标识**：内核里每个 Namespace 对象有一个全局唯一的 inode 号。只要两个进程的 `/proc/[pid]/ns/net` 指向同一个 inode（比如都是 `net:[4026532281]`），它们就**共享同一个 Network Namespace**。

2. **判断是否在同一 Namespace**：这是运维中最实用的技巧——不用进容器，直接在宿主机上比对 inode 号就知道两个进程是否共享某个 Namespace：

```bash
# 容器主进程（PID=25686）的 net namespace inode
$ readlink /proc/25686/ns/net
net:[4026532281]

# docker exec 进去的 bash（PID=28499）的 net namespace inode
$ readlink /proc/28499/ns/net
net:[4026532281]   # ← 同一个 inode，说明共享同一个 Network Namespace
```

---

**第三层：为什么设计成"文件"？—— 为了 `setns()` 和保持 Namespace 存活**

把 Namespace 暴露为文件有两个设计目的：

**(1) 作为 `setns()` 的入口参数**

这是第四节会讲到的核心机制。`setns()` 系统调用需要传入一个文件描述符来指定"加入哪个 Namespace"：

```c
int fd = open("/proc/25686/ns/net", O_RDONLY);  // 通过"虚拟文件"拿到 fd
setns(fd, CLONE_NEWNET);                         // 用这个 fd 加入目标 Namespace
```

没有这个"虚拟文件"，你就没法用文件描述符的方式把 Namespace 对象传给 `setns()`。

**(2) 通过 bind mount 保持 Namespace 存活**

正常情况下，当一个 Namespace 里所有进程都退出后，内核会回收该 Namespace。但如果你先把 `/proc/[pid]/ns/net` **bind mount** 到一个普通路径：

```bash
touch /var/run/netns/myns
mount --bind /proc/25686/ns/net /var/run/netns/myns
```

那么即使原进程退出了，只要 `/var/run/netns/myns` 这个挂载还在（有引用计数），内核就不会回收这个 Network Namespace。这就是 `ip netns` 命令的底层实现原理。

---

**一句话总结**

> `net:[4026532281]` 不是一个路径，而是一个 **`类型:inode`** 的身份证号。`/proc/[pid]/ns/` 下的这些"虚拟文件"是内核开的窗口，让用户态能通过文件描述符来**引用、传递、持久化**内核中的 Namespace 对象。

## 二、Linux Cgroups：资源的"紧箍咒"

### 2.1 问题的提出

仅仅通过 Namespace 创建"障眼法"是不够的。考虑以下场景：

- 容器内的 PID=1 进程虽然在"视图"上被隔离
- 但它仍然是宿主机上的普通进程，可以占用任何资源
- 这个进程可以把宿主机的 CPU、内存全部吃光

**这就是"限制"的必要性。**

### 2.2 什么是 Cgroups？

Linux Cgroups它的核心作用是：**限制一个进程组能够使用的资源上限**。

支持的资源限制包括：
- CPU
- 内存
- 磁盘 I/O
- 网络带宽

### 2.3 Cgroups 的使用方式

Cgroups 通过文件系统暴露接口，位于 `/sys/fs/cgroup/`：

```bash
$ ls /sys/fs/cgroup/
cpuset  cpu    cpuacct  memory  blkio  ...
```

#### 实践：为进程设置 CPU 限制

1. 创建控制组（目录）：
```bash
$ mkdir /sys/fs/cgroup/cpu/container
```

这里的 `container` 只是一个 cgroup 名称，对应一组资源控制规则。单独创建目录并不会自动绑定任何进程，只有当进程被加入这个 cgroup 后，才会受到该组配置的限制。

2. 查看默认配置：
```bash
$ cat /sys/fs/cgroup/cpu/container/cpu.cfs_quota_us
-1  # -1 表示无限制
$ cat /sys/fs/cgroup/cpu/container/cpu.cfs_period_us
100000  # 默认周期 100ms
```

3. 设置 20% CPU 限制：
```bash
$ echo 20000 > /sys/fs/cgroup/cpu/container/cpu.cfs_quota_us
```

这表示在每个 `100000us`（100ms）的调度周期内，这个 cgroup 最多只能使用 `20000us`（20ms）的 CPU 时间，也就是最多使用 20% 的单核 CPU 时间。

4. 将进程加入控制组：
```bash
$ echo 226 > /sys/fs/cgroup/cpu/container/cgroup.procs
```

其中 `226` 表示一个实际存在的进程 ID。将它写入 `cgroup.procs`，表示把该进程加入 `container` 这个 cgroup；此后内核在调度这个进程及其后续子进程时，会按照 `container` 目录下的 CPU 配置进行限制。

更准确地说，Cgroups 控制资源的方式不是“给某个进程单独写一份配置”，而是“先为一个组设置资源规则，再把进程加入这个组”：

- `cpu.cfs_period_us` 定义统计周期
- `cpu.cfs_quota_us` 定义该周期内允许使用的 CPU 时间
- `cgroup.procs` 用来把进程加入当前 cgroup

因此，内核区分“哪个进程使用哪套资源限制”的依据，不是目录名，而是该进程当前归属于哪个 cgroup。

补充说明：`tasks` 也是可用接口，但它是线程级入口；如果要表达“将某个进程加入控制组”，使用 `cgroup.procs` 更严谨，也更符合直觉。

### 2.4 Docker 中的 Cgroups

Docker 启动容器时，通常会为该容器创建独立的 cgroup，并将容器内进程加入其中。这样，内核就能按容器这一组进程统一施加资源限制。

```bash
$ docker run -it --cpu-period=100000 --cpu-quota=20000 ubuntu /bin/bash
```

在 `cgroup v1` 场景下，常见的示意路径如下：
```text
/sys/fs/cgroup/cpu/docker/[容器ID]/cpu.cfs_quota_us = 20000
/sys/fs/cgroup/cpu/docker/[容器ID]/cpu.cfs_period_us = 100000
```

这里出现容器 ID，是因为 Docker 通常会为每个容器创建一个独立的 cgroup 目录，容器内的多个进程共同加入这个目录对应的 cgroup，因此它们共享同一组 CPU 限制。

需要注意的是，这里的路径是常见示意，并不是所有环境下都完全一致。实际目录结构会受到 `cgroup v1` 或 `cgroup v2`、是否使用 `systemd` 以及容器运行时实现方式的影响；但核心机制不变，即“为容器创建独立 cgroup，再将容器内进程加入其中，从而控制整个容器的资源使用”。

## 三、容器的"边界"：rootfs 与文件系统

### 3.1 什么是 rootfs？

容器需要自己的文件系统视图。rootfs 是容器启动时挂载的根文件系统，提供了容器内的"完整"操作系统视图。

但这个 rootfs 是由多个层（layer）组成的：

```
联合文件系统（UnionFS）结构：
├── 只读层 1（来自镜像）
├── 只读层 2（来自镜像）
├── ...
├── Init 层（Docker 添加的初始化配置）
└── 可读写层（容器内修改的复制）
```

### 3.2 Init 层

Init 层是 Docker 添加的特殊层，用于存放被临时修改的配置文件（如 /etc/hosts），确保这些修改不会被 `docker commit` 提交。

### 3.3 可读写层（Copy-on-Write）

容器运行过程中对文件系统的一切修改，都会在可读写层进行。这就是 Copy-on-Write 机制：

- 读取时：直接读取只读层
- 写入时：先从只读层复制到可读写层，再修改

## 四、docker exec 的实现原理

### 4.1 用户疑问

> 既然容器是一个进程，那 docker exec 是怎么"进入"容器并执行命令的呢？

### 4.2 Namespace 的跨进程共享

理解 docker exec 的关键在于：**一个进程可以加入另一个进程的 Namespace**。

这是通过 `setns()` 系统调用实现的。

### 4.3 setns() 的使用

假设我们要进入容器（PID=25686）的 Network Namespace：

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <sched.h>
#include <unistd.h>

int main(int argc, char *argv[]) {
    int fd = open(argv[1], O_RDONLY);  // 打开 Namespace 文件
    setns(fd, 0);                       // 加入该 Namespace
    execvp(argv[2], &argv[2]);         // 在该 Namespace 中执行命令
}
```

编译并使用：
```bash
$ gcc -o set_ns set_ns.c
$ ./set_ns /proc/25686/ns/net /bin/bash
```

执行后，当前 shell 进程就加入到了容器的 Network Namespace 中，**看到的网络设备与容器一致**。

### 4.4 验证 Namespace 共享

```bash
# 容器进程
$ ls -l /proc/25686/ns/net
net:[4026532281]

# exec 后的进程
$ ls -l /proc/28499/ns/net
net:[4026532281]  # 与容器进程指向相同的 Namespace 对象
```

两个进程共享同一个 Network Namespace，这就是 docker exec 的本质。

### 4.5 Docker 的 --net 参数

Docker 提供了 `--net` 参数来控制网络 Namespace 的共享方式：

```bash
$ docker run -it --net=container:<容器ID> ubuntu /bin/bash
```

新容器会加入指定容器的 Network Namespace。

而 `--net=host` 则不为容器创建 Network Namespace，直接使用宿主机网络。

## 五、容器内新进程的管理机制

### 5.1 用户疑问

> 进入容器后执行的命令或启动的新进程，是怎么管理的？

### 5.2 两类进程：fork 子进程 vs docker exec 进程

容器内出现的"新进程"实际上来自**两条完全不同的路径**，必须分开理解：

| 路径 | 创建方式 | 与 PID 1 的关系 | PID 1 能回收吗？ |
|------|----------|-----------------|:---:|
| **PID 1 自己 fork** | 容器主进程内部 `fork()` + `exec()` | 真正的父子关系 | ✅ 是 |
| **docker exec** | containerd 在宿主机创建新进程，通过 `setns()` 加入容器的 PID Namespace | 兄弟关系（真实父进程是 containerd，在 Namespace 外不可见） | ❌ 否 |

```
容器内进程视图（正确的关系）：

PID 1:  python app.py (PPID=0, 容器 init)
PID 10: /bin/bash      (PPID=0, docker exec 进来的，真实父进程在 ns 外)
  └── PID 11: ps aux   (PPID=10, bash 自己 fork 的子进程)
```

**关键洞察**：docker exec 的 bash 不是 PID 1 "生"出来的——它是 containerd 在宿主机上独立创建，然后通过 `setns()` "搬"进容器的 PID Namespace。PID 1 对它没有 `wait()` 权限，它退出后产生的僵尸进程**不由 PID 1 回收**（由 containerd 回收）。

而 `PID 11: ps` 则是 bash 自己 fork 出来的，是 bash 真正的子进程，由 bash 负责回收。

### 5.3 PID Namespace 的角色：编号隔离，而非进程管理

一个常见的误解是把 PID Namespace 当成"进程管理器"——实际上它的角色更窄：

- **PID Namespace 做的事**：给同一个进程在不同 Namespace 里分配不同的 PID 编号（宿主机 PID 25686 = 容器内 PID 1），并提供 `/proc` 视图的过滤（容器内的 `ps` 只看得到本 Namespace 的进程）。
- **PID Namespace 不做的事**：不负责回收僵尸、不处理孤儿进程、不响应信号。

进程生命周期管理（僵尸回收、孤儿处理）是 **PID 1 进程** 的责任——这和传统 Linux 中 init 进程的角色完全一样。

### 5.4 PID 1 在容器中的特殊语义

容器中的 PID 1 继承了 Linux 内核对"PID namespace init 进程"的全部特殊规则：

1. **不可杀死**：PID 1 默认忽略 `SIGKILL` 和 `SIGTERM`（除非进程自身显式注册了 handler）。这意味着你不能像普通进程那样 `kill -9` 容器的主进程——它必须自己退出。

2. **孤儿进程自动过继**：PID Namespace 内任何进程的父进程退出后，内核会将该孤儿进程的 PPID **自动改为本 Namespace 的 PID 1**。PID 1 必须通过 `wait()` / `waitpid()` 回收它们，否则变成僵尸堆积。

3. **PID 1 退出 = 容器终止**：内核规定，当 PID Namespace 的 init 进程（PID 1）退出时，内核会向该 Namespace 内所有其他进程发送 `SIGKILL`，然后销毁整个 PID Namespace。

4. **只管理"自己人"**：PID 1 只能通过 `wait()` 回收**被内核过继给它的孤儿进程**和**自己主动 fork 的子进程**。docker exec 进来的进程不由它回收——那些进程的回收由 containerd 负责。

### 5.5 容器主进程退出的影响

当容器的主进程（PID 1）退出时：

```
1. 内核向容器 PID Namespace 内所有进程发送 SIGKILL
2. 所有进程被强制终止（不论是否 docker exec 进来的）
3. PID Namespace 被销毁
4. 容器进入 "exited" 状态
```

这就是"容器停了"的底层含义——不是 Docker 发了什么信号，而是 **PID Namespace 的 init 退出触发了内核的清理机制**。

### 5.6 为什么推荐"一个容器一个进程"？

基于以上机制，"单进程模型"虽然不是技术硬限制（完全可以运行多个），但它是最简单、最符合容器设计的模式：

| 原因 | 说明 |
|------|------|
| **PID 1 不可被杀** | 如果主进程有 bug 导致僵死，你无法 `kill -9` 它——只能重启整个容器 |
| **僵尸回收责任** | 大多数应用（nginx、python、node）不处理 SIGCHLD、不调用 `wait()`。如果它们做 PID 1，fork 的子进程退出后会变成僵尸堆积 |
| **PID 1 退出 = 全死** | 多进程模式下，一个进程崩溃若连带 kill 了 PID 1，容器内所有进程都被内核清场——"一荣俱荣，一损俱损" |
| **编排友好** | K8s 按容器粒度做健康检查、扩缩容、滚动更新。一个容器一个进程使得每个单元的状态明确，故障域清晰 |

如果确实需要在一个容器内运行多个进程，标准做法是使用 **tini**、**dumb-init** 或 **supervisord** 作为 PID 1，由它们负责僵尸回收和信号转发。K8s 的 Pod 则提供了另一个思路：把多个进程放进多个容器，共享同一个 Pod 的 Namespace（见第九节）。

### 5.7 容器进程与宿主机进程的关系

```
宿主机视角（真实 PID）：
PID 25686: python app.py (容器主进程, PID 1 in ns)
PID 28499: /bin/bash       (docker exec, containerd 的子进程)
PID 28500: ps aux          (PID 28499 fork 的子进程)

容器内视角（PID Namespace 隔离后）：
PID 1:  python app.py (PPID=0)
PID 10: /bin/bash      (PPID=0, 真实父进程 containerd 在 ns 外)
PID 11: ps aux         (PPID=10)
```

## 六、Volume 的挂载原理

### 6.1 问题背景

容器使用 rootfs 后，容器内的修改不会影响宿主机。但需要：
- 宿主机向容器传递文件
- 容器向宿主机暴露文件

### 6.2 Docker Volume 机制

两种 Volume 声明方式：
```bash
$ docker run -v /test ...           # Docker 自动创建临时目录
$ docker run -v /home:/test ...     # 指定宿主机目录
```

### 6.3 绑定挂载（bind mount）

Docker 使用 Linux 的绑定挂载机制：

```bash
mount --bind /home /test
```

这将 `/test` 的目录项（dentry）重定向到 `/home` 的索引节点（inode）。

**关键点**：由于此时 Mount Namespace 已经开启，这个挂载只在容器内可见，不影响宿主机。

### 6.4 Volume 与 docker commit

- Volume 内的文件修改发生在宿主机对应目录
- 执行 `docker commit` 时，Volume 内容不会被提交
- 因为 Mount Namespace 隔离，宿主机看不到 Volume 挂载点内的真实内容

## 七、综合总结：容器的全景图

一个运行中的 Docker 容器，可以用以下结构描述：

```
容器进程 (python app.py)
│
├── Linux Namespace（隔离）
│   ├── PID Namespace：进程编号隔离
│   ├── Network Namespace：网络隔离
│   ├── Mount Namespace：文件系统视图隔离
│   ├── UTS Namespace：主机名隔离
│   ├── IPC Namespace：进程间通信隔离
│   └── User Namespace：用户ID隔离
│
├── Linux Cgroups（限制）
│   ├── CPU限制
│   ├── 内存限制
│   ├── I/O限制
│   └── ...
│
└── rootfs（文件系统）
    ├── 只读层（来自镜像）
    ├── Init 层（Docker 配置）
    └── 可读写层（Copy-on-Write）
```

## 九、K8s Pod 与 Docker 容器的区别

### 9.1 Docker 容器的本质

```
宿主机：
dockerd → containerd → shim → 容器进程 (PID 在宿主机上是真实值)

容器内：
PID 1: 你的应用进程
```

**每个 Docker 容器是独立的进程，拥有自己隔离的 Namespace。**

### 9.2 K8s Pod 的本质

**Pod 是 K8s 的最小调度单位，一个 Pod 可以包含多个容器。**

```
┌─────────────────────────────────────────┐
│              K8s Pod                     │
│  ┌─────────────┐  ┌─────────────┐      │
│  │  Container A │  │  Container B │      │
│  │  (nginx)     │  │  (app)       │      │
│  └─────────────┘  └─────────────┘      │
│                                         │
│  ════════════════════════════════════   │
│       共享 Network + PID + IPC          │
│  ════════════════════════════════════   │
│                                         │
│  ┌─────────────┐                       │
│  │ Pause 容器  │  ← 共享的 PID Namespace │
│  │  (PID=1)    │    所有容器都加入这个    │
│  └─────────────┘    Namespace           │
└─────────────────────────────────────────┘
```

### 9.3 核心区别对比

| 特性 | Docker 容器 | K8s Pod |
|-----|------------|---------|
| 最小单位 | 单进程 | 一组容器 |
| 进程关系 | 独立 PID Namespace | 共享 PID Namespace |
| 网络 | 独立网络栈 | 共享 localhost |
| 进程可见性 | 只能看到自己 | 可以看到同 Pod 其他容器 |
| 调度 | 进程级别 | Pod 级别 |

**关键理解**：同一个 Pod 内的容器共享 PID=1（Pause 容器），所以它们能看到彼此的进程。

## 十、K8s 多容器与 Init 容器

### 10.1 同一 Pod 内的多容器

同一个 Pod 内的容器**共享 Network 和 PID Namespace**：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 80
  - name: app
    image: myapp
```

在这个 Pod 里：
- **nginx** 和 **app** 共享网络 → 可以用 `localhost:80` 互相访问
- **共享 PID Namespace** → 在 nginx 容器里 `ps aux` 能看到 app 容器的进程
- **共享挂载** → 可以通过 Volume 共享文件

### 10.2 Init 容器（初始化容器）

**Init 容器是在主应用容器启动之前运行的特殊容器。**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
spec:
  initContainers:
  - name: init-myservice
    image: busybox
    command: ['sh', '-c', 'echo Init container ran']
  
  containers:
  - name: myapp
    image: myapp
```

**特点**：
1. **按顺序执行** - 所有 Init 容器必须完成，下一个才执行
2. **必须成功退出** - 如果 Init 容器失败，主容器不会启动
3. **可重复执行** - 每次 Pod 启动都会执行

**用途**：
- 等待依赖服务（如数据库）ready
- 预先拉取配置或凭证
- 准备数据目录

## 十一、容器内运行程序的进程结构

### 11.1 直接运行程序

执行 `docker run ubuntu python main.py`：

```
容器内视角（隔离后看到的）：
PID 1: python main.py  ← 你是 PID=1

宿主机视角（真实情况）：
PID 30000: python main.py  ← docker exec 创建的新进程
```

**你运行的就是 PID=1 进程本身。**

### 11.2 先启动容器再运行程序

```bash
docker run -it ubuntu /bin/bash
# 容器内执行：
python main.py
```

```
容器内进程树：
PID 1: /bin/bash           ← 你的 bash 是 PID=1
  └── PID 10: python main.py  ← python 是 bash 的子进程

宿主机进程树：
PID 20000: /bin/bash (容器主进程)
  └── PID 20001: python main.py (bash 的子进程)
```

**Python 进程是容器 ENTRYPOINT 进程的子进程。**

### 11.3 关键理解

无论哪种方式：
- **容器内**看到的 PID 是 Namespace 后的"障眼法"
- **宿主机上**看到的是真实的 PID
- **所有容器内进程都是宿主机进程的子进程或孙进程**

## 十二、Volume 数据持久化

### 12.1 绑定挂载（Bind Mount）

```bash
docker run -v /home:/container/data ubuntu
```

**挂载的是宿主机目录，容器退出后数据不会丢失！**

```
宿主机：/home 目录
     ↓ mount --bind 挂载
容器内：/container/data
```

即使容器删除，宿主机的 `/home` 目录完好无损。

### 12.2 Docker 管理的 Volume（匿名卷）

```bash
docker run -v /data ubuntu
```

Docker 会在 `/var/lib/docker/volumes/` 下创建临时目录。

**容器删除后，这个临时目录会被 Docker 自动清理。**

### 12.3 命名卷（Named Volume）

```bash
docker run -v mydata:/data ubuntu
```

**容器删除后，命名卷的数据仍然保留。**

### 12.4 Volume 类型对比

| 挂载方式 | 容器删除后数据 | 命令示例 |
|---------|--------------|---------|
| 绑定宿主机目录 | **保留** | `-v /home:/data` |
| 匿名卷 | 删除 | `-v /data` |
| 命名卷 | **保留** | `-v mydata:/data` |

### 12.5 查看 Volume 信息

```bash
# 查看 Volume 列表
docker volume ls

# 查看容器挂载信息
docker inspect <container_id> -f '{{.Mounts}}'
```

## 十三、常见问题解答

### Q1: 为什么容器内的 top 命令显示的是宿主机信息？

这是因为 `/proc` 文件系统不了解 Cgroups 限制的存在。解决方案是使用 `lxcfs` 等工具来提供容器内正确的资源视图。

### Q2: cgroup Namespace 是什么？

Linux 4.6+ 新增的 cgroup Namespace，用于隔离 cgroup 文件系统的视图，让容器内的进程看到自己独立的 cgroup 层级结构。

### Q3: docker run -v /home:/test 时，容器内 /test 原有的内容去哪了？

绑定挂载会**隐藏**原有的内容。由于挂载点重定向到 `/home`，原本挂载点的内容被隐藏了，这就是 bind mount 的特性。

## 十四、知识回顾与思考

### 核心要点

1. **容器是进程**：容器本身不是实体，是通过 Namespace 和 Cgroups 隔离和限制的进程
2. **Namespace 是视图隔离**：修改进程看到的资源视图，但资源本身是共享的
3. **Cgroups 是资源限制**：防止进程占用过多资源
4. **rootfs 是文件系统**：提供容器内独立的文件系统视图
5. **docker exec 是 Namespace 加入**：通过 setns() 加入容器的 Namespace
6. **容器内新进程分两类**：PID 1 fork 的子进程由 PID 1 管理；docker exec 进来的进程由 containerd 管理，只是共享 PID Namespace
7. **K8s Pod 是容器组**：同 Pod 容器共享 PID 和 Network Namespace
8. **Init 容器先于主容器执行**：用于初始化准备工作
9. **Volume 数据持久化**：绑定挂载和命名卷在容器删除后数据保留

### 深入思考

1. 如果容器内 PID=1 的进程退出，容器会怎样？（容器也会退出）
2. 如果使用 `--net=host`，容器的网络隔离会发生什么变化？（隔离被移除）
3. 为什么容器不能完全替代虚拟机？（隔离不彻底、安全性问题）
4. K8s 中同一个 Pod 的两个容器如何通信？（通过 localhost 或者共享的 Volume）
5. Init 容器和应用容器谁先启动？（Init 容器先启动，必须全部成功才会启动应用容器）

## 十五、K8s Pause 容器详解

### 15.1 你看到的：每个 Pod 里都有一个"多余的"容器

在任意 K8s 节点上执行 `docker ps`（或 `crictl ps`），你会发现每个 Pod 除了你的业务容器之外，还多了一个"陌生的"容器：

```bash
$ docker ps | grep myapp-pod
a1b2c3d4e5f6   k8s.gcr.io/pause:3.9    "/pause"    ...   k8s_POD_myapp-pod_default_...
f6e5d4c3b2a1   nginx:latest            "nginx -g…"  ...   k8s_nginx_myapp-pod_default_...
b2a1f6e5d4c3   myapp:v1                "python app…" ...   k8s_app_myapp-pod_default_...
```

这个 `pause` 容器几乎不消耗资源（镜像只有 ~700KB），它执行的是一个极简的 C 程序——只做一件事：**无限期暂停（`pause()` 系统调用）**，等待信号。

```c
// Pause 容器的核心逻辑（简化）
#include <signal.h>
int main() {
    // 屏蔽所有信号，然后无限暂停
    sigset_t mask;
    sigfillset(&mask);
    sigdelset(&mask, SIGKILL);  // SIGKILL 不能屏蔽
    sigdelset(&mask, SIGSTOP);  // SIGSTOP 不能屏蔽
    sigprocmask(SIG_SETMASK, &mask, NULL);
    for (;;) pause();           // 永远睡下去，等信号
    return 0;
}
```

它不处理请求、不监听端口、不读写文件——那它存在的意义是什么？

### 15.2 Pause 容器的核心职责：Namespace 的"锚点"

回顾前面第四节的 `setns()` 机制：一个进程想加入某个 Namespace，必须有一个**已经在那个 Namespace 里的进程**作为"入口"——通过打开它的 `/proc/[pid]/ns/xxx` 文件来拿到 Namespace 的 fd。

Pause 容器就是这个"入口"。它是 **Pod 中第一个被创建的容器**，也是**最后一个被销毁的容器**。

**它的生命周期决定了整个 Pod 的 Namespace 生命周期：**

```
时间线：
1. Kubelet 创建 Pause 容器
   → 内核为其创建全新的 Network + PID + IPC Namespace
2. Kubelet 依次启动业务容器（nginx、app）
   → 每个业务容器通过 setns() 加入 Pause 容器的 Namespace
3. 业务容器正常运行
   → 它们看到的 localhost、PID 列表、共享内存都来自 Pause 的 Namespace
4. Pod 被删除
   → 业务容器先被停止
   → Pause 容器最后被停止
   → 所有 Namespace 随着最后一个进程退出而被内核回收
```

### 15.3 三个 Namespace 的锚定

Pause 容器同时锚定了 Pod 内的三种共享 Namespace：

```
┌──────────────────────────────────────────────────────┐
│                    K8s Pod                            │
│                                                       │
│   ┌──────────────────────────────────────┐            │
│   │        Pause 容器 (PID=1)             │            │
│   │   ● Network Namespace  ←── 锚定 ──┐   │            │
│   │   ● PID Namespace      ←── 锚定 ──┤   │            │
│   │   ● IPC Namespace      ←── 锚定 ──┤   │            │
│   └──────────────────────────────────────┘            │
│                                          │            │
│   ┌──────────┐  ┌──────────┐            │            │
│   │ nginx    │  │  app     │   setns()  │            │
│   │ :80      │  │ python   │ ← 加入 ───┘            │
│   └──────────┘  └──────────┘                         │
│                                                       │
│   效果：                                               │
│   ● nginx 和 app 共享 localhost → localhost:80 可通    │
│   ● app 里 ps aux 能看到 nginx 的进程                  │
│   ● 共享内存 / 信号量 / 消息队列在容器间互通             │
└──────────────────────────────────────────────────────┘
```

| Namespace | Pause 容器锚定的作用 |
|-----------|---------------------|
| **Network** | Pod 内所有容器共享同一个网络栈——同一个 IP、同一个 localhost、同一组端口。没有 Pause，每个容器各自有独立网络栈，`localhost` 互访就不存在了 |
| **PID** | Pod 内所有容器共享同一个 PID 视图。`shareProcessNamespace: true` 时，容器间可以 `ps` 看到彼此进程 |
| **IPC** | Pod 内容器可以通过共享内存、信号量、POSIX 消息队列通信，无需走网络 |

### 15.4 为什么不能"随便挑一个业务容器当锚点"？

一个自然的疑问：为什么不直接用 nginx 或 app 容器充当 Namespace 锚点，非要额外跑一个 Pause？

**核心原因：稳定性和生命周期解耦。**

| 场景 | 如果 nginx 当锚点 | 有 Pause 容器时 |
|------|-------------------|----------------|
| nginx 崩溃重启 | Network Namespace 随 nginx 退出而销毁，app 容器网络瞬间断裂，Pod 内所有容器都受影响 | nginx 重启不影响 Pause，Network Namespace 毫发无损，app 容器网络照常 |
| nginx 镜像更新/配置变更 | 重建 nginx = 重建整个 Pod 的 Namespace | nginx 重建只是业务容器替换，Pod 网络层不变 |
| 多容器任意重启组合 | 锚点容器不能随便死 | 任何业务容器崩溃、重启、替换，Pause 始终存活 |

**一句话：Pause 把"Pod 的基础设施层"（网络、PID、IPC）和"业务层"（nginx、app）解耦了。** 业务容器可以随意创建、销毁、重启，而 Pod 的 IP、网络栈、共享内存等基础设施在 Pod 的整个生命周期内保持稳定。

### 15.5 Pause 容器的创建过程（底层视角）

当 Kubelet 收到"创建 Pod"的指令时，它不是直接启动业务容器，而是先走以下流程：

```
1. CRI: RunPodSandbox
   → containerd 创建 Pause 容器
   → 内核创建 Network + PID + IPC Namespace
   → CNI 插件为 Pause 容器配置网络（分配 IP、创建 veth pair、配置路由）
   → Pause 容器进入 pause() 无限睡眠

2. CRI: CreateContainer (nginx)
   → containerd 创建 nginx 容器进程
   → nginx 进程通过 setns() 加入 Pause 的 Network + PID + IPC Namespace
   → 启动 nginx

3. CRI: CreateContainer (app)
   → containerd 创建 app 容器进程
   → app 进程通过 setns() 加入 Pause 的 Network + PID + IPC Namespace
   → 启动 python app

4. CRI: StartContainer (逐个启动)
   → nginx 和 app 开始工作，共享 Pause 容器的 Namespace
```

关键细节：**CNI 网络配置是给 Pause 容器做的**——Pod 的 IP 地址实际上是绑定在 Pause 容器的网络 Namespace 中。业务容器什么都没做就"自动"有了网络，因为它们加入了 Pause 的网络 Namespace。

### 15.6 一个实验：手动验证 Pause 的作用

可以通过 `lsns` 和 `/proc` 来验证上述机制：

```bash
# 1. 找到 Pause 容器的 PID
$ ps aux | grep pause
root     12345  ... /pause

# 2. 查看 Pause 容器的所有 Namespace inode
$ ls -l /proc/12345/ns/
net -> net:[4026533001]
pid -> pid:[4026533002]
ipc -> ipc:[4026533003]

# 3. 找到 nginx 容器的 PID
$ ps aux | grep nginx
root     12350  ... nginx: master process

# 4. 确认 nginx 和 Pause 共享同一个 Network Namespace
$ readlink /proc/12350/ns/net
net:[4026533001]   # ← 和 Pause 完全相同的 inode！

# 5. 同理检查 PID Namespace
$ readlink /proc/12350/ns/pid
pid:[4026533002]   # ← 同一个！

# 6. 检查 app 容器
$ readlink /proc/12355/ns/net
net:[4026533001]   # ← 三个容器，同一个 Network Namespace
```

三个容器（Pause、nginx、app）的 `/proc/*/ns/net` 指向同一个 inode，证明它们共享同一个 Network Namespace。

### 15.7 对应到笔记前面的知识

| 前面的知识点 | Pause 容器中的体现 |
|-------------|-------------------|
| `clone()` + `CLONE_NEWNET` | Pause 容器创建时，内核为它创建全新的 Network Namespace |
| `/proc/[pid]/ns/net` 虚拟文件 | 业务容器通过打开 Pause 的 `/proc/12345/ns/net` 拿到 Namespace fd |
| `setns()` 系统调用 | 业务容器通过 `setns(fd, CLONE_NEWNET)` 加入 Pause 的网络栈 |
| bind mount 保持 Namespace 存活 | Pause 进程本身就是"活锚点"，只要 Pause 不退出，Namespace 就不会被内核回收 |
| PID 1 退出 = 容器终止 | Pause 是 Pod 的 PID 1，但它是极简 C 程序，几乎不会崩溃——这正是选它做锚点的原因 |

### 15.8 一句话总结

> **Pause 容器是 Pod 的"地基"——它不干任何业务活，只负责创建并持有一组 Namespace，让 Pod 内的所有业务容器能通过 `setns()` 共享同一个网络栈、PID 视图和 IPC 空间。它是 Pod 中第一个创建、最后一个销毁的容器，把基础设施的生命周期和业务容器的生命周期完全解耦。**
