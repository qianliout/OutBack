# Kubernetes 认证与授权机制笔记

## 1. 引入与核心概念

当一个请求到达 Kubernetes 的 API Server 时，它会经历三个主要的安全关卡：
1. **认证 (Authentication)**：你是谁？提取请求中的身份信息。
2. **授权 (Authorization)**：你能做什么？判断提取出的身份是否有权限执行特定的操作。
3. **准入控制 (Admission Control)**：你的请求内容合法吗？对请求进一步校验或修改。

在 K8s 中，主要有两种安全主体（访问者）：
- **User Accounts (普通用户)**：比如集群管理员、开发人员。K8s 本身不管理普通用户，通常由外部的身份管理系统（如企业级身份认证系统）管理。
- **Service Accounts (服务账户)**：K8s 内部管理的用户，专门给运行在 Pod 中的进程使用，让它们能够合法地访问 API Server。

可以把它理解为 Pod 中程序的身份，而不是人的账号。Pod 里的应用、控制器或脚本如果需要读取 Pod、监听资源变化、更新 ConfigMap 等，就需要以某个 ServiceAccount 的身份访问 API Server。它负责说明“我是谁”，至于“我能做什么”，还需要再结合 RBAC 等授权机制判断。

### ServiceAccount 补充说明

#### 1. ServiceAccount 在 Pod 里是怎么挂载 Token 的

当 Pod 使用某个 ServiceAccount 启动后，Kubelet 会在 Pod 内挂载一组与身份相关的文件，默认路径通常是 `/var/run/secrets/kubernetes.io/serviceaccount`。其中最重要的是 `token`、`ca.crt` 和 `namespace` 这几个文件。

- `token`：供 Pod 内程序访问 API Server 时使用的身份凭证。
- `ca.crt`：API Server 的 CA 证书，用来校验服务端证书是否合法。
- `namespace`：当前 Pod 所在的命名空间，方便程序感知自身运行环境。

Pod 内程序如果使用官方客户端库，通常会自动读取这几个文件并组装访问配置；如果直接发 HTTP 请求，也可以手动读取 `token` 并放到请求头 `Authorization: Bearer <token>` 中。

在较新的 Kubernetes 版本中，ServiceAccount Token 一般通过投射卷动态挂载，而不是长期保存在普通 Secret 中。这样做的好处是 Token 生命周期更短、可以自动轮转、泄露后的风险更小。

如果不希望某个 Pod 自动获得这类凭证，可以在 Pod 或 ServiceAccount 上关闭自动挂载。例如将 `automountServiceAccountToken` 设置为 `false`。这在一些完全不需要访问 API Server 的业务 Pod 中很常见。

#### 2. ServiceAccount 和 RBAC 的完整配合流程

ServiceAccount 解决的是认证问题，RBAC 解决的是授权问题。两者通常按下面的顺序配合工作：

1. 创建或指定一个 ServiceAccount，作为 Pod 中程序的身份。
2. Pod 启动后，获得与该 ServiceAccount 对应的 Token。
3. 程序使用这个 Token 请求 API Server。
4. API Server 先验证 Token 是否有效，并识别出请求者是谁。
5. 认证成功后，授权模块继续检查这个身份是否拥有目标操作的权限。
6. 如果该 ServiceAccount 被 RoleBinding 或 ClusterRoleBinding 绑定到了合适的 Role 或 ClusterRole，请求才会被允许。

可以把这个过程理解成“先验明身份，再检查权限”。

举个例子，一个运行在 Pod 中的控制器想读取当前命名空间下的 Pod 列表：

- 它先以某个 ServiceAccount 的身份发起请求。
- API Server 认证通过后，确认它确实是这个 ServiceAccount。
- RBAC 再检查它是否具备 `get`、`list`、`watch` 这些针对 `pods` 资源的权限。
- 如果没有绑定相应 Role，请求就会返回 `403 Forbidden`，即使认证已经成功也一样不能操作资源。

所以可以记住一个关键点：有 ServiceAccount 不代表有权限；能否执行操作，最终取决于 RBAC 规则是否放行。

#### 3. 为什么生产环境里要避免滥用 default ServiceAccount

每个命名空间通常都会自动带一个名为 `default` 的 ServiceAccount。如果创建 Pod 时没有显式指定 `serviceAccountName`，这个 Pod 往往就会默认使用它。

这样做在开发和测试环境里很方便，但在生产环境里容易带来以下问题：

- 身份不清晰：多个不同业务共用同一个 `default` ServiceAccount，审计时很难快速分辨到底是谁在访问 API。
- 权限容易扩散：一旦有人为了图省事给 `default` 绑定了较高权限，这个命名空间下大量未显式声明身份的 Pod 都会继承这些权限。
- 不符合最小权限原则：不同应用需要的权限通常不同，共用一个默认身份会让权限设计变得粗糙。
- 风险面更大：某个 Pod 一旦被入侵，攻击者就可能直接利用这个默认身份去访问集群资源。

更推荐的做法是：

- 为不同应用、控制器或任务创建专门的 ServiceAccount。
- 每个 ServiceAccount 只绑定完成当前工作所需的最小权限。
- 对不需要访问 API Server 的 Pod，关闭 `automountServiceAccountToken`。
- 避免给 `default` ServiceAccount 绑定额外高权限，必要时仅保留最基础配置。

总结一下，`default` ServiceAccount 最大的问题不是“不能用”，而是“很容易被无意识地滥用”。生产环境更强调身份隔离、最小权限和可审计性，因此最好显式为关键工作负载设计独立身份。

## 2. 认证机制 (Authentication)

认证的目的是从请求中提取出用户的身份信息（如用户名 Username、用户 ID UID、用户组 Groups）。

K8s 支持同时开启多种认证方式。只要有一种方式认证成功，请求就会进入下一环节。如果都不成功，则返回 `401 Unauthorized`（未授权）。

常见的认证方式主要包括以下几种，下面为你详细拆解：

### 1. X.509 客户端证书
这是 K8s 中最基础、也是最常用的一种安全认证方式。
- **适用场景**：集群内部组件之间的通信（比如 kubelet、kube-proxy 与 API Server 的通信），以及集群管理员通过 `kubeconfig` 文件操作集群。
- **工作原理**：K8s 启动时会配置一个受信任的根证书（CA）。客户端在发送请求时，必须携带由这个 CA 签发的证书。
- **身份提取**：API Server 会验证证书的合法性，并从证书的字段中提取身份信息。通常把证书的 `CN (Common Name)` 字段作为 K8s 的用户名（User），把 `O (Organization)` 字段作为用户组（Group）。

### 2. 静态 Token 文件
这是一种非常原始和简单的认证机制。
- **适用场景**：通常只在测试环境或极简单的场景下使用，**强烈不推荐用于生产环境**。
- **工作原理**：管理员事先在一个普通的文本文件（CSV格式）中写好 Token、用户名、用户ID和所属组。然后在启动 API Server 时通过参数加载这个文件。
- **致命缺点**：Token 永久有效，且如果要增加或修改用户，必须修改这个文件并**重启 API Server** 才能生效，非常不灵活。

### 3. Bootstrap Token (引导 Token)
这是一种特殊的、动态管理的 Token。
- **适用场景**：主要用于新节点（Node）首次加入集群时的引导认证（比如使用 `kubeadm join` 命令时）。
- **工作原理**：新节点刚启动时，并没有属于自己的 X.509 证书。它会使用一个短期的 Bootstrap Token 去向 API Server 证明自己的合法性，并申请属于自己的永久证书（TLS Bootstrapping）。
- **特点**：它是以 K8s Secret 的形式存在于集群中（存在 `kube-system` 命名空间下），可以动态创建、过期和撤销。

### 4. Service Account Tokens
这是 K8s 专门为集群内部的应用程序设计的一种认证方式。
- **适用场景**：运行在 Pod 内部的代码或进程，需要调用 K8s API（例如获取当前集群有哪些 Pod）时使用。
- **工作原理**：当你创建一个 Pod 时，K8s 会自动（或根据你的指定）将一个包含 Token 信息的目录挂载到容器内部（通常在 `/var/run/secrets/kubernetes.io/serviceaccount`）。这个 Token 本质上是一个 JWT（JSON Web Token）格式的字符串。
- **特点**：它与特定的命名空间（Namespace）绑定，由 K8s 内部全自动管理（签发、轮转），开发者无需手动干预。

### 5. OpenID Connect (OIDC) Tokens
这是一种基于 OAuth2 协议的企业级认证扩展。
- **适用场景**：当公司规模变大，需要把 K8s 集群接入公司统一的身份认证中心（如企业微信、钉钉、GitLab、AD 域等单点登录系统）时使用。
- **工作原理**：K8s API Server 不直接负责验证密码。用户先去外部的认证中心登录，拿到一个 OIDC Token（也是 JWT 格式），然后把它放在请求头中发给 API Server。API Server 只需要向认证中心核实这个 Token 是不是伪造的即可。
- **特点**：非常适合企业级多集群的人员权限统一管理，员工离职后在统一后台禁用账号，K8s 集群的权限也随之失效。

## 3. 授权机制 (Authorization)

认证成功后，API Server 知道了你是谁。接下来，授权组件会检查你是否有权限执行当前的操作（比如查看 Pod、删除 Deployment 等）。

常见的授权模式：
- **Node Authorization**：专门给 kubelet 组件使用的特殊授权模式，限制 kubelet 只能访问自己节点上的资源。
- **Webhook Authorization**：将授权检查委托给外部服务，支持动态的复杂策略（如 OPA Gatekeeper）。
- **RBAC (Role-Based Access Control)**：基于角色的访问控制。这是目前 K8s 中最核心、最常用、也是必须掌握的授权模式。

### RBAC 深度解析与场景实战

RBAC 通过四个核心对象来管理权限。我们可以将其通俗地理解为：“谁（Subject）”在“哪里（Namespace/Cluster）”能对“什么（Resource）”执行“哪些操作（Verb）”。

1. **Role (角色)**：定义了一组对特定命名空间（Namespace）内资源的操作权限。
2. **ClusterRole (集群角色)**：和 Role 类似，但它的权限范围是整个集群，不局限于某个特定的命名空间。
3. **RoleBinding (角色绑定)**：将 Role 绑定给特定的用户（User）或服务账户（ServiceAccount），使其在特定的命名空间内拥有相应的权限。
4. **ClusterRoleBinding (集群角色绑定)**：将 ClusterRole 绑定给用户或服务账户，使其在整个集群范围内拥有相应的权限。

在定义权限规则（`rules`）时，我们通常需要明确三个关键字段：
- `apiGroups`：API 组，例如 `""`（核心组，包含 pod, service 等）、`apps`（包含 deployment, statefulset 等）。
- `resources`：资源类型，例如 `pods`, `deployments`, `secrets`。
- `verbs`：动作，例如 `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`。

下面通过三种最典型的实战场景，把理论和配置结合起来：

#### 场景一：单命名空间授权 (Role + RoleBinding)
- **理论**：最基础的场景，将权限严格限制在单个命名空间内，适合多团队多项目的隔离环境。
- **实操**：允许开发人员 `alice` 在 `dev` 命名空间下管理（增删改查）Deployment。

```yaml
# 1. 创建 Role (定义能做什么)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: deployment-manager
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
---
# 2. 创建 RoleBinding (决定谁能做，在哪里做)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-manage-deployments
  namespace: dev
subjects:
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: deployment-manager
  apiGroup: rbac.authorization.k8s.io
```

#### 场景二：全局集群授权 (ClusterRole + ClusterRoleBinding)
- **理论**：适用于集群管理员，或者需要监控整个集群的系统组件。权限在所有命名空间及集群级别的资源（如 Nodes, PersistentVolumes）上生效。
- **实操**：允许监控组件的 ServiceAccount `monitor-sa` 查看集群所有的 Node 和全命名空间的 Pod。

```yaml
# 1. 创建 ClusterRole (注意：没有 namespace 字段)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-monitor
rules:
- apiGroups: [""]
  resources: ["nodes", "pods"]
  verbs: ["get", "list", "watch"]
---
# 2. 创建 ClusterRoleBinding (全局生效)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: monitor-global-binding
subjects:
- kind: ServiceAccount
  name: monitor-sa
  namespace: monitoring # SA 所在的命名空间
roleRef:
  kind: ClusterRole
  name: cluster-monitor
  apiGroup: rbac.authorization.k8s.io
```

#### 场景三：定义复用，按需下发 (ClusterRole + RoleBinding) **【重点技巧】**
- **理论**：如果你有几十个命名空间，每个命名空间都需要一个“只读”角色。如果在每个命名空间都去创建一个相同的 Role，维护成本极高。K8s 允许你创建一个 ClusterRole 作为“权限模板”，然后通过 **RoleBinding** 将其绑定到特定的命名空间。这样权限定义只有一份，但在哪里生效由 RoleBinding 所在的命名空间决定。
- **实操**：复用 K8s 内置的 `view` 这个 ClusterRole 模板，将其授予用户 `bob`，但只允许他在 `test` 命名空间生效。

```bash
# 我们甚至不需要写 YAML，可以直接使用 kubectl 命令行快速创建 RoleBinding
kubectl create rolebinding bob-view-test \
  --clusterrole=view \
  --user=bob \
  --namespace=test
```

**核心逻辑总结**：Role 和 ClusterRole 决定了“能做什么”，而 Binding 决定了“谁能做”。特别是场景三中，虽然绑定的角色是 `ClusterRole`（全局的），但由于使用的是 `RoleBinding`（局部的），`bob` 最终只能在 `test` 命名空间里行使 `view` 权限。这就是 RBAC 极具灵活性的一面。

## 4. 准入控制 (Admission Control)

当请求通过了认证和授权后，还会经过准入控制器的检查。它可以在资源被持久化到 etcd 之前，对请求进行拦截、修改或拒绝。属于安全防线的最后一环。

主要分为两类 Webhook：
- **Mutating (变更)**：可以自动修改请求的对象。比如给新建的 Pod 自动注入某个特殊的 Sidecar 容器。
- **Validating (校验)**：检查请求对象是否符合规范。比如检查 Pod 的镜像是否来自受信任的内部镜像仓库，如果不是则拒绝创建。

## 5. 认证与授权的操作实战

光有理论不够，下面通过两个最典型的场景，演示具体的命令行操作和 YAML 配置文件。

### 实战一：为新员工签发 X.509 证书并分配 RBAC 权限

假设新员工叫 `zhangsan`，属于 `dev-group` 组，我们需要只允许他查看 `dev` 命名空间下的 Pod。

**第一步：生成私钥和证书签名请求 (CSR)**
在终端执行以下命令：
```bash
# 1. 生成张三的私钥
openssl genrsa -out zhangsan.key 2048

# 2. 生成 CSR，注意这里 CN 就是用户名(User)，O 就是组名(Group)
openssl req -new -key zhangsan.key -out zhangsan.csr -subj "/CN=zhangsan/O=dev-group"
```

**第二步：在 K8s 中创建并批准 CSR**
把上面生成的 `zhangsan.csr` 内容进行 Base64 编码后，提交给 K8s 集群：
```yaml
# zhangsan-csr.yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: zhangsan-access
spec:
  request: <这里填入 base64 编码后的 csr 内容>
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - client auth
```
执行命令并由管理员审批：
```bash
kubectl apply -f zhangsan-csr.yaml

# 管理员审批通过该证书请求
kubectl certificate approve zhangsan-access

# 提取生成的有效证书文件
kubectl get csr zhangsan-access -o jsonpath='{.status.certificate}' | base64 -d > zhangsan.crt
```

**第三步：配置 RBAC 权限**
创建 Role 和 RoleBinding，赋予 `zhangsan` 权限：
```yaml
# rbac-zhangsan.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
- apiGroups: [""] # "" 代表核心 API 组
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-zhangsan
  namespace: dev
subjects:
- kind: User
  name: zhangsan # 对应证书中的 CN 字段
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader # 绑定上面的 Role
  apiGroup: rbac.authorization.k8s.io
```
执行 `kubectl apply -f rbac-zhangsan.yaml` 即可生效。

**第四步：新员工配置 kubeconfig**
张三拿到 `zhangsan.key` 和 `zhangsan.crt` 后，写入自己的 kubeconfig 即可安全访问集群：
```bash
# 设置凭证
kubectl config set-credentials zhangsan --client-certificate=zhangsan.crt --client-key=zhangsan.key
# 设置上下文
kubectl config set-context zhangsan-context --cluster=kubernetes --namespace=dev --user=zhangsan
# 切换使用该上下文
kubectl config use-context zhangsan-context
```

### 实战二：Pod 内部使用 ServiceAccount 访问 API

如果你的应用程序（比如一个自定义控制器或者监控插件）跑在 Pod 里，需要调用 K8s API 获取集群信息：

**第一步：创建 ServiceAccount**
```bash
kubectl create serviceaccount my-app-sa -n dev
```

**第二步：为 ServiceAccount 绑定权限**
我们复用上面实战一中的 `pod-reader` Role：
```yaml
# bind-sa.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-sa
  namespace: dev
subjects:
- kind: ServiceAccount # 这里变为了 ServiceAccount
  name: my-app-sa      # 指定刚才创建的 SA 名字
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```
执行 `kubectl apply -f bind-sa.yaml`。

**第三步：在 Pod 中使用该 ServiceAccount**
```yaml
# my-app-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  namespace: dev
spec:
  serviceAccountName: my-app-sa # 关键：指定刚才创建的账户
  containers:
  - name: my-app-container
    image: nginx:latest
```
Pod 启动后，K8s 会自动将 JWT Token 挂载到容器内部的 `/var/run/secrets/kubernetes.io/serviceaccount/token` 路径。应用直接读取该文件作为 Bearer Token 发送 HTTP 请求即可访问 API Server。

> **💡 避坑提示：如果我不设置 `serviceAccountName` 会怎样？**
> 如果你在 Deployment/Pod 中没有显式指定 `serviceAccountName`，K8s 准入控制器会**自动为你挂载当前命名空间下名为 `default` 的 ServiceAccount**。
> - **权限情况**：在默认情况下，这个 `default` 账户**没有任何权限**（除了能验证自己的身份外，调用任何 API 都会报 `403 Forbidden`）。
> - **安全风险**：如果有的管理员为了图省事，直接把高权限（比如 `cluster-admin`）绑定给了某个命名空间的 `default` 账户，那么这个命名空间下**所有未指定账户的 Pod 都会继承这个高权限**！这会导致严重的安全隐患（例如被黑客攻破的业务 Pod 可以直接删掉整个集群）。
> - **最佳实践**：为每个需要访问 API Server 的应用创建**独立的 ServiceAccount**。如果业务 Pod 完全不需要访问 API Server，可以在 Pod 的 spec 中设置 `automountServiceAccountToken: false`，彻底关闭 Token 的自动挂载。

---

## 6. 安全最佳实践与排错

- **权限最小化原则 (Least Privilege)**：永远只赋予用户或服务账户完成工作所需的最小权限。绝不要滥用 ClusterRoleBinding 授予集群管理员权限（如 `cluster-admin`）。
- **排错利器**：使用 `kubectl auth can-i` 命令快速测试自己或别人的权限。
  - 测试自己：`kubectl auth can-i delete pods --namespace dev`
  - 测试特定的 ServiceAccount：`kubectl auth can-i list secrets --as=system:serviceaccount:default:my-sa`
- **审计日志 (Audit Logging)**：开启 K8s 审计日志，记录所有 API 请求。当出现安全事件或频繁被拒绝的请求时，审计日志是追踪的最好工具。
- **常见错误排查**：
  - **401 Unauthorized**：通常是证书过期、Token 无效或 kubeconfig 配置错误导致身份未被识别。
  - **403 Forbidden**：通常是身份认证通过了，但是 RBAC 权限没有配对。比如：配错了 Namespace、忘记绑定对应的动作 (Verb)，或者绑定的对象名字拼写错误。
