## 一、基础概念

### 1. 什么是负载均衡？

负载均衡（Load Balancing）是将工作负载（网络请求、计算任务等）分摊到多个计算资源（服务器、容器、进程等）上的技术。其核心目标：

| 目标 | 说明 |
| :--- | :--- |
| **高可用** | 单节点故障时自动摘除，流量切换到健康节点 |
| **高性能** | 并行处理，提升系统整体吞吐量 |
| **可扩展** | 水平扩容时流量自动分配到新节点 |
| **可维护** | 灰度发布、滚动升级时平滑切流 |

### 2. 负载均衡的分层

```
┌──────────────────────────────────────────────────────┐
│  二层 (数据链路层) 负载均衡                              │
│  基于 MAC 地址转发，代表：LVS-DR 模式                     │
├──────────────────────────────────────────────────────┤
│  三层 (网络层) 负载均衡                                  │
│  基于 IP 地址转发，代表：LVS-NAT、LVS-TUN 模式             │
├──────────────────────────────────────────────────────┤
│  四层 (传输层) 负载均衡                                  │
│  基于 IP:Port 转发，代表：LVS、Nginx Stream、HAProxy TCP │
├──────────────────────────────────────────────────────┤
│  七层 (应用层) 负载均衡                                  │
│  基于 HTTP Header/URL/Cookie 转发，代表：Nginx HTTP、Traefik│
└──────────────────────────────────────────────────────┘
```

**面试关键区分**：四层只看 IP + Port，不关心内容，性能高；七层能解析 HTTP 协议，可以做基于 URL/Cookie/Host 的路由，性能略低但功能强。

## 二、负载均衡算法及原理

### 算法全景图

| 算法 | 类型 | 核心思想 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 轮询 (Round Robin) | 静态 | 按顺序轮流分配 | 节点性能一致 |
| 加权轮询 (Weighted RR) | 静态 | 按权重比例轮流分配 | 节点性能异构 |
| 随机 (Random) | 静态 | 随机选择节点 | 简单场景 |
| 加权随机 (Weighted Random) | 静态 | 按权重概率随机选择 | 节点性能异构 |
| 最小连接数 | 动态 | 选择当前连接数最少的节点 | 长连接场景 |
| 加权最小连接数 | 动态 | 连接数/权重最小的节点 | 长连接 + 异构节点 |
| 最少响应时间 | 动态 | 选择响应最快的节点 | 对延迟敏感 |
| 源地址哈希 (IP Hash) | 静态 | 对客户端 IP 哈希取模 | 会话保持 |
| 一致性哈希 | 静态 | 哈希环映射，节点变化时影响最小 | 分布式缓存、会话保持 |
| 最低延迟 (EWMA) | 动态 | 指数加权移动平均，兼顾最近和历史延迟 | 现代微服务 |
| 加权最少请求 (LWR) | 动态 | 当前活跃请求数/权重最小 | 请求耗时差异大 |

### 2.1 轮询 (Round Robin)

**原理**：按顺序将请求逐个分配给后端服务器，循环往复。

```
请求序列: R1  R2  R3  R4  R5  R6
分配结果: S1  S2  S3  S1  S2  S3
```

**Go 实现**：

```go
type RoundRobin struct {
    servers []string
    index   uint32  // 用 atomic 保证并发安全
}

func (r *RoundRobin) Next() string {
    idx := atomic.AddUint32(&r.index, 1)
    return r.servers[(idx-1)%uint32(len(r.servers))]
}
```

**优点**：实现简单，绝对均匀。
**缺点**：无视节点当前负载，无视不同节点的处理能力差异。

### 2.2 加权轮询 (Weighted Round Robin)

**原理**：给每个节点分配一个权重，权重越大的节点分配越多的请求。

**平滑加权轮询（Nginx 采用的算法）**：解决传统加权轮询"权重高的节点连续被选中"导致瞬时压力集中的问题。

```
三个节点权重: A=5, B=1, C=1

传统 WRR:  A A A A A B C A A A A A B C ...  (A 被连续打)
平滑 WRR:  A A B A C A A ...  (A 被均匀分散在所有周期中)
```

**Go 实现（Nginx 平滑加权轮询）**：

```go
type SmoothWeighted struct {
    nodes   []*SWNode
}

type SWNode struct {
    Addr          string
    Weight        int // 配置权重（固定）
    CurrentWeight int // 当前权重（动态变化）
}

func (s *SmoothWeighted) Next() string {
    totalWeight := 0
    var best *SWNode

    for _, node := range s.nodes {
        node.CurrentWeight += node.Weight // 每一步累加配置权重
        totalWeight += node.Weight
        if best == nil || node.CurrentWeight > best.CurrentWeight {
            best = node
        }
    }
    best.CurrentWeight -= totalWeight // 被选中的节点减去总权重
    return best.Addr
}
```

**算法步骤**：
1. 每轮所有节点的 CurrentWeight 加上自身的 Weight
2. 选出 CurrentWeight 最大的节点
3. 该节点的 CurrentWeight 减去总权重

**面试追问**：为什么这个算法平滑？因为权重大的节点每次被选后减去总权重，会"掉"下去，其他节点有机"追"上来，权重大的节点追得快，所以被选频率高但不会连续被选。

### 2.3 最小连接数 (Least Connections)

**原理**：记录每个节点当前的活跃连接数，新请求分配给连接数最少的节点。

```go
type LeastConnections struct {
    nodes []*LCNode
}

type LCNode struct {
    Addr    string
    ConnNum int64 // atomic
}

func (l *LeastConnections) Next() string {
    var best *LCNode
    for _, node := range l.nodes {
        if best == nil || atomic.LoadInt64(&node.ConnNum) < atomic.LoadInt64(&best.ConnNum) {
            best = node
        }
    }
    atomic.AddInt64(&best.ConnNum, 1)
    return best.Addr
}
```

**适用场景**：请求处理时间差异大，长连接居多（如 WebSocket、数据库连接池）。
**缺点**：新增节点会瞬间承接大量请求（"冷启动"问题）。

### 2.4 源地址哈希 (IP Hash)

**原理**：对客户端 IP 做哈希运算，映射到固定节点，同一 IP 的请求始终打到同一节点。

```go
func ipHash(clientIP string, servers []string) string {
    h := fnv.New32a()
    h.Write([]byte(clientIP))
    idx := h.Sum32() % uint32(len(servers))
    return servers[idx]
}
```

**优点**：天然支持会话保持（Session Sticky），无需额外存储。
**缺点**：节点增减会导致大量映射关系变化（哈希重分布），引发缓存雪崩。

### 2.5 一致性哈希 (Consistent Hashing) — ⭐ 必问

**原理**：将哈希空间组织成一个环（0 ~ 2³²-1），节点和请求都映射到环上，请求沿环顺时针找到第一个节点。

```
哈希环 (0 ~ 2³²-1):
        0
   s3 ●    ● s1
        /\
       /  \
      /    \
     /  ●k1 \      —— k1 打到 s1
    /        \
   ●  s2      ●
```

**节点变化影响**：
- 传统哈希取模：增删节点导致几乎所有映射变化
- 一致性哈希：增删节点只影响相邻一小段

**虚拟节点**：解决节点分布不均导致的"数据倾斜"问题。每个物理节点映射为多个虚拟节点，均匀散布在哈希环上。

**Go 实现**：

```go
type ConsistentHash struct {
    hashRing  []uint32           // 排序的哈希值列表
    hashMap   map[uint32]string  // 哈希值 → 节点地址
    vNodeNum  int                // 每个物理节点的虚拟节点数
}

func (c *ConsistentHash) Add(addr string) {
    for i := 0; i < c.vNodeNum; i++ {
        hash := crc32.ChecksumIEEE([]byte(fmt.Sprintf("%s#%d", addr, i)))
        c.hashRing = append(c.hashRing, hash)
        c.hashMap[hash] = addr
    }
    sort.Slice(c.hashRing, func(i, j int) bool {
        return c.hashRing[i] < c.hashRing[j]
    })
}

func (c *ConsistentHash) Get(key string) string {
    hash := crc32.ChecksumIEEE([]byte(key))
    idx := sort.Search(len(c.hashRing), func(i int) bool {
        return c.hashRing[i] >= hash
    })
    // 环形：超出范围则回到第一个
    if idx == len(c.hashRing) {
        idx = 0
    }
    return c.hashMap[c.hashRing[idx]]
}
```

**面试深入**：
- 为什么用虚拟节点？解决节点少时环上分布不均问题（数据倾斜）。
- 新增节点的影响范围？只影响顺时针方向到下一个节点之间的数据。
- 和 Redis Cluster 的哈希槽有什么区别？Redis 用 16384 固定哈希槽，不是一致性哈希环。

### 2.6 最少响应时间 / EWMA

**原理**：记录每个节点的历史响应时间，通过指数加权移动平均（EWMA）计算当前估算延迟，选择延迟最低的节点。

```
EWMA(t) = α × 本次延迟 + (1-α) × EWMA(t-1)
         ↑                      ↑
      α 越大，对最近变化越敏感
      α 越小，越平滑（默认常用 0.2）
```

**适用场景**：微服务间 RPC 调用（如 gRPC 客户端负载均衡），节点处理能力因 GC、资源争抢等原因波动。

### 2.7 加权最少请求 (Least Requests)

**原理**：记录每个节点当前的 inflight（已发出未收到响应的）请求数，选择 `inflight / weight` 最小的节点。

```go
type LeastRequests struct {
    nodes []*LRNode
}

type LRNode struct {
    Addr     string
    Weight   int
    InFlight int64
}

func (l *LeastRequests) Next() string {
    var best *LRNode
    var bestRatio float64
    for _, node := range l.nodes {
        ratio := float64(atomic.LoadInt64(&node.InFlight)) / float64(node.Weight)
        if best == nil || ratio < bestRatio {
            best, bestRatio = node, ratio
        }
    }
    atomic.AddInt64(&best.InFlight, 1)
    return best.Addr
}
```

**对比最小连接数**：Least Requests 考虑的是 **inflight 请求数** 而非 TCP 连接数，更适合 HTTP/2 多路复用或 gRPC 场景（一个连接上有多个请求）。

## 三、常见负载均衡组件及实现

### 3.1 组件总览

| 组件 | 层级 | 性能 | 灵活度 | 典型场景 |
| :--- | :--- | :--- | :--- | :--- |
| **LVS** | L4 | ⭐⭐⭐⭐⭐ (内核态) | ⭐⭐ | 四层高性能入口 |
| **HAProxy** | L4 / L7 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 全能型接入层 |
| **Nginx** | L4 / L7 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 反向代理 + Web 服务 |
| **Traefik** | L7 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 云原生 / K8s Ingress |
| **Envoy** | L7 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | Service Mesh 数据面 |
| **Kong** | L7 | ⭐⭐⭐ | ⭐⭐⭐⭐ | API 网关 |
| **Nginx Stream** | L4 | ⭐⭐⭐⭐ | ⭐⭐⭐ | TCP/UDP 代理 |
| **Keepalived** | L3/L4 | ⭐⭐⭐⭐ | ⭐⭐ | VIP 漂移 / 高可用 |

### 3.2 LVS (Linux Virtual Server) — 四层性能之王

LVS 工作在内核态 `netfilter` 框架上，通过修改/转发 IP 数据包实现负载均衡。不建立 TCP 连接，不解析应用层协议，性能极高。

**三种工作模式**：

| 模式 | 原理 | 优缺点 |
| :--- | :--- | :--- |
| **NAT** | 修改目标 IP 和端口，响应经 LVS 返回 | 简单；LVS 成瓶颈（所有流量双向经过） |
| **DR（直接路由）** | 改 MAC 地址，请求不经 LVS 直接返回 | 性能最高；要求 LVS 和 RS 在同一二层网络 |
| **TUN（隧道）** | IP 隧道封装，请求不经 LVS 直接返回 | 跨网段；IP 隧道有头部开销 |

```
LVS-DR 模式数据流:

Client → LVS(VIP) → 修改 MAC → Real Server
                                Real Server → Client（直接回，不经过 LVS）
```

**面试关键**：LVS 和 Nginx 的区别？
- LVS 是四层，工作在 Linux 内核态，性能极高，但不看 HTTP 内容
- Nginx 是七层（或 Stream 模块做四层），工作在用户态，功能丰富但性能低于 LVS
- 常见组合：LVS 四层入口 → Nginx 七层反向代理 → 应用服务

### 3.3 Nginx 负载均衡

**四层（Stream 模块）**：

```nginx
stream {
    upstream mysql_cluster {
        server 192.168.1.10:3306 weight=5 max_fails=3 fail_timeout=30s;
        server 192.168.1.11:3306 weight=3;
    }
    server {
        listen 3306;
        proxy_pass mysql_cluster;
    }
}
```

**七层（HTTP 模块）**：

```nginx
upstream backend {
    # 算法：默认轮询，可指定 ip_hash / least_conn / random
    least_conn;  # 最小连接数

    server 10.0.0.1:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=1;
    server 10.0.0.3:8080 backup;   # 备份节点，其他都挂时才启用
    server 10.0.0.4:8080 down;     # 手动下线

    keepalive 32;  # 连接池：保持到后端的空闲连接数
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
        proxy_next_upstream error timeout http_500 http_502 http_503;  # 失败重试条件
        proxy_next_upstream_tries 2;       # 最多重试 2 次
        proxy_next_upstream_timeout 5s;    # 重试超时
    }
}
```

**Nginx 健康检查**：

| 机制 | 说明 |
| :--- | :--- |
| **被动检查** | `max_fails` + `fail_timeout`，请求失败 N 次后标记为 down |
| **主动检查** | Nginx Plus 付费版支持主动发送健康检查请求 |
| **第三方模块** | `nginx_upstream_check_module`（淘宝开源） |

**面试追问**：`keepalive` 的作用？
- Nginx 与后端 upstream 之间的连接池大小
- 减少 TCP 三次握手开销，推荐和 `proxy_http_version 1.1` 配合使用

### 3.4 HAProxy

HAProxy 是纯负载均衡器，比 Nginx 更专注代理能力，配置更灵活。

```
frontend web
    bind *:80
    default_backend app

backend app
    balance roundrobin              # 算法
    option httpchk GET /health      # 主动健康检查
    server s1 10.0.0.1:8080 check inter 3s rise 2 fall 3
    server s2 10.0.0.2:8080 check inter 3s rise 2 fall 3
    # check: 开启健康检查
    # inter 3s: 每 3 秒检查一次
    # rise 2: 连续 2 次成功标记为健康
    # fall 3: 连续 3 次失败标记为不健康
```

**HAProxy vs Nginx 选型**：

| 维度 | HAProxy | Nginx |
| :--- | :--- | :--- |
| 定位 | 纯代理/负载均衡 | Web 服务器 + 反向代理 |
| 健康检查 | 原生丰富 | Plus 付费或第三方 |
| 统计页面 | 内置丰富 | 需配置 |
| 静态文件 | 不支持 | 天然支持 |
| 生态 | 少 | 极其丰富（Lua/JS 扩展） |

### 3.5 Keepalived — VIP 高可用

Keepalived 通过 VRRP 协议在多台负载均衡器之间漂移 VIP，解决负载均衡器自身的单点故障。

```
Master (持有 VIP 192.168.1.100)
   │
   │ VRRP 心跳 (组播 224.0.0.18)
   │
Backup (VIP 备份，Master 挂了自动接管)
```

**Keepalived + LVS/Nginx 组合**：

```
         VIP (192.168.1.100)
              │
   ┌──────────┼──────────┐
   │ Keepalived + Nginx  │  Keepalived + Nginx  (Backup)
   │     (Master)        │     (Backup)
   └──────────┼──────────┘
              │
   ┌──────────┼──────────┐
   │   后端服务集群        │
   └─────────────────────┘
```

## 四、Kubernetes 中的负载均衡

### 4.1 K8s 负载均衡全景

外部流量进入 K8s 集群并最终到达 Pod，经过多层负载均衡：

```
Client
  │
  ▼
云厂商 LB (LoadBalancer Service)      ← 第一层：云负载均衡
  │
  ▼
NodePort / ClusterIP                  ← 第二层：kube-proxy (iptables/IPVS)
  │
  ▼
Ingress Controller (Nginx/Traefik)    ← 第三层：七层路由
  │
  ▼
Service → Endpoints                   ← 第四层：服务发现
  │
  ▼
Pod                                   ← 最终目标
```

### 4.2 kube-proxy：Service 的负载均衡实现

kube-proxy 是 K8s Service 负载均衡的核心组件，有三种模式：

| 模式 | 原理 | 性能 | 策略 |
| :--- | :--- | :--- | :--- |
| **userspace** | kube-proxy 本身做代理转发 | ⭐ | 轮询（已废弃） |
| **iptables** | 写 iptables 规则，内核转发 | ⭐⭐⭐ | **随机**（不可配） |
| **IPVS** | Linux IPVS 内核模块转发 | ⭐⭐⭐⭐ | rr/lc/dh/sh 等十种算法 |

**iptables 模式（默认）**：

```
Client → ClusterIP (iptables DNAT)
                    ↓
         随机选一个 Pod IP (通过 -m statistic --mode random --probability)
                    ↓
                  Pod
```

**注意**：iptables 模式下的 Service 负载均衡是 **随机** 的，不是轮询。因为 iptables 规则是固定概率匹配。

**IPVS 模式（生产推荐）**：

```bash
# 查看 IPVS 规则
ipvsadm -Ln
```

```
TCP  10.96.0.1:443 rr       # rr = round robin
  -> 172.17.0.2:6443
  -> 172.17.0.3:6443
```

IPVS 支持的调度算法：

| 缩写 | 算法 |
| :--- | :--- |
| rr | 轮询 |
| wrr | 加权轮询 |
| lc | 最少连接 |
| wlc | 加权最少连接 |
| dh | 目标地址哈希 |
| sh | 源地址哈希 |
| sed | 最短期望延迟 |
| nq | 永不排队 |

### 4.3 Service 类型与负载均衡范围

| Service 类型 | 负载均衡范围 | 原理 |
| :--- | :--- | :--- |
| **ClusterIP** | 集群内部 | kube-proxy 通过 iptables/IPVS 转发到 Pod |
| **NodePort** | 集群外部（通过节点 IP:端口） | 在 ClusterIP 基础上，在每个 Node 上开一个端口 |
| **LoadBalancer** | 公网/外网 | 调用云厂商 API 创建外部 LB，转发到 NodePort |
| **ExternalName** | DNS CNAME | 无负载均衡，纯 DNS 映射 |
| **Headless Service** | 无 | `clusterIP: None`，直接返回 Pod IP 列表，客户端自行负载均衡 |

### 4.4 Ingress / Ingress Controller

Ingress 是七层（HTTP/HTTPS）负载均衡入口规则的抽象，具体转发由 Ingress Controller 实现。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  rules:
  - host: api.example.com      # 基于 Host 的七层路由
    http:
      paths:
      - path: /users           # URL 前缀路由
        pathType: Prefix
        backend:
          service:
            name: user-service
            port:
              number: 80
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 80
```

**Ingress Controller 数据流**：

```
外部请求 → 云 LB → NodePort (或 HostNetwork) → Ingress Controller Pod
                                                      │
                                             根据 Host+Path 路由
                                                      │
                                     ┌────────────────┼────────────────┐
                                     ↓                ↓                ↓
                                user-service    order-service    payment-service
                                  ClusterIP       ClusterIP        ClusterIP
                                     ↓                ↓                ↓
                                   Pods             Pods             Pods
```

**常见 Ingress Controller**：

| Controller | 特点 |
| :--- | :--- |
| **Nginx Ingress** | 最成熟，基于 OpenResty/Nginx |
| **Traefik** | 云原生，自动发现 K8s 服务，支持 Let's Encrypt |
| **Kong Ingress** | API 网关 + Ingress 一体 |
| **Istio Ingress Gateway** | Service Mesh 入口，Envoy 数据面 |
| **AWS ALB Ingress** | 直接创建 AWS Application Load Balancer |

### 4.5 kube-proxy IPVS 模式下的完整转发链路

```
curl http://my-svc.default:80

1. DNS 解析 my-svc.default  →  ClusterIP (如 10.96.1.100)
2. 内核网络栈查找路由，命中断所在的 Node
3. 命中 IPVS 规则: 10.96.1.100:80 → (rr 轮询) → 10.244.1.5:8080 或 10.244.2.3:8080
4. 从 iptables MASQUERADE 规则做 SNAT (源 IP 改为节点 IP)
5. 通过 CNI (Calico/Flannel) 将包送到目标 Pod 所在 Node
6. Pod 收到请求，处理返回
```

**为什么需要 SNAT？** 如果不做源地址转换，Pod 的直接回复可能绕过原路径，客户端收到的回包源 IP 不是 ClusterIP，会被丢弃。

## 五、Go 语言实现负载均衡器

### 5.1 设计一个生产级负载均衡器

需要以下核心组件：

| 组件 | 职责 |
| :--- | :--- |
| **Backend Pool** | 后端节点列表管理（增删改查） |
| **Algorithm** | 负载均衡算法接口 |
| **Health Check** | 主动/被动健康检查，自动摘除/恢复 |
| **Reverse Proxy** | 反向代理，请求转发 |

### 5.2 基础框架

```go
package main

import (
    "net/http"
    "net/http/httputil"
    "net/url"
    "sync"
    "sync/atomic"
    "time"
)

// ============ 1. 后端节点 ============

type Backend struct {
    URL         *url.URL
    Alive       atomic.Bool      // 是否存活
    ReverseProxy *httputil.ReverseProxy
}

// ============ 2. 负载均衡算法接口 ============

type Algorithm interface {
    NextBackend(backends []*Backend) *Backend
}

// ============ 3. 后端池 ============

type ServerPool struct {
    mu       sync.RWMutex
    backends []*Backend
    algo     Algorithm
}

func (p *ServerPool) AddBackend(rawURL string) error {
    u, err := url.Parse(rawURL)
    if err != nil {
        return err
    }
    proxy := httputil.NewSingleHostReverseProxy(u)
    // 自定义错误处理
    proxy.ErrorHandler = func(w http.ResponseWriter, r *http.Request, err error) {
        // 标记此节点不可用，重试下一个
        http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
    }
    backend := &Backend{URL: u, ReverseProxy: proxy}
    backend.Alive.Store(true)

    p.mu.Lock()
    p.backends = append(p.backends, backend)
    p.mu.Unlock()
    return nil
}

func (p *ServerPool) GetAliveBackends() []*Backend {
    p.mu.RLock()
    defer p.mu.RUnlock()
    var alive []*Backend
    for _, b := range p.backends {
        if b.Alive.Load() {
            alive = append(alive, b)
        }
    }
    return alive
}

// GetNextPeer 获取一个健康的后端节点
func (p *ServerPool) GetNextPeer() *Backend {
    alive := p.GetAliveBackends()
    if len(alive) == 0 {
        return nil
    }
    return p.algo.NextBackend(alive)
}

// ============ 4. 健康检查 ============

func (p *ServerPool) HealthCheck(interval time.Duration, path string) {
    ticker := time.NewTicker(interval)
    for range ticker.C {
        p.mu.RLock()
        backends := p.backends
        p.mu.RUnlock()

        for _, b := range backends {
            resp, err := http.Get(b.URL.String() + path)
            alive := err == nil && resp.StatusCode == http.StatusOK
            if resp != nil {
                resp.Body.Close()
            }
            b.Alive.Store(alive)
        }
    }
}

// ============ 5. HTTP Handler ============

func (p *ServerPool) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    // 重试逻辑：失败自动换下一个节点
    maxRetries := 3
    for i := 0; i < maxRetries; i++ {
        backend := p.GetNextPeer()
        if backend == nil {
            http.Error(w, "No backend available", http.StatusServiceUnavailable)
            return
        }
        backend.ReverseProxy.ServeHTTP(w, r)
        return // httputil.ReverseProxy 已处理响应
    }
}
```

### 5.4 标准库中的负载均衡 —— `httputil.ReverseProxy`

Go 标准库 `net/http/httputil` 提供了 `ReverseProxy`，但实际上**没有内置负载均衡**——`NewSingleHostReverseProxy` 只代理到一个后端。

要添加负载均衡，需要自定义 `Director` 函数：

```go
func newLoadBalancedReverseProxy(pool *ServerPool) *httputil.ReverseProxy {
    return &httputil.ReverseProxy{
        Director: func(req *http.Request) {
            backend := pool.GetNextPeer()
            if backend == nil {
                return
            }
            req.URL.Scheme = backend.URL.Scheme
            req.URL.Host = backend.URL.Host
            req.Host = backend.URL.Host

            // 添加 X-Forwarded-For 等头
            if clientIP, _, err := net.SplitHostPort(req.RemoteAddr); err == nil {
                if prior := req.Header.Get("X-Forwarded-For"); prior != "" {
                    req.Header.Set("X-Forwarded-For", prior+", "+clientIP)
                } else {
                    req.Header.Set("X-Forwarded-For", clientIP)
                }
            }
        },
        Transport: &http.Transport{
            MaxIdleConns:        100,
            MaxIdleConnsPerHost: 10,
            IdleConnTimeout:     90 * time.Second,
        },
    }
}
```

### 5.5 gRPC 客户端负载均衡

gRPC 在 Go 中有内置的客户端负载均衡支持：

```go
import (
    "google.golang.org/grpc"
    _ "google.golang.org/grpc/xds" // 高级 LB 策略
)

func main() {
    // round_robin：轮询
    // pick_first：总是连第一个（默认）
    conn, err := grpc.Dial(
        "dns:///backend-service:8080", // DNS 解析多个后端 IP
        grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`),
        grpc.WithInsecure(),
    )
    // ...
}
```

**gRPC 支持的 LB 策略**：

| 策略 | 说明 |
| :--- | :--- |
| `pick_first` | 连接第一个可用地址，失败后换下一个（默认） |
| `round_robin` | 对所有可用后端轮询 |
| `ring_hash` | 一致性哈希（需要 xDS 支持） |
| `least_request` | OTel 加权最少请求（需要 xDS 支持） |

**注意**：gRPC 的 `round_robin` 是基于 **SubConn** 粒度的，即每个已建立的连接轮流使用，不是每个 RPC 请求都重新选节点。

## 六、面试高频追问及回答

### 1. 负载均衡器自身怎么实现高可用？

核心方案：**VIP 漂移**。通过 Keepalived (VRRP 协议) 在多台 LB 之间共享一个虚拟 IP。Master 持有 VIP，故障时 Backup 自动接管。

```
Nginx-1 (Master, VIP)  ←→  Nginx-2 (Backup)
         │
    VIP: 10.0.0.100
```

云厂商环境下通常用 **云 LB + 多 AZ 部署** 替代自建 Keepalived。

### 2. 四层和七层负载均衡的区别？什么时候用哪个？

| 维度 | L4 | L7 |
| :--- | :--- | :--- |
| 处理内容 | IP:Port | HTTP Header/URL/Body |
| 性能 | 高（内核态/简单转发） | 较低（需解析协议） |
| 路由能力 | 仅按 IP:Port | 可按 URL/Cookie/Host/Header |
| 会话保持 | IP 哈希 | Cookie 注入 |

**选型建议**：
- 入口流量大且不需要 HTTP 路由 → LVS (L4) + Nginx (L7) 组合
- 微服务网关 / API 路由 → Nginx / Kong / Traefik (L7)
- 数据库 / Redis 代理 → HAProxy (L4) 或 Nginx Stream

### 3. 一致性哈希中，新增一个节点会有什么影响？

只有新节点顺时针方向到下一个节点之间的数据需要重新分配，不影响其他数据段的映射关系。影响范围 ≈ `1/N`（N 为节点数）。配合虚拟节点，数据倾斜引入的问题也被缓解。

### 4. 如何实现会话保持（Session Sticky）？

| 方式 | 原理 | 缺点 |
| :--- | :--- | :--- |
| IP Hash | 同一 IP 打到同一节点 | 客户端 IP 变化则失效；NAT 网络下大量 IP 相同 |
| Cookie 注入 | Nginx 在 Set-Cookie 中注入 `route=xxx` 标识后端 | 需要七层能力 |
| 统一 Session 存储 | Session 存 Redis，后端节点无状态 | 依赖 Redis；每个请求都需查 Redis |

**生产推荐**：统一 Session 存储（Redis），避免有状态后端。

### 5. Nginx 的健康检查机制？

- **被动**（默认）：`max_fails=3 fail_timeout=30s`，3 次失败后 30 秒内不转发
- **主动**：Plus 付费版或 `nginx_upstream_check_module` 模块，定期主动发送健康检查请求

HAProxy 原生支持主动检查，语法比 Nginx 简洁。

### 6. 负载均衡器"脑裂"是什么？怎么解决？

**脑裂**：两台 Keepalived 都认为自己是 Master，同时持有 VIP，导致流量混乱。

**原因**：VRRP 心跳网络中断，但两台机器本身都正常。

**解决**：
- `split_brain` 脚本检测：ping 网关 + 第三方仲裁节点
- 云环境下直接用云 LB 替代自建
- 配置 `nopreempt`（非抢占模式）

### 7. 如何设计一个支持动态扩缩的负载均衡器？

```
┌──────────────┐       ┌──────────────┐
│  服务注册中心  │ ←── │  新节点注册    │
│ (Etcd/Consul) │      └──────────────┘
└──────┬───────┘
       │ Watch (长轮询/事件)
┌──────▼───────┐
│ 负载均衡器     │ ← 自动感知节点上下线，更新 backends 列表
└──────────────┘
```

结合 Etcd / Consul / Nacos 做服务发现，LB Watch 节点变更事件，动态更新后端池。

## 七、总结：面试速记表

| 考点 | 一句话答案 |
| :--- | :--- |
| L4 vs L7 | L4 看 IP:Port（性能高），L7 看 HTTP（灵活） |
| 轮询 vs 加权轮询 | 轮询绝对均匀无视能力差异；加权按比例分配 |
| Nginx WRR 原理 | CurrentWeight 累加 → 选最大 → 减去总权重 |
| 一致性哈希 | 哈希环 + 顺时针查找 + 虚拟节点解决数据倾斜 |
| LVS-DR | 改 MAC 不经过 LVS 回包，性能最高但需同二层 |
| K8s Service LB | kube-proxy 通过 iptables（随机）或 IPVS（rr/lc/sh 等十种算法） |
| gRPC LB | 客户端侧 LB，`round_robin` 基于 SubConn 粒度 |
| HA 方案 | Keepalived VIP 漂移（VRRP），云上直接用 LB |
| Session 保持 | 推荐 Redis 统一存储，避免 IP Hash 和 Cookie 注入的局限性 |
| Go 实现 | `httputil.ReverseProxy` + 自定义 Director + 算法接口 |
