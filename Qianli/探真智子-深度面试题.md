# 探真智子深度面试题与详细答案

说明：以下内容围绕简历中的“探真智子：AI Agent驱动的智能运维风控系统”项目设计。每道题都给出一个偏真实项目复盘口径的详细答案，回答重点不是概念定义，而是如何落到架构、流程、评测和故障治理上。

## 1. Agent 五类核心能力如何分层设计

题目：在你的描述里，探真智子具备“任务理解、计划生成、多步推理、工具调用、结果校验”五类核心能力。请你从系统架构层面拆解这五类能力分别由哪些模块承担、模块之间如何传递上下文，以及为什么要这样分层，而不是做成一个“大一统”的单 Agent 流程？

详细答案：

如果让我从系统架构上拆，我会把它分成六层，而不是把所有能力都塞进一个统一 Prompt 里。

第一层是接入层，负责接收告警、工单、日志摘要、用户提问等原始输入，并完成基础预处理，比如字段归一、敏感信息脱敏、事件类型初判、租户和环境上下文补全。这样做的原因是，运维风控场景里的原始输入质量差异很大，如果不先清洗，后面的 Agent 理解能力会被脏数据拖垮。

第二层是任务理解层，核心职责是把自然语言需求或者风险事件描述转成结构化任务对象。我一般会抽象出几个核心字段，包括任务类型、对象范围、优先级、约束条件、证据需求和预期输出格式。这里不是直接让模型出最终结论，而是先做意图识别和问题拆解，确保后面的执行是有边界的。

第三层是计划生成层，也就是 Planner。它根据结构化任务生成执行计划，明确需要调用哪些知识源、哪些工具、先做什么后做什么、每一步的退出条件是什么。计划层和执行层一定要分离，因为在复杂事件里，计划本身就是一个需要审计和复用的中间产物。计划分离后，我们可以单独统计“计划质量”，也可以在工具异常时只替换执行策略，而不必重做整个推理链。

第四层是执行与推理层，通常由 Executor 来驱动。它按计划逐步调用检索、工具、规则引擎和子 Agent，在每一步把中间结果写入状态机。这里的重点不是让大模型自由发挥，而是让它在一个受控流程里进行局部判断。多步推理本质上是“受约束的状态迁移”，而不是“无限自由推演”。

第五层是工具编排层，负责统一管理外部能力，比如知识库查询、告警系统查询、工单系统、配置中心、资产系统、漏洞情报接口等。工具层负责参数 schema、超时、重试、熔断、结果标准化和权限控制。这样上层 Agent 不需要关心每个外部系统的接入细节，只关心工具能力语义。

第六层是结果校验层，负责把最终结论和中间证据做一致性核查。比如判断结论是否引用了足够证据、证据是否来自可信源、结论与规则引擎输出是否冲突、风险级别是否和处置动作匹配。如果校验不通过，就回退到指定步骤重新执行，或者降级到人工复核。

这些层之间的上下文传递，我更倾向于使用结构化状态对象，而不是把所有上下文都拼成 Prompt 文本。结构化状态里至少包含 task、plan、toolResults、evidence、intermediateConclusion、finalConclusion、confidence、traceId 这些字段。这样做的好处有三个。

第一，可观测。每一步状态都能落库和回放。

第二，可控。我们可以明确哪些字段可以被模型看到，哪些字段只能给规则引擎或校验器使用。

第三，可降级。某一步失败时，可以从最近一个合法状态继续执行，而不是整条链路重来。

为什么不做一个大一统的单 Agent 流程，核心原因有四个。

第一，复杂风险场景需要可审计，单 Agent 很难回答“为什么得出这个结论”。

第二，工具调用多且不稳定，必须把外部依赖的不确定性隔离出去。

第三，评测要分层做，不然你无法知道问题是理解错了、计划错了、检索错了还是校验没拦住。

第四，系统必须支持灰度和替换，比如换检索策略、换 Planner、换校验器，而不是整个系统一起动。

如果继续追问状态管理放在哪一层，我会回答：状态管理是横切能力，不属于某一个 Agent，而是由工作流引擎统一管理。计划和执行必须分离。某个子模块失效时，我会按“检索降级、工具降级、结论降级”三个层级处理，比如检索失败就切规则库，工具失败就切缓存结果，校验不过就直接转人工，而不是强行输出一个看似完整的答案。

## 2. 多 Agent 协作如何设计

题目：你提到设计了多 Agent 协作框架来处理复杂风险事件。请结合一个真实的高复杂度案例，详细说明主 Agent 和子 Agent 的角色边界、消息协议、协作顺序以及冲突裁决机制。如果两个 Agent 对同一风险事件给出了相互矛盾的结论，你如何判定谁更可信？

详细答案：

我会用一个比较典型的案例来回答，比如“某业务 Pod 在凌晨出现异常外联，镜像最近刚更新，节点上还有异常进程告警，同时镜像仓库扫描提示依赖组件存在高危漏洞”。这种场景不是单点问题，而是镜像、运行时、漏洞情报、行为侧多条证据同时出现，适合多 Agent 协作。

在这个场景里，我一般会定义一个主 Agent 和多个子 Agent。

主 Agent 的职责不是自己分析所有细节，而是做任务拆解、调度和最终裁决。它负责回答三个问题：当前事件需要拆成几个子任务、子任务的执行顺序是什么、最终结论能否闭环。

子 Agent 我通常会拆成四类。

第一类是资产上下文 Agent，负责拉取目标资产、业务归属、最近变更、镜像版本、部署环境等背景信息。

第二类是行为分析 Agent，负责分析运行时进程、网络连接、命令执行链和异常行为特征。

第三类是知识检索 Agent，负责从漏洞知识库、内部案例库、告警规则库里找相似案例和可解释证据。

第四类是处置建议 Agent，基于前面聚合出来的证据，给出隔离、回滚、观察、升级人工等建议。

消息协议上，我不会让 Agent 之间自由传文本，而是统一用结构化消息。每条消息至少包括 requestId、agentRole、inputSchemaVersion、taskGoal、inputPayload、outputPayload、evidenceRefs、confidence、nextAction、errorCode。这样设计是为了让每个子 Agent 的输出都能被主 Agent、校验器和观测系统稳定消费。

协作顺序上，我通常采用“先背景、再证据、后结论”的顺序。

第一步，主 Agent 先调用资产上下文 Agent，拿到对象身份和最近变更，避免后续分析脱离业务上下文。

第二步，并发调用行为分析 Agent 和知识检索 Agent，一个看事实行为，一个看知识证据。

第三步，主 Agent 做一次中间裁决。如果证据冲突明显，就追加一个专门的验证任务，比如重新拉取运行时日志或检查漏洞利用条件是否满足。

第四步，把通过校验的证据交给处置建议 Agent 输出建议。

第五步，主 Agent 统一做最终风险定级和处置动作选择。

冲突裁决机制上，我不会简单按照“哪个 Agent 置信度高就听谁的”，而是看三类因素。

第一类是证据源可信度。直接来自运行时日志、系统调用记录、镜像 SBOM、官方漏洞公告的数据，可信度高于模型总结和二手知识。

第二类是任务适配度。行为分析 Agent 对“是否存在异常外联”更有话语权，知识检索 Agent 对“某漏洞是否具有真实可利用性”更有话语权。

第三类是证据完备性。不是只看结论，而是看结论后面有没有足够支撑链条，比如时间、对象、条件、影响面是否闭环。

如果两个 Agent 结论矛盾，比如行为分析 Agent 认为高危，知识检索 Agent 认为漏洞不可利用，我会优先判断它们是不是在回答两个不同问题。很多冲突其实不是谁对谁错，而是分析维度不同。前者关注行为异常，后者关注漏洞利用条件。我的处理方式是把结论拆成“事实层”和“解释层”。只要事实层已经显示高风险行为，即便知识层暂时不能证明漏洞被利用，我也会先按高危处置，但在结论里注明“不将风险归因到该漏洞本身，需进一步验证利用路径”。

为了避免循环调用、上下文膨胀和重复推理，我会做三件事。

第一，限制工作流深度和最大回合数。

第二，Agent 只接收与自己任务相关的最小上下文，而不是全量会话历史。

第三，中间结果一律结构化沉淀并可复用，相同任务命中缓存就不重复推理。

如果做可观测性，我会记录链路耗时、每个 Agent 的输入输出摘要、工具调用次数、失败原因、证据覆盖率、冲突次数、回退次数和最终人工接管率。因为多 Agent 系统真正难的不是“能跑起来”，而是出了问题后能不能知道到底卡在哪个 Agent。

## 3. RAG 混合检索链路如何设计

题目：你们在 RAG 中使用了“语义 + 关键词”的混合检索和多路召回策略。请你完整描述检索链路：查询改写、召回策略设计、召回结果去重、重排策略、上下文拼装分别怎么做？如果线上出现召回率高但最终回答准确率下降的情况，你如何定位是召回问题、重排问题，还是生成阶段的问题？

详细答案：

在安全运维场景里，纯向量检索和纯关键词检索都不够。纯向量容易语义相近但事实不对，纯关键词又容易漏掉表达方式不同但本质相同的问题。所以我一般会做一条完整的混合检索链路。

第一步是查询改写。原始输入可能是自然语言、告警文本、日志片段、镜像名甚至是一段模糊描述，所以我会先把它改写成多个检索视角。通常包括事件主体词、行为词、风险词、上下文限定词和时间范围词。比如一条“容器异常外联并疑似拉起挖矿进程”的描述，会拆成外联行为、进程特征、镜像版本、运行环境、历史案例几个子查询。这一步的目标不是让模型回答，而是把“一个模糊问题”变成“多个可检索信号”。

第二步是多路召回。一般至少有四路。

第一路是向量召回，找语义相近案例、分析结论和历史处置记录。

第二路是关键词召回，针对 CVE、进程名、域名、镜像标签、配置项等强实体做精确匹配。

第三路是规则库召回，直接查命中的安全规则、处置 SOP、告警关联规则。

第四路是元数据过滤召回，比如限定租户、业务线、K8s 集群、镜像仓库、时间窗口，避免不相关结果混进来。

第三步是结果去重和归并。这里不能只按文档 ID 去重，因为很多内容来自不同知识源但表达的是同一件事。我会做基于实体和事件主键的归并，比如同一个 CVE、同一个镜像 digest、同一个进程哈希、同一条运行时告警要合并成一个证据簇。这样后面做重排时，比较的是证据簇而不是碎片文档。

第四步是重排。我的经验是重排不能只看语义相似度，还要引入业务特征。最终得分一般是语义相关分、关键词命中分、证据新鲜度分、来源可信度分、租户上下文匹配分的加权结果。比如官方漏洞通告和内部已复盘案例通常会比论坛贴子权重更高，近 30 天的处置记录也会比两年前的旧案例权重更高。

第五步是上下文拼装。拼装不是把 TopK 全部塞进 Prompt，而是按“结论所需最小证据集”组装。通常我会把上下文分成四块：背景信息、直接证据、补充证据、冲突证据。这样模型不只是看支持性材料，也能看到少量反例，降低一边倒推断的风险。

如果线上出现“召回率高，但最终回答准确率下降”的情况，我会按三层去定位。

第一层看召回。检查召回结果里是否真的包含了正确证据。如果没有，说明是查询改写或召回策略有问题。如果有，但排名太靠后，说明是重排问题。

第二层看重排。检查最终送给模型的上下文中，正确证据是否被无关证据淹没。如果正确证据在 TopK 里，但拼装上下文时被截断或排到了低优先级，那就是重排和上下文控制的问题。

第三层看生成。若正确证据已经进入上下文且位置合理，但模型仍然得出错误结论，那就是生成阶段的问题，可能是 Prompt 约束不足、结论模板不严谨，或者模型更倾向于“解释得通”而不是“证据闭环”。

关于“复杂风险识别准确率 80%”，我不会只用一个笼统准确率来表述。我会拆成事件级识别准确率、风险定级准确率、处置建议采纳率、人工复核通过率等多个指标。离线评估集解决可比性，线上反馈数据解决真实性。离线用来做方案筛选，线上用来做持续迭代，两者不能混为一谈。

## 4. Agent 评测体系如何建设

题目：你提到构建了 Agent 效果评测体系，并利用真实运维处理结果反哺提示词与检索策略迭代。请具体说明这个评测体系的指标设计、样本采集方式、标注标准和回归机制。尤其是在安全运维场景里，很多事件并没有绝对标准答案，你如何定义“正确”与“足够好”？

详细答案：

Agent 评测体系如果只看最终回答是否“像人写的”，基本没有意义。在运维风控场景里，我会把评测拆成四层。

第一层是链路层指标，也就是系统能不能稳定跑完。包括任务成功率、平均耗时、工具失败率、回退率、人工接管率。这一层解决的是可用性问题。

第二层是过程层指标，也就是每个环节做得对不对。比如任务理解准确率、计划合理性、检索命中率、关键证据覆盖率、结果校验拦截率。这一层解决的是可解释的诊断问题。

第三层是结果层指标，也就是最终结论有没有业务价值。包括风险识别准确率、定级准确率、误报率、漏报率、处置建议采纳率、事件闭环时间缩短比例。

第四层是业务层指标，也就是系统上线后是否真的提升效率。比如人工研判时长减少多少，高优先级事件漏过的比例是否下降，夜间值班压力是否降低。

样本采集上，我一般会有三类来源。

第一类是真实线上事件，这类最有价值，但要注意脱敏和分层抽样，不能只拿简单样本。

第二类是人工构造难例，比如多信号冲突、知识库缺失、工具部分失效、跨租户混淆等，这类适合做回归集。

第三类是历史事故复盘样本，这类能覆盖真正高风险但低频的场景。

标注标准上，安全运维里很多事件确实没有唯一标准答案，所以我不会把标注做成“唯一结论题”，而是做成“三段式标注”。

第一段标事实是否正确，比如时间、对象、风险行为、依赖组件、影响范围这些基础事实是否准确。

第二段标推理是否成立，也就是结论是否被足够证据支撑。

第三段标处置是否可接受，也就是即便不是最优方案，是否在业务上属于安全、稳妥、可执行的方案。

所以我定义“正确”通常不是“和人工一句话完全一致”，而是满足三个条件：事实不错、证据足够、处置不冒进。定义“足够好”则是：虽然表述和人工不同，但没有引入明显风险，且能支持后续处置闭环。

回归机制上，我会把所有失败样本按类型归档，比如理解错误、检索漏召回、重排失真、工具异常、证据不足、过度推理、规则冲突等。每次改 Prompt 或改召回策略，都必须跑固定回归集和最近一段时间的线上抽样集。如果某项能力提升了，但另一项能力回退了，就不能直接上线。

如果模型输出和人工结论不一致，但最终处置结果是正确的，我会把它归成“路径不同但结果可接受”的样本，不会简单打成错误。因为很多时候系统和人工不是在同一推理路径上收敛，但最终动作一样且风险可控，这类样本对优化很重要，它说明系统可能在找另一条可行决策路径。

## 5. 工具调用治理如何设计

题目：在风控和运维场景中，工具调用失败、超时、返回脏数据是高频问题。请你设计一套完整的工具调用治理机制，覆盖参数校验、超时控制、幂等重试、熔断降级、结果可信度评估和审计追踪，并说明哪些能力应该放在 Agent 框架层，哪些应该由具体工具适配层负责。

详细答案：

我对工具调用的理解是，工具不是模型的“外挂”，而是整个 Agent 系统最容易失控的边界。所以工具治理必须系统化，而不是靠某个 Prompt 里写一句“如果失败请重试”。

在架构上，我会分成框架层和适配层两部分。

框架层负责通用治理能力，包括工具注册中心、参数 schema 校验、统一超时、统一重试策略、调用链 trace、权限校验、熔断规则和审计日志。这些能力必须由框架统一负责，否则每个工具各写一套，最终不可维护。

适配层负责具体工具的接入细节，包括接口签名映射、返回结果标准化、字段清洗、鉴权方式、异常码翻译和特定限流逻辑。因为不同系统差异很大，这部分很难完全通用。

参数校验上，我一定会要求每个工具都有明确的输入输出 schema。调用前先做必填校验、类型校验、范围校验和租户权限校验。尤其是像资产 ID、时间范围、集群名、命名空间这种字段，必须在进入工具前就验证，避免无效调用浪费时延。

超时控制上，我会做两层超时。外层是整个任务级超时，防止单个事件无限拖长。内层是工具级超时，不同工具设置不同阈值，比如知识库查询可以短一些，日志检索可以稍长一些。超时后不是一律失败，而是进入降级分支。

重试策略上，我只对幂等读操作做有限次重试，比如指数退避重试两到三次。写操作或者会触发外部副作用的操作必须显式声明是否可重试，默认不可自动重试。

熔断降级上，我会按工具维度做健康监控。如果某个工具在短时间内超时率或错误率飙升，就触发熔断。熔断后有三种降级策略。

第一，切换备用数据源。

第二，使用最近一次可信缓存。

第三，降低自动化程度，转成人工辅助模式。

结果可信度评估上，我不会把工具返回值当绝对真相。每个工具返回结果都需要带 source、timestamp、completeness、parseStatus 这些元信息。比如某条漏洞情报来自官方源还是社区源、是实时数据还是缓存数据、字段是否齐全、解析是否有异常，这些都会影响证据权重。

审计追踪上，我会记录每一次工具调用的 requestId、toolName、inputHash、outputHash、latency、retryCount、errorCode、degradeAction。这样后续出了错误结论，我们可以很快反查是不是因为某次工具返回了脏数据。

如果外部知识库接口短时间抖动严重，而业务又要求稳定，我会优先保稳定而不是强行追求“最新最全”。具体做法是先启用缓存和只读快照，保证结果一致性；然后在结论里标记数据新鲜度下降；对于需要强实时数据才能下结论的高风险事件，直接转人工。这本质上是在可用性、准确性、时延之间做有意识的权衡，而不是假装三者都能同时最优。

## 6. 多轮记忆如何设计

题目：你提到系统支持多轮交互状态跟踪与上下文记忆。请从“短期会话记忆”和“长期知识记忆”两个层面说明设计方案：哪些信息进入上下文窗口，哪些信息做结构化持久化，哪些信息应该被摘要压缩或主动遗忘？如果用户在第六轮对话推翻了前两轮的关键假设，你如何防止旧记忆污染当前决策？

详细答案：

在多轮系统里，记忆如果设计不好，越聊越错。所以我通常把记忆拆成短期会话记忆和长期知识记忆两套体系。

短期会话记忆服务于“这次任务”。它记录的是当前会话中的目标、约束、已经确认的事实、已执行步骤、中间证据、待确认问题和最新结论。不是所有对话内容都要进上下文窗口，真正应该保留的是对当前决策有作用的信息。

长期知识记忆服务于“未来复用”。它存的是稳定知识，比如历史案例、已验证处置方案、租户偏好、系统常见异常模式、已知误报模式。这类信息不会随着一轮对话结束就失效，但也不能未经筛选直接回灌到每次会话里。

具体到哪些信息进上下文窗口，我一般只放四类。

第一，当前任务目标和最新约束。

第二，已经确认的关键事实。

第三，尚未解决的分歧点。

第四，最近几步高价值证据。

哪些信息做结构化持久化，我会重点存这些：实体对象、事件主键、用户确认的事实、被采纳的处置动作、失败原因、最终结论和可复用标签。因为这些字段适合后续检索、过滤和统计。

哪些信息应该摘要压缩或主动遗忘，主要是冗长推理过程、重复提问、无效尝试和已经被新证据推翻的旧假设。这类内容如果一直塞在上下文里，很容易污染后续判断。

如果用户在第六轮推翻了前两轮的关键假设，比如最初说问题发生在生产环境，后面又澄清其实是测试环境，我不会简单把新信息接在后面，而是执行一次“记忆修正”。

第一步，把被推翻的旧假设标记为 invalidated，而不是物理删除。因为删除会丢失审计线索。

第二步，更新结构化事实表，把新的事实提升为当前有效版本。

第三步，对基于旧假设产生的中间结论做级联失效，要求 Planner 或校验器重新判断哪些步骤要重跑。

第四步，重新生成精简上下文，只保留当前有效事实和必要的修正记录。

记忆更新方式上，我更倾向于“事件驱动为主，回合驱动为辅”。用户明确确认、工具返回关键证据、系统得出阶段性结论时，就触发事件驱动更新。每一轮对话结束后，再做一次回合级摘要和压缩。

对于表达含糊、指代不清和跨轮纠错，我不会直接把模型猜测写进长期记忆，而是把它标成待确认状态。只有被用户确认，或者被可信工具证据验证后，才升级成稳定记忆。这样可以显著降低“错误记忆固化”的问题。

## 7. 如何降低幻觉和错误推断风险

题目：安全运维类 Agent 很容易出现“看起来逻辑完整，但其实事实依据不足”的问题。假设模型基于不充分证据将某个高危事件误判为低危，导致漏报，你会如何从提示词、工具链、证据约束、结果校验和人工兜底五个层面重构这条链路，以显著降低幻觉和错误推断风险？

详细答案：

这个问题本质上不是“模型会不会幻觉”，而是“系统有没有设计成不允许无证据下结论”。我的治理思路一般分五层。

第一层是提示词约束。Prompt 里不能只要求“给出判断”，还要明确要求“结论必须引用证据、证据不足时必须输出不确定、不得用常识补全缺失事实”。也就是说，Prompt 不是让模型更聪明，而是让模型学会在不确定时收手。

第二层是工具链增强。对于高危场景，我会强制要求至少经过两类不同来源证据的交叉验证，比如行为日志和配置数据、镜像信息和漏洞情报、资产归属和运行时行为。只靠单一来源，很容易被局部噪声误导。

第三层是证据约束。系统要定义“证据充分性”的硬条件。比如必须明确事件对象、时间范围、风险行为、影响范围中至少若干项；如果缺少关键字段，就不能自动输出低风险结论。这里最重要的一点是，低风险结论不能比高风险结论更容易产出。很多系统恰恰反过来，证据不足时也默认低风险，这很危险。

第四层是结果校验。最终结论出来后，要由独立校验器检查：结论是否被证据支持、风险级别是否和证据一致、是否存在未解释冲突、是否违反硬性规则。如果校验器发现“高危信号存在，但结论给了低危”，直接打回。

第五层是人工兜底。不是所有场景都适合自动闭环。像高价值资产、生产环境、跨租户传播、外联可疑域名、涉及权限提升这类高风险条件，只要命中一个，就算模型倾向低危，也必须升级人工复核。

我认可的“证据充分性”标准一般包括三个维度。

第一，证据真实性，也就是来源可信、时间可追溯、字段可校验。

第二，证据相关性，也就是证据直接对应当前事件，而不是泛化知识。

第三，证据闭环性，也就是证据能支撑从事实到结论的关键链条，而不是只有一两个散点。

必须阻断自动处理并升级人工的情况，我通常会设几类硬规则：高价值资产、关键生产环境、证据冲突未消解、工具链异常导致证据不完整、模型置信度低但结论影响大、存在潜在扩散风险。这些规则本质上是在告诉系统，某些错误是不能用“概率上大多数情况没问题”来接受的。

## 8. 自动定级与规则边界如何划分

题目：你们已经实现了复杂风险事件的自动定级与处理。请你从系统工程角度解释：自动定级的标签体系如何设计，规则和模型的边界如何划分，为什么某些场景应该优先交给规则引擎而不是大模型？如果后续要支持不同业务线、不同租户的差异化风险标准，你如何做配置化和可扩展设计？

详细答案：

自动定级如果只是分高、中、低，落地价值其实不够。真正可用的定级体系至少要包括风险等级、事件类型、影响范围、处置紧急度、可信度和建议动作这几类标签。因为同样是高危，漏洞暴露和异常外联的处置优先级并不一样。

我通常会把标签体系设计成“基础标签 + 业务标签”两层。

基础标签是平台统一的，比如事件类型、风险等级、证据来源、影响范围、置信度，这些字段方便跨业务线对齐。

业务标签是租户或场景自定义的，比如某租户特别关注镜像凭证泄露，另一个租户更关注合规违规配置，这部分允许按业务扩展。

规则和模型的边界，我的原则是“确定性高、代价敏感、可枚举边界清晰的场景优先规则；模糊理解、多源归纳、知识补全场景优先模型”。

比如以下场景我会优先交给规则引擎。

第一，硬性合规规则，比如某端口暴露、某配置缺失、某镜像来源不可信。

第二，涉及高风险处置动作的准入门槛，比如是否允许自动隔离、是否允许阻断发布。

第三，明确的黑白名单判定，比如已知恶意域名、已知违规镜像标签、已知敏感路径。

这些场景优先规则而不是大模型，原因有三个。

第一，可解释性更强。

第二，行为更稳定。

第三，便于审计和合规签字。

而模型更适合做这些事情：模糊告警描述理解、多源证据归纳、相似案例召回、复杂上下文中的风险解释、处置建议生成。也就是说，模型更像“认知层”和“归纳层”，规则更像“守门层”和“兜底层”。

为了支持不同业务线、不同租户的差异化风险标准，我会做配置化分层。

第一层是平台公共策略，不允许业务方随意改，比如高危基线规则和最小安全门槛。

第二层是租户策略模板，比如权重、阈值、关注标签、自动化动作开关。

第三层是租户实例配置，允许在模板范围内个性化。

版本管理上，每一套策略、Prompt、检索配置都要版本化，并和评测结果绑定。新策略上线时先跑离线回归，再做小流量灰度，观察误报率、漏报率、人工接管率。如果某租户策略变更，只作用于租户自己的命名空间和配置域，绝不能污染平台公共规则，更不能影响其他租户判断结果。

## 9. 如何平台化为通用 Agent 平台

题目：如果现在让你把“探真智子”从单一运维风控场景升级成一个面向云原生安全场景的通用 Agent 平台，你会如何设计平台的抽象边界？请从 Agent 编排、工具注册、知识源接入、评测中心、记忆中心、权限控制和观测平台几个方面给出你的平台化方案，并说明哪些能力必须是平台内建的，哪些能力适合业务团队自定义。

详细答案：

如果要平台化，我会把它从“做一个项目 Agent”升级成“做一个可复用的 Agent 操作系统”。抽象边界一定要先划清楚，不然最后平台会变成一个大杂烩。

Agent 编排层是平台内建能力。因为工作流调度、状态机、回退重试、回合上限、并发控制、人工介入节点这些能力如果不统一，所有业务方都会各写一套，最终无法观测和治理。

工具注册中心也是平台内建。平台统一管理工具 schema、鉴权、限流、熔断、版本和审计日志。业务团队只需要按规范注册工具，不应该自己决定调用链怎么做 trace 和权限控制。

知识源接入我会做成“平台提供接入框架，业务提供知识内容”。也就是说，平台负责向量化流程、索引管理、元数据过滤、召回链路、缓存和权限隔离；业务团队负责把内部案例、规则库、SOP、资产知识接进来。

评测中心必须平台内建。因为评测集管理、离线回放、线上抽样、版本对比、指标看板、回归门禁这些能力必须统一，不然每个业务方都会用不同标准证明自己“效果不错”，平台就无法形成真实闭环。

记忆中心我也会内建，但开放扩展点。平台负责记忆模型、生命周期、压缩策略、失效机制和权限隔离；业务团队可以定义自己关心的记忆字段，比如云原生团队更关心集群拓扑和工作负载变更，漏洞团队更关心组件版本和利用条件。

权限控制必须完全内建，因为它直接关系到安全边界。我会把权限拆成四层：用户权限、Agent 权限、工具权限、数据权限。也就是说，不是“用户能看什么”就够了，还要限制“某个 Agent 能调什么工具、能读什么数据、能不能执行某类动作”。

观测平台也必须内建。至少要能看链路追踪、Agent 执行树、工具调用拓扑、失败类型分布、证据命中率、人工接管点、版本差异对比。平台化之后，最怕的不是效果差，而是效果差但没人知道差在哪。

适合业务团队自定义的能力，主要有四类：领域 Prompt、领域规则、领域知识、领域输出模板。因为这些东西和业务语义深度绑定，平台很难抽象成统一标准。

平台化后最容易出现两个反模式。

第一个反模式是“平台只做工具集市，不做治理骨架”。这样看似灵活，实际上每个业务都在重复造调度、状态、评测和审计轮子。

第二个反模式是“平台过度封装，业务完全不能扩展”。这样会导致业务团队绕开平台私搭流程，最终平台形同虚设。

所以我的做法是，平台只强控那些和稳定性、安全性、可治理性强相关的能力，把领域表达权留给业务团队，但要通过模板、配额、权限和评测门禁限制滥用 Prompt、工具和记忆能力。

## 10. 线上误报率暴涨如何排查

题目：假设线上出现一个棘手问题：某类风险事件在过去一周内误报率突然从 8% 上升到 27%，但模型版本、Prompt 和主流程代码都没有发布变更。请你设计一个系统化排查方案，要求覆盖输入数据漂移、知识库污染、检索质量波动、工具接口变更、反馈闭环误学习、评测样本偏移等因素，并说明每一步排查希望验证什么假设、读取哪些证据、如何快速止血。

详细答案：

这种问题最容易掉进一个误区，就是因为模型版本没变，就默认不是 Agent 系统的问题。实际上这类问题很多都发生在系统外围，所以排查一定要按链路展开。

第一步，我会先确认问题是否真实存在，以及问题边界是什么。要看误报率上涨是全局上涨，还是只集中在某租户、某事件类型、某时间段、某数据源。如果边界都没划清，后面排查会很散。这一步要读取线上统计看板、抽样事件明细、人工复核结果，验证“问题是局部的还是系统性的”。

第二步，排查输入数据漂移。即使模型没变，输入变了，效果也会变。我要看最近一周告警文本格式、日志字段完整性、资产标签、镜像元数据、上游规则产出的结构是否发生变化。比如某个上游系统改了字段命名，导致实体抽取质量下降，就会直接影响后续召回和判断。

第三步，排查知识库污染。我要看最近是否有批量导入新的案例、规则、漏洞情报，是否存在错误标注、重复案例、低质量总结、过时处置建议进入知识库。很多时候误报率上升不是模型变笨了，而是检索进来的参考样本变差了。

第四步，排查检索质量波动。这里重点看召回结果分布是否变了，比如 TopK 中低质量文档比例是否升高、租户过滤是否失效、重排分数分布是否漂移、缓存命中是否异常。我要验证的假设是：正确证据有没有被召回，召回后有没有被正确排序。

第五步，排查工具接口变更。虽然主流程代码没发版，但外部接口可能变了。我要检查知识库接口、资产系统、工单系统、日志查询接口是否有字段变化、默认值变化、权限收紧、超时增加、空值增多等情况。很多误报其实是因为工具返回不完整数据，系统却没有识别为不完整。

第六步，排查反馈闭环是否误学习。如果系统会用线上反馈持续调整权重、样本或规则，就要看最近一周是否引入了偏置反馈。比如某一批人工标注本身不稳定，或者某类高频低风险样本被过度放大，导致系统越来越倾向保守判断。

第七步，排查评测样本是否偏移。很多团队误以为“离线评测没退化就说明系统没问题”，但可能是评测集太旧，已经不能代表当前线上输入。我会抽最近一周新样本，和历史评测集做分布对比，验证是不是评测盲区导致问题长期没被发现。

第八步，做链路级 case replay，也就是把最近出错的典型案例回放到每个中间环节，逐步看是从哪一步开始偏掉。是输入解析错了、查询改写偏了、召回混入噪声、重排压错了、还是生成阶段过度解释。只有做逐步回放，才能把问题定位到具体模块。

如果必须在 2 小时内先把误报率降下来，我会优先做止血动作，而不是一上来追根因。

第一，回滚最近的知识库增量或关闭可疑知识源。

第二，收紧自动定级阈值，提高人工复核比例。

第三，对问题集中的事件类型临时切换到规则优先模式。

第四，关闭最近新增的反馈学习入口，防止继续放大偏差。

这些都属于临时止血。真正的根因修复，通常包括修复上游数据格式、重建低质量知识索引、调整重排特征、增加证据完整性校验、更新评测集和改进反馈闭环规则。我的经验是，线上先稳住，再系统排查，不然误报会一边发生一边污染新的反馈数据，问题只会越滚越大。
